### 坑 1：官方 OneBot 适配器已废弃

`@koishijs/plugin-adapter-onebot@6.0.2`（2024-05）拖着 `@satorijs/satori@3.7.0` →
嵌套 `@satorijs/core@3.7.0`，与根 `4.6.0` 冲突 → **`Session2 is not a constructor`**。
安装时 npm 会警告 `official support for onebot has been dropped`。

**改用 `koishi-plugin-adapter-onebot@6.9.4`**（repo `koishijs/koishi-plugin-adapter-onebot`，
peer `koishi ^4.18.6`，依赖只有 `qface`，无 satori 链）。

### 坑 2：`@koishijs/cli` 不能用

它内嵌 **cordis 2.10.3**，而当前插件代用 **cordis 3.18.1** → 两份实例 →
`Cannot set property name of #<_MainScope>` / `this.ctx.debounce is not a function`。

**`koishi` 包自带 bin**（`node_modules/koishi/bin.js` → `lib/cli`），不要装 `@koishijs/cli`。

### 坑 3：配置字段是 `endpoint` 不是 `url`

写错会报 schemastery 校验错误。

### 坑 4（最坑）：`help` / `echo` 是独立插件

`@koishijs/plugin-commands` **不带** `help` 和 `echo`。少了它们，
发 `/help` 的现象是**彻底静默**——不回复、不报错、日志无痕，跟链路断了长得一模一样。
必须装 `@koishijs/plugin-help` 和 `@koishijs/plugin-echo`。

依据：[指令系统 | Koishi](https://koishi.chat/zh-CN/manual/usage/command.html)
「help 指令由 help 插件提供……echo 指令由 echo 插件提供」。

### 坑 5：debug 日志开不出来

- 环境变量是 **`KOISHI_LOG_LEVEL`**（不是 `LOG_LEVEL`），且**必须是数字**（3 = debug）
- **CLI 会把它清空**：`koishi/lib/cli/index.js` 里 `process.env.KOISHI_LOG_LEVEL = logLevel || ""`

**只能用命令行参数**：`node node_modules/koishi/bin.js start --log-level 3`

### 坑 6：重复启动实例 → 静默半死

新实例抢不到 5140 会报 `Error: No open ports available` + `server closing`，
**但适配器仍照常连 NapCat**。极易把"控制台起不来"误判成"机器人不工作"。
重启前先查：`Get-NetTCPConnection -State Listen -LocalPort 5140`

### 坑 7：`koishi.yml` 由 Koishi 自己重写

启动后它会：给插件名加实例 ID（`server:meey6h`）、**删掉所有注释**、规范化引号。
→ **手改配置前必须先停进程**，否则改动被覆盖。

### 坑 8：`PacketBackend` 报错是**有条件的**无害 —— 它一挂，戳一戳等功能直接失效

```
[error] [Core] [Packet] PacketBackend 不支持当前QQ版本架构：9.9.36-53644-x64
```

> ⚠️ **本条 2026-10-06 更正过。** 原来的结论是「报这个错功能也正常，不必降级」，
> 那是**错的** —— 当时只用 `get_login_info` 验证过，而它根本不走 PacketBackend。

**这个报错到底影响什么**

- `PacketBackend` 是 NapCat 自带的原生模块（`native\packet\MoeHoo.<platform>.node`），
  它把 QQ 内部**收发函数的地址**写死了 —— 地址随 QQ 构建号变化，所以 NapCat 里是一张
  **「构建号 → 地址」硬编码表**，只能一个版本一个版本地适配（不是 QQ 的 bug，也不是
  NapCat「修一下」就能覆盖所有版本）。
- 表里没有你这个构建号 → 模块不加载 → **一切走 PacketBackend 的能力全废**：
  戳一戳（`send_poke` / `group_poke` / `friend_poke`）、私聊文件直链
  （`get_private_file_url`）等。它们**不会报错给调用方**，只在 action 结果里回
  `{"status":"failed","retcode":1400,"message":"packetBackend发包能力不可用…"}`。
- 不依赖它的（收消息、发消息、`get_login_info`）照常工作 —— 所以"功能正常"的假象很容易成立。

**判据（30 秒分清）**：绕开 Koishi 直接打一次真实调用，看回包：

```powershell
node tools\napcat-probe.cjs call group_poke '{"group_id":454444539,"user_id":2791932480}'
```

`status: ok` = 通；`retcode 1400` = 这个 QQ 构建不在表内。

**怎么知道哪些构建号在表内**：别信文档。直接读本地 NapCat bundle 里那张表：

```powershell
# 表里所有 Windows 构建号（含 send/recv 地址），看最大到哪
Select-String -Path D:\deepseek\QQbot\NapCat.Shell\napcat.mjs -Pattern '"9\.9\.\d+-\d+-x64"' |
  ForEach-Object { $_.Line.Trim() }
```

2026-10-06 实测 NapCat **4.18.30** 的表里有 100 条 Windows 记录，最高到 `9.9.36-53489`。
官方文档写的「Windows 支持 28418-36580」**已经过期**，别拿它当依据。

**根治：把 QQ 换成表里有的构建号**（历史版本镜像：<https://rodert.github.io/qq-versions/>；
NapCat release 里给的 `dldir1.qq.com` 链接已 404）。本机 2026-10-06 换到
`9.9.33-52230` 之后 `group_poke` / `send_poke` 都返回 `status: ok`。

> 顺带一个坑：`chatluna-toolbox` 的 `poke_user` 工具**不看** action 的 `status`，
> NapCat 明明回了 1400，它还告诉模型「已在群 X 戳了一下 Y」。查问题时别拿工具的话当证据。

### 坑 9：反向 WS 到 8080 的 ECONNREFUSED 是无害的

NapCat 在往**旧的 NoneBot 项目**（`ws://localhost:8080`）重连，它没运行。
想消噪音：把那条 `websocketClients` 的 `enable` 改成 `false`。

### 坑 10：插件市场报 `TypeError: this is not a function`（上游 bug，有绕行方案）

现象（`--log-level 3` 下可见）：

```
[W] market TypeError: this is not a function
    at _Scanner.<anonymous> (@cordisjs/plugin-http/lib/index.cjs:178:36)
    at _Scanner.search (@koishijs/registry/lib/index.js:213:31)
    at MarketProvider.collect (@koishijs/plugin-market/lib/node/index.js:384:26)
```

**根因**：`plugin-market/lib/node/index.js:377` 把方法**脱绑**传递：

```js
this.scanner = new import_registry2.default(registry.get);   // ← get 没有绑定 this
```

Scanner 内部执行 `this.request(...)`，于是 `this` 变成 Scanner 实例；
而 `@cordisjs/plugin-http` 的 `get` 依赖 `this` 是可调用 Proxy：

```js
defineProperty(_HTTP.prototype, "get", async function(url, config) {
  const response = await this(url, { method, ...config });   // this 不是函数 → 炸
```

**绕行方案**：紧邻的 `if (this.http)` 分支**完全不走 Scanner**，而 `this.http` 只在
**配置了 `endpoint` 时**才被赋值（`if (config.endpoint) this.http = ctx.http.extend(config)`）。

→ **在 `market.search.endpoint` 填上注册表地址即可**。这正是官方文档
「市场加载不出来就填 search.endpoint」背后的真实原因。

### 坑 11：注册表索引 JSON 的包名在 `objects[].package.name`

排查 ChatLuna 时踩的：索引顶层是 `{version, time, total, forceTime, shared, objects[]}`，
包名**不在** `objects[i].name`，而在 `objects[i].package.name`。
写成 `o.name || o.package` 会取到**对象**，正则匹配 `[object Object]`，必然 0 命中——
当时差点得出「官方源没有 ChatLuna」的错误结论。

### 坑 12：PowerShell 里读 UTF-8 文件会显示乱码

PowerShell **5.1** 的 `Get-Content` 默认按 ANSI 解码，读 UTF-8 文件时中文变乱码
（如 `鑷缓`）。**文件本身没问题**，别被吓到、别去"修"它。
要看内容请用 read 工具，或 `[System.IO.File]::ReadAllText($p,[Text.Encoding]::UTF8)`。

### 坑 13：`chatluna-storage-service` 的 `storageBackend` 必填，不填会连报三个错

`chatluna` 的 **peerDependency** 里有 `koishi-plugin-chatluna-storage-service ^1.0.6`——
**光装 `chatluna` 不够**，还得装它。但装上后如果配置写 `{}`，会看到**三个**错误：

```
[E] app ValidationError: $.storageBackend missing required value
[E] app TypeError [ERR_INVALID_ARG_TYPE]: The "path" argument must be of type string. Received undefined
        at new LocalStorageBackend (... storage-service/lib/index.cjs:361:42)   ← path.join(storagePath,"temp")
[E] app TypeError: Cannot read properties of null (reading 'backendPath')
```

第三个是第二个的连带（服务构造失败 → 拿到 null）。**根因只有第一个**：
`schema` 里 `storageBackend` 是 `.required()` **没有默认值**（尽管代码里写了 `?? "local"`）：

```js
storageBackend: Schema.union([
  Schema.const("?").description("别选，特么的"),   // ← 作者的玩笑，别选
  Schema.const("local"), Schema.const("s3"), Schema.const("webdav"), Schema.const("r2")
]).required()
```

正确配置：

```yaml
  chatluna-storage-service:
    storageBackend: local
    serverPath: http://127.0.0.1:5140
    storagePath: ./data/chatluna-storage
    backendPath: /chatluna-storage
```

修好后日志出现 `[I] chatluna-storage-service Storage backend initialized: local`。
另注意它自己的说明：**需要 Koishi 与适配器在同机或同局域网**（本地后端靠 Koishi 的 HTTP 服务发文件）。

### 坑 15（很坑）：ChatLuna 的**预设名是 `keywords[0]`，不是文件名**

`koishi-plugin-chatluna/lib/preset.cjs` 的 `_updateSchema()`：

```js
this.ctx.schema.set("preset", Schema.union(
  this._presets.value.map(preset => Schema.const(preset.triggerKeyword[0]))   // ← keywords[0]
```

**`defaultPreset` 要填 `default-persona`（= keywords[0]），填文件名 `default-persona.yml` 或旧名 `星源` 都可能踩到**：

> `getPreset()` 用的是 `triggerKeyword.includes(k)`，**keywords 里任意一个都能命中解析**，

### 坑 16：ChatLuna 的模型名是**三段式**，且模型列表是**懒加载**的

1. **名字格式**：`koishi-plugin-chatluna/lib/llm-core/platform/service.cjs:227`

   ```js
   toModelName: () => platform + "/" + model.name
   ```

   `platform` = 适配器构造时的 `"deepseek"`；`model.name` = 端点原始 id（`deepseek/deepseek-v4.1-flash`）。
   → 完整名 = **`deepseek/deepseek/deepseek-v4.1-flash`**（是的，两个 `deepseek/`）。

2. **模型列表是懒加载的**，不是启动时拉：

   ```js
   async getModels(config) {                    // client.cjs:107
     let models = Object.values(this._modelInfos);
     if (models.length > 0) return models;      // 有缓存就直接返回
     try { models = await this.refreshModels(config); ... }
     catch (e) { err.message = `获取模型列表失败 (${this.platform}): ${reason}`; this.ctx.logger.error(err); throw err }
   }
   ```

   → **控制台 `/plugins/` 里 `defaultModel` 显示「无」是正常的**（还没人聊过天，没触发过拉取）。
   失败一定会打 `获取模型列表失败`，日志里没有这条**就说明压根没调用过**，别去怀疑网络。
   → 但 `defaultModel` 还是应该**显式填上**，否则会看到 `Model "" does not support image input`。

### 坑 17：`proxy-agent` 插件配 `{}` 等于没配

`@cordisjs/plugin-proxy-agent/lib/index.js`：

```js
var Config = z.object({ proxyAgent: Schema.string() })   // 没有默认值
function apply(ctx, _config) {
  ctx.on("http/fetch-init", (url, init, config) => {
    const proxy = config?.proxyAgent ?? _config.proxyAgent;
    if (!proxy) return;          // ← 没配就直接返回，什么都不做
```

所以 `proxy-agent: {}` **不会**自动读 `HTTP_PROXY`。
本项目实际走代理靠的是环境里的 **`NODE_USE_ENV_PROXY=1`**（Node 内置 undici 的 EnvHttpProxyAgent，
启动日志里那串 `[UNDICI-EHPA] Warning: EnvHttpProxyAgent is experimental` 就是它在生效）。
要在 Koishi 层面强制走代理，得显式写：

```yaml
  proxy-agent:
    proxyAgent: http://127.0.0.1:7890
```

### 坑 18（很坑）：ChatLuna 把模型**存在会话行里**，改 `defaultModel` 不会影响已有会话

`chatluna_conversation` 表有独立的 `model` 列。`defaultModel` 只在**新建会话**时被采用。

### 坑 19：`prefixMode: strict` —— 不设的话**私聊里不打斜杠也能触发指令**

`@koishijs/core` 的 `Commander`（`lib/index.cjs:1446`）：

```js
const isStrict = this.config.prefixMode === "strict" || (!isDirect && !stripped.appel)
if (argv.root && stripped.prefix === null && isStrict) return
```

- 默认 `prefixMode` 是 `auto` → **群聊**里没前缀、也没 @bot 时不会当指令；但**私聊**里不设防，
  `help` 直接就能触发。
- 设成 `strict` 后，**私聊也必须带 `/` 或 `.`**。群聊里 @bot 但没打斜杠同样不触发指令。
- 位置：**`koishi.yml` 顶层**（跟 `prefix` 同级），不是插件配置。
- 注意它**不拦** ChatLuna 的聊天触发——那走的是 `allow_reply` 里的 `atSelf`/`botNames` 逻辑，两套体系。

### 坑 20：ChatLuna 的 `allow_reply` 是**整条链的第一个中间件**

`lib/index.cjs:2902`，`.before("lifecycle-check")`。它返回 STOP 时，
`read_chat_message` 和 `transform_chat_message` **根本不会跑**。

推论（做图片策略时必须知道）：群里**没 @bot 的消息压根不会进 `messageTransformer`**，
所以"群聊里 AI 不知道有图"这个需求在默认配置下是**天然的**，不依赖我们的插件。
真正需要插件介入的是：**@了 bot 的消息**（`allowAtReply` 默认 `true`）、
**以 botNames 开头的消息**（`isNickname` 默认 `true`）、
**以预设 keywords 开头的消息**（`enablePresetKeywordTrigger` 默认 `true`，见坑 15 的 preset keyword 机制）、
以及 `randomReplyFrequency > 0` 时的随机插话（**默认 0**）。

### 坑 21：ChatLuna **已经内建**消息聚合/延迟，别自己写

`lib/index.cjs:3267-3520`（`message_delay.ts`），配置项两个：

| 字段 | 默认 | 说明 |
|---|---|---|
| `messageQueue` | `true` | 总开关 |
| `messageQueueDelay` | `0` | **单位是秒**（源码 `config.messageQueueDelay * 1e3` 喂给 setTimeout）。范围 0–1800 |

行为：
- 第一条消息进来 → 建一个 turn，state = `collecting`，**起一个 `messageQueueDelay` 秒的定时器**
- 同一个用户在定时器没到之前又发消息 → **并进同一个 turn**，并把定时器**顺延**（真正的 debounce）
- 定时器到点 → `mergeMessages()` 把这段时间的消息按时间排序、用换行拼成**一条**输入，再送给模型
- 换人说话会开新 turn（`tailTurn.userName === userName` 才合并）

**所以"延迟收集同一用户的连续消息再一次回复"是配置问题，不是开发问题。** 设 `messageQueueDelay: 3` 即可。

⚠️ 注意它挂的位置是 `.after("transform_chat_message")`，所以**图片解析发生在 3 秒收集窗口之前**，
总延迟 ≈ 图片解析时间 + messageQueueDelay + 模型时间。

### 坑 22：`prefixMode: strict` 之后，私聊里打裸指令名会掉进 Koishi 的"猜测指令"

`@koishijs/core` 的 `Commander` 里有一个 suggest 中间件（`lib/index.cjs:1294-1316`）：

```js
if (argv?.command || !isDirect && !prefix && !appel) return next()
```

**私聊**这一支不设防：没前缀也会去猜。实测（2026-09-29 15:02）：私聊发 `help` →
bot 回「您要找的是不是"help"？回复句号以使用推测的指令。」，回复 `.` 之后才真的执行 `/help`。

也就是说：私聊里恰好撞上指令名（`help` / `echo` / `emotion` / `vision` / `chatluna` / `plugin` / `followup`）
且相似度够高的消息，会**先被指令系统截走**，模型要等 suggest 超时才拿到这条消息。
中文群聊里基本撞不上，暂时不动它；哪天觉得烦，优先考虑把 `help` 插件关掉。

### 坑 23（★ 踩了两次）：子指令必须用**点号全名**注册，`ctx.command('a/b')` 出来的指令**用户根本敲不出来**

```js
ctx.command('scene/begin <title:string>')   // ✗ 子指令的 name 只有 'begin'
ctx.command('scene.begin <title:string>')   // ✓ 子指令的 name 是 'scene.begin'
```

原因在 `Commander` 的解析：`_resolve(key)`（`@koishijs/core` core:1432）把 `key` 按 `.` 切开后，
**每一段都拿"整名"去 `_commandList` 里查 `_aliases`**（core:1411 `get`）：

```js
_resolve(key, session) {
  const segments = Command.normalize(key).split('.')
  let i = 1, name = segments[0], command
  while ((command = this.get(name, session)) && i < segments.length) {
    name = command.name + '.' + segments[i++]
  }
  return { command, name }
}
```

点号注册的子指令 `name` 就是完整路径（core:1485-1491 `parent.name + seg`），所以 `get('scene.begin')` 命中；
斜杠写法只取最后一段（`name = 'begin'`），`get('scene.begin')` 永远是 `undefined`
→ 解析失败 → 不是指令 → 消息原样往下走。

**实测现象极具误导性**：`/scene.begin 猜数字 …` **完全没反应**（日志里连 `command scene` 都不打），

### 坑 24（★ 测试台专属）：测试实例的**插件解析根**跟着"用哪个 koishi 二进制起"走，不跟 cwd

`@koishijs/loader` 建解析器时：

```js

if (this.prefixes.some(prefix => name.startsWith(prefix))) return [name]
```

### 坑 25（★ 自研插件必踩）：`ctx.model.extend` 忘了写 → `cannot resolve table`，而且**写入是静默失败的**

写 R15 时忘了注册表模型就直接 `ctx.database.get('qqbot_guard', {})`，运行期报
`cannot resolve table "qqbot_guard"`。**真正致命的是它的表现方式**：

- 读失败被 `reload()` 的 catch 吃掉了 → 只看到一串 `[W]`，功能看起来"在跑"
- **写失败被中间件的兜底 catch 吃掉** → 用户在群里发 `开口`，bot **什么都不回**，
  日志里只有一行 `屏蔽判定出错（放行）`；而如果写路径在指令里，用户会看到"操作成功"其实没生效

教训（已落进代码）：
1. `ctx.model.extend(表名, {...}, { primary: [...] })` 必须写在 `apply()` 里，别拖到用的时候才想起来
2. **每一条写库路径都要包一层 `tryWrite`**，失败了要**说出来**（`开关没改成：<原因>`），
   否则"以为已经闭嘴了，其实还在说"是最坏的结果
3. 读库失败的 `warn` 要做限流（每分钟最多一条），否则轮询会刷满屏

判据：日志里出现 `cannot resolve table` = 模型没注册，不是数据问题。

### 坑 27（★ 自研 chatluna 插件必踩）：从自研插件里 `require('koishi-plugin-chatluna/...')` 会解析到**另一份** chatluna

自研插件是用 **junction** 挂在 `<app>/node_modules/` 下的（`file:external/...`），
Node 默认按 **realpath** 解析，于是 `require('koishi-plugin-chatluna/lib/...')`
会顺着**真实源码路径**走回 `koishi-app/node_modules/`，而不是"当前正在跑的那个实例"的
`node_modules`。生产实例里两者恰好是同一份，所以**只有测试实例会炸**；
但一旦哪天跑第二个实例、或者 npm 提升方式变了，生产也会炸。

症状（rig 32b 实测，全是"看起来像模型没配好"的假象）：

```
[W] chatluna-long-memory The model bge-small-zh-v1.5 is not embeddings, return empty embeddings
[E] chatluna Error: Embedding dimension is 0, Try to change the embeddings model.
```

真因是 chatluna 内部那句 `model instanceof ChatLunaBaseEmbeddings` —— 两份 chatluna = 两个类 = `false`。

**正确写法**（见 `external/koishi-plugin-chatluna-local-embeddings/lib/index.js`）：

```js
const Module = require('node:module')
/** 从宿主应用根目录解析，保证拿到"正在运行的那一份" */
function appRequire(ctx, spec) {
  const req = Module.createRequire(path.join(ctx.baseDir, 'index.js'))
  return req(spec)
}
// 运行时类必须走它，而且要在 apply/ready 里现取现拼（不能写在模块顶层 class extends）
const { PlatformEmbeddingsClient } = appRequire(ctx, 'koishi-plugin-chatluna/llm-core/platform/client')
const { ChatLunaEmbeddings } = appRequire(ctx, 'koishi-plugin-chatluna/llm-core/platform/model')
const { ChatLunaPlugin } = appRequire(ctx, 'koishi-plugin-chatluna/services/chat')
```

例外：**只用来拼 Config schema 的那种**（`ChatLunaPlugin.Config`）可以照常顶层 `require`，
schema 是纯数据、不存在类 identity 问题，而且顶层 require 才能在模块加载期拿到。

顺带两个同源小坑：

- `BasePlatformClient` 上有个 **`get config()`**（返回 configPool 里那条平台配置），
  子类里 `this.config = ...` 会报
  `Cannot set property config of #<BasePlatformClient> which has only a getter` → 自己的字段要叫 `_config`。
- `super(ctx, plugin.platformConfigPool)` —— 传的是 `platformConfigPool`，不是 `configPool`。

### 坑 30：跑剧本的日志只增不减，几十轮就堆成几 MB

以前每跑一轮都手写一遍重定向：`node tools\run-rig.cjs ... *> tools\rig-24-all.log`，
文件名各不相同 → `koishi-app/tools/` 下攒了 **58 个日志、4.9 MB**，而且永远只增不减。
（`last-run.log` 是脚本自己用 `flags: "w"` 覆盖写的，不在其中。）

**现在的规矩**：

- 要存整场输出就加 `--keep-log`，写到 `koishi-app/tools/logs/rig-<剧本名>.log` ——
  **同名覆盖**，同一个剧本跑一百遍也只有一个文件。
- `run-rig.cjs` 每次收尾会自动清扫超过 `--keep-days`（默认 7 天）的日志；
  想手动清就 `node tools\clean-logs.cjs`（预演）→ `--force`（真删）。
- 日志文件名里的 `-all` 后缀是"连着 koishi 的 stderr 一起重定向"的意思，
  能拿到完整时间线；`last-run.log` 只有伪 OneBot 的收发，看 koishi 侧日志得用 `--keep-log`。

**★ 两个实现上的坑（都踩过）**：

1. **清扫必须排在 tee 落盘之后**。反过来的话本次刚写的日志会被自己删掉 ——
   `keep-days 0` 时尤其明显（cutoff 就是"现在"，而刚写完的文件 mtime 早几毫秒）。
   解法是 `pruneLogs({ keepFiles: [tee.file] })` 把本次日志钉住。
2. 不要用 `writeFileSync` 逐行写日志。剧本一轮几万行，同步写盘会明显拖慢时间线；
   用 `createWriteStream`，并且**记得 `await end()`**，否则最后几行不落盘。

### 坑 31（★ 最阴的一个：**全程零报错**）：OneBot 断线后**永远不会重连**，日志里连一条错误都没有

**症状**：群里发消息机器人毫无反应；而 Koishi 进程活着、5140 在听、日志 **零 `[E]`**，看起来一切正常。
用户当时还看到 NapCat 掉过一次登录，登回来仍然不回话 —— 于是很容易误判成 NapCat 的问题。

**根因**（`koishi-plugin-adapter-onebot` × `@satorijs/core` 叠出来的真 bug）：

`socket` 的 `close` 监听器**按注册顺序触发**。core 的在 `connect()` 里**先**注册，onebot 适配器的
要等 `open` 时 `accept(socket)` 才注册，所以**在后**。于是断线那一刻：

1. core 的 close 监听器跑 → 守卫 `getActive()` **还是 true** → 算出"5 秒后重试"、
   `setStatus(RECONNECT)`、打印**唯一**那条 `will retry in 5s...`、**把重试排进 `setTimeout`**；
2. onebot 的 close 监听器跑（`lib/index.js:683`）→ **`bot.offline()`** → `status = OFFLINE`；
3. 5 秒后定时器触发 → 守卫 `if (!this.getActive()) return`（`@satorijs/core/src/adapter.ts:72`）
   → **静默 return**。

`isActive` = 非 `OFFLINE`/`DISCONNECT`（`bot.ts:125-127`）。
**重试被第 1 个监听器排进队列，又被第 2 个监听器作废，最后一声不响地丢掉。**
注意 `retryCount` 只加了一次，**连 `retryLazy`（60s）那档都轮不到** —— 不是"退避变慢"，是**彻底停止**。

**为什么极难发现**：

- 只有**一条**警告，之后**永远安静**：没有重试、没有报错、没有连接。
- 故障发生在**成功路径**上，只看错误数的监控完全瞎。
- 触发条件极普通：NapCat 掉登录 / 被挤下线 / NapCat 重启 / 网络瞬断。
- 模型兜底队列**救不了它** —— 消息根本没进 ChatLuna，四个组一个都不会被调用。

**分层定位（5 分钟，可复用）**：

```powershell
# ① 有没有一条到 NapCat 的活连接？空 = 适配器没连上
Get-NetTCPConnection -RemotePort 3001 -ErrorAction SilentlyContinue

# ② NapCat 侧本身健康吗？（绕开 Koishi 直连它的 OneBot 端点）
node --no-warnings tools\napcat-probe.cjs info
```

**② 通过 + ① 一条连接都没有 ⇒ 命中本坑，重启是唯一出路。**
日志特征：`adapter websocket closed with 1006` + **恰好一条** `will retry in 5s`，然后再无下文。

**已修复（2026-10-02 23:39）**：自写 `koishi-plugin-onebot-watchdog` ——
状态事件看门狗 + 心跳探活（治半开连接）+ 连接卡死判定（治握手卡死）。
已做 A/B 验证：**关掉它 → 98 秒死寂、精确复现本坑；开着它 → 15 秒自愈**。
注意它还要排除 `chatluna-sandbox` 的模拟 bot `onebot:20001`（`excludeSids`）。
详见 [OneBot 断线与静默重连死锁](23-OneBot断线与静默重连死锁.md)。

### 坑 32（★ 通用陷阱：**装好了、日志干净、功能完全不工作**）：`session.argv` 在 `before-send` 里永远是空的

**症状**：在 `ctx.on('before-send', ...)` 里读 `session.argv?.command` 判断「这条消息是不是
指令产生的」，**一次都不会命中**，而且没有任何报错。

**根因**（`@satorijs/core/lib/index.cjs:739-742`）：出站编码器会 **new 一个 session**，
再把原 session 上**可枚举**的键逐个拷过去：

```js
for (const key in this.options.session || {}) {
  if (key === 'id' || key === 'event') continue
  this.session[key] = this.options.session[key]
}
```

而 `argv` 是 Koishi 用 `defineProperty` 挂上去的（`@koishijs/core:1285`）——**不可枚举**，
被这个循环漏掉。

**正确做法**：在 `command/execute`（指令真要执行的那一刻）打一个**普通赋值**的标记：

```js
ctx.before('command/execute', (argv) => {
  const s = argv?.session
  if (s && argv?.command) s.__pageCommand = argv.command
})
```

`chatluna-guard` 的 `__guardControl` 一直有效，正是因为它是一次普通赋值。

> ★ 提炼成通用规则：**任何「中间件里打标记、`before-send` 里读」的写法，
> 标记必须是普通赋值，不能用 `defineProperty`。**

**排查手法**：`before-send` 里加一行 debug 日志把识别到的指令名打出来 ——
打印 `(没有标记)` 就是命中本坑。见 [docs/24 第 8 节](24-指令页面化与图片库.md)。

### 坑 33（★ 出图必踩的两个排版坑）：Markdown 折平换行 + `fullPage` 不会小于视口

**症状一**：把「一行一条」的状态输出渲染成图片，**所有行被折成一整段**，完全没法读。
**根因**：CommonMark 规定单个 `\n` 是**软换行**，渲染成空格。
**修法**：`marked.parse(content, { breaks: true })`（GFM 硬换行）。
★ 它会改变 `render_image` 工具出图的风格，所以做成**按次覆盖的参数**：
`chatluna-render` 默认 `false`，`chatluna-page` 传 `true`。

**症状二**：每张短图下面拖着约 900px 空白（内容只占 300px 高，图却有 1350px）。
**根因**：`page.screenshot({ fullPage: true })` 只会**向下**扩展到内容高度，
**不会向上缩到视口以下**。
**修法**：把视口高度设成很小的值（`chatluna-render` 的 `viewportHeight`，默认 10），
让 fullPage 贴着内容收边 —— 短页面 1320×1350 → 1320×437，**长页面完全不受影响**。

> 注意：**「用 `page.evaluate` 量内容高度」这条路走不通** ——
> `allowJavaScript: false` 时页面脚本是关的。只能用「视口高度 + fullPage」。

### 坑 34（★ 想拿指令说明就必踩）：`Command.toJSON().description` 是 `[object Object]`

**症状**：用 `cmd.toJSON().description` 取指令说明，**每一条**都是 `[object Object]`。
本次第一版帮助页 124 条指令的说明栏全废。

**根因**（`@koishijs/core/lib/index.cjs:1648-1655`）：`I18n.get(key, locales)`
返回的是 **locale → 文案 的映射对象**，不是字符串：

```js
get(key, locales = []) {
  const result = {}
  for (const locale of this.fallback(locales)) {
    const value = this._data[locale]?.[key]
    if (value) result[locale] = value
  }
  return result
}
```

而 `Command.toJSON()` 正是用它填 `description` 的（同文件 1125 行）。
**框架自己的 help 插件也绕开了 toJSON**（`plugin-help/lib/index.js:170` 用的是
`session.text(['commands.X.description',''])`）。

**正确做法**：`ctx.i18n.render([], [path, ''], params).join('')`。
第二段路径 `''` 是兜底 —— 文案缺失时返回空串而**不会**打 `missing` 警告，
否则只要有一条指令没写说明，日志就会被刷屏。

### 坑 35（★ 装新插件前必查）：同名指令的多个 action **按顺序取第一个非空返回**

**症状**：自己注册的 `help` 指令明明写了 action，`/help` 却还是框架那套输出。

**根因**：框架的 `@koishijs/plugin-help` 也注册 `ctx.command("help [command:string]")`
（`plugin-help/lib/index.js:129`，而且 `authority: 0`）。同名指令的多个 action 串在一条队列里，
**谁先返回非空谁生效**。

**正确做法**：`koishi.yml` 里摘掉 `help:3nsrbd`，并在插件启动时**自检这个指令名到底指向谁**：

```js
const c = cmdr.get('help')
if (c?.name !== 'help') logger.warn('`help` 解析到了 %s —— 多半是 @koishijs/plugin-help 没关掉', c.name)
```

★ 这条自检**必须走 `logger.info`，不能走 debug 门控的 `log()`**：
生产 `debug=false`，用 `log()` 的话「通过」永远不打印，于是「没打印」既可能是没通过、
也可能是没开 debug —— 自检就失去意义了。（第一版就是这么写的。）

### 坑 36（★ 和坑 32 同类，**最会浪费时间的一个**）：`ctx.before('message')` 注册的是 `before-message`，而 preend 中间件跑在 `attach` 之前

**症状**：新插件 `chatluna-reply-style`（出站加引用和 @）装好、启动日志正常、零报错，
但**一次都没生效** —— 每条出站都打印「出站无触发记录」，引用一个都没加上。

**根因是两条叠在一起，得分开看：**

**① Koishi 的中间件链不是在 `dispatch` 里跑的，而是在一个 `message` 监听器里。**
`@koishijs/core:679` —— `Processor` 构造时就 `ctx.on("message", this._handleMessage)`
（Processor 是随 app 一起建的，**注册得极早**），而 `_handleMessage` 的最后一步才是
`if (result) await session.send(result)`（core:839）。
所以插件里写普通的 `ctx.on('message', fn)`，fn 永远排在 Processor **后面** ——
等我们来打标记，回复早就发出去了。

**② `ctx.before(name, fn)` 根本不是"排在 name 前面"。**
`@koishijs/core:2399`：

```js
before(name, listener, append = false) {
  const seg = name.split('/')
  seg[seg.length - 1] = 'before-' + seg[seg.length - 1]   // ← 给事件名加前缀
  return this.on(seg.join('/'), listener, !append)
}
```

于是 `ctx.before('message', fn)` 注册的是 **`before-message`** —— 一个没人会 emit 的事件。
`ctx.before('command/execute')` / `ctx.before('attach')` 之所以能用，是因为框架真的会 emit
`command/execute` / `attach` 的 `before-` 版本（生命周期），**不是所有事件名都有这一层**。

**正确做法**：用 prepend 中间件，本项目里这条路已经验证过（`chatluna-guard` 闸门 1）：

```js
ctx.middleware((session, next) => {
  session.__myMark = { ... }   // 普通赋值 = 可枚举 = 出站时会被编码器拷过去
  return next()
}, true)                       // ← 第二个参数 true = unshift
```

**附带踩到的第三个坑**：prepend 中间件比 `ctx.before('attach')` 还早，而
`session.stripped.prefix` 是在 attach 里才写上去的（core:1275-1284）。
同在 `chatluna-help` 的未知指令兜底里，第一版直接读 `session.stripped.prefix` 来切前缀，
拿到的永远是 `null`，于是 token 是 `/ext`（带斜杠），正则 `^[a-z]...` 不匹配 ——
**一次都没兜底，日志里连一行都没有**。正解是自己按 `_resolvePrefixes()` 切：

```js
let content = String(session.stripped.content || '').trim()
for (const p of prefixList(session)) {
  if (content.startsWith(p)) { content = content.slice(p.length).trim(); hadPrefix = true; break }
}
```

★ 这一条和 **坑 32**（`session.argv` 在 `before-send` 里永远是空的）是同一类错误：
**代码本身没错，是"什么时候被调用"错了，于是静默失效**。
以后再遇到"装好了、日志干净、功能完全不工作"，先问一句：**我这个回调到底在什么时候被调用？**

### 坑 37（★ 用户凭直觉报的 bug，代码里确实写着）：图片压缩**对每一张图都生效**，不只看大小

**症状**（用户原话）：「我怀疑图片压缩会对所有大小的图片起作用（应该是超过大小的才压缩），
导致图片没有正确理解到」。而且他还怀疑 AI 会把一张图的理解安到另一张图上。

**根因**：`chatluna-vision` 的 `compress()` 是**无条件**的：

```js
const out = await sharp(buf).rotate().resize({...}).flatten().jpeg({ quality: 85 }).toBuffer()
if (out.length >= buf.length) return { buf, mime }   // 只有"压完更大"才不压
return { buf: out, mime: 'image/jpeg' }
```

**实测（生产日志 01:52:06）**：一张 **123727 字节的表情包**被压成 78633 字节。
省下的 45KB 对一次 7 秒的视觉调用毫无意义，而 JPEG 的有损重编码把图里的文字和细节抹掉了。
**用户是对的，代码就是那样写的。** 当时写这段的理由是"1.1MB 的 PNG 压到 68KB，耗时从 19 秒降到几秒"
—— 那条理由只对**大图**成立，实现却推广到了所有图。

**正确做法**：判据改成「**不压会付代价**」才压，两个条件满足其一：

| 条件 | 为什么 |
|---|---|
| 长边 > `maxEdge`（默认 1024） | 不缩就是几千像素，token 和时间都受不了 |
| 字节 > `compressMinBytes`（默认 256KB） | base64 之后进请求体，是真的贵 |

外加一个例外：带 EXIF 旋转信息的图（`orientation >= 5`）必须过一遍 sharp 才能摆正。
`metadata()` 只读文件头，比整图解码便宜得多。

**还有一个连带问题**：缓存键是**原图**的 sha256（当时的注释写着"换压缩参数不会让缓存失效"
—— 那时是特性，现在是 bug）。不处理的话，旧库里「被压糊了的描述」会一直被命中，
**改了参数却不生效**。所以给 `chatluna_image_cache` 加了一列 `v`，读的时候要求
`v >= CACHE_VERSION`，老的自动重解析。Koishi 会自己 `ALTER TABLE ... ADD COLUMN`（实测日志：
`sqlite auto updating table chatluna_image_cache` → `ADD \`v\` INTEGER NULL DEFAULT 0`）。

**顺带修掉的"串行"**：描述原来是**裸的 `{desc}`** 直接替换进用户消息，跟用户自己打的话长得一模一样 ——
模型于是回出「**你这描述也太渗人了**」这种把机器描述当成用户发言的话。
现在正文用 `[图片{i}] {desc}`、引用用 `[引用的图片{i}] {desc}`，
一条消息里多张图时 `{i}` 展开成 ` 1` / ` 2`。**正文和引用分开**这一点尤其重要：
之前两处共用一套模板，模型分不清"哪张是他刚发的、哪张在他引用的那条里"，描述会串。

### 坑 38（★ 静默的惩罚比报错更伤用户）：整群熔断触发后是**彻底静默**，用户只会以为"bot 不理我了"

**症状**（用户原话）：「偶尔回复的延迟很高，需要单独@才会产生回复，不清楚是否是模型的延迟」。
**跟模型延迟无关。**

**根因**：`chatluna-followup` 的**整群熔断**（`groupMaxPerWindow` / `groupWindowSeconds`）
在窗口内接满 N 条后直接 `SKIPPED` —— 一个字都不发。生产实测：

```
01:52:17 [I] chatluna-followup 群 454444539 触发整群熔断（120s 内最多 3 条），跳过 2791932480
```

4 个人的测试群、120 秒最多接 3 条，用户聊到第 4 句就撞上了。**他没有任何办法知道原因。**

**正确做法**：加 `burstNotice` —— 熔断时发一句
「（我先安静一会儿 —— 这 60 秒里已经接了 2 次话，约 20 秒后恢复。急事直接 @ 我。）」，
**每个时间窗最多一次**。默认关（活跃大群里主动出声本身就是噪声），小群/测试群按群打开。

**顺带发现的结构问题**：`groupMaxPerWindow` / `groupWindowSeconds` 原本**只有全局档**，
于是 4 人的测试群和 30 人的真群被迫共用「120 秒 3 条」—— 小群太紧、真群不够紧。
现在这两个也能按群覆盖（`resolveProfile` 一并扩展）。

**★ 同日晚些时候：这一整段被推翻了，`burstNotice` 也删了。**
用户看完这份说明后直接问：「这个应该就是那个出站令牌规则了吧，但是我设想的仅仅是按照时间
添加令牌，其他的没有额外的限制，熔断机制还有必要吗？」+「不要发送固定语句『我先安静一会儿…
急事直接 @ 我』，除了命令产生的回复以及 ai 做出的回复，我不想要逻辑代码额外产生的回复，
宁愿不说话（因为人也可能断线，但是人不会说固定的话）」。

**他是对的，这里犯了两个错**：
1. **重复造闸**：`chatluna-guard` 早就有**真正的令牌桶**（`outboundBurst` / `outboundPerMinute`，
   按时间匀速补令牌，`before-send` 总闸），而 followup 的「熔断」是在它之上**又加了一道
   固定窗口计数**。两套口径、两处参数，算法还更差：固定窗口能跨边界连发 `2×limit` 条
   （t=119s 发 3 条、t=121s 又发 3 条），令牌桶不会。
2. **用固定语句填黑箱**：静默确实让用户困惑，但解法不该是让逻辑代码说人话 ——
   那正是他讨厌的东西。正确解法是**把闸本身修好**（让限流不再频繁触发、规则只有一条），
   而不是在触发时解释。

**最终形态**：followup 的整群参数与 `burstNotice` 全部删除，改成入站时问 guard
`qqbotGuard.bucket.peek(gid)`（**只看不扣**，扣令牌仍只在 `before-send` 一处），
桶空就安静跳过 —— 连模型调用都不发生。见 [docs/24 第 14 节](24-指令页面化与图片库.md)。

### 坑 39（★ 做"指令别名层"的两条死路，都会静默失效）：要抽象指令名，只能用 `Command#alias()`

**背景**：用户要求「给当前的命令抽象一层……只显示别名（英文，一个单词），命令也是使用
斜杠加别名的方式调用」。直觉上有三种做法，**前两种都是坑**：

**死路 A：转发指令**（自己注册 `model`，action 里再 `session.execute('chatluna.use.model …')`）
参数和选项得自己抄一遍，抄漏了就**静默丢参数**；`argv.command` 指向假指令，
权限判定、`-h` 用法、`/help model` 的详情页全部错位。

**死路 B：改写内容**（prepend 中间件里把 `/model` 换成 `/chatluna.use.model`）
**群里直接失效**。`ctx.before('attach')` 是先从 content 上切前缀、再解析
（`@koishijs/core:1275-1289`），而 `inferCommand` 里有一句
`if (argv.root && stripped.prefix === null && isStrict) return`（core:1447），群聊恒为 strict。
**内容里没有前缀 = 这条消息根本没有指令可解析**，而且不报错。要把前缀拼回去就得自己
再实现一遍 `_resolvePrefixes`，纯属重复造轮子。

**正解：`cmd.alias('model')`**（core:963）。别名与主名挂在**同一条指令对象**上：
参数解析、选项、usage、i18n、authority 门槛全部自动继承，一行都不用抄。
rig 47 实测：`/model` 返回的正是 `chatluna.use.model` 自己的文案
「请指定目标模型，或使用 `-a` 恢复跟随默认模型。」，`/models` 正常列模型。

**附带的一个"为什么必须等 ready"**：`_registerAlias` 在名字**已被别的指令占用**时
**直接抛异常**（core:934-940 `duplicate command names`），而各插件的指令是在自己的 apply
里建的。只有 `ready` 之后 `_commandList` 才是完整的，这时判「这个别名有没有被占用」才有意义。
所以我们自己先 `cmdr.get(name)` 查一遍，被占用就 warn 跳过 —— 绝不让一条配错的别名
把整个插件带崩。

### 坑 40（★ 我自己制造的事故，**静默写坏文件**）：PowerShell 5.1 的 `Get-Content -Raw` 默认按 GBK 解码，改一行 UTF-8 文件 = 双重编码

**症状**：往 `package.json` 里插一行依赖，用的是最常见的写法：

```powershell
$t = Get-Content $p -Raw            # ← 这里就已经坏了
$t = $t.Insert($idx, $line)
Set-Content -Path $p -Value $t -NoNewline -Encoding utf8
```

结果 Koishi 启动时报：

```
[W] app failed to migrate manifest  SyntaxError: Unexpected token '﻿'
[E] app Error: Invalid package config \\?\D:\deepseek\QQbot\koishi-test\package.json.
```

**根因**：PowerShell **5.1**（不是 pwsh 7）的 `Get-Content -Raw` 不指定 `-Encoding` 时
按**系统 ANSI（这台机器是 GBK/936）**解码，而文件是 UTF-8。于是中文被"UTF-8 字节当成 GBK
读出来"变成乱码字符串，再以 UTF-8 写回 —— 双重编码：

```
自建 → 鑷缓      测试实例 → 娴嬭瘯瀹炰緥      跳过 → 璺宠繃
```

更糟的是 `）`（U+FF09）这类字符在 GBK 里落到未映射区，来回一趟**丢掉一个字节**，
直接写出一个非法 JSON（`Bad control character in string literal`）。
另外 `-Encoding utf8` 在 5.1 里**会写 BOM**（`EF BB BF`），Node 读 `package.json` 时是 BOM 开头。

**正确做法**：改文本文件一律用 `edit` / `write` 工具（它们按 UTF-8 处理，不碰其它字节）。
实在要在 PowerShell 里做，用 .NET 显式指定编码：

```powershell
$enc = New-Object System.Text.UTF8Encoding($false)   # false = 不写 BOM
$t = [System.IO.File]::ReadAllText($p, $enc)          # 会正确识别并吃掉 BOM
[System.IO.File]::WriteAllText($p, $t, $enc)
```

**怎么发现和修的**：`.scratch/fix-pkg-json.cjs`（按行替换回原文，不做有损的编码反转）
+ `.scratch/check-pkg-encoding.cjs`（扫全文件非 ASCII 行，标出乱码特征字）。
**教训**：这类事故**不报错也能跑很久** —— package.json 里只有 description 和一句
`postinstall` 提示受影响，功能完全正常，只有 Koishi 自己解析 manifest 时才会炸。

> **★ 2026-10-06 复发记录（明知故犯，代价最大的一次）**：为了把 `run-prod.cjs` 里两处

### 坑 41（★ 只有"文字模式"才会撞上）：Markdown 里的 `<br>` 会被 `h.parse` + OneBot 编码器**连子节点一起丢掉**

**症状**：rig 47 用 `/page.text on` 把帮助页切成文字后，`/help` 只剩标题和一句话 ——
**别名表格整张消失**；`/help -all` 的类目表也只剩上半截，页脚第二三行没了。
出图路径完全正常，所以之前几十轮都没发现。

**根因**：出图时 md 交给 marked 渲染（`<br>` 正常变换行）；文字模式下
`page.output()` 把 md **原样 return**，而调用方返回的字符串最终走
`session.send(string)` → `h.parse`。`h.parse` 把 `<br>` 解析成一个**元素**，
OneBot 编码器不认识 `br`，丢弃它时**把它的子节点一起丢了** ——
而 h.parse 的容错解析恰好会把 `<br>` 之后的内容都收成它的子节点。

**正确做法**：`chatluna-page` 新增 `plainify()`，在**所有非出图路径**（文字模式、没服务、
渲染失败）把 md 压成纯文本：`<br>` → 真换行、`</div>` → 收尾换行、其余标签剥掉。
★ **但 `&lt;别名&gt;` 这类实体必须原样留着，不能反转义成 `<别名>`** —— 压完的文本还是要过
`h.parse`，真写成尖括号就又被当成标签吃掉了（这是同一个坑的第二层，第一版 `plainify`
顺手做了反转义，结果页脚「单条详情：/help 」后面的占位符还是没了）。
留在实体态，`h.parse` 会在文本节点里把它还原成 `<别名>` 显示出来。
判据写进 rig 47 的步骤 ③：`/help` 的文字里**必须**能看到 `/model` 那一行表格。

### 坑 42（★ 第一轮就带着、第三轮复核分页才发现）：`[arg:string]` 是**贪婪**的，第二个位置参数永远拿不到值

**症状**：`/help` 类目页的页脚一直写着「下一页：`/help chat 2`」，但真发 `/help chat 2`
得到的是「**找不到「chat 2」**」。同一条指令的单条详情、`/help 2` 都正常，
只有"目标 + 页码"这种两个位置参数的写法是坏的 —— 而且**不报错**，只是查不到。

**根因**：Koishi 把 `string` 这个类型域定义成**贪婪**的
（`@koishijs/core:1331-1333`，`ctx.domain("string", h.unescape, { greedy: true })`；
`text` / `rawtext` / `el` 同样贪婪）。解析位置参数时有一条：

```js
// core:385-388
if (content[0] !== "-" && this.ctx.$commander.resolveDomain(argDecl.type).greedy) {
  args.push(this.ctx.$commander.parseValue(Argv2.stringify(argv), "argument", argv, argDecl))
  break                                    // ← 把**剩下所有 token** 一次性塞给第一个参数
}
```

而 `Argv.stringify()` 是把剩余 token 全拼起来（`core:239-248`）。
所以 `help [target:string] [page:number]` 里：
`/help chat 2` → `target = "chat 2"`、`page = undefined` → 拿整串去查类目 → 查不到。

**正确做法**（两种，按需要选）：

### 坑 43（★ 只坑日志，但坑得很像 bug）：Koishi 的 logger 走 Node `util.format`，**不支持 `%.1f`**

```js
logger.info('出站排队：%s 等 %.1fs 再发', key, wait / 1000)
// 实测输出：[I] chatluna-guard 出站排队：454444539 等 %.1fs 再发 1.764
//                                              ^^^^^ 占位符原样打出来，参数被甩到行尾
```

`console.log` / `util.format` 只认 `%s %d %i %f %j %o %O %c %%`，**精度写法 `%.1f` 不在其中**
（那是 C 的 printf / Python 的 %）。它不会被当成占位符，于是既原样留在字符串里，
又把多出来的那个参数按"多余的参数"追加到末尾 —— 一行日志同时错两处。

**正确做法**：

```js
logger.info('出站排队：群 %s 等 %ss 再发', key, (wait / 1000).toFixed(1))
```

**怎么发现的**：rig 51 验"出站最小间隔"，日志里要读等待秒数，一眼看到 `%.1fs`。
排查方向一度跑偏到"是不是 logger 的参数顺序错了"—— 记住这条：**要精度就先自己 `toFixed`**。

### 坑 44（★ 静默给出错误数据）：`h.image(buffer)` 把 Buffer 放在 `attrs.src`，**不在 `attrs.file`**

```js
logger.info('... %d 字节 ...', el?.attrs?.file?.length ?? 0)   // → 永远是 0，而且不报错
```

### 坑 45（★ 想改"发送时机"必须知道的事实）：cordis 的 `serial` 是**顺序 await**，不是并发

`@satorijs/core` 的 `MessageEncoder.send()` 用 `app.serial(session, 'before-send', ...)` 调所有出站监听器。
`serial` 到底怎么跑，决定了"能不能在这里排队"：

```js
// @cordisjs/core/lib/index.cjs
async serial(...args) {
  for await (const result of this.dispatch("serial", args)) {
    if (isBailed(result)) return result
  }
}
```

`for await` 逐个 await 每个返回值 → **监听器是一个接一个跑的**（不是 `Promise.all`），
而且返回值非空（`bail`）会**立刻中止**后面的监听器。

这条事实有两个方向的影响：

* **能做**：在 `before-send` 里 `await` 一个定时等待，就真的把这条消息的发送推后了；
  后面几个监听器（page 的出图、reply-style 的引用/@）也会一起等 —— 这正是"两条消息之间至少隔 N 秒"。
  （注意顺序：先注册的先跑，所以 guard 的等待发生在 page 渲染**之前**，总延迟是相加而不是重叠。）
* **不能忘**：一个监听器 await 很久，会把**同一条消息**后面的监听器全堵住；
  别在 before-send 里做慢查询或长网络请求。

**怎么确认的**：写最小间隔之前先把 `node_modules/@cordisjs/core` 里的 `serial/parallel/emit`
三个实现读了一遍（`parallel` 是 `await Promise.all`，`emit` 是同步派发不等结果）。
**别凭直觉猜事件语义** —— 猜错的表现是"插件装了但没效果"，本项目已经栽过两次（坑 39 的两条死路）。

### 坑 46（★ 验规则的坑，不是代码的坑）：验一条规则之前，先把**另一条规则的干扰**排掉

### 坑 51（★ 自写插件的自伤循环）：看门狗把**自己刚接好的**连接每 30 秒掐一次

2026-10-03 17:03，NapCat 重启（QQ 客户端 17:04:45 起）。此后日志变成这样，**每 30 秒一轮、永不停止**：

```
17:15:06 [I] onebot-watchdog ✓ 重连成功，已恢复 ONLINE
17:15:36 [I] onebot-watchdog 状态变成 OFFLINE（core 自己不会重连了） —— 连接状态还是 ONLINE，先 stop() 断开旧连接
17:15:36 [W] onebot-watchdog 状态变成 OFFLINE（core 自己不会重连了） —— 30.0s 后自动重连
17:15:36 [I] onebot-watchdog ✓ 重连成功，已恢复 ONLINE
（16:06 / 16:36 / 17:16:06 … 无限重复）
```

一天 40 次 OFFLINE、21 次重连，**其中每 30 秒有 0.x 秒连接是断的** ——
这段时间里进群的消息直接丢、出站发送报 `网络连接异常!`（`retcode 1200`）。

**成因是"自己踩自己"，两处叠加**：

1. `recover()` 里 `await bot.stop()` 会让适配器**异步** emit 一次 `bot-status-updated(OFFLINE)`；
2. 那次事件到达时 `s.busy` 已经落回 `false` —— 因为 `bot.start()` 是"发起即返回"的，
   `recover()` 早在事件到达前就跑完了。于是状态事件那条路**又排了一个 30s 后的重连**。

**修法（两层，缺一不可）**：

- **硬规矩**：`recover()` 开头 —— `if (bot.isActive && bot.status === ONLINE && !force) return`。
  **已经是 ONLINE 就不许再 `stop()`**。唯一例外是探活判死（半开连接时 status 也停在
  ONLINE 但连接其实死了），由 `scheduleRecover(bot, reason, true)` 显式 force 放行。
- **掐掉燃料**：`recover()` 里 `stop()` 之前记 `s.selfStopAt = Date.now()`，
  状态事件里 5 秒内的 OFFLINE 直接不排重连（`recover()` 的尾巴会按真实结果决定要不要重试）。

**教训**：自写的"兜底重连"层，最大的风险不是"连不上"，而是**它自己制造断线**。
凡是"收到 A 事件就做危险动作 B"的看门狗，都要先问一句：**这个 A 是不是我刚才做 B 造成的？**

### 坑 53（★ 主动插话被挂上"引用 + @"）：出站整形不能靠"频道里最近一条消息"兜底

`chatluna-reply-style` 的引用/@ 目标解析顺序是：

主动插话的伪 session 是**凭空造出来的**（`bot.session(event)`），没有 `__rsTrigger`，

### 坑 54（★ 设计缺陷，不是 bug）：清历史池把"群聊热度"一起清了，于是最该插话时分数永远起不来

`chatluna-proactive` 的历史池语义是"**bot 上次说话之后**群里聊了什么"，
所以每轮正常回复后 `proactive-pool-reset` 会把它清空（这是对的，避免重复作答）。

但活跃度分数**也是拿这个池子算的** —— 于是：一群人在刷屏，中途有人 @ 了 bot 一句，
bot 正常回话 → 池子清零 → 热度归零 → **这一波最该插话的时刻，分数永远到不了阈值**。
实测频率：10-02 全天 28 次评估、10-03 白天 270 次评估，**只有 1 次越过 0.6 阈值**。

**修法**：把"热度"独立出来 —— `pool.heat`（只收非 direct 消息的时间戳，清池不影响，上限 240 条）
专供 `activityScore`；池子 `pool.msgs` 继续只服务提示词与条数兜底。
顺带把"决定插话"的那行日志改成**不看 debug 开关**的 INFO，并把
`活跃度 / 阈值 / 热度 N 条 / 待插话 M 条` 全打出来 —— 否则"到底判没判它插话"在日志里根本看不见。

**教训**：一个数组别背两种语义。**"给模型看的上下文"和"用来做决策的统计量"必须分开存。**

### 坑 55（★ 一次匹配毒化后面全部判断）：关键词黑名单必须限定"最近几条"，拒绝之后还要截池

第六轮续加的"话题黑名单"（群在聊电竞就**直接**不插话）。第一版拿**整个历史池**去匹配：

```js
const text = pool.msgs.filter(m => !m.direct).map(m => m.content).join('\n')   // ← 全池
```

rig 55 第一次跑就露馅 —— 6 次触发**全部**命中：

```
放弃插话：命中话题黑名单「比分」（10 秒内不再试）        ← 群里早就换话题了
```

**教训**：任何"按内容做判断"的门禁，都要先问一句 **"这段内容什么时候算过期？"** ——
池子/缓存/窗口这类"攒起来的东西"，攒的语义和判的语义往往不是一回事。

### 坑 57（★ 每条命令被回答两次）：杀不干净留下的"孤儿 worker"，而端口检查看不见它

**现象**（10-03 19:17 用户报）：群里**每条命令都收到两条回复**；同时另一个群的 `/mem` 直接报错。

查法：先看**谁连着 NapCat**，而不是看端口。

```powershell
Get-NetTCPConnection -RemotePort 3001 | Select State,LocalPort,OwningProcess
```

```
Established  9147  3001  27672    ← 17:03 起的那个实例，还活着
Established  2535  3001  30212    ← 18:57 起的当前实例
```

`27672` 是个**孤儿**：它的父进程 `8552`（`node node_modules\koishi\bin.js start`）是 17:03 那次启动留下的，
`job_kill` 只收掉了 pwsh 那一层，node 那棵树活了下来。它**不监听任何端口**
（`Get-NetTCPConnection -State Listen | Where OwningProcess -in 8552,27672` → 空），
所以 `run-prod.cjs` 的"5140 被占就拒绝启动"检查**完全看不见它**；
而 NapCat 的 WS 服务端是**广播**给所有客户端的，于是两个实例都在处理同一条消息、都回一次。

同一条证据链解释了 `/mem` 那半边：孤儿跑的是 18:57 之前的旧代码，两边行为还不一样（见坑 58）。

**教训 / 规矩**：

| 判据 | 为什么 |
|---|---|
| "有没有实例在跑" = **谁连着 NapCat**，不是"谁占着 5140" | 孤儿收不到端口却照样收事件，端口判据对它天然失明 |
| 收尾要按**进程树**收（`taskkill /PID <run-prod 或 bin.js> /T /F`），启动脚本里再兜一次底 | `job_kill` 只保证 pwsh 那一层结束 |
| 启动前自检，别靠人记得 | `node tools\run-prod.cjs --check` 打印"端口谁占着 / NapCat 上有几个客户端 / 有没有孤儿"，并给出收尾命令 |
| `--kill-orphans` 只收**丢端口**的；`--takeover` 才连健康实例一起收 | 手滑的代价不该是"把正在服务的实例杀了"；"重启"是明确动作，用明确的开关 |

`run-prod.cjs` 现在在启动前做这道检查：`NapCat 客户端数 > 1` 或"有客户端但不持有 5140"就**拒绝启动**
并打印现成的 `taskkill` 命令（`--kill-orphans` / `--takeover` 让它自己收）。

**顺带一条**：那个孤儿在 19:25 前后自己死了 —— 它的 stdout 管道早断了，**它的日志一个字都没留下**。
所以"日志里没有异常"永远不能当作"没有第二个实例"的证据。

### 坑 58（★ 整条消息一个字都发不出去）：元素标记当成正文打出来，又被解析回元素

**现象**：`/mem`（`episode.preview`）在 1040488785 群里必失败：

```
19:18:11 [D] onebot [response] { status: 'failed', retcode: 1200, data: null,
             message: '下载文件失败: Bad Request', echo: 48 }
19:18:11 [W] session Error: Error with request send_group_msg, args: {...16 个元素, 10 张图...}
```

同一条命令在 454444539 群**正常**（126 字符 → `page` 渲染成图）。区别只有一个：那个群近况里没图片。

**根因**：`session.content` 是**元素标记**不是文字 —— 图片消息存进库的是

```
<img src="https://multimedia.nt.qq.com.cn/download?appid=1407&amp;fileid=…&amp;rkey=…" summary="" file="…" sub-type="0"/>
```

`renderLines()` 原样把它打进 `{episode()}`，而 `/mem` 又把这个字符串**返回给框架发送** ——
Koishi 对指令返回值会 `h.parse()`，于是：

1. `<img src="…">` 变回**真的图片元素**，NapCat 去下载那个**早就过期**的 rkey 链接 → `retcode 1200` → 整条失败；
2. `<at id="123"/>` 变回**真的 at 元素** —— 打一行调试信息顺手 @ 一下群友；
3. 模型那份提示词里也塞满带签名的长 URL（一张图几百字符），纯噪音。

实测往返语义（`.scratch/probe-escape.cjs`）：

```
escape : 玩法 &lt;img src="…"/&gt; 结束 &lt;at id="123"/&gt;
解析回 : 玩法 <img src="…"/> 结束 <at id="123"/>      ← 往返一致，用户看到的字符不变
不转义 : 元素类型 = text,img,text,at,text             ← 这就是事故现场
```

**修法（两层，缺一不可）**：

| 层 | 位置 | 做什么 |
|---|---|---|
| 渲染层 | `chatluna-episode` 的 `plainText()`；`chatluna-proactive` 的 `plainTextOf()` | 元素标记 → 可读文字：`<img>` 丢掉（条数已由 `［含 N 张图］` 标注）、`<at id="x">` → `@x`、其余标记丢掉；顺手把 `img/image/video/audio` 翻成 `[图片]/[视频]/[语音]` |
| 出口层 | `episode.preview` / `focus.status` 的 `return` | `h.escape()`：**用户原文和模型产出**（滚动总结、专注标题）里任何 `<…>` 都只当字面量 |

**为什么出口层不能省**：渲染层只清得掉"我们已知的元素标记"，而这两段里混着**群友手打的字**
（有人真的会发 `<3`）和**模型写的总结**。`h.escape` 是唯一能保证"原样送到群里"的关口，
且已实测与 `h.parse()` 往返一致。

**验证**：新增 [rig 56](../koishi-app/tools/scenarios/56-episode-preview-markup.json) ——
先发两条纯图片消息（保证近况里真有图片标记），再敲 `/mem`，判据三条：
出站**没有 http 图片段** / 正文**保留** `［含 1 张图］` / 正文**没有** `<img` 与签名 URL。
修复前那条消息是 16 个元素 10 张图，修复后是 **1 个 text**。

**附带收获**：`chatluna-proactive` 的 `plainTextOf()` 兜底原本也是 `return session.content`，
于是**纯图片消息**在插话提示词里就是一行 `<img src="…rkey=…">`。
除了噪音，它还会让**话题黑名单误命中** —— 图片链接里凑巧含 `lpl`/`vct` 这种子串，bot 就以为群里在聊电竞而闭嘴。
现在兜底走 `stripMarkup()`，提示词里那行变成 `[图片]`。

**教训**：**"给人看/给模型看/给框架解析"是三种不同的字符串**。
凡是把"存下来的消息"再拼出去的地方，都要先问一句：**这个字符串等下会被谁解析？**
Koishi 对**指令返回值**默认按元素解析，这一条尤其容易忘。

### 坑 59（★ 一条咽喉全程静默，日志里连一行都没有）：`session.uid` 是**两段**的，我按三段写

**现象**：短期情景记忆（`chatluna-episode`）号称"入站 + 出站双向落库"，入站那半一直好好的，
**出站那半一条都没记过** —— 而且不报错、不打日志、没有任何异常：

```
sqlite> select isBot, kind, count(*) from chatluna_episode group by isBot, kind;
isBot=0  kind=chat  n=417          ← 全是别人说的话
（isBot=1 一行都没有）
```

历次日志里的 `渲染 {episode()}：… 其中 bot 自己 N 条` 也**全是 0**（含专门验情景记忆的 rig 52）。
更糟的是：这条咽喉正是当初用户提的那个 bug 的解药 ——
「ai 和我说了晚安，我两小时后找它，它却不觉得我起太早」= **它连自己说过什么都不记得**。

**根因（两层，第二层是顺手挖出来的）**：

1. **`session.uid` 只有两段**。`@satorijs/core` 的 `src/session.ts:79`：

   ```ts
   get uid() { return `${this.platform}:${this.userId}` }   // onebot:2178517838
   ```

   而事件处理器里写的是 `/^(?<platform>[^:]+):(?<channel>[^:]+):(?<bot>[^:]+)$/` ——
   三段式，`exec()` 永远返回 `null`，于是**每一条出站消息都在第一行 `return`**。
   出站 session 上真实存在的是 `platform` / `channelId` / `selfId` 三个独立字段
   （`userId` 是**触发者**、`uid` 是 `platform:userId`，都认不出"这是 bot 自己发的"）。

2. **出站 session 的 `session.content` 不是"要发的文字"，是"同一段内容的标记串"**：

   ```ts
   get content() { return this.event.message?.elements?.join('') }
   ```

   实测它长这样（含 reply-style 刚加上的引用/@ 前缀）：

   ```
   content 字段="<quote id=\"100003\"/><at id=\"2791932480\"/>在。\n\n<p>你今天第几遍了啊…"
   ```

   照它入库 = 把 `<quote>`/`<at>` 标记写进情景库 —— 坑 58 的同类（`/mem` 打出来会被当元素解析、
   `<at>` 还会真的 @ 到人）。**只能从 `session.elements` 重建纯文本**（page / replyshaper /
   reply-style 读的也都是 elements）。

**修法**：出站咽喉改成从 `session.platform / channelId / selfId` 三个字段分别取值
（私聊频道号是 `private:<对方>`，`scopeKeyOf` 要用对方拼 scope），正文用递归的元素遍历重建：
`text` 取 `attrs.content`、`img` 计入张数、`at` → `@id`、`face` → `[表情]`、`quote` 丢掉、
`br` → 换行、其余容器**递归进 `children`**。

**为什么必须递归**：模型回复里写 `<p>…</p>` 时，编码器会把它解析成真的 `p` 元素 ——
文字在 `children` 里，不在 `attrs.content`。第一版只取后者，实测把
`在。\n\n<p>你今天第几遍了啊……有事直接说</p>` 记成了 `在。  [p]`（尾巴整段丢了）。

**刻意的例外**：带 `__guardIsCommand` 标记的**指令输出**（`/help`、`/mem`、`/guard.*` 的回执）
仍然不记。这既符合直觉（"bot 说过的话"指的是它自己聊的内容），也挡住一个真会咬人的反馈环：
`/mem` 打印的是记忆本身，把它再记回记忆里，下一轮就会读到上一轮的转储，越滚越大。

**验证**：[rig 57](../koishi-app/tools/scenarios/57-episode-outbound.json)（`/guard.allow` →
@bot 闲聊一句 → @bot 让它调 `render_image` 发图 → `/mem`），判据 A–E 全过：

```
记录出站消息：onebot:channel:777000556 ｜元素 5 个（图 0）｜content 字段="<quote id=…/><at id=…/>在。…"
              ｜入库=@2791932480在。 你今天第几遍了啊……有事直接说，别老「在吗在吗」的。
记录出站消息：… ｜元素 4 个（图 1）｜入库=@2791932480喏，出站测试。
/mem：实取 6 条（…，其中 bot 自己 3 条）      ← 修复前恒为 0
```

**教训**：**"没报错"不等于"跑了"**。一条只在开头做形状判断就 `return` 的咽喉，
失败姿势是**完全静默**的 —— 所以落库类逻辑必须有一行"我记了什么"的日志（rig 57 的判据就是它），
而验收判据不能只看"条数对不对"，要专门看**分方向的分项计数**（`其中 bot 自己 N 条`）。
rig 52 当初放过了这个 bug，就是因为它的判据只数了窗口总条数。

**同族小坑（这一轮又踩了一次）**：剧本 JSON 里混进 ASCII 双引号（坑 56）→ 伪服务端启动即崩、
日志里一条群消息都没有，看着像"插件没生效"；另外**别用 PowerShell 的
`Get-Content -Raw` + `Set-Content` 去改 UTF-8 剧本** —— 会把中文整段变成乱码
（`_说明` 变 `_璇存槑`），JSON 还是"合法"的，只有内容没了。改剧本统一用编辑器/写文件工具。

**附带查清的一件事（"入库文本里能不能有 `<`"）**：rig 57 第三轮里模型把自己的 HTML 卡片尾巴
写进了正文（`喏，你要的卡片</caption>`），于是入库文本带了个**孤立闭合标签**。写判据时别一刀切
"不许有 `<`" —— 实测（`.scratch/probe-stray-html.cjs`）三种情况完全不同：

| 输入 | `h.parse` 结果 | 危险吗 |
|---|---|---|
| `喏</caption>`（孤立闭合标签） | `text("喏")` —— 标签**直接丢掉** | 不危险（不产生元素、不发请求） |
| `<caption>x</caption>`（孤立开标签） | `caption("")` —— **内容被吞掉** | 不下载，但会丢字（模型自己写坏的） |
| `<img src="…"/>` / `<at id="…"/>` | 真的 `img` / `at` 元素 | ★ 危险：下载过期 rkey → `retcode 1200`；真 @ 到人 |

所以出站入库文本的判据只该盯**会变元素的那几种标签**（`img/image/at/quote/face/button`），
其余 `<` 照原样留着才是忠实的记忆；真正的安全网是**出口的 `h.escape()`**
（`h.parse(h.escape(s)) === s`，三种情况都往返一致）。

### 坑 60（★ 改配置 = 换数据库命名空间）：affinity 的 `scopeId` 同时当**指令根**用

**背景**：用户提出「`/rank` 显示的依然是 `xingyuan.rank`，检查所有的 xingyuan 部分，
全部替换成功能性描述」——`xingyuan` 是小号的旧名「星源」。

**为什么不能只改 koishi.yml**：`chatluna-affinity` 拿配置里的 `scopeId` 干两件事：

| 用途 | 表现 |
|---|---|
| **数据库命名空间** | 所有读写都带 `where scopeId = '…'`（`chatluna_affinity_v2` / `_blacklist_v2` / `_user_alias_v2` / 两个 snapshot 表 / `_migrations`，主键里都有 `scopeId`） |
| **指令命名空间** | `buildScopedCommandName(scopeId, suffix)` → 指令全名是 `<scopeId>.rank` / `.inspect` / `.adjust` …（lib/index.js:1206） |

所以只改配置 = 换了一个命名空间：`/rank` 会**突然空掉**、所有人好感度回到初始值
（旧行还躺在库里，只是再也读不到），而 `qqbot-auth.affinityScopeId`、预设里的
`{affinity("…")}`、别名表的 target、帮助页的 prefixes 也全得跟着改 ——
**一处不改就是"静默失效"**（变量渲染成空串、别名目标缺失）。

**修法**（这一次是完整的五步）：

1. `koishi-app/tools/migrate-affinity-scope.cjs`：扫 sqlite_master 找出**所有带 `scopeId` 列的表**
   （不写死表名，插件以后加表也跟得上），`update … set scopeId='affinity' where scopeId='xingyuan'`。
   有 `--apply` 才真写，默认 dry-run；幂等。
2. `koishi.yml`：`chatluna-affinity.scopeId` + `qqbot-auth.affinityScopeId` → `affinity`
   （生产、测试两份配置 + `tools/gen-test-config.cjs` 三处）。
3. 预设 `default-persona.yml`：`{affinity("xingyuan")}` → `{affinity("affinity")}`
   （不写参数会**静默返回空串**，这是老坑，见 docs/13）。
4. `chatluna-alias` 的 5 条 target：`xingyuan.inspect/rank/adjust/block/unblock` → `affinity.*`。
5. `chatluna-help` 的类目前缀：`['affinity','xingyuan']` → `['affinity']`（留着旧的也无害，但没必要）。

**执行顺序**：**先停 Koishi** → 迁移 → 改配置 → 起。运行中的实例会拿旧 scopeId 继续写，
边跑边迁 = 两边各有半份数据。

**顺带查清的命名权归属**：`scopeId` 的 schema 里本来就写着「**不要使用与 bot 名称相同的
scopeId**，建议优先使用英文」—— 换成功能性名字（`affinity`）正是它推荐的用法，
`xingyuan` 属于历史遗留。

### 坑 61（★ 上游插件的一半功能挂在**这个版本根本不存在的服务**上）：好感度从来不自动更新

**现象**（2026-10-03 深夜查库）：`/rank` 的内容从 10-02 起一个字没变。

```
chatluna_affinity_v2：只有 2 行，两行的 chatCount / lastInteractionAt 都是 NULL
chatluna_affinity_dashboard_snapshot：10-03 那条和 10-02 完全一样（chatCount: 0, latestInteractionAt: null）
整天日志里对 chatluna_affinity_v2 **只有 SELECT，没有任何 INSERT/UPDATE**
```

**根因**：`recordInteractionFromReply`（chatCount+1、lastInteractionAt、连续互动天数、
新用户建档）不在消息事件上，而是挂在 `chatluna_character.getTemp` 上：

```js
ctx.inject(['chatluna_character'], (innerCtx) => { … modelResponseRuntime.start() })
// node_modules/koishi-plugin-chatluna-affinity/lib/index.js:6668
```

而 `chatluna_character` 是 ChatLuna **角色版**分支的服务，社区版 `koishi-plugin-chatluna@1.4.0`
整包（lib 下所有 .cjs/.mjs/.js）grep `chatluna_character` → **0 命中**。它被声明成
`inject.optional`，所以缺了也不报错 —— 表现就是**一行日志都没有**
（插件自带 `debugLogging: true`，本该每轮打「拦截到模型输出事件」，实测整个日志 0 行）。

**修法**：不重写它的逻辑，而是**把它缺的那个服务补上**（`chatluna-affinity-bridge`）：
runtime 只需要 `getTemp(session)` 返回一个带 `completionMessages` 数组的对象
（`registerGetTempListener` lib/index.js:136-182、`handleTemp` 307-336），
我们就在**出站咽喉** `before-send` 把 bot 真正发出去的话 push 进那个数组 ——
剩下全用 affinity 自己的代码，一行都不碰它的表结构。

**为什么这不是"伪造"**：垫片只提供 runtime 契约里最小的那一块（一个数组），
不假装任何业务语义；将来装了带真 `chatluna_character` 的版本，本插件会检测到已存在而**自动让位**。

**代价与取舍**（都写进插件注释了）：temp 全局只给一个（一个数组 = runtime 只订阅一次；
`trackedMessages` 那个 Set 只增不减，一条回复一个数组就是一份永不释放的订阅）；
`push` 前必须先 `getTemp` 刷新 runtime 里的 `sessionByMessages`，顺序不能换。

### 坑 62（★ 出站 session 上 `userId` 恒为 `undefined`）：说话人只能从消息内容里认

**现象**：垫片挂上、记账代码跑到了，但一条都不记。加探针后一眼看穿：

```
【探针】before-send 进来了：guard=- user=undefined self=2178517838 elems=1
【探针】记账跳过：self-or-broadcast
```

**根因**：Satori 建出站 session 的方式（`@satorijs/core` index.cjs:733-742）：

```js
this.session = this.bot.session({ type: 'send', channel: {...}, guild: {...} })
for (const key in this.options.session) this.session[key] = this.options.session[key]
```

它只搬入站 session 的**自有可枚举属性**，而 `userId` / `selfId` / `channelId` 都是
**Session 原型上的 getter**（分别读 `event.user.id` / `event.self.id` / `event.channel.id`）。
新 session 的 event 是现造的、里面只有 channel 和 guild —— 所以搬过来的 session 上
`selfId` 有值、**`userId` 是空的**。
（坑 59 的注释里写着"出站 session 上 `userId` 是触发者"，那句是**错的**；
episode 之所以没受影响，是因为它压根不需要说话人。）

**修法**：按可靠性三级认人，全失败就**不记账**（宁可漏记，也不能把 A 说的话记到 B 头上）：

| 级别 | 依据 | 说明 |
|---|---|---|
| ① | `<quote id="…">` 元素的 id | 就是被回复的那条**入站消息 id**，查"入站 messageId → 说话人"索引，一一对应 |
| ② | `<at id="…">` 元素 | reply-style 的 `@ first` 会带上，排除 bot 自己 |
| ③ | 本频道最近一个说话的人 | 兜底，`fallbackSeconds`（默认 180s）窗口内；填 0 可关 |

**还有一步不能省**：affinity 读的是 `session.userId`，所以喂进去的不能是出站 session 本身，
而是一个 `Object.create(出站session)` 出来的**伪 session** —— 只覆盖 `userId`（+私聊标记），
`bot` / `guildId` / `platform` / `selfId` 沿原型链继承，这样它内部的
`fetchMember(session, userId)` 还能正常去 NapCat 查群名片建档。

### 坑 63（★ 新增自研插件时"少建了一个链接"）：koishi-test 的 node_modules **不是 junction**

`tools/setup-test-app.cjs` 里写着"node_modules 用 junction 复用"，但**现在它不是** ——
测试实例上跑过一次 `npm install` 之后，那里变成了**真实目录**，里面每个依赖是
"目录 + 指向 `koishi-app/external/<插件>/{lib,package.json}` 的链接"。

后果：新插件只在 `koishi-app/node_modules` 建了链接时，测试实例启动会直接报

```
[E] app cannot resolve plugin "chatluna-models"
[E] app cannot resolve plugin "chatluna-affinity-bridge"
```

**而且是"两条 [E] 就完了"**：插件不加载 → 它注册的指令不存在 → 别名层紧接着报
「目标缺失 2」、`/models` 变成"没有这个指令"。**看到 `cannot resolve plugin` 就别往下猜了。**

**规矩**：新加一个自研插件 = 三处都要动
① `koishi-app/package.json` 的 dependencies（`file:external/<名字>`）；
② `koishi-app/node_modules/<名字>` 建链接；
③ **`koishi-test/node_modules/<名字>` 也建一份**（`mklink /J` 到同一份源码，改代码两边同时生效）。

**有脚本了**：`node tools/link-plugin.cjs <插件名>` 一次建好两边 + 写进两份 package.json，
最后自己 `require.resolve` 验一遍；`node tools/link-plugin.cjs --list` 体检全部自研插件。
★ 体检出"只有 koishi-app 一边有"**不一定**是错的 —— 没链进测试台的那几个
（`cmdname` / `replyshaper` / `sticker-admin`）是因为测试台压根没装它们；
真正的判据永远是**测试台启动日志里有没有 `cannot resolve plugin`**。

### 坑 64（★ 别名"被自己撞了"）：Commander 会给 `a.b` 自动建出父指令 `a`

### 坑 65（小但气人）：上游 `/models` 的页脚**不提怎么翻页**

`chatluna.model.list` 是支持翻页的（`-p <page>` / `-l <limit>`，lib/index.cjs:632），
但它的文案是（locale 实测）：

```
pages : 当前为第 [page] / [total] 页
footer: 你可以通过 chatluna.new -p [preset] 或 chatluna.switch 为会话设置默认模型。
```

`pages` 只说"你在第几页"，`footer` 讲的是预设/会话切换 —— **一个字都没提怎么去下一页**。

→ 自研 `chatluna-models` 接管 `/models`：页码做成**位置参数**（`/models 2`），
页脚直接写出下一步敲什么；而且**改过 `-l` 之后提示会把 `-l` 一起带上**
（页码和每页条数不联动，只提示 `/models 2` 会跳到另一个"第 2 页"）。


### 坑 66（★ 同一个 http 服务，`get` 和 `file` 拿到的字节数不一样）：`ctx.http.get(..., {responseType:'arraybuffer'})` 返回 **0 字节**

第九轮写 `chatluna-persona` 时要在启动时把 bot 的 QQ 头像拉下来当"参考形象图"，写法是：

```js
const res = await ctx.http.get(url, { responseType: 'arraybuffer' })
const buf = Buffer.isBuffer(res?.data) ? res.data : Buffer.from(res?.data || [])
```

实测（koishi-test，rig 61）：`参考形象图下载失败（https://q1.qlogo.cn/...）：下到 0 字节` ——
`res.data` 既不是 Buffer 也不是能 `Buffer.from` 出内容的东西，转完就是空。

**同一个 URL、同一个进程**，换成 vision 插件一直在用的写法就成功了：

```js
const res = await ctx.http.file(url, { timeout })   // Koishi 的 http 服务专门为这个封的
const buf = Buffer.isBuffer(res.data) ? res.data : Buffer.from(res.data)
```

教训：**Koishi 的 `ctx.http` 不是裸 axios**，`file()` 才是"要字节"的正路
（它内部处理 responseType / mime 嗅探 / 重定向）。写自研插件要下载文件时，
先去已有插件里搜 `ctx.http.file` 抄一份，不要凭 axios 的经验写 `get`。
→ 修法见 `chatluna-persona/lib/index.js` 的 `fetchToCache()`：**先 `file()`，失败了再退回 `get()`**。

**同一处的第二层坑（上线时才发现）**：头像 URL 里的 QQ 号我是从 `ctx.bots` 里猜的
（"找平台是 onebot 的第一个 bot"）。启动 5 秒后去取时**真正的 OneBot bot 还没连上**，
`ctx.bots` 里是个占位 bot，`selfId` 是 `20001` —— 于是拉回来一张**别人的**头像当成了参考形象图
（日志：`参考形象图已更新：…avatar-20001.jpg`）。占位 bot 在，所以连"拿不到 selfId"的兜底都没触发。
→ 现在生产/测试配置里都**写死** `chatluna-persona.avatarSelfId: '2178517838'`。
凡是"启动早期从 `ctx.bots` 推断自己是谁"的写法都有这个坑，能写配置就别猜。


### 坑 67（rig 的 strict 前缀模式）：指令和图片**必须写在同一段里、文字在前**

要测"引用图片 + 指令"，剧本里最自然的写法是把图放前面：

```json
"elements": [["image", "http://127.0.0.1:3003/x.png"], ["text", "/look -f"]]
```

**这样指令不会被识别**。测试实例的 `prefixMode: strict` 要求消息**以 `/` 开头**，
而第一段是图片元素 —— 于是整条消息被当成普通聊天，指令处理器根本不看它。
正确写法是文字在前：

```json
"elements": [["text", "/look -f"], ["image", "http://127.0.0.1:3003/x.png"]]
```

`chatluna-vision` 的 `vision.this` 因此**两处都收图**：`session.quote.elements`（引用里的图）
和 `session.event.message.elements`（本条消息自带的图），引用优先。
两种真实用法（引用一张图再发指令 / 图和指令发在同一条）都能用。

### 坑 70（★ 一条命令两条回复，第三次了）：防线修在了"不会被敲的那条命令"上

**现象**（2026-10-04 14:4x 用户报）：群里一条命令两条回复。用户原话：
「koishi 似乎老是断线？我重启了 NapCat 依然没有正常工作，然后我手动去重新开启 Koishi 就会出现一个命令两条回复的情况，
**估计是我的启动命令将原来的那个唤醒了**（当前状况是 koishi 假死了应该，我没有自己启动 koishi）」。

**先分清三件事**（都查了，结论和直觉不一样）：

| 用户看到 | 实际是什么 |
|---|---|
| 「koishi 老是断线」 | **NapCat 掉了两次**（08:39:46 / 14:38:50），不是 Koishi 断的。日志里是 `websocket closed with 1006` → `connect ECONNREFUSED 127.0.0.1:3001` ×7 → 14:40:29 **看门狗自己接回来了**（`重连成功，已恢复 ONLINE`） |
| 「koishi 假死了」 | 14:43 实测：**一个实例**、5140 在听、到 3001 一条 ESTABLISHED、探活 2ms —— **它是好的**。那次"假死"的感觉来自 14:38~14:40 那 99 秒的重连窗口 |
| 「我没有自己启动 koishi」 | 对：跑着的那个是 **10-04 03:49 一个 agent 用后台 job 起的**（`run-prod.cjs` → `bin.js` → worker）。**用户看不见它，它却在给群服务** —— 这正是下一次冲突的引信 |

**"两条回复"的真身还是 [坑 57](#坑-57-每条命令被回答两次杀不干净留下的孤儿-worker而端口检查看不见它)**：
NapCat 的 WS 服务端把每条事件**广播**给所有客户端，两个 Koishi 都处理同一条消息、各回一次。

**为什么坑 57 的修复没挡住这一次** —— 这是本条真正的教训：

坑 57 把检查加进了 `tools/run-prod.cjs`（5140 被占就拒绝 / 有孤儿就拒绝）。
但**会被敲下回车的那条命令不是它**：

```powershell
# docs/17 里的这两条，以及 npm start，全都直达 Koishi CLI，一步都不经过启动器：
node node_modules\koishi\bin.js start --log-level 3     # ← 用户"手动重新开启"用的就是这条
npm start                                               # ← package.json 里也是裸的 bin.js
```

于是第二个实例：
1. 抢不到 5140 → `[E] app Error: No open ports available` + `server closing`（[坑 6](#坑-6重复启动实例--静默半死)）；
2. **但适配器照常连上 NapCat** → 第二个客户端；
3. 它的日志打在自己的终端里，`prod-<日期>.log` 里**一个字都没有**（同一天还是覆盖写）。

**A/B 反证**（2026-10-04 14:50，测试台 + 伪 OneBot，全程没碰生产 NapCat）：

```
A) 守卫开：第二个实例 apply 时被拦下 → 退出码 52，3002 上始终只有 1 个客户端
   [E] onebot-singleton-guard 拒绝启动：同一个 OneBot 端点已经有实例在服务 …
   [E] onebot-singleton-guard   OneBot 端点 ws://127.0.0.1:3002：PID 26920 连着
   [E] onebot-singleton-guard   控制台端口 5141：PID 26920 占着

B) 守卫关（enabled: false）：同一个命令 → 它真的连上去了
   [I] onebot-singleton-guard 已按配置关闭（enabled: false）
   [E] app Error: No open ports available          ← 控制台死了
   [I] server server closing
   [I] adapter connect to server: ws://127.0.0.1:3002/   ← 却照样连上 NapCat
   → Get-NetTCPConnection -RemotePort 3002 变成 **2 个**：PID 26920 + 15452
```

**修法**：新增自研 **`koishi-plugin-onebot-singleton-guard`**（约 200 行），把这道检查**搬进 Koishi 自己的配置**里 ——
插件的 `apply()` 在所有插件装配时、适配器建连**之前**跑，所以**从哪条命令启动都躲不过它**：

| 机制 | 治什么 |
|---|---|
| ① 启动前自检：`netstat` 看**谁连着配置的 OneBot 端点**（口径沿用"有没有实例在跑 = 谁连着 NapCat"）+ 控制台端口有没有被**别的进程**占着 | 人/agent 在已有实例还在服务时又起一个（现实中 100% 的场景） |
| ② 连上后 20s 复查 | 两个实例**几乎同时**启动的窄缝。约定 **PID 大的（后起的）让位**，两边判定一致 → 恰好活下来一个 |
| 自己人排除 | 本进程 + 父进程不算冲突（插件热重载时会带着**自己**那条老连接重跑 `apply()`） |
| 扫不到就放行 | `netstat` 偶尔失败只打 WARN —— 不能让机器人因为工具打嗝而起不来；兜底还有 `run-prod.cjs` |

**★ 退出码必须是 52，不能是 1**：`koishi/lib/cli/index.js` 的 `shouldExit()` 里
**51 = 重启、52 = 真退出**，其它非 0 码在 `daemon.autoRestart`（默认 true）下会**自动重生 worker**
→ 守卫要是 `exit(1)`，就变成"拒绝启动 → 重开 → 再拒绝"的**死循环**。实测确认：`exit code: 52`。

**配置**：生产 `onebot-singleton-guard:sgd001`（endpoint 3001 / consolePort 5140）、
测试 `sg0001`（endpoint 3002 / consolePort 5141）—— 两边端口不同，**测试台和生产可以并存**。

**验证**（2026-10-04 15:2x，测试台 + 伪 OneBot，全程没碰生产 NapCat；复验脚本留档 `.scratch/guard-verify.ps1`）：

| 场景 | 期望 | 实测 |
|---|---|---|
| A 端点上只有一个**非 Koishi 的观察者**（模拟 `napcat-probe`） | **放行**，且 20s 复查不许把健康实例退掉 | `提醒：端点上还有非 Koishi 的客户端 … PID 9204（node …ws-observer.cjs）` → `启动自检通过` → 实例照常连上；复查 `端点上还有 1 个非 Koishi 客户端（PID 9204）—— 不是第二个实例，继续服务`，实例存活 ✓ |
| B 真·第二个实例 | 拒绝、`exit 52`、**不建立连接** | `[E] 拒绝启动 … 控制台端口 5141：PID 25420` + `OneBot 端点 …：PID 25420`；退出码 **52**；3002 上始终只有 1 个客户端 ✓ |
| C 观察者 + 真实例共存 | 观察者不许"掩盖"真实例 | 仍拒绝、退出码 **52**、点名 PID 11628 ✓ |
| 反证：守卫关掉（`enabled: false`） | 第二个实例**真的连上**（复现事故） | `[E] app Error: No open ports available` + `server closing` 之后**仍然** `adapter connect to server: ws://127.0.0.1:3002/`；`RemotePort 3002` 变成 **2 个 PID**（26920 + 15452）✓ |

★ "观察者"那一条不是洁癖：docs/23 教的排障第一步就是"**先跑 `napcat-probe`**"，紧接着才重启 Koishi。
只按"有几个客户端"判，**这条正经流程会被自己拦住**，连上后的复查还会把刚起来的健康实例当成
"后起的那个"给退掉。所以守卫用 `Get-CimInstance` 查命令行**辨认身份**：像 Koishi
（`koishi/lib/worker`、`koishi/bin.js`）才算冲突，其它程序只告警放行；
**认不出身份时"启动前从保守（拒绝）、连上后从宽（只告警）"** —— 宁可拦住一次启动，也不能误杀在服务的实例。

**顺带查清的第一个洞：`retryLazy` 默认 60 秒 —— "我重启了 NapCat 依然不工作"有一半时间耗在这里。**
今天两次掉线（08:39:46 / 14:38:50）**都不是 Koishi 断的**，是 NapCat/QQ 进程整个没了
（端点端口关闭 → `ECONNREFUSED`，**全程零 `bot_offline` 通知**，所以不是"被别的登录挤下线"）。
看门狗 8 秒后就把重连踢起来了，但 `@satorijs/core` 的阶梯是 `5s × retryTimes(6)`，之后是
**`retryLazy`（默认 60s）**：

```
14:38:50 websocket closed with 1006
14:38:58 看门狗 已发起重连（当前 CONNECT）
14:39:29 failed to connect … will retry in 1m      ← 6 次 5s 用完，进入懒重试
14:39:39 ★ 用户已经把 NapCat 重新起来了（QQ.exe 新 PID），端口已经通了
14:40:29 才 connect to server                      ← 白白多等 50 秒
```

**那 50 秒就是"我重启了 NapCat 依然没有正常工作"** —— 用户于是去手动重启 Koishi，
而那一步才造出"两条回复"。→ 生产与测试的 `adapter-onebot` 都加 `retryLazy: 10000`
（该字段本来就属于 `Adapter.WsClientConfig`，控制台里可见，也不会被配置重写吃掉）。
实测（测试台，看门狗调成生产时序，杀掉端点再拉起）：
`… will retry in 5s` ×6 → **`will retry in 10s`** —— 阶梯确实换成了 10 秒一档，
上游一回来最多再等 10 秒（原来最多 60 秒）。

**顺带查清的第二个洞：排障第一步自己就是坏的。**

| 判据 | 为什么 |
|---|---|
| **防线要修在"真会被敲的那条命令"上** | 只堵住便利入口（`run-prod.cjs`）而放过裸入口（`bin.js start` / `npm start`），等于没堵 —— 因为人和 agent 敲的恰恰是裸的 |
| "第二个实例"的**唯一权威判据是"谁连着 NapCat"** | 它抢不到 5140 时会"半死"着照样收事件（坑 6）；丢了端口的孤儿更是连端口检查都看不见（坑 57） |
| 能放在**配置里**的检查，别只放在**启动脚本**里 | 配置是所有启动路径的公共必经点；脚本只是其中一条路 |
| **`process.exit(52)` 才是 Koishi 语境下的"我拒绝启动"** | 其它非 0 码会被 CLI 当成"崩了，重开" |
| 「我没启动 koishi」≠「没有实例在跑」 | agent 的后台 job 起的实例，用户看不见；而它照样在服务、照样和用户手起的那个撞车。**排障第一步永远是 `node tools\run-prod.cjs --check`** |
| 「重启了上游还是不工作」要看**上游回来之后**多久才重连 | 阶梯最后一档默认 **60 秒**：NapCat 已经好了，机器人还在睡（今天实测白等 50 秒，正是用户去手动重启 Koishi 的原因） |
| **按命令行匹配杀进程时，必须把生产排除掉** | 生产 CLI 的命令行里**同样**有 `bin.js start`。2026-10-04 15:24 我用 `-match 'bin\.js start'` 收测试实例，**把生产一起杀了、停了 7 分钟**（15:31:40 才被重新拉起）。收测试台一律要带 `-notmatch 'koishi-app'`，杀完立刻 `run-prod.cjs --check` 复核 |

**顺带记一笔**（同一次排查里的发现）：`koishi.yml` 会在**任何实例启动/保存配置时被重写**
（坑 7）。这次给测试配置加完插件块后，一次被拒绝启动的实例也把它重写了一遍（14:51:21）——
**手加的块没丢**（归一化后的形态和手写的一致），但改动配置前先停进程这条规矩依然成立。


### 坑 71（★ 单位混了一次，"只有一半功能生效"）：作息表的**进入语**从来没写进记忆

第九轮新增的 `chatluna-routine` 在 `stateAt()` 里把 `absStart` 算成 **epoch 分钟**
（`baseMin + w.start`），而 `tick()` 里却是 `(now - cur.absStart) / 60000` —— `now` 是**毫秒**。
两个单位一减，任何"**进入**某个时段"的转换都得到两千万分钟，直接命中 `tooLate`
（`catchUpMinutes` 默认 20）那一条，于是 `enterText` **一次都没写过**。

**它的伪装性极强**：只有"进入时段"这一侧错，"离开时段 → 醒着"那一侧是对的
（醒着状态的 `absStart` 是 `null`，`lateMin` 走 0 分支）。所以上线当天生产里看到的是：

```
2026-10-04 07:48:24 作息切换：sleep → 醒着（写入记忆）      → 我睡醒了。        ✅
2026-10-04 11:46:25 作息切换：awake → 午饭，已开始 29850929 分钟（★ 错过太久，只更新状态、不写记忆）
2026-10-04 12:26:25 作息切换：lunch → 醒着（写入记忆）      → 吃完了，回来啦。   ✅
```

**"我睡醒了""我吃完了"都正常，"我先去吃饭啦"永远不出现** —— 如果只看"有没有生活事件进记忆"，
这条链是"好的"；只有把三句话对着作息表逐条数，才看得出少了一句。
（29850929 分钟 ≈ 56 年，就是这个 bug 的指纹：`(ms - min) / 60000`。）

**修法**：`stateAt` 里的 `absStart/absEnd` 一律改成**毫秒**（`absStart * 60000`），
`startedAt/endsAt` 由它派生；并把这条算式写成注释钉在代码里。

**验证方式**（不等真实时间点）：把测试实例的午饭时段临时改成"两分钟后开始"、`jitterMinutes: 0`，
起实例跑一轮，看日志与库：

```
修复前：[I] 作息切换：awake → 午饭，已开始 29850929 分钟（★ 错过太久，只更新状态、不写记忆）
修复后：[I] 作息切换：awake → 午饭，已开始 0 分钟（写入记忆）
        [I] chatluna-episode 作息事件写进 8/8 个群会话：我先去吃饭啦！这个你测一下~
```

★ 这类"时间/单位"改动的测试**必须用"把时间点挪到眼前"的办法**，不要等真实作息 ——
否则一轮验证要花半天，而且会让人误以为"没触发就是没到点"。


### 坑 72（运维）：让 bot 活着的那个进程，不该是我的会话的后台任务

第九轮的实例是当**后台 job** 起的（项目一直这么干）。当天它被杀了两次：

| 时间 | 谁杀的 | 证据 |
|---|---|---|
| 15:24 | **另一个会话按命令行匹配收测试实例时误杀**（见坑 70 最后一条） | 坑 70 自己记着「停了 7 分钟（15:31:40 才被重新拉起）」 |
| 15:29 | 同类清理（我 15:26 刚起的那个又被带走） | 日志停在 15:29:13，无 `[E]`、无堆栈 |

**做法**：把生产**脱离当前会话的进程树**启动（WMI 起进程，父进程是 `WmiPrvSE.exe`）：

```powershell
$cmd = 'node.exe "D:\deepseek\QQbot\koishi-app\tools\run-prod.cjs" --log-level 3'
Invoke-CimMethod -ClassName Win32_Process -MethodName Create `
  -Arguments @{ CommandLine = $cmd; CurrentDirectory = 'D:\deepseek\QQbot\koishi-app' }
# 回执：ReturnValue=0 PID=<run-prod 的 pid>；父进程链应为 WmiPrvSE.exe → node.exe → node.exe → node.exe
```

日记照旧写 `tools/logs/prod-<UTC 日期>.log`，不受影响（run-prod 自己 tee 到文件，不依赖控制台）。

**代价（要记住）**：这样起的实例**没有窗口**，控制台里也看不到 —— 正是坑 70 里
「我没有自己启动 koishi」那种困惑的来源。所以：

| 想知道 | 敲什么 |
|---|---|
| 有没有实例在跑 / 有几个 | `node tools\run-prod.cjs --check`（看 5140 与"谁连着 NapCat"） |
| 停掉它 | 先 `Get-NetTCPConnection -LocalPort 5140 -State Listen` 拿 PID，再 `taskkill /PID <pid> /T /F`（**按 PID**，别按命令行 —— 坑 70） |
| 它今天说了什么 | `tools\logs\prod-<日期>.log` |

★ 另外：`IsHidden`/无窗口**不影响**新增的 `onebot-singleton-guard` —— 那道闸门在 Koishi 进程内部，
不管实例是从哪条命令、哪个终端、哪个会话起来的都会拦（这正是它存在的意义）。


### 坑 73（★ 最会骗人的一种故障："所有指标全绿"但消息进不来）：NapCat 的 API 一切正常，是 **QQ 自己的网络栈死了**

2026-10-04 16:13 之后 bot 彻底不回消息。把所有"看起来在线"的指标查一遍，**全是绿的**：

| 指标 | 当时的值 | 为什么不能信 |
|---|---|---|
| `get_status` | `{"online":true,"good":true}` | NapCat 的自述状态（本地乐观值） |
| `get_login_info` | `2178517838 大肥鱼` | 读本地登录态 |
| `get_group_list` / `get_recent_contact` | 正常返回 2 个群 | 读本地缓存 |
| WS 心跳 | 30 秒一条，一条不少 | NapCat 自己的定时器，跟 QQ 的网络无关 |
| 3001 连接 | Koishi 连着 | 只证明"Koishi↔NapCat"这段是好的 |

**唯一能问出真话的问题**，是让 QQ 真的去做一次网络动作：

```powershell
node tools\napcat-probe.cjs send-private <自己的号> "链路测试"
# → retcode 1200：{"result":1006514,"errMsg":"网络连接异常!"}
#    来自 QQ 内核 NodeIKernelMsgService/sendMsg —— QQ 自己承认网络是断的
```

**入站是什么时候断的**：`call get_recent_contact` 里每个会话的 `lastestMsg.time` —— 它停在几点，就是入站死掉的时刻。本例测试群停在 `16:13:03`（最后一条 `/mood`），另一个 30 人活跃群停在 `15:55`，之后 45 分钟**两个群一条都没有**。

**日志侧成因**：`recv failed with error: 10054`（`WSAECONNRESET`，对端重置）→ QQ 尝试重登（MMKV 重新加载 + `[ServerTime] 时间同步完成`）→ **底层连接没真正重建**：重启前 QQ 只剩 2 条 IPv6 到 `:443` 的残连接，其中一条 `CLOSE_WAIT` 卡着不回收。QQ 在这种"半死连接"下**不会自愈**，必须重启进程。

★ **工具陷阱（我自己就误判了一次）**：Windows 的 `netstat -ano -p TCP` **会把 IPv6 整个过滤掉**，而 QQ 恰好走 IPv6（`240e:…`）。照它看会得出"QQ 没有任何对外连接"的**错误结论**。正确姿势：

```powershell
netstat -ano | Select-String ':3001'                    # 不带 -p 才含 IPv6
Get-NetTCPConnection -OwningProcess <QQ 的 pid>          # 或者用这个（含状态与远端地址）
```

★ **重启姿势（这就是"我重启了 NapCat 却没用"的原因）**：

1. `launcher*.bat` **只负责注入，不杀旧 QQ**。QQ 已经在跑时再点它 = 起了**第二个 QQ 实例**：旧实例还占着 3001（新实例的 NapCat 绑不上端口，等于白重启），而账号会话还在旧实例手里。**判断有没有真重启，要看 `NapCatWinBootMain`/`QQ.exe` 的启动时间**，不是看有没有点过脚本。
2. 那个旧 QQ 是**管理员进程**（`launcher.bat` 会自我提权）。普通权限的 `taskkill /f /im QQ.exe` 会 `Access is denied` —— 于是"重启"永远只是叠加一个新实例。必须**以管理员身份**先杀干净：

```
taskkill /f /im QQ.exe
taskkill /f /im NapCatWinBootMain.exe
cd /d D:\deepseek\QQbot\NapCat.Shell
launcher-win10-user.bat -q 2178517838
```

（`-q` = 快捷登录，省得扫码；本机装有 `KillQQ.bat`，但它同样需要右键**以管理员身份运行**才有用。）

3. 有用的旁证：重启成功后 `F:\qq\Tencent Files\2178517838\nt_qq\nt_db\nt_msg.db`（★ 注意有 `nt_qq\nt_db`
   两层子目录，别照抄成短路径 —— 短路径是不存在的）会立刻开始被写（消息库在同步）；`send-private`
   也从 `retcode 1200` 变回 `retcode 0`。
   ★ **"QQ 网络通不通"的日常判据**：看它有没有一条到腾讯 **`:14000` 的 `ESTABLISHED`**（那才是 QQ 的消息
   通道；`:443` 上的 `CloseWait` 是正常的连接churn，别当成故障）。健康时也可能**只有这一条**连接，
   所以"连接数少"不等于坏，"`:14000` 没了"才是坏。
4. **Koishi 不用重启**：NapCat 一回来，适配器自己就接上了（本次实测 `retryLazy: 10000` 下 10 秒内重连；日志确认 `17532 → 3001 ESTABLISHED`）。

★ **fileLog 为什么不产文件**：`config\napcat.json` 里的 `"fileLog": true` 在 NapCat 4.18.28 的**多进程模式**下会被代码强制关掉 —— `napcat.mjs` L82216：`NAPCAT_WORKER_PROCESS!=1 && NAPCAT_DISABLE_MULTI_PROCESS!=1 && NAPCAT_DISABLE_MULTIPROCESSING!=1 → setFileLogEnabled(false)`。所以 `NapCat.Shell\logs\` 一直是空的。想要真日志用 `tools\napcat-launch-logged.bat`（它设 `NAPCAT_DISABLE_MULTI_PROCESS=1` 再调 launcher），日志落在 `NapCat.Shell\logs\`。

**教训表**：

| 想知道 | 别用 | 用 |
|---|---|---|
| QQ 到底连没连上服务器 | `get_status` / `get_login_info` / `get_group_list` / `get_recent_contact`（全走本地缓存 + IPC） | `send-private`（或任何真发消息的调用）看 retcode |
| 入站是什么时候断的 | 猜 | `call get_recent_contact` 里各会话的 `lastestMsg.time` |
| 看某进程的连接 | `netstat -p TCP`（丢 IPv6） | `netstat -ano`（不带 `-p`）或 `Get-NetTCPConnection` |
| 重启 NapCat | 直接点 launcher（会叠加第二个实例） | 先**提权**杀 `QQ.exe` + `NapCatWinBootMain.exe`，再 launcher |
| NapCat 的文件日志 | 只改 `fileLog: true` | 关多进程：`tools\napcat-launch-logged.bat` |

### 坑 74（★ 静默、只影响"长的那一半"，而且**"写在配置前面"根本不算数**）：`inject` 会推迟 `apply`，`before-send` 的先后只能靠 `prepend` 自己声明

做「出站文本替换层」（[docs/29](29-出站文本替换层.md)）时，替换必须发生在
`chatluna-page` 把长回复转成图片**之前** —— 一旦先出了图，`session.elements`
里只剩一个 image 元素，文字改不动了。

**现象**：短回复替换正常、`[image]` 也照常出，**只有长回复里的 😏 留着**。
不报错、日志里看不出异常。

**第一反应（错的）**：把插件在 `koishi.yml` 里挪到 `chatluna-page` 前面。**没用。**
实测日志顺序仍然是 `page → replystyle → replacer`。`loader apply plugin` 明明是按
新顺序打印的（`replacer` 在 `page` 之前），但 `before-send` 里就是最后跑。

**根因**：`inject` 会**推迟 `apply`**。

- 本插件声明了 `inject = { required: ['database'] }` → `apply` 要等 database 就绪；
- `chatluna-render` / `chatluna-page` / `chatluna-reply-style` 没有这层等待，
  `apply` 立刻完成、`before-send` 监听器**先**注册；
- `app.serial` 是按**注册顺序**遍历的（`@cordisjs/core:523` `dispatch('serial')`
  + `:534` `hooks[prepend ? 'unshift' : 'push']`）。

于是"配置里排第 28、page 排第 31"完全不影响执行顺序 —— **配置顺序 ≠ 注册顺序 ≠ 执行顺序**。

**修法**：位置由插件自己声明。

```js
ctx.on('before-send', handler, true)   // 第三参 true → { prepend: true } → unshift()
```

`ctx.on(name, listener, options)` 里传布尔会被规范化成 `{ prepend: options }`
（`@cordisjs/core:545-548`），`register()` 走 `unshift`，插到队首，
**从此与插件加载顺序无关**。改完实测日志变成
`chatluna-replacer 出站替换… → page 长回复出图…`，顺序正确。

★ **怎么确认顺序真的对了（这条最容易自欺）**：不能只看"出图了没有"——
顺序反了**照样出图**，只是图里留着没换掉的字。要同时满足：

1. 有替换层的日志（`出站替换：3 处 / 2 条规则`）；
2. 同一条消息落成 `[image]`；
3. **最硬的一条**：看 `page 长回复出图：… （正文 N 字符）` 里的 **N**。
   原长 295、替换后 293（`😏😏→哈哈` 少 2 个码元）—— 日志报 **293**，
   就证明 page 拿到的是**替换后**的文本。

★ **顺带纠正一条容易写错的日志**：「N 处」在长正文里是**替换次数**，
不是"命中的规则条数"（😏 命中 2 次 + 😏😏 1 次 = 3 处，但只有 2 条规则）。
第一版把后者当"处"打，排查顺序问题时差点被自己这行日志带偏 —— 两个数都打出来。

**教训表**：

| 想知道 | 别用 | 用 |
|---|---|---|
| `before-send` 里谁先跑 | `koishi.yml` 里的先后（受 `inject` 推迟 `apply` 影响） | `ctx.on(事件, 回调, true)` 显式 `prepend` |
| 替换有没有发生在出图之前 | "出图了没有"（顺序反了也出图） | 替换日志 **+** `page 长回复出图` 的**字符数** |
| 出站消息的"处数" | 把它当成"命中规则条数" | 次数与规则数分开打 |

### 坑 75（★ 出整页图必踩）：puppeteer 22 里 `clip` 与 `fullPage` **互斥**

**症状**：网页预览的"整页模式"一调就抛

```
Error: 'clip' and 'fullPage' are mutually exclusive
```

**根因**：想同时要"整页"和"高度上限"，很自然会写成
`page.screenshot({ fullPage: true, clip: { x:0, y:0, width, height } })`。
但 puppeteer 22 明确禁止这两个参数共存（旧版本允许，所以网上抄来的写法会炸）。

**修法**：整页模式不要 `fullPage`，改成**自己量高度 + `clip` + `captureBeyondViewport`**：

```js
await page.screenshot({
  type: 'png',
  clip: { x: 0, y: 0, width, height: Math.min(scrollHeight, maxCaptureHeight) },
  captureBeyondViewport: true,
})
```

顺带就有了"整页高度上限"，不会出现一张几万像素高的图。

**★ 随之而来的第二个坑（判据写错，不是代码错）**：`scrollHeight` 对**百度首页**量出来**等于视口**
（它的整页布局是视口高、内容在内层容器里滚）。那时整页模式截出来和首屏一样高是**正确行为**。
第一版验收脚本拿百度当判据，于是把一个正确行为判成了失败 —— 换 `news.qq.com`（`scrollHeight` 1967px）才对。

### 坑 76：URL 的结尾不能按空白切 —— **中文标点必须当分隔符**

**症状**：群里发「看这个 https://a.com/x），挺好的」，预览必然失败，报"打不开这个网址"。

**根因**：抽链接用的 `/https?:\/\/[^\s]+/` 只把空白当分隔符，于是抽出来的是
`https://a.com/x），挺好的` —— `new URL()` 不会报错（中文会被百分号编码成路径），
于是真的去请求一个不存在的超长路径。

**修法**：正则里把中文标点也算作终止符：


### 坑 77（装新插件的必踩）：测试实例的 `node_modules` **不是** junction 到 `koishi-app/node_modules`

**症状**：新写的插件在**生产实例**能加载，在**测试台**报

```
[E] app cannot resolve plugin "chatluna-webpreview"
```

`require.resolve` 从 `koishi-app` 找得到、从 `koishi-test` 找不到。

**根因**：`tools/setup-test-app.cjs` 当初确实是把 `koishi-test/node_modules` 建成
**junction → koishi-app/node_modules**，但那个目录后来变成了**真实目录**
（532 项），里面是**每个外部插件一条独立 junction**、直接指向 `koishi-app/external/<插件>`。
于是"只在 `koishi-app/node_modules` 建一条 junction"这个直觉做法对测试台**完全不生效**。

**修法**：新插件要建**两条** junction：

```powershell
cmd /c mklink /J D:\deepseek\QQbot\koishi-app\node_modules\<包名>  D:\deepseek\QQbot\koishi-app\external\<包名>
cmd /c mklink /J D:\deepseek\QQbot\koishi-test\node_modules\<包名> D:\deepseek\QQbot\koishi-app\external\<包名>
```

**判据**（一秒确认，别靠猜）：

```powershell
node -e "console.log(require.resolve('<包名>', { paths: ['D:/deepseek/QQbot/koishi-test'] }))"
```

### 坑 78（运维）：`run-prod.cjs --takeover` 单独用**根本不动手** —— 文档与代码不一致

**症状**：按 `docs/17` 和脚本自己的文件头写的"重启 = `node tools\run-prod.cjs --takeover`"，
跑出来却是：

```
✗ 已经有孤儿实例连着 NapCat（3001 端口）：PID
  端口没被占 **不等于** 没有实例在跑：……
```

而 PID 那一栏**是空的**（当时 `orphans` 为空、端口被健康实例占着）—— 报错信息与事实不符。

**根因**（`run-prod.cjs`）：`targets = takeover ? clients : orphans`，
但真正执行杀进程的分支条件写的是 `if (has('kill-orphans'))`。
`--takeover` 单独用时 `kill-orphans` 为假 → 掉进 `else` → 打印"孤儿"报错并 `exit 1`。
**只有 `--takeover --kill-orphans` 才真的动手**。

第二个半边：注释里说 `--takeover` 覆盖"端口被占、但占它的进程没连 NapCat"的情形，
可那时 `clients` 为空 → `targets` 为空 → 上面整段跳过 → 端口检查再报错退出，**也收不掉**。

**修法**（2026-10-06）：
1. 执行分支改成 `if (takeover || has('kill-orphans'))`（并区分打印"旧实例已清掉 / 孤儿已清掉"）；
2. 补一段：`takeover && 端口忙 && 占它的不是 NapCat 客户端` 时，**只在该进程是 `node.exe` 时**才
   `taskkill /T /F`，否则拒绝启动并让人自己确认。

**教训**：这条属于"文档写了、代码没做、报错还指向别处"的三重错位 ——
**改完启动器要在真实状态上跑一次 `--check` + 一次真重启**，别只读代码。

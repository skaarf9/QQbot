# R9 择机插话 + R11 会话生命周期

> 属于 [QQ 机器人项目 —— 进度与交接](../进度与交接.md) 的分册。
> 旧编号（如「第八·十三节」）的去向见索引页的章节对照表。

两个自写插件：`chatluna-proactive`（活跃度 / 空闲触发）与 `chatluna-scene`（scene 状态机 + 收局终止会话）。

### 需求原文

> 「定时监控群聊、择机插话」

### 结论先行：生态里那个现成插件**用不了**

`koishi-plugin-chatluna-proactive-trigger@0.3.12`（2026-07-26 发布，对的是 chatluna **1.4.0-alpha**）
在 chatluna **1.4.0 正式版**（2026-09-19）上会炸。原因是**正式版把整个 room 层删了**：

- 它 `require('koishi-plugin-chatluna/chains')` 要 `resolveConversationRoom` /
  `queryJoinedConversationRoom` / `getConversationRoomCount` / `createConversationRoom`；
- 而 1.4.0 的 `lib/chains/index.cjs` **只导出** `ChainMiddleware` / `ChainMiddlewareRunStatus` / `ChatChain`；
  `lib/chains/rooms.d.ts` 里那 27 个函数的声明**一个实现都没有**（只有 `.d.ts`，没有 `.cjs`）。

实测现象（触发判定全对，执行时死）：

```
[I] chatluna-proactive [evaluateTriggers] group:454444539: activityScore=0.094 threshold=0.050
[I] chatluna-proactive [verboseLog][message-eval] … finalDecision=activity-trigger reason="活跃度触发"
[I] chatluna-proactive [ensureUserRoomForGroup] 使用模板 room 进行补建 …
[E] chatluna-proactive 主动触发响应失败：TypeError: (0 , import_chains.getConversationRoomCount) is not a function
```

所以**自写** `koishi-plugin-chatluna-proactive`（约 590 行），只借它的思路：
活跃度打分公式（90s/20s 速率 + logistic + 新鲜度衰减，照抄，与 chatluna 版本无关）、
群级历史池、回复后清池、冷却与失败退避。执行路径改成 1.4.0 的会话模型。

### 三个关键机制（改之前先看）

**1. 怎么让 chatluna 认账一次"没被叫的发言"**

```js
ctx.chatluna.chatChain.receiveCommand(session, '', { message: els, is_proactive: true })
//                                        ↑ 空字符串是故意的
```

- `allow_reply` 里 `if (context.command != null) return CONTINUE`（`lib/index.cjs:2961`）——
  空串不是 `null`，于是**绕过**「必须 @bot / 引用 bot / 叫昵称」的判定。
- `read_chat_message` 里 `context.command != null ? context.message : session.elements`
  （`lib/index.cjs:3578`）会采用我们塞进去的 `message`。

**2. 伪造会话必须走 `bot.session(event)`，不能克隆**

Koishi 的 session 方法（`resolve` / `text` / `stripped` …）**不在原型上**，是
`KoishiSession` 服务构造时 `ctx.mixin(this, { resolve: 'session.resolve', … })`
**混入到实例**上的（`@koishijs/core/lib/index.cjs:1762-1785`）。
照「`Object.getPrototypeOf(base)` + 拷 own descriptors」克隆（那个第三方插件就是这么写的），
方法会全丢，实测：

```
[E] chatluna chat-chain: allow_reply error TypeError: session.resolve is not a function
[E] chatluna TypeError: session.text is not a function
```

正确姿势：

```js
const event = { ...base.event, timestamp: Date.now(),
                user: { id: '__proactive_trigger__', name: 'proactive' } }
delete event.member      // satori 的 author = {...event.user, ...event.member}，留着会被真实群名片盖掉
event.message = { id: …, content: text, elements }
return base.bot.session(event)
```

`userId` **不能是自己的 QQ 号**，否则 `allow_reply` 开头
`if (ctx.bots[session.uid]) return STOP` 会当成 bot 自己的消息掐掉。

**3. 回复后清池**：挂一个链中间件 `.after('request_conversation')` ——
能跑到那里就说明这一轮真的请求模型了（`allow_reply` 提前 STOP 就到不了），此时清空该群历史池。

### 配套改动

- **`chatluna-vision` 两个补丁**：① `download()` 支持 `data:` URL —— 主动发言里的图是
  `data:image/png;base64,…` 形式塞进来的；② 新增配置 `parseWhenUserIds`（默认
  `['__proactive_trigger__']`）—— 否则这些图会被当成「群里没叫 bot 的图」**直接丢掉**，
  bot 等于瞎着插话。
- **夜间免打扰**：`quietHours`（默认 `01:00-08:00`，支持跨零点）。半夜群里没人说话是正常的，
  不需要它来暖场。
- 与 R10 的关系：主动发言 `command === ''`，`messageQueue` 判定 `context.command?.length > 0`
  为假 → 会进 pending 队列，实际开口时间 = 轮询命中 + `messageQueueDelay`。
- **指令消息不进历史池、也不算活跃度**：`record()` 里按 `ctx.root.config.prefix`（`/`、`.`）
  过滤 —— 否则群友敲几条指令就能把"群聊热度"顶起来，bot 会对着指令插话。

### 验收（`tools/scenarios/19-proactive-activity.json` / `20-proactive-idle.json`）

**活跃度触发**：群里 5 条普通聊天、全程没人 @bot / 没引用，第 5 条之后 bot 自己开口：

```
[ 41952ms] 📥 第5步  自己做啊，煮个面都比外卖强
[ 47996ms] 📤 BOT → 群454444539  食堂吃不下去就对了，那玩意儿能有我家大米饭香？
                                 说真的，中午那顿别将就，宁可多走两步也别糟蹋自己胃。
```

（★ 还顺带用上了 R3 记的「大米饭」偏好。）

**空闲触发**：群里只有一句「这个点都没人啊」，之后 70 多秒无人说话：

```
[ 99547ms] 📤 BOT → 群454444539  有人，我在呢。就是懒得说话，尾巴泡水里挺舒服的。你们呢。
```

日志侧：`chatluna-proactive 已主动发言（空闲触发）：群 454444539，池内 1 条消息，0 张图，阈值调到 0.050`
与 `群 454444539 已在对话中回复，清空历史池（1 条）`。

### 生产参数与调参

`koishi-proactive:pr0001`（只有测试群 454444539 在监控列表里）：

| 项 | 值 | 说明 |
|---|---|---|
| `pollSeconds` | 5 | 轮询间隔 |
| `cooldownSeconds` | 300 | 两次主动发言的最小间隔 |
| `quietHours` | `01:00-08:00` | 免打扰 |
| `activityThreshold` → `thresholdCeiling` | 0.5 → 0.65 | 每开口一次阈值往上挪 10%（越聊越克制） |
| `activityMessageInterval` | 15 | 消息数兜底 |
| `idleMinutes` | 180 | 冷场 3 小时才起话头（测试台压成 1 分钟） |

想加群就往 `groups` 里加一条；`/proactive` 能看当前池子/冷却/阈值，`/proactive.speak` 强制开口。

## 一、R11 会话生命周期：自写插件

### 需求原文

> 「会话生命周期（如"开始游戏"→"达成/中断"需终止）」

### 设计：场景（scene）状态机 + 真的终止会话

`koishi-plugin-chatluna-scene`，按会话隔离（`scopeMode: channel`，跟默认的群共享会话一致）：

```
idle ──scene_begin（模型自己判断这是一件有始有终的事）──▶ active
active ──scene_end(达成/中断) / 空闲超时 / 单局超时──▶ ended ──▶ 终止会话（默认 clear）
```

- 提示词注入 `{scene()}`：告诉模型「现在没在玩」/「正在进行什么、结束条件是什么、聊了几轮」/
  「上一局刚刚结束，别再提了」。
- 模型工具 `scene_begin {title, goal}` / `scene_end {result, summary}`。
- 指令：`/scene`（a=1）、`/scene.begin`（a=3）、`/scene.end`（a=2）。
- 自动中断：`abortIdleMinutes`（默认 30 分钟没人接话）/ `maxMinutes`（默认单局 180 分钟上限）。

### ★★ 最大的坑：**绝不能在模型回合里清历史，会死锁**

`clearConversationHistory` 内部是 `withConversationLock`（`chat.cjs:3826`），
而正在跑的这一轮聊天自己就占着**同一个** conversationQueue
（`chat()` → `withConversationAndPlatformLock`，`chat.cjs:3526/3685/3703`；
队列是 `RequestIdQueue`，同一 key 同时只有一个 active，`utils/queue.cjs:45-89`）。
在工具里直接清 = 等自己那一轮结束 → 永远等不到。

**连 `chatluna/after-chat` 事件也不能直接用**：它是在**锁内**被 emit 的
（`llm-core/chat/app.cjs:514-523` 这段代码本身跑在 `withConversationAndPlatformLock` 的回调里）。

正确做法：**只登记"待终止"，由轮询任务（不在任何回合里）执行**。
轮询即使撞上正在进行的回合，也只是那一格 await 等一会儿，不会死锁。
（`endMode` 可选 `clear` / `archive` / `mark`；`archive` 走 `archiveConversationById`，同样在轮询里做。）

**另一个坑**：`{ pendingMode: { $ne: null } }` 翻成 SQL 是 `<> NULL`，**永远不成立**
（NULL 的比较结果是 NULL 而不是 true），查出来是空集 —— 现象就是"待终止：clear"永远挂着、
`会话已终止（clear）` 永远不打。改成按 `status: 'ended'` 取、在 JS 里筛 `pendingMode`。

### conversationId 不用自己算

`bindingKey` 的拼装函数（`computeBaseBindingKey`，`index.cjs:4716`）**没有导出**，
所以别自己拼。直接用 `chatluna/after-chat` 的第 1 个参数（conversationId），
用第 6 个参数（session）把它映射回我们的 scope，顺手给进行中的互动计轮数。

### 验收

**模型自己开局**（`tools/scenarios/21-scene.json`）：

```
[I] chatluna-scene 互动开始：scope=onebot:channel:454444539 标题=猜数字（1-100） 结束条件=主人猜中我心里想的那个数就结束
[I] chatluna Call tool: scene_begin with {"title":"猜数字（1-100）","goal":"主人猜中我心里想的那个数就结束"}
```

`/scene` 回：

```
状态：进行中
互动：猜数字（1-100）
结束条件：主人猜中我心里想的那个数就结束
已进行 1 分钟｜2 轮
会话 ID：627af697-87d2-4cc4-83c2-6c9678947739      ← 会话绑定成功
待终止：无
作用域：onebot:channel:454444539
```

**模型自己收局**：主人说「算了不玩了」→

```
[I] chatluna-scene 互动结束：scope=onebot:channel:454444539 结果=中断（模型判定）→ 会话处置 clear
[I] chatluna Call tool: scene_end with {"result":"中断","summary":"主人猜了一次50就嫌麻烦不玩了"}
```

之后 `/scene` 显示 `状态：已结束 / 结果：中断（…）`；轮询把待终止兑现：

```
[I] chatluna-scene 会话已终止（clear）：scope=onebot:channel:454444539 conversation=627af697-87d2-4cc4-83c2-6c9678947739
```

（★ 这一段还暴露了上面那个 `$ne: null` 的坑：修之前 `/scene` 一直显示 `待终止：clear`。）

**自动中断**（`tools/scenarios/26-proactive-speak-and-abort.json`）：`/scene.begin` 之后 90 秒没人接话
（测试配置 `abortIdleMinutes: 1`）→

```
[I] chatluna-scene 互动结束：scope=onebot:channel:454444539 结果=中断（空闲超时）→ 会话处置 clear
[I] chatluna-scene 会话已终止（clear）：scope=onebot:channel:454444539 conversation=627af697-…
```

`/scene` 随之变成 `状态：已结束 / 结果：中断（1 分钟没人接话） / 待终止：无`。

同一个剧本还顺手验了 R9 的 `/proactive.speak`（强制开口）：
`command proactive.speak` → `已主动发言（活跃度触发）：群 454444539，池内 1 条消息` → 群里真的发出了一句「在」。

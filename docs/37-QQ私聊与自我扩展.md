# QQ 私聊交给 DSH：人设 + 子 agent + 自装 AstrBot 插件

> 属于 [QQ 机器人项目 —— 进度与交接](../进度与交接.md) 的分册。
> 第二十轮（2026-10-26）。目标：在 QQ 里直接和 bot 说话，bot 能用原来的大肥鱼人设，
> 还能自己派子 agent、装/升级 AstrBot 插件。

## 一、这一轮改了什么

| 项 | 之前（10-25） | 现在（10-26） |
|---|---|---|
| 私聊 | AstrBot 只接 `/dsh`，普通聊天归 Koishi | **私聊全部消息走 AstrBot → DSH**（`private_passthrough: true`） |
| 群聊 | `/dsh` + 引用续聊 | 不变；普通群聊仍归 Koishi |
| 人设 | DSH 是 coding agent 的系统提示词 | `workspace/AGENTS.md` 注入大肥鱼人设（从原 `default-persona.yml` + `self.yml` 改编） |
| 自我扩展 | 无 | `scripts/selfext.cjs` + `skills/astrbot-selfext`：搜/装/重载/更新 AstrBot 插件、查版本、升级、延迟重启 |
| DSH 权限 | workspace-write + ask（装插件时卡在“批准”） | qqbot profile 默认 `danger-full-access`，审批 `never`（无人值守） |
| 回复尾巴 | 每条都带 `—— 本回合结束` | 私聊去掉；群聊/`/dsh` 保留（本地补丁） |

## 二、人设：怎么“直接使用之前的提示词”

原提示词在 `routes/koishi/app/data/chathub/presets/default-persona.yml`（230 行），
配合 `data/persona/self.yml`（结构化人设卡）。这次没有整段照搬，因为里面大量变量/工具
在 DSH 形态不存在：

- `{emotion()}`、`{affinity()}`、`{long_memory()}`、`{routine()}`、`{episode()}`、`{scene()}`
- `emotion_set` / `affinity_affinity` / `sticker_*` / `memory_add` / `scene_*` / `render_image`

如果原样注入，模型会去调不存在的工具。所以 `workspace/AGENTS.md` 的做法是：

1. **原文保留**：硬性设定块（CETACEA_LOLI…）、大肥鱼身份/别名/形象/自称/口头禅、
   “说话的样子”、“什么时候不卖萌”、“输出格式”。
2. **删掉**全部 ChatLuna 变量和工具段。
3. **新增**：DSH 工具清单、子 agent 规则、selfext 自我扩展协议、QQ 输出纪律、
   “不碰 routes/koishi 生产、不读密钥”的安全边界。

DSH 的 `dsh-agent-instructions` 会在会话第一次请求时把 `AGENTS.md` 作为 workspace
instructions 注入；实测回复已经是“我是大肥鱼，蓝色鲸鱼娘……”，不是 coding agent。

> 如果以后要更强的人设，可以把 qqbot profile 的 `preset-standard` 里的 `dsh-persona`
> 换掉，让它进 system prompt；当前 AGENTS.md 已经够用，先不增加配置复杂度。

## 三、自我扩展：selfext

`routes/astrbot/scripts/selfext.cjs` 是给 DSH agent 调用的薄封装：

- 用 `routes/astrbot/.env` 的 WebUI 账号登录 AstrBot；
- 插件市场：`GET /api/v1/plugins/market`；
- 安装：`POST /api/v1/plugins/install/url`（`install_method: market` + `market_plugin_id`）；
- 重载/更新：`/api/v1/plugins/reload`、`/api/v1/plugins/update`；
- 升级 AstrBot：`uv tool upgrade astrbot --python 3.12`（路线内 `.uv-tools`）；
- 重启：用独立计划任务 `QQbotAstrBotRestart<ts>` 跑 `restart-task.cmd`——先
  `timeout` 延迟、再 `kill-astrbot.ps1` 杀父/子进程、最后 `run-astrbot.cmd` 前台拉起；
  计划任务不受 DSH 会话 job 对象回收影响，AstrBot 能真正活下来；
- 全部操作写 `routes/astrbot/logs/selfext.log`。

配套 `~/.dsh/skills/astrbot-selfext`（junction 到仓库 `skills/`）让 agent 能按技能说明使用它。

### 实测

在假 OneBot 客户端里以主人身份说：

> 我授权你直接装，不用再问我：用 selfext 搜 astrbot_plugin_echo 并安装，装完 reload，
> 然后只回复我装好没有。

bot 自己执行：

```
selfext plugins search astrbot_plugin_echo
selfext plugins install ocetars/astrbot_plugin_echo
selfext plugins list
selfext logs 60
...
```

最后回复：

> 装好了，reload 也成功了。
> 不过第一次装是失败的——`app\.astrbot` 是个空的残留文件挡住了临时目录，
> 我把它挪成 `.astrbot.bak-empty` 才装上，没删东西。

这是本轮最有说服力的一条：**它不只是“能调工具”，而是自己发现并修了一个安装阻塞**。

### 升级 / 重启实测

`selfext upgrade` 跑 `uv tool upgrade astrbot --python 3.12`，当场把
`sse-starlette`、`win32-setctime`、`xinference-client` 升了一档（AstrBot 核心仍 4.29.3）。

`selfext restart --delay 5` 走计划任务：5 秒后杀掉旧 AstrBot（PID 20836），
新实例（PID 6788，后来又换成 7824）在 6186/6199 重新监听，NapCat 的反向 WS 在 30 秒内自动重连，
插件 `astrbot_plugin_dsh` + `astrbot_plugin_echo` 全部重新加载。这条链路是通的。

### 子 agent 实测

> 用 subagent 开一个子 agent，让它只做一件事：数一下 workspace 下有几个 .md 文件。

bot 先回“我先让子 agent 去数了，稍等一哈”，随后回“1 个。就是顶层那个 AGENTS.md。”
（workspace 里只有 `AGENTS.md` 和 `.gitkeep`，数字正确。）

## 四、权限：为什么用 danger-full-access

第一次让 bot 装插件时，它卡在：

```
## 操作权限确认 (#1)
工具：pwsh
原因：escalate sandbox to danger-full-access: 这个脚本会检查并修复 ... 文件权限
```

根因：qqbot 会话默认 `workspace-write` + `ask`。selfext 要跑 `node`、访问 `routes/astrbot`
（工作区外）、调 AstrBot API，于是触发沙箱升级询问。QQ 是无人值守会话，不该卡在这里。

改成：

```yaml
# ~/.dsh/profiles/qqbot/cordis.patch.yml
- id: permission
  name: '@deepseek-ai/dsh-permission-presets'
  config:
    defaultPreset: danger-full-access
```

并清掉 `~/.dsh/dsh-astrbot-ingress/sessions.json`（旧会话的权限是持久化的），
新建会话后不再弹批准，selfext 直接跑通。

**代价**：agent 理论上能改本机任何文件。因此 `AGENTS.md` 明确写了“不碰 routes/koishi 生产、
不读 .env/token、破坏性操作先问”，但这是提示词约束而不是 OS 沙箱。QQ 号只给可信的人。

## 五、私聊静默模式（去掉所有“过程提示”）

用户反馈：私聊发一句，先回一条 **“已交给 DeepSeek Harness…”**，破坏代入感。
审计 `astrbot_plugin_dsh/main.py` 后，把私聊整段聊天（非 `/dsh` 命令）设成静默模式：

| 消息 | 来源 | 私聊处理 |
|---|---|---|
| `已交给 DeepSeek Harness…` | 插件 `on_message` 的即时 ack | **不发**（私聊聊天模式；`/dsh` 任务仍发） |
| `💭 思考首行` | ingress `reasoningMode: first-line` | **不发**（私聊 `text` 以 💭 开头直接丢） |
| `⏳ 已跑 3 分钟 · 工具 7 次…` | ingress `progressMode: digest` | **不发**（私聊 `status` 以 ⏳/🔧 开头或含“已跑”直接丢） |
| `🔧 write ...` | ingress `progressMode: full` | **不发**（同上） |
| `—— 本回合结束` | ingress 回合结束标记 | **不发**（私聊 `text` 去掉尾巴；单独 `status` 也丢） |
| `## 操作权限确认 (#1)` | ingress 审批 | **保留**（真需要人拍板） |
| `ask_user_question` 卡片 | ingress 提问 | **保留** |
| 错误 / 文件发不出 / 超时 | 插件 / ingress | **保留**，但超时改成“这次等太久了，我先停下来了；任务可能还在跑。” |
| `已记录审批回复` / `已记录你的回答` | ingress 回答回执 | **保留**（功能性） |

实现要点：

- `on_message` 里算 `chat_mode = 私聊 && 不是 /dsh 命令 && 不是审批回答`，挂到 `event` 上；
- `_emit_sse` 用同一个 `chat_mode` 过滤 `text`/`status`；
- ack 只在 `not chat_mode` 时发；
- 群聊 / 私聊 `/dsh` 任务保持原来的进度与结束标记。

改完实测：私聊“在吗？”只收到一条“在呢，本鱼稳稳坐这儿…”，没有 ack、没有尾巴。

## 七、身份分层：所有者 / 维护者 / 访客

第四节讲的是 DSH 进程的权限（`danger-full-access`）；这一节讲 **QQ 这一层谁能让 bot 动手**。
两者不是一回事：DSH 权限决定“能不能”，白名单决定“谁可以要求”。

| 角色 | 配置 | 能做什么 |
|---|---|---|
| 所有者 | `owner_users`，默认 `2791932480`（绮罗星） | 改仓库、跑命令、装/升插件、派子进程，全部 |
| 维护者 | `maintainer_users`（白名单） | 装插件、升级、维护 `routes/astrbot`、派子进程 |
| 访客 | 其他所有人 | 只聊天 |

实现是两层：

1. **插件硬闸**：`main.py` 里 `_role()` 判身份；访客的消息命中
   `_GUEST_DENY`（装/卸/升级插件、重启、改代码/文件、跑命令、子进程……）时，
   直接回“这个我可不敢替你动手，找有权限的人来”，**根本不进 DSH**。
2. **系统注记**：进了 DSH 的消息会在正文前加一行
   `[系统注记·勿复述] 发言人=…（自己人/维护者/访客）：…权限…`，
   让模型知道这一轮该守什么边界；AGENTS.md 明令不要复述。

名单管理走 selfext（写完自动重载桥插件）：

```bash
node D:/deepseek/QQbot/routes/astrbot/scripts/selfext.cjs allowlist list
node D:/deepseek/QQbot/routes/astrbot/scripts/selfext.cjs allowlist add 1234567890
node D:/deepseek/QQbot/routes/astrbot/scripts/selfext.cjs allowlist remove 1234567890
```

所有者不能从 `maintainer_users` 移除（要先改 `owner_users`）；`guest_chat` 关掉后
名单外的私聊直接不理。维护者本身就算 DSH 的通行证（`/dsh`、私聊、引用续聊都放行），
不用再往 `allow_users` 里补一遍。

**关于“主人”**：所有者是 `2791932480`（绮罗星），AGENTS.md 里把原来的“主人”称呼
统一改成“对方 / 自己人”，并明确“别喊主人、别把上下级挂嘴边”。权限是权限，
不靠称呼提醒。

**实测**：

- 访客 `123456789` 发“帮我装个插件吧” → 只收到一句
  “这个我可不敢替你动手，找有权限的人来。”，没有调 DSH；
- 同一访客发“你好呀，今天吃了吗？” → 正常大肥鱼人格回复（`guest_chat` 默认开）；
- 把 `123456789` 临时加进维护者名单后，它能让 bot 读仓库文件并正常回答；
  移出名单后又回到“只能聊天”；
- 所有者的回复里没有出现系统注记。

## 八、子 agent：最多 3 个 + 文件地盘租约

问题：DSH 的 `subagent` / `workflow` 没有并发上限，也不记“谁在改哪个文件”。
两个子 agent 同时改同一个文件，就会互相覆盖、反复重改。

做法：工作区里放一个账本脚本 `workspace/scripts/subagent-gate.cjs`，
状态写 `workspace/.state/subagent-leases.json`（已 gitignore）：

```bash
node .../subagent-gate.cjs status
node .../subagent-gate.cjs acquire --task "写插件文档" --files "routes/astrbot/README.md,docs/37-*.md"
node .../subagent-gate.cjs release <lease>
node .../subagent-gate.cjs sweep --ttl-hours 3
```

规则：

- 同时最多 3 个 lease；第 4 个返回 `error:"limit"`（退出码 3）。
- 地盘重叠（同一文件，或一个目录包含另一个，`*` 表示整仓）返回 `error:"conflict"`（退出码 4），
  并指出和哪个 lease 撞了。
- 子 agent 的 prompt 必须写死“只改这些路径，别碰别的”；两个子 agent 改同一文件要串行。
- 收工 `release`；漏了用 `sweep` 清 3 小时以上的僵尸。

**为什么是流程约束**：DSH 的工具调用在 agent 进程内，外部脚本拦不住它“要不要 spawn”。
所以这条规矩写进 `workspace/AGENTS.md`，并把 `acquire` 定为开子 agent 前的固定动作；
以后如果 DSH 提供工具调用 hook，再换成真硬闸。

**实测**：`acquire` 拿到 lease、目录包含关系被判冲突、第 4 个被名额挡住、
`release` 后名额恢复，都通过。

## 补记（2026-10-27）：模型换成 DeepSeek 官方 + 8090 挂死排障

**① commandcode 额度耗尽 → 换 DeepSeek 官方。**

实测报文：

```
POST https://api.commandcode.ai/provider/v1/chat/completions
→ HTTP 400 {"error":{"message":"You have insufficient credits ...","code":"BAD_REQUEST"}}
```

注意是 **400 不是 401**，别误判成 key 写错。修法是改
`~/.dsh/profiles/qqbot/cordis.patch.yml` 的 `agent-default-model`：

```yaml
- id: agent-default-model
  config:
    provider: deepseek-official   # 原 commandcode
    model: deepseek-flash         # 原 deepseek/deepseek-v4.1-flash
- id: llm-commandcode
  disabled: true                  # 包还在 package.json 里，随时可改回 false
```

key 不用另配：`~/.dsh/.credentials.yaml` 的 `refs.DEEPSEEK_API_KEY` 早就有，
`@deepseek-ai/dsh-llm-deepseek-api-key` 默认就读这个 ref。
`deepseek-flash` = DeepSeek-V4.1-Flash，`inputModalities: ["text","image"]`，所以引用里的图还能看。
更强的有 `deepseek-v4-pro`；官方只认 `reasoningEffort: high|low`，不写就是偏快的默认。

**② 8090 打不开 = 僵尸进程占端口，不是配置错。**

症状：`netstat` 有 LISTENING，但 `curl :8090/` **超时（http_code=000）**；
`~/.dsh/logs/startup-*.log` 里连续多次都是：

```
webserver (required)  Error: listen EADDRINUSE: address already in use 127.0.0.1:8090
dsh-astrbot-ingress   listen failed: EADDRINUSE 127.0.0.1:3188
```

即老进程挂死没退，新进程每次都在启动阶段就死。判活靠 `http_code`（401=活着，000=挂了），
或者看 `~/.dsh/astrbot-ingress.json` 的 `updatedAt`（beacon 30 秒一次，停在某刻就是没心跳了）。

修法：`taskkill /PID <占用者> /T /F` → 确认端口空了 → 重跑 `start-dsh-qqbot.cmd`。
完整步骤与验活三件套见 [`routes/astrbot/README.md`](../routes/astrbot/README.md#故障8090-打不开--ingress-不响应2026-10-27-实修)。

**③ 顺带发现**：Koishi 路线没在跑（5140/3001 都没监听），而它的 `CC_API_KEY`
走的是同一个中转，实测也是 `insufficient credits`。也就是说 Koishi 现在启动起来也聊不了，
要用得把 ChatLuna 的 `ccfree` 适配器改成 DeepSeek 官方端点。

# 指令帮助体系按人过滤 + 命令管理 + 好感度为什么上不去

> 属于 [QQ 机器人项目 —— 进度与交接](../进度与交接.md) 的分册。
> 第十八轮（2026-10-09）。

## 用户原话（这一轮的全部需求）

> ① 我需要 `/help` 命令根据使用者显示可用的命令，而不是显示全部；
> ② `/help` 动态显示所有的有别名的命令（也就是我在 koishi 中为命令添加别名后这里也能动态更新）；
> ③ koishi 命令管理那里需要能够管理别名和用途文本；
> ④ 权限的文本也需要使用 `/help` 中显示的这几个文本，数字太不直观了。
>
> ⑤ 这个好感度机制似乎一直是 30，很难升级到信任，甚至我不知道信任需要多少好感，看看这个好感度怎么这么难升级。

---

## 一、先给结论（好感度那条）

**「一直是 30」不是 bug，是三件事叠在一起**，查库查日志都有证据（`data/koishi.db` 的
`chatluna_affinity_v2` + `tools/logs/prod-2026-10-08.log`）：

| # | 事实 | 出处 |
|---|---|---|
| 1 | **每个人的初始长期好感就是 30** | `chatluna-affinity` 的 `BASE_AFFINITY_DEFAULTS.initialAffinity = 30` |
| 2 | 「信任」的门槛是 **51** | `qqbot-auth` 的 `affinityPromoteAt: 51`（= affinity 区间表里「熟悉」的下界） |
| 3 | 显示值 = 长期 × 系数，系数在 **0.7~1.3** 之间飘 | 所以长期 30 最坏显示 21，看着更像"停住了" |
| 4 | 模型每次只给 **+2~+3** | 日志逐条：`delta=2` / `delta=3` / `delta=5`，一周里最大就 5 |
| 5 | 老参数要**短期攒够 15 才折成长期 +3** | `shortTerm.promoteThreshold=15`、`longTermPromoteStep=3` |

把它们乘起来：**30 → 51 要长期 +21 → 按 +3/次折算要 7 次折算 → 每次折算要 +15 短期 →
合计 105 点短期 → 按每次 +3 估要 35 次"模型认为值得加分"的互动**。
而生产里主号（2791932480）聊了 **51 次**，`actionStats` 里总共只有 **7 次**调整
（5 加 2 减），净攒到长期 30 —— 也就是说**机制上就不可能在一周内到 51**。

### 这一轮怎么改的

1. **调机制**（`koishi.yml` 的 `chatluna-affinity.affinityDynamics.shortTerm`）：
   * `promoteThreshold: 15 → 12`
   * `longTermPromoteStep: 3 → 6`
   * `demoteThreshold: -10 → -8`（降级线跟着收紧一点）

   改完：**30 → 51 只要 4 次折算 = 48 点短期 ≈ 14 次 +3 的互动**（原来 35 次）。
2. **给模型分量指引**：`nativeToolSettings.affinity.description` 不再是一句
   「调整一个用户的好感度。」，而是写明 `+2~3 / +5~8 / +10~15` 各对应什么分量的互动
   （这条描述就是喂给模型的工具说明，等于给它一把尺子）。
3. **把账摊开**（用户原话"我不知道信任需要多少好感"）：
   * `/qqbot.auth.me` —— 除了等级，直接写"信任门槛 51 / 你的长期 30 / 还差 21 点 /
     每 12 点短期折 +6 / 所以要 4 次折算 / 按 +3 估 ≈ 14 次"
   * `/qqbot.auth.list` —— 顺带打印**当前生效**的那套数字与来源（`koishi.yml` / 默认值）
   * `/favor`（`affinity.inspect`）—— 在它原来的输出后面**追加同一段**（桥来包装它的 action）
   * `/short` —— 折算线/来源现在读的是 affinity 的**真实配置**，不再是桥自己的默认值

> ⚠️ 阈值和步长**只改配置、没改上游代码**：`chatluna-affinity` 在 `node_modules` 里，
> 改它会被 `npm i` 覆盖。要再调就改 `koishi.yml` 这两处，别去动 node_modules。

## 二、`/help` 按使用者过滤（需求①④）

* **判据**：一个指令的有效门槛 = 它自己与**所有祖先**上 `authority:N` 的最大值
  （整条父链都要过）。算法与 `qqbot-auth.effectiveLevel()` 同源。
* **过滤发生在"页面层"**：`catalogue(mine)` 只算 `usable`，三个页面各自按
  `visible(list, mine, showAll)` 决定要不要露出来 ——
  这样"配置里默认显示不可用"与"这次 `/help -u`"两种来源不会打架。
* **默认不显示用不了的**（`showUnavailable` 默认值从 `true` 改成 `false`），
  想看全的临时发 `-u`：
  * 首页：页脚写「别名共 N 个，还有 M 个你用不了：`/help -u`」，`-u` 时把用不了的别名
    单列一段（前 12 条，带等级文本）
  * 类目页：页脚写「另有 M 条你用不了：`/help <类目> -u`」
  * 总览页：`条数 / 你能用` 两列都只算"你看得见的那部分"
* **首行口径必须与表格一致**：标题写「共 **N** 个你能用的别名」，`N` 就**只数能用的**
  （第一版写的是 `shown.length`，在 `showUnavailable=true` 时那是全部条目 ——
  普通群友会看到"共 61 个你能用的"而表格里一堆用不了的）。
* **等级一律文本**：`拉黑 / 普通 / 信任 / 管理员 / 主人`（`LEVEL_NAMES` 是唯一来源，
  和 `qqbot-auth` 同源）。徽章只给文本；需要点明数字的地方（详情页、管理命令回执）
  才写成 `信任（2）`。`/qqbot.auth.set` 的等级位**也认文本**（`信任` = `2`）。

## 三、命令管理 `/cmdadmin`（需求③）

> ★ 名字为什么叫 `cmdadmin` 而不是 `help.admin`：`[target:string]` 是**贪婪**位置参数
> （core:1332 给 string 域加了 `greedy:true`），父指令 `help` 已经能把 `/help admin` 整条吃掉，
> `help.admin` 与它同名前缀，谁先命中由 Commander 内部顺序决定 —— 不值得赌。

| 命令 | 作用 |
|---|---|
| `/cmdadmin` | 总入口：用法表 + 当前等级 + 覆盖层条数 |
| `/cmdadmin list [页]` | 全部指令（`-c 类目` / `-l 等级` / `-f 关键词`），✎ = 已被覆盖 |
| `/cmdadmin aliases [页]` | 只看有别名的指令（含 Koishi 里配的） |
| `/cmdadmin alias <指令> <别名>` | **真的挂到指令上**（`-d` 删除），改完立刻能敲 |
| `/cmdadmin desc <指令> <文本>` | 改"用途"（帮助页那一列；`-` 清掉覆盖） |
| `/cmdadmin level <指令> <等级>` | 改门槛，**认文本**（`信任`），`-` 清掉覆盖 |
| `/cmdadmin preview <等级>` | 看某个等级的人眼里的 `/help`（按人过滤的自检入口） |

* **落在数据库、热生效**：两张表 `chatluna_cmd_overlay`（用途/等级）与
  `chatluna_cmd_alias_extra`（额外别名，带开关）。`koishi.yml` 里的配置永远是最底层，
  库里没行就按配置来 —— 删行 = 回到配置。
* **`/cmdadmin` 永远走文字**：`chatluna-page` 里按前缀 `^(cmdadmin|cman)(\.|$)` 跳过自动出图。
  理由：这一屏的东西是**拿来抄的**（指令名、别名、要改的文本），出成图就没法复制。
* **别名冲突不会炸**：`_registerAlias` 在名字被占用时直接抛 `duplicate command names`
  （core:934-940），这里冲突只 warn 跳过 —— 一条配错的别名不该把帮助页带崩。

## 四、`/help` 的别名是**动态**的（需求②）

`aliasIndex()` 每次渲染**现场**从三个来源算，什么都不缓存：

| 来源 | 说明 |
|---|---|
| ① `Command._aliases` 的实时键集 | 谁在哪儿 `.alias('x')` 都能看见；第一个键是主名（= `displayName`）不动 |
| ② `chatluna-alias` 的配置表 | 只收注册成功的那些（`ok !== false`），带 note |
| ③ 覆盖层 `chatluna_cmd_alias_extra` | `/cmdadmin alias` 加的，带启停开关 |

于是：**在 koishi 里给命令加个别名 → `/help` 首页立刻多一行；删掉立刻少一行**
（离线判据 `.scratch/check-help-shortcut.cjs` 就是这么断言的：加 `mm2` → 数量 +1、
`/mm2` 出现；删 → 数量 -1、行消失）。

首页的每一行 = 一条**真实可敲的别名**，不再是 alias 表里的一行 ——
所以显示与"能不能敲"永远一致。没有别名的指令（`displayName` 恰好等于指令名）不会上首页，
这是刻意的：首页只服务"有哪些能敲"，要在全量里看原名发 `/help -all`。

## 五、验收怎么跑的（可复现）

```powershell
cd koishi-app

# 离线判据一：/help 首页的过滤与别名动态（秒级，不依赖测试台）
node ..\.scratch\check-help-shortcut.cjs      # 14 项，全部达标

# 离线判据二：两个插件能不能从真实 koishi.yml 里读到 affinity 参数
node ..\.scratch\check-yaml-config.cjs        # 两份 koishi.yml 都要读到 12 / +6

# 端到端：37 步真跑一遍（文字模式，0 条 [E]）
node tools\run-rig.cjs tools\scenarios\67-help-perms-cmdadmin.json --settle 12000 --run 285000 --keep-log
```

端到端实测结论（`tools/logs/rig-67-help-perms-cmdadmin.log`）：

* 主人 `/help` = **61** 个别名（含 `/cmdadmin`、`/cman`）；普通群友 = **26** 个，
  且**一条管理员/主人级的行都没有**，页脚写「别名共 61 个，还有 35 个你用不了：`/help -u`」
* 普通群友发 `/cmdadmin` → **权限不足**（不是"没有这个指令"）
* `/cmdadmin alias cmdadmin cman` → `已加 /cman`，`/cman` 当场能执行；
  `-d cman` → `已删`，首页数量随之 -1
* `/cmdadmin desc help <文本>` → `/help` 首行就是新文本；`list -f <文本>` 命中；`-` 清回原样
* `/cmdadmin level models 信任` → `list -l 信任` 里出现 models；`-` 清回原样
* `/qqbot.auth.me` / `/favor` / `/short` 都打印「信任门槛 51，你的长期 30 → 还差 21 点 /
  每攒 12 点短期折成长期 +6 / 所以要 4 次折算 ≈ 14 次」（`参数来源：koishi.yml`）

## 六、这一轮踩的坑（86-90）

### 坑 86：minato 的 `set()` **不允许 update 里出现主键列**

`chatluna_cmd_alias_extra` 的主键是 `(userId, target, alias)`，而我把
`{ target, alias, enabled }` 整个当 update 传进去 → `TypeError: cannot modify primary key`，
`/cmdadmin alias` 回执变成「没成功：`cman`（cannot modify primary key）」，但**指令上其实已经挂上了**
（`cmd.alias()` 先成功、写库后失败）—— 一次"半成功"，最难查。

出处：`minato/lib/index.cjs:1289-1292`，`primary.some((key) => key in update)` 直接抛。

**修法**：`set()` 的 update 只放**非主键列**（`{ enabled }` / `{ note, level }`）。

### 坑 87：自己写 YAML 解析器，**空值键 + `- 项` + 多段键**三个都能把它带歪

读 `koishi.yml` 里那几行 affinity 参数本来想省一个依赖，结果连踩三下
（判据脚本 `.scratch/check-yaml-config.cjs` 现在还留着，改解析器必须一起改它）：

1. **键里有冒号**：Koishi 的实例键是 `http:aa0001: {}` 这种 `名字:实例id` 形状。
   用 `/^([^:#]+):(.*)$/` 抓键会切成 `key=http` / `value=aa0001: {}`，
   于是 `plugins` 里一个真插件都认不出来（键数恒为 2）。
   → 按**最后一个冒号**切键值，取段名时按第一个冒号切。
2. **空值键是不是容器要看下一行缩进**：`plugins:`（下面更深）是容器，
   `mode:`（下一行同缩进）是空字符串。第一版"空值一律当容器并压栈"，
   空字符串键把栈顶顶住，兄弟键全被吞。
3. **栈顶缩进 ≥ 本行缩进就说明本行是兄弟**，必须先弹栈顶再挂。
   第一版容器节点缩进写成 0，兄弟键被一层层塞进彼此树里 —— 最后 `root` 只有一个键。

另外读取时要 **unwrap**：节点把子项放在 `[ASC]` 里，`Object.entries(节点)` 只看得到
`Ascending/List/indent/marker` 四个内部字段。

**教训**：这种"就是个显示用的兜底"最容易写成静默出错 —— 数字全错但页面正常。
**必须配一个拿真实文件跑的判据脚本**，否则它错了你只会看到"参数来源：默认值"。

### 坑 88：`ctx.loader.baseDir` 在 Koishi 4.18 上**不存在**

两个插件都要读 `koishi.yml`，第一版写的是 `ctx.loader?.baseDir ?? process.cwd()`。
实测（rig 67 第二轮）：读不到文件 → 静默回落默认值 → `/short` 显示
「折算线 +15，参数来源：本插件配置（显示用默认值）」，而真正生效的是 +12。

`baseDir` 的正确出处是 loader 自己 provide 的服务：`@koishijs/loader/lib/shared.js:354`
`app.provide('baseDir', this.baseDir, true)` → 走 `ctx.get('baseDir')` / `ctx.baseDir`。

**修法**：`ctx.get('baseDir') ?? ctx.baseDir ?? ctx.root?.baseDir ?? process.cwd()`，
并且在启动日志里**打印来源**（`logger.info('… 参数来源：%s')`）—— 这一行是"到底读到哪份"的唯一证据。

### 坑 89：改完文件**必须 `node --check`**，否则会看到"幽灵现象"

排查"新加的别名没进首页"折腾了三轮 test rig，最后发现是我一次 `edit` 把两行合到了一起：

```js
const shown = visible(items, mine, showAll)    const pageSize = Math.max(...)
```

文件语法错误 → **插件整个加载失败** → `/help` 那条命令压根没注册 →
但群里照样有回执（别的插件/旧实例的响应），于是现象看起来像"逻辑不对"。
`run-rig` 的日志里**没有任何 `[E]`** 也是因为那个失败发生在 koishi 进程启动早期、
被 loader 吞成了别的形态（不是每个失败都会打 `[E]`）。

**规矩**：改完插件文件先 `node --check`（三个插件各一条），再跑 rig。
离线判据脚本（`.scratch/check-help-shortcut.cjs`）之所以值钱，就是它**秒级**能抓到这类问题。

### 坑 90：自检脚本自己的 stub 会骗人（同名对象要复用、`alias()` 要照做）

写离线判据时，stub 的 `ctx.command(name)` **每次新建一个对象**，
于是 `_commandList` 里出现**两条同名 Command**：`cmdr.get()` 看到一条、列表遍历看到另一条，
"运行时加的别名到底在不在首页"这件事根本测不出来（我一度以为是插件 bug）。

同一个脚本里还漏了"真实 Command 对象一定有 `_aliases`"这件事，
导致 alias 表里那条 `mm → models` 被判成"目标没别名"而跳过。

**教训**：stub 必须**照抄真实对象的关键不变量**（同名唯一、`_aliases` 一定存在、
`.alias()` 真的会写进 `_aliases`），否则判据自己就在制造假象 ——
而且它比不放判据更危险：你会拿着一个错的红/绿灯去改好代码。

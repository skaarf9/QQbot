## 1. 出站令牌桶（防限流总闸）

**为什么放在 `chatluna-guard` 里**：按 [硬约束](05-硬约束.md) 第 0 条"先本地"——
guard 本来就有 `before-send` 出站闸（第 3 道闸门），而 `before-send` 是**所有出站消息的唯一必经之路**
（普通 @ 回复、R9 主动插话、followup 跟进、指令回执全都经过它）。
在它上面加令牌桶，等于用一个钩子覆盖了全部出站路径，不需要新插件。

**实现**：经典令牌桶，按**群**计数（私聊默认不限）。

```yaml
outboundEnabled: true
outboundBurst: 3        # 桶容量（允许的突发条数）
outboundPerMinute: 12   # 每分钟匀速补充
outboundApplyToPrivate: false
outboundGroups:         # 按群覆盖
  - guildId: '454444539'   # 测试群（自己人）
    burst: 6
    perMinute: 30
  - guildId: '1040488785'  # 真群（30 人）
    burst: 2
    perMinute: 8
```

桶空了就**丢弃这条消息**并打 `[W]` 日志（丢消息比被腾讯限流/封号好）。
新增指令：`/限速 [群号]`（1 级，看剩余令牌与累计丢弃数）、`/限速重置 [群号]`（4 级，应急补满）。

**验证**（`_research/test-newmechs.cjs`，桩注入）：

```
桶容量2/每分钟1，连发 5 条: send send DROP DROP DROP
私聊（未开启限速）→ 放行: true
```

**这是 2026-10-02 限流事故（[真群事故](16-真群接入与限流事故.md)）的真正补完**：
当时只给 followup 补了"整群熔断"，普通回复与 proactive 仍无总闸；现在所有出站路径都被同一只桶罩住。

### 2.2 ★ 一个必须先解决的拦路问题：deepseek 适配器会过滤模型

`koishi-plugin-chatluna-deepseek-adapter` 的 `refreshModels` 里写死：

```js
return models.filter((model) => model.includes("deepseek") || model.includes("embedding"))
```

→ **名字不含 `deepseek` 的模型根本不会出现在 ChatLuna 的模型列表里**，
`createChatModel('deepseek/stealth/space-bunny-alpha')` 会直接 `MODEL_NOT_FOUND`。

**解法**：装一个通用适配器 `koishi-plugin-chatluna-openai-like-adapter@1.4.1`（平台名 `ccfree`），
它支持 `additionalModels` + `modelCapabilities`，可以**手动声明某个模型支持 `image_input`**
（绕过 ChatLuna 的名字白名单 `imageModelMatchers`——`space-bunny-alpha` 本来不匹配任何一条）。

生产配置：

```yaml
  chatluna-openai-like-adapter:ccfree:
    platform: ccfree
    pullModels: false          # 不拉全量，只认下面两个
    additionalModels:
      - model: stealth/space-bunny-alpha
        modelType: LLM 大语言模型
        modelCapabilities: [text_input, tool_call, image_input]
        contextSize: 1000000
      - model: inclusionai/ling-3.1-flash:free
        modelType: LLM 大语言模型
        modelCapabilities: [text_input, tool_call]
        contextSize: 262144
    apiKeys:
      - - >-
          <同一个 commandcode key>
        - https://api.commandcode.ai/provider/v1
        - true
```

## 3. 图片去重：改用感知哈希（pHash）

**问题**：原实现是 `sha256` 精确匹配。同一张图被**转发 / 重压 / 换格式**后字节变了，
sha256 认不出来 → 重新烧一次视觉调用。而表情包插件用的是 **pHash**，两套口径不统一。

**实现**（`external/koishi-plugin-chatluna-vision/`）：
- 表 `chatluna_image_cache` 新增 `phash` 列（16 位 hex，64 bit）。
- 查缓存顺序：**先 sha256 精确命中 → 再 pHash 近似命中**（汉明距离 ≤ `phashThreshold`，默认 5）。
- 内存索引 `phash → {hash, description}`，启动 3 秒后建一次、写入时增量更新（热路径不扫库）。
- 并发合并的 key 从 sha256 改成 **pHash**，同一张图的不同字节副本也能并成一次调用。
- pHash 用 `imghash`（**与 chatluna-sticker 同一个库、同一套 64 位 pHash**）——两边认的是同一批图。

**实测鲁棒性**（对同一张图重压/缩放后比对 pHash）：

| 变换 | pHash | 汉明距离 |
|---|---|---|
| 原图 PNG | `027fcd8392b6929e` | — |
| JPEG q85 / q60 / q40 / q20 | 全部 `027fcd8392b6929e` | **0** |
| 缩到 300px 宽 | `027fcd8392b6929e` | **0** |

→ **重压到 q20、缩到 300px 都完全免疫**，去重会非常有效。

新增配置：`dedupeByPhash`（默认 true）、`phashThreshold`（默认 5）；
`/vision.stat` 现在会显示"其中带 pHash 的 N 条 / 内存索引 M 条"。

## 4. 「还有 N 条消息等待回复」的来源与关闭

**根因**：这是 **ChatLuna 内建**的"思考中提示"，不是我们自己发的。

- 开关：`sendThinkingMessage`，**默认 `true`**
  （`koishi-plugin-chatluna/lib/index.cjs:6751`）
- 默认文案（locale `chatluna.thinking_message`）：
  > **「我还在思考中，前面还有 {0} 条消息等着我回复呢，稍等一下~」**

这行正是用户看到的"当前还有 xx 条消息等待回复"。

**修法**：`chatluna:03llpk` 加一行

```yaml
sendThinkingMessage: false
```

源码依据：`thinking_message_send` 中间件首行 `if (!config.sendThinkingMessage || …) return SKIPPED`；
`thinking_message_recall` 同样判断。关掉后**既不发送也不再尝试撤回**，任何情况下都不会再出现该文案。

```

```

**但自写 rig 不建议废弃**：它的"固定剧本 + 断言 + 独立实例"仍然是最省事的**回归**手段
（改一次配置跑一遍 35 个剧本）。**建议分工**：

- **日常调参、看效果、试"怎么写才能唤醒"** → 用 `chatluna-sandbox`（控制台 `/sandbox` 页）。
- **回归、防退化** → 用自写 rig 跑剧本。

>
> 🔑 **它还会把 API key 明文写进库**（2026-10-02 22:3x 补记）：每次模型调用的**完整请求头**都落在
> `chatluna-sandbox.model-request.header`，其中 `headers.Authorization = "Bearer user_…"`。
> **这是关不掉的**——`persistenceMode: memory` 只切换沙箱模拟的 QQ 环境状态，模型请求记录走
> `createModelRequestPersistence` **无条件落库**（插件 `lib/index.js:14862-14872`）。
> 所以 `koishi.db` 属于**敏感文件**：分享/备份它等于交出 key。旧记录已打码并 `VACUUM`，
> 但**下次模型调用会把新 key 写回去**（用户已知情并决定暂不修）。
> 想根治只能 fork 到 `koishi-app/external/` 把 `Authorization` 打码。
>
> ⚠️ **另一个坑：`VACUUM` 之前，打码是"假"的**。SQLite 的 `UPDATE` 只把新行写进新页，
> 旧值仍留在**空闲页**里——表查询 0 命中，但整个文件的原始字节里还能捞到明文 key。
> 清完必须 `VACUUM`（实测空闲页 26→0、文件 892 KB→782 KB 后才真正零残留）。

## 6. 表情包为何"从未触发"

**先看事实**（生产库 `koishi-app/data/koishi.db`）：

| 观测 | 值 | 说明 |
|---|---|---|
| `data/sticker-library/` 文件数 | 46 个图、37 个哈希分桶 | **收集在正常工作** |
| `sticker_occurrence` | 46 行 | 46 张不同的图 |
| 状态分布 | `new` 45 行 / `collected` **仅 1 行** | 只有 1 张图达到了 `judgeThreshold` |
| `sticker_meta` | 1 行，`useCount = 0` | **收藏过，但从未真正发出过** |
| `judgeError` | 全部为空 | 视觉判断没有报错 |

**结论：不是插件坏了，是"没料 + 没场合"**：

1. `judgeThreshold` 原来是 **3** —— 同一张图要在群里**出现 3 次**才会送模型判断是否收藏。
   真群里的图几乎都是一次性发的（各出现 1 次），所以 45 张一直停在 `new`。
2. 唯一被收藏的那张（`027fcd8392b6929e`，出现 5 次）是**测试时**反复发的。
3. 即使库里只有 1 张，模型也很少想起调 `sticker_send`；而真群放行 2 分半就被限流静音了，
   bot 根本没有"想发表情"的场合。

**已做的调整**：

```yaml
  chatluna-sticker:stk001:
    judgeThreshold: 2            # 3 → 2：出现 2 次就判断，更容易攒出可用的库
    judgeModel: ccfree/stealth/space-bunny-alpha   # 判断改用免费模型，成本不再是顾虑
```

**怎么确认它真的能发**：用 `chatluna-sandbox` 的 WebQQ 工作台，在测试空间里发一张图两次
（触发判断→收藏），然后 `@bot 发个表情包，要能表达无语的` —— 应当看到 `sticker_send` 工具被调用并真的发出图。

## 7. 结构化输出实现「一次调用、多回复」——评估

### 需求

> 让 AI 返回结构化内容，解析后发给不同的人 / 分多条发，两条之间可设间隔，模拟人类分条回复。

### 结论：**可行，且值得做，但建议分两期**，本期未实现。

**可行性依据**：所有出站都经过 `before-send`，我们的 `chatluna-replyshaper` 已经证明了
"在发送口拦下/改写/取消"这条链路是通的。多回复只是"拦下原文 → 自己按计划发多条"。

### 建议的分期

**第一期（低风险、高收益）：分条发送（不做定向）**
- 预设里要求：想分多条说就**用空行分隔**（或用一个安全分隔符，如 `|||`）；
- 插件在 `before-send` 里切分，取消原文，然后 `ctx.setTimeout` 按"每条间隔 0.8~2.5 秒（可加抖动）"逐条 `session.send`；
- 效果：**同一轮 API 调用，发出 2~3 条短消息**，正是人类聊天的节奏；
- 成本：**零额外 API 调用**。

**第二期（有明确需求再做）：定向分发（`to=某人`）**
- 需要模型输出带目标的标记（如 `@某人`），插件在群里发 `h('at') + 文本`；
- 私聊跨人分发要 `bot.sendPrivateMessage()`，涉及"bot 主动私聊别人"，**需要用户明确同意**才做。

### 必须注意的坑（评估里最重要的一段）

1. **别用 `<tag>` 当分隔符**：Koishi/Satori 会把 `<...>` 当**元素**解析，消息可能在到我们之前就被拆成元素。
   用 `|||` 或换行更安全。
2. **自己发的消息会被自己的钩子再次拦截**：`session.send()` 同样触发 `before-send`。
   必须给二次发送打一个"旁路标记"（像 guard 的 `__guardControl` 那样），否则会无限递归或被重复整形。
3. **必须走令牌桶**：多条消息会因为突发而撞上第 1 项新加的桶（这是设计意图）。
   分条发送前应先问 `ctx.qqbotGuard` 拿配额，或者把"一次分条"当成**一次**配额。
4. **模型标记不可靠**：必须容忍解析失败 —— 解析不出来就当普通文本整条发，绝不能丢消息。
5. **顺序与撤回**：分条发送后 `recallThinkingMessage` 之类要能对应上；间隔太长时用户可能已经接了下一句。
6. **与 R9 主动插话的关系**：分条对"主动插话"尤其自然（人插话也很少只发一句），但要把条数压到 2 条以内，
   否则在真群就是刷屏。

### 一句话建议

**先做第一期（分条），别急着做定向分发。** 分条能拿到 80% 的"像真人"收益、几乎零风险；
定向分发的收益不明显，却要打开"bot 主动私聊别人"这个口子，得单独评估。

## 8. 去掉回复里的空行

**实现**：新插件 `koishi-plugin-chatluna-replyshaper`（`external/koishi-plugin-chatluna-replyshaper/`）。
在 `before-send` 里逐段整形：

- 行尾空格去掉；
- **连续换行压成一个**（`\n{2,}` → `\n`）；
- 去掉首尾换行；
- 整段变空的文本元素**直接丢掉**（避免发出空消息）；
- 图片等非文本元素原样保留。

**验证**（`_research/test-newmechs.cjs`）：

```
去空行: ["第一行\n第二行"]        ← 输入是第一行\n\n第二行\n\n
带图混合: ["img:","text:图\n好"]   ← 图片保留，文本被整形
```

配置：`cleanBlankLines`（默认 true）、`stripTrailingSpaces`（默认 true）、`skipWhenEmpty`（默认 true）。
预设里也加了一句"不要在回复里留空行"（双保险）。

## 9. 给 AI 加「是否回复」的判断

**机制（哨兵法）**：模型在**判断这轮不该开口**时，整条只输出 `[SKIP]`；
`chatluna-replyshaper` 在发送口看到整条消息**只有**哨兵就取消发送。

- 哨兵可配：`skipTokens`，默认 `['[SKIP]', '【不回复】', '（不回复）']`，比较时忽略空白与标点；
- 带图/带 at 的混合消息不会被误判为哨兵（只对"全是文本"的消息判定）；
- guard 自己的开关回执带 `__guardControl` 标记，**不做哨兵判定**（避免吞掉回执）。

**预设新增段落**（`data/chathub/presets/default-persona.yml`，当时还叫 `xingyuan.yml`）：

```
【是否开口】
你有权利**选择这一轮不说话**。遇到下面这些情况，就**只**输出 [SKIP]：
- 群里这波话题跟你没关系、插进去只会显得多余（择机插话时尤其要克制）；
- 你现在心情很差（烦躁/生气/难过），不想搭理；
- 对方只是在自说自话、或者@你是为了跟别人说话。
该回的时候好好回，别动不动就 [SKIP]。
```

**为什么用哨兵而不是空回复**：ChatLuna 对空内容可能直接不发、也可能发一条空消息，
行为不稳定；哨兵是一个**明确、可配置、可观测**的开关，而且**同一套机制同时覆盖**
"群聊插话时机"（R9）与"生气时不想说话"（R14）两个需求——这正是用户要的。

**验证**：

```
哨兵 [SKIP] → 取消: true
哨兵 带标点「（不回复）」→ 取消: true
正常回复 → 放行: true
```

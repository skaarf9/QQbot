## 1. 主对话模型：vision 版并不贵，但额度只有 1/3

### 1.1 先把定价摊开（GOAT 计划，per 1M tokens，均为 off-peak 价）

| 模型 | 输入 | 输出 | 缓存读 | 额度（请求/5h · /周 · /月） | 智能分 | 视觉 |
|---|---|---|---|---|---|---|
| `deepseek-v4-flash-vision-exp`（**原来的主模型**） | $0.15 | $0.60 | $0.003 | 10,300 · 25,600 · **51,300** | 34.8 | ✅ |
| **`deepseek-v4.1-flash`（本次切换）** | $0.15 | $0.60 | $0.003 | 30,800 · 76,900 · **154,000** | **39.5** | ✅ |
| `deepseek-v4.1-flash-fast` | $0.16 | $0.58 | $0.016 | 11,500 · 28,700 · 57,500 | — | ✅ |
| `deepseek-v4-flash-fast` | $0.28 | $0.56 | $0.07 | 1,040 · 2,610 · 5,210 | — | ❌ |
| `deepseek-v4-flash`（latest） | $0.15 | $0.60 | $0.003 | 30,800 · 76,900 · 154,000 | 34 | ❌ |
| `deepseek-v4-pro` | $0.66 | $1.98 | $0.022 | 1,980 · 4,940 · 9,880 | 36.0 | ❌ |

**★ 关键事实：vision 版和 v4.1-flash 的单价完全一样（$0.15/$0.60，缓存读 $0.003）。**
用户担心的"视觉版更贵"不成立——**贵的是额度**：vision 版每月只有 51,300 次请求、
而 v4.1-flash 有 154,000 次（**3 倍**），智能分还更高（39.5 vs 34.8）。

> 定价来自 <https://commandcode.ai/docs/plans/goat> 的实际抓取（`/models` 接口不返回价格，
> 只有 context_length，所以必须看计划页）。

> **★ 视觉这一列怎么读（2026-10-07 定论，别再当成"待确认"）：**
> **DeepSeek v4 系列不支持图像输入；从 v4.1 起，flash 与 pro 都支持。**
> 所以 `deepseek-v4-flash-vision-exp`（v4 的专用视觉实验版）之外的 v4 型号都是 ❌，
> 而 `deepseek-v4.1-flash` / `-flash-fast` / v4.1 pro 都是 ✅。
> 详细说明与"ChatLuna 白名单"那层障碍见下面 §1.2。

### 1.2 为什么换成 `v4.1-flash`：额度 ×3 + 智能分更高（视觉另有其人）

**先把「DeepSeek 支不支持视觉」一句话说清楚：**

| 档 | 支持图像输入？ |
|---|---|
| **v4 系列**（`deepseek-v4-pro` / `deepseek-v4-flash` / `deepseek-v4-flash-fast`） | ❌ **不支持** |
| `deepseek-v4-flash-vision-exp`（v4 的**专用视觉实验版**，名字里的 `vision` 就是它存在的理由） | ✅ 支持 |
| **从 v4.1 起**（`deepseek-v4.1-flash` / `deepseek-v4.1-flash-fast` / v4.1 pro） | ✅ **支持** |

实测依据：2026-09-29 拿用户发的真实表情包**直接打 API**，`deepseek-v4.1-flash` HTTP 200 / 6.4 s
就正确读出了画面（对照表见 [ChatLuna 生态实测](06-阶段2计划与ChatLuna生态.md)）。

> ⚠️ **"中转侧支持" ≠ "ChatLuna 肯传图"。** ChatLuna 靠**模型名白名单** `imageModelMatchers`
> （`vision` / `vl` / `gpt-4o` / `claude` / `deepseek-flash` …）判断，`deepseek-v4.1-flash`
> 一条都不匹配 → 它会拒绝传图并打 `Model "..." does not support image input`。
> 想让它传图，必须在本项目的适配器配置里**显式声明 `image_input`**（做法见 [图片策略](09-图片策略与表情包.md)）。

**真实的切换理由是额度和智能分**（见上表）：两者单价**完全一样**，
但 `v4.1-flash` 的月额度是 vision 版的 **3 倍**、智能分还高 4.7 分。

而且 —— **"换成没有视觉的模型"这个顾虑本来也不成立**：
`chatluna-vision` 在消息进模型之前就把图片换成了文字描述
（`transformer.before`，priority -100，见 [图片策略](09-图片策略与表情包.md)）。
逐条核对过它的每个分支，**没有任何一条会把 `img` 元素留给模型**：

| 情况 | 处理 |
|---|---|
| 缓存命中（sha256 / pHash） | 换成 `{desc}` 文本 |
| 群里没 @bot 且没缓存 | `elements[i] = null`（`ignoreUnparsedInGroup` 默认 **true**）→ 直接丢掉 |
| 该解析但下载失败 | 换成"无法读取（图片已失效）"文本 |
| 解析成功 | 换成描述文本 |
| 解析抛错 | 换成"解析失败"文本 |
| R9 主动插话塞的图 | `parseWhenUserIds` 强制放行 → 正常解析 |

→ 主模型收到的一直是**文字**（图上信息以描述的形式进来），所以主模型**不需要自己看图**。
⚠️ 安全前提：`chatluna-vision` 必须**保持启用** —— 它的价值和"主模型支不支持视觉"无关，
而是**把图换成稳定、可缓存、可去重的文字描述**（缓存按 sha256/pHash 命中，见 [图片策略](09-图片策略与表情包.md)）；
关掉它，图片元素会直接进上下文，而**队列里只要有一个不吃图的中转模型，整组能力就会降级**。

**工具调用能力已实测**（这是 agent 功能的前提，不能只信文档）：

```
deepseek/deepseek-v4.1-flash        HTTP 200  tool_calls: get_weather {"city":"北京"}   ×3 次稳定
deepseek/deepseek-v4.1-flash-fast   HTTP 200  tool_calls: get_weather                  ×2 次稳定
deepseek-v4-flash-vision-exp        HTTP 200  tool_calls: get_weather
```

## 2. 记忆抽取 / 插话判断能不能交给免费 AI？本地小模型呢？

### 2.1 记忆抽取 → 免费 AI：**已经这么干了，而且实测通过**

现状就是免费模型（上一轮已切）：`longMemoryExtractModel: ccfree/inclusionai/ling-3.1-flash:free`。

**实测**（`_research/test-memory-extract.cjs`，把插件源码里真正用的
`ENHANCED_MEMORY_PROMPT` 抠出来喂仿真聊天记录）：

| 模型 | 结果 | 耗时 |
|---|---|---|
| **`ling-3.1-flash:free`（当前）** | ✅ 抽出 **5 条**，YAML 围栏格式完全合规 | 6.7 s |
| `space-bunny-alpha`（免费） | ✅ 4 条 | 5.7 s |
| `deepseek-v4-flash-fast`（付费） | ✅ 4 条 | 5.6 s |

抽出来的东西质量也对：

```
· [personal/8] 用户是做后端开发的
· [personal/7] 用户在杭州
· [interest/6] 用户喜欢玩硬核动作游戏，最近在玩《黑神话：悟空》
· [preference/4] 用户玩动作游戏时偏好棍法流，不玩召唤
· [habit/6] 用户周末一般去爬山，基本每个月一次
```

**结论：记忆抽取这类"输入一段文本、输出固定结构"的活，免费模型完全够用，可以放心交给它。**
唯一要留意的是它比付费模型慢 ~1s（可以接受，因为它是**异步后台**跑的，不挡回复）。

> ⚠️ 一个真实的坑（写在这里免得以后再踩）：插件的解析失败是**静默**的。
> 源码 `extractMemoriesFromChat` 只认 ```yaml 围栏里的 `memories:` 键，
> 拿不到就直接 `return []`，只打一行 `debug` 日志（默认看不到）。
> 所以"格式不对"和"这轮没什么值得记的"在日志里长得一模一样。
> **`_research/test-memory-extract.cjs` 就是为这个写的** —— 换模型后先跑它。

### 2.2 插话时机判断 → 免费 AI / 本地小模型：都可行，但要分层看

先说清楚**现在已经是什么样**（避免重复造）：

- `chatluna-proactive`（R9）自己有一套**启发式活跃度打分**（消息频率、空闲时长、冷却、`activityThreshold`）
  决定"要不要起个话头"，然后才调主模型生成内容。
- `chatluna-replyshaper` 的 **`[SKIP]` 哨兵**让**主模型**可以在生成后说"这轮我不开口"（上一轮刚加的）。

也就是说"AI 判断要不要说话"已经有了，只是**用的是主模型 + 在生成之后判断**，
而不是"先用一个便宜模型判断、再决定要不要花主模型的钱"。

**三个层次，按性价比排**：

| 方案 | 成本 | 延迟 | 质量 | 评价 |
|---|---|---|---|---|
| **A. 规则/特征门槛**（纯逻辑代码：@了没、是不是问句、上条消息多久前、bot 最近说了几句、情绪值、好感度） | 0 | ~0 ms | 可预测、可调试 | **最该先做的**。R9 已经有雏形，把特征补齐就够了 |
| **B. 免费 API 模型当"闸门"** | 0（免费额度） | **5~7 s**（实测 ling 6.7s / bunny 5.7s） | 中上 | 对**主动插话**够用（反正在等轮询）；对**普通回复**太慢，会让人干等 |
| **C. 本地小模型当"闸门"** | 0（电费） | **0.2~1 s** | 4B 起步可用，1.5B 中文语境偏弱 | 高频闸门的最优解，但要装环境 |

**本机能不能跑本地模型？能，而且够用**（实测硬件）：

```
CPU    12th Gen Intel i5-12400F（6 核 12 线程）
内存   15.8 GB
GPU    NVIDIA RTX 3060 Ti（8 GB 显存；WMI 显示 4GB 是 32 位溢出的老 bug）
```

- **7B/8B Q4_K_M**（约 4.5~5 GB）→ 全塞进显存，推理约 30~60 tok/s，判断一句话 <1 s；**推荐这个档位**。
- **1.5B~3B Q4**（约 1~2 GB）→ 更快，但中文"该不该插话"的微妙判断会翻车，只适合当粗筛。
- 纯 CPU 跑 1.5B 也能到 10~20 tok/s，不装显卡驱动也能用。

**接入路径（不用写新适配器）**：本机没装 Ollama（`11434` 未监听），但有两条现成路：

1. **`koishi-plugin-chatluna-ollama-adapter@1.4.1`**（市场有）——装 Ollama + 拉一个 Qwen3-4B，
   加个平台就行。
2. **复用上一轮已经装好的 `koishi-plugin-chatluna-openai-like-adapter`** ——
   本地用 llama.cpp / vLLM 起一个 OpenAI 兼容端点（`http://127.0.0.1:8080/v1`），
   当成一个新平台（比如 `local`）加进 `additionalModels`。**这条最省事，一个适配器复用到两处。**

**我的建议（可行性排序）**：
1. **先做 A**：把 R9 的启发式门槛补全（零成本、零延迟、立刻见效）。
2. **再做 B**：把免费模型当**主动插话**的闸门（反正要等轮询，5~7s 无所谓），实测误插率。
3. **最后才考虑 C**：只有当"闸门延迟"成为问题时，才上本地 7B。
   **不要一上来就本地部署** —— 多一个常驻进程要运维，而收益（省钱）在免费额度下几乎为零。

### 2.3 一句话总结

**记忆抽取 → 免费 AI 已经够用（已验证）；插话判断 → 先用规则、再用免费 AI 当闸门、本地模型放最后。**

## 3. 记忆去哪看？还要知识库吗？

### 3.1 先说一个**实测发现**：长短期记忆现在是**空的**

这不是猜的，是把落盘文件与向量库都翻了一遍：

| 存储 | 位置 | 实际内容 |
|---|---|---|
| 长期记忆 · 向量库 | `data/chathub/vector_store/luna_vdb/<hash>/docstore.json` | **120 字节 = 空** |
| 长期记忆 · 向量索引 | 同上 `luna_db.index` | 2 KB = 空索引 |
| 长期记忆 · 知识图谱 | `data/chatluna/long-memory/hippo/<hash>.json` | `{"adj":[],"postings":{},"simhashEntities":{}}` = **零三元组** |
| 长期记忆 · 图谱（另一引擎） | `data/chatluna/long-memory/emgas/<hash>.json` | `nodes:[] / edges:[] / totalObservations:0` = **空** |
| 会话（短期） | `data/chatluna/archive/<会话id>/messages.jsonl.gz` | ✅ **有内容**（3 个已归档会话，各约 28 条） |
| `chatluna_docstore`（Koishi 库里的） | `data/koishi.db` | 0 行 |

**所以"记忆发挥得怎么样"的答案是：短期（会话上下文）在正常工作，长期目前是 0 条。**

### 3.2 为什么是空的 —— 三个原因，都不是 bug

翻源码（`koishi-plugin-chatluna-long-memory/lib/index.cjs`）得到：

1. **抽取有频次门槛**：`chatCount % longMemoryExtractInterval(默认3) !== 0` 就直接返回。
   也就是**每 3 轮才抽一次**，而且是"每个会话各自计数"——会话一归档/重启，计数就重置。
2. **★ 自动抽取只写 `User` 层**：`after-chat` 里写死了
   `initMemoryLayers(..., MemoryRetrievalLayerType.USER)` 与 `addMemories(memoryInfo, memories)`。
   虽然我们配了 `enabledLayers: [Guild, User]`，**群层（Guild）永远不会被自动写入**
   （这正是 [19 号文档](19-API调用机制梳理与评审.md) 点评过的那条）。
3. **模型非常克制**：提示词明确要求"大多数对话没有任何长期价值，只抽真正值得记几个月的"，
   而且给了"闲聊 → `memories: []`"的范例。我们之前的测试内容多是"嗷什么嗷你才是老鼠"这类斗嘴，
   **模型返回 `[]` 是正确行为**，不是故障。

> 换句话说：管道是通的、模型是好的，只是**还没有真正值得记的对话发生过**。

### 3.3 怎么看记忆（三个层次，都能用）

| 方式 | 命令 / 路径 | 适合 |
|---|---|---|
| **① 聊天里看**（推荐） | `/chatluna.memory` 列表；`/chatluna.memory.search <关键词> --view User` 搜 | 日常巡检、确认"它记不记得我" |
| **② 手动写入验证链路** | `/chatluna.memory.add "我是做后端的" --view User` → 再 `/chatluna.memory.search 后端` | **最快验证"记忆到底通不通"** |
| **③ 只读脚本看落盘** | `node --no-warnings tools/peek-docstore.cjs`（可加 `--grep 词` / `--full`） | 排查"为什么没存进去"；已跑过，当前输出就是 **0 条** |
| **④ 直接翻文件** | `data/chathub/vector_store/luna_vdb/*/docstore.json`、`data/chatluna/long-memory/*/*.json` | 看原始 JSON |

权限已经就位（qqbot-auth 启动日志）：
`chatluna.memory`（查看）= 2 级，`add/edit/delete/clear` = 3 级。

**建议先做一次 ②**：如果 `/chatluna.memory.add` 之后能搜出来，说明整条链路（写入→向量化→检索）
是好的，只是"自动抽取"还没触发过；如果也搜不出来，那才是真有问题（本地嵌入模型 / 向量库）。

### 3.4 有了记忆，还需要知识库吗？—— **需要，两者不是一回事**

|  | 长期记忆 | 知识库 |
|---|---|---|
| 内容 | **关于"你/这场关系"**的私有事实（名字、喜好、住哪、习惯） | **领域事实**（游戏机制、wiki 条目、产品文档） |
| 来源 | 聊天里**自动抽取** | 人工**导入**（文档 / 网页 / 结构化数据） |
| 变化 | 随对话持续变化、会衰减过期、**会记错** | 权威、稳定、可版本化 |
| 体量 | 几十~几百条 | 几万~几十万条 |
| 失效 | 过期就删 | 版本更新就重导 |

**记忆解决的是"它认不认识我"，知识库解决的是"它懂不懂这件事"。**
把游戏攻略塞进"记忆"会立刻撑爆（而且记忆会被模型按"重要性"裁剪），
把"用户在杭州"塞进知识库又毫无意义。**所以：不是二选一，是各管一段。**

### 3.5 想精通某款游戏：wiki MCP 还是内建知识库？

**结论：优先 wiki MCP，只把"高频且稳定"的那一小部分固化进知识库。**

| 维度 | Wiki MCP | 内建知识库 |
|---|---|---|
| 时效性 | ✅ **永远跟最新版本走** | ❌ 版本一更新就过期，要重导 |
| 建设成本 | ✅ 低（配一下地址就行） | ❌ 高（抓取、清洗、切分、嵌入、调参） |
| 调用成本 | 每次查询一次网络往返（+ 可能被限流） | ✅ 本地向量检索，快且不依赖外网 |
| 覆盖 | 只有 wiki 有的 | 你想塞什么就塞什么 |
| 游戏适配 | ✅ **游戏是最吃"版本更新"的场景** | ⚠️ 只适合机制类稳定知识 |

**推荐做法（游戏场景）**：

1. **主用 wiki MCP**：查询型问题（"这个 BOSS 弱点是什么"、"材料在哪刷"）直接查 wiki，
   数据永远是新的。ChatLuna 的 MCP 支持已经在手上：
   - 核心自带管理命令：`/chatluna.mcp.add <json>` / `list` / `remove` / `enable`（改完需重启生效）
   - 但**运行时**（真正去连 MCP server 的那个部分）需要装 `koishi-plugin-chatluna-mcp-client`
     （`@modelcontextprotocol/sdk`）。**这个包本轮已经装好了**（`package.json` 里有），
     只是**没在 `koishi.yml` 里启用**——因为不配任何 server 时它会启动报一行
     `[W] Failed to initialize MCP client`。等你有具体的 wiki MCP 地址了，加一行
     `chatluna-mcp-client:mcp001: {}` 再重启就生效。
2. **知识库只放"稳定 + 高频"**：例如当前版本的属性克制表、常用配装表——
   这类东西每次问都要查外网太慢，且版本内不变。
3. **别做全量 wiki 镜像**：游戏 wiki 动辄几千页且一直在改，导入即过期，纯属浪费。

## 5. HTML / Markdown → 图片（结构化渲染）

### 5.1 先查过市场（硬约束第 0 条）

| 插件 | 能干什么 | 为什么不直接用 |
|---|---|---|
| **`koishi-plugin-puppeteer@3.9.0`** | 提供 `ctx.puppeteer` 渲染服务 | **✅ 直接用**（本插件复用它）|
| `koishi-plugin-shotkit@0.1.3` | 同形 API、**不需要浏览器**（WebKit 内核） | 备选（本机已有 Edge，用 puppeteer 更稳）|
| `koishi-plugin-chatluna-image-renderer@1.4.0` | 官方：把**整条回复**渲染成图（Markdown+LaTeX+代码） | 它是「**输出模式**」不是「工具」，也不认结构化数据 |
| `koishi-plugin-html-renderer@1.0.0` | EJS + playwright 渲染 HTML | 也是服务，不暴露给模型 |
| `koishi-plugin-to-image-service@1.9.3` | satori 系，非浏览器渲染 | 复杂 HTML/CSS 支持弱 |

**结论：渲染"能力"市场有（且成熟），"给模型调用的工具"和"结构化输出适配"没有。**
→ 按第 0 条，**能力用市场的，只自写最薄的一层适配**。

已安装：`koishi-plugin-puppeteer@3.9.0`（它用 `puppeteer-core` + `puppeteer-finder`，
**不下载 Chromium**，自动找到本机 `C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`）。

### 5.2 自写的那一层：`koishi-plugin-chatluna-render`

位置：`koishi-app/external/koishi-plugin-chatluna-render/`。三件事：

**① 一个稳定服务**（给未来的结构化输出链复用）：
`ctx.chatlunaRender.renderToBuffer(kind, content)` / `renderElement(...)` / `available()` / `stats()`

**② ChatLuna 工具 `render_image`** —— 模型可以自己决定"这段该出图"：

```
kind: 'html' | 'markdown'      # 拿不准用 markdown
content: string                # 内容本体
caption?: string               # 可选：图前配一句话
```

调用后插件把渲染结果**直接发到当前会话**，只回给模型一句短话
（"已经把 Markdown 渲染成图片发到当前会话，不要再重复发送"）——
**绝不把 base64 塞回模型上下文**（那会瞬间撑爆 token）。

**③ 结构化输出适配（给未来留的接口）**：模型回复里出现

```
%%render:html
<div>…</div>
%%endrender
```

→ 在 `before-send` 里把这一段**换成渲染好的图片**（其余文字保留）。
**默认关闭**（`blockEnabled: false`），等你的结构化输出方案定了再打开。
选 `%%` 而不是 `<tag>` 做标记，是因为 Koishi/Satori 会把 `<...>` 当**元素**解析，
消息可能在到我们手上之前就被拆了（这条在 [20 号文档第 7 项](20-2026-10-02改动与评估.md) 里已经踩过）。

### 5.3 安全（内容来自模型 = 不可信输入）

| 开关 | 默认 | 作用 |
|---|---|---|
| `allowJavaScript` | **false** | 关掉页面 JS，防止模型用渲染去执行脚本 |
| `allowRemoteResources` | **false** | 拦截所有非 `data:`/`about:` 请求 → **防 SSRF**、防拉一堆 CDN 拖慢渲染 |
| `maxContentChars` | 30000 | 内容太长直接拒绝 |
| `maxBlocksPerMessage` | 2 | 一条回复最多渲染几块，防刷屏 |
| 出图后 | — | 走正常发送通道 → **自动受 guard 的令牌桶约束**（不用自己再造限流） |

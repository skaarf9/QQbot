## 3. 帮助体系（`chatluna-help`）

### 3.1 为什么必须重写，而不是改文案

原来 `/help` 打印的是 `qqbot-auth` 里**手写的 8 行**，只覆盖 `qqbot.*`。
运行期指令表实际有 **143 条**（生产实测）。

手写清单有一条铁律：**它一定会越写越旧**。所以新插件**不在代码里列任何指令**，
一律从 `ctx.$commander._commandList` 现场枚举 —— 装一个新插件，帮助页自动多出它的指令。

### 3.2 三级结构（用户要的「按类型逐级展示」）

| 级别 | 触发 | 内容 |
| --- | --- | --- |
| ① 总览 | `/help` | 有哪些类目、各多少条、我能用几条、最低等级 |
| ② 类目 | `/help <代号>` `[页码]` | 这一类每条一行：指令名 / 说明 / 等级徽章，**每页 18 条**分页 |
| ③ 单条 | `/help <指令名>` | 用法、参数、选项、别名、等级、类目 |

每一页底部都写着**下一步该发什么**，用户不需要记语法。

类目代号是 ASCII（`/help chat` 好打），同时也接受中文类目名（`/help 对话与模型`）。

### 3.3 有效等级怎么算

**一个指令的有效门槛 = 它自己与所有祖先指令上 `authority:N` 的最大值**
（`@koishijs/core` 判定时整条链都要过，只读自己的 `config.permissions` 会漏）。

`chatluna-help` 的 `effectiveLevel()` 与 `qqbot-auth` 的同名函数是**同一套算法、必须同源** ——
那边管**提权**，这边管**展示**，两边不一致的话帮助页会显示错的等级。

### 3.4 类目规则

`koishi.yml` 里可配（`categories`），默认规则见插件里的 `DEFAULT_CATEGORIES`。
**前缀匹配按最长优先**，所以 `chatluna.memory` 会先于 `chatluna` 命中。

两个实测才发现的坑：
- **好感度插件的指令根是 `<scopeId>` 而不是插件名** —— 它拿配置里的 `scopeId` 当命名空间
  （`koishi.yml` 里 `chatluna-affinity.scopeId`）。漏了这条，10 条指令全落进「其他」。
  这个值 2026-10-04 从 `xingyuan` 改成了 `affinity`（用户要求去掉旧角色名，
  见 [坑 60](../04-踩坑记录.md)）—— 类目前缀、别名 target、预设变量要跟着一起改。
- 生产比测试台多 19 条指令，多出来的 `assign` / `authorize` / `user` / `channel` 来自
  `@koishijs/plugin-admin`、`replyshaper` 是自研的。**测试台跑通不代表生产归类干净**，
  启动日志里那句「未归类 N 条（…）」就是给这件事用的。

### 3.5 `/help` 的归属

**框架的 `@koishijs/plugin-help` 也会注册一个 `help`**（`plugin-help/lib/index.js:129`，
而且 `authority: 0`）。两个同名指令叠在一起时，**命令的多个 action 是按顺序取第一个非空返回**，
谁先注册谁生效 —— 留着它，我们自己的 action 可能永远不执行。

所以 `koishi.yml` 里**摘掉了 `help:3nsrbd`**，并在插件里做了启动自检：

```
help 自检通过：`help` 指向本插件
```

**这条自检必须走 `logger.info` 而不是 debug 门控的 `log()`** ——
生产 `debug=false`，用 `log()` 的话「通过」永远不打印，于是「没打印」既可能是没通过、
也可能是没开 debug，自检就失去意义了。（第一版就是这么写的，踩了。）

## 4. 图片库（`chatluna-page`）

### 4.1 为什么选「缓存」而不是「一次性出图」

用户给了两条路。实测（`.scratch/bench-render*.cjs`）之后选缓存，但**理由和直觉不一样**：

- **出图本身很便宜**：热态 130~330 ms。
- **真正贵的是体积**：880px 视口下，40 行表格 2.0x 是 836 KB、1.5x 是 644 KB、1.0x 是 211 KB。
  JPEG 不比 PNG 小（同页 877 KB），所以格式不用换，**像素密度才是那个旋钮**。
- ★ **落盘缓存省的是渲染 CPU，不省上传体积** —— 每次 /help 还是要把 PNG 发给 QQ。
  所以缓存的价值是「省 CPU + 抗并发 + 重复访问即时」，**不是省流量**。别把它的作用记错。

### 4.2 键是内容哈希

`sha1(CACHE_VERSION, kind, width, dsf, breaks, maxContentChars, css, content)`

好处：**指令表一变（装了新插件、改了描述），哈希就变，缓存自动失效** ——
不需要任何手工「刷新」动作，也不会出现「改了配置还在发旧图」这种脏状态。
`CACHE_VERSION` 用于「页面样式改了但内容没变」的情况（本次 v1 → v2：
视口收边 + 硬换行改变了出图结果）。

### 4.3 上限必须双管

`cacheMaxEntries`（默认 80 张）**和** `cacheMaxMB`（默认 40 MB）**都要卡** ——
只卡条数挡不住「50 张 800KB 的大表」。淘汰顺序：先按 TTL 过期（默认闲置 168 小时），
再按最久未用（LRU）。

启动时**扫盘重建索引**，不额外维护 meta 文件 —— 避免索引和文件不一致。

### 4.4 图片库指令

| 指令 | 等级 | 作用 |
| --- | --- | --- |
| `/page.status` | 3 | 图片库状态卡（存量/上限/命中率/上次耗时） |
| `/page.list [条数]` | 3 | 列出最近用过的图（键 / 大小 / 最后使用） |
| `/page.prune` | 3 | 按 TTL + 上限立刻清理一次 |
| `/page.clear` | 4 | 清空图片库 |
| `/page.text [on\|off]` | 1 | **把页面化输出切回文字**（调试用，见 5.3） |

## 5. 状态命令自动出图 —— **16 个插件零改动**

### 5.1 做法

所有出站消息都经过 `before-send`，而 `session` 上带着「这条消息是哪条指令产生的」这个标记。
所以只要在 `chatluna-page` 里挂一个 `before-send`，就能把名单里指令的**文字输出自动换成图片**：

```js
ctx.on('before-send', async (session) => {
  const cmd = session.__pageCommand          // ← 见坑 B，不能读 session.argv
  if (!autoWanted(cmd)) return
  if (session.elements.some((el) => el.type !== 'text')) return   // 只处理纯文本消息
  const md = 标题 + 正文
  session.elements = [h.image(await render(md))]
})
```

**为什么不在每个插件里各写一遍**：12 处重复，而且**将来装的插件不会自动覆盖**。
挂在这里是单点改动，新指令只要加进 `autoRenderCommands` 就有图。
（和 `chatluna-cmdname` 用运行期净化而不是改 `node_modules` 是同一个思路。）

### 5.2 名单：只挑「给人看的」，不碰「给人抄的」

默认名单 18 条：`emotion`、`guard.status`、`guard.list`、`guard.limit`、`vision.stat`、
`render.status`、`scene`、`proactive`、`followup`、`localemb`、`selfext.requests`、
`sticker.admin.stat`、`qqbot.auth`、`qqbot.auth.list`、`page.status`、`page.list` …

**故意不出图的**：`vision.list`、`sticker.admin.inspect`、`sticker.admin.pin`、
`cmdname.scan`、`qqbot.auth.me`。

判据一句话：**输出里有要抄进下一条指令的标识符 → 留文字**。
`/vision.list` 列出图片描述和 hash 前缀，用户要**原样复制**那个 hash 去发
`/vision.correct <hash> <text>`；出图会让它没法复制。

> ★ **2026-10-03 晚（第四轮）这条判据被用户收窄了**：他要求"群聊里的长文本一律图片化"，
> 于是出图规则从"白名单"改成 14.2 那三条 —— 名单外的指令只要不短于 40 字符也出图，
> `vision.list` 因此**不再默认留文字**（想改回来把它加进 `keepTextCommands` 即可）。
> 仍然留在文字里的只剩 `cmdname.scan`（纯诊断）与 `page.text` / guard 四条开关回执。

### 5.3 退路

`/page.text on` 让当前会话的所有页面化输出退回文字 —— 出图是给人看的，文字是给手抄的。
另外 `output()` **永远不会抛错**：关了 / 没服务 / 出图失败，一律原样返回文字，宁可丑也不能把指令搞挂。
长内容出图后还可以用 `/more [n]` 翻页（第四轮新增，见 14.3）。

## 6. 思考过程（`chatluna-think`）

### 6.1 不调用 API 是怎么做到的

模型返回的 reasoning 会**随回复一起**到达。ChatLuna 在 `chatluna/after-chat` 事件里把这条
回复对象直接交出来（`@chatluna` 系 `llm-core/chat/app.cjs:515`）：

```
ctx.parallel('chatluna/after-chat',
             conversationId, arg.message, displayResponse, variables, chatInterface, session)
                                          ^^^^^^^^^^^^^^^ 第 3 个就是 AI 回复
```

所以这里只是**接住它、存下来**，`/think` 再把存下来的东西出图 —— **全程零请求**。

### 6.2 reasoning 在哪个字段

适配器（`@chatluna/v1-shared-adapter`）把增量拼进 `additional_kwargs.reasoning_content`
（`index.cjs:949-996` 非流式 / `1173-1236` 流式）。插件里做了多路探测（`reasoning_content` /
`reasoning` / `response_metadata.reasoning_content` / content 数组里的 reasoning 块），
因为不同适配器放的层不一样。

**它不落库**：`chatluna_message` 表 56 行里 `additional_kwargs_binary` **全是 NULL**
（本次离线取证），所以只能从事件现场抓，事后查库查不到。

### 6.3 ★ 现状：现在 `/think` 大概率会说「这次没有思考过程」

**这是上游的事实，不是插件坏了。** 离线统计了库里 24 次调用的 usage：

```
reasoning token 非零的次数: 0
output_token_details: { audio: 0, reasoning: 0 }   ← 24 次全为 0
```

即 `stealth/space-bunny-alpha` 与 `deepseek/deepseek-v4.1-flash` **当前都不吐 reasoning**。
哪天队列里换成会思考的模型，`/think` **不用改代码**就会开始有内容。
`/think.status` 可以看「观察了多少次回复、其中几次真的带了 reasoning」。

### 6.4 安全

reasoning 是**不可信输入**（模型生成的，而模型受用户影响），要进 HTML 页面，
所以先把 `& < >` 转义掉再交给渲染。页面本来就禁 JS、拦外网（`chatluna-render` 的默认姿态），
转义是第二道，防的是「用一段 HTML 把页面排版搞烂」。

## 7. guard 出站限流豁免命令驱动的回复

### 7.1 为什么必须改

令牌桶防的是**模型刷屏**，那才是不可控的。而 `/help`、`/guard.status` 这类输出的
**条数与时机完全由人控制** —— 一个群 `burst=2`，用户敲两次帮助页就把自己的模型回复额度
吃光了，这显然不对。用户原话：**「这种命令应全都不占配额才对，因为是命令驱动的」**。

### 7.2 A/B 验证（rig 剧本 `41-guard-quota-exempt.json`）

做法：先在群里 `/guard.allow` 放行，然后**连发 6 条指令**把桶（容量 3）打空。
指令之间 `wait` 必须是 0，否则桶按每分钟 12 条自己补回来，打不空。

| `outboundExemptCommands` | 结果 |
| --- | --- |
| **`true`（默认）** | 6 条指令**全部**有回执，日志逐条打印 `指令输出不占配额：<指令名>`，**0 丢包** |
| `false` | 只有前 3 条有回执，后 3 条 `出站超速，丢弃一条（群 454444539：剩余 0.00 / 3 个令牌…）` |

模型回复 / proactive 主动发言 / followup 跟进都**没有**这个标记，照旧受限。

## 8. ★ 踩到并修掉的四个坑

这四个坑的共同特征：**装好了、日志干净、但功能完全不工作**。改这些插件前先读这一节。

### 坑 A：`Command.toJSON().description` 全是 `[object Object]`

第一版渲染出来的帮助页，**124 条指令的说明栏全是 `[object Object]`**。

根因在 Koishi 的 i18n —— `I18n.get(key, locales)` 返回的是**locale → 文案 的映射对象**，
不是字符串（`@koishijs/core/lib/index.cjs:1648-1655`）：

```js
get(key, locales = []) {
  const result = {}
  for (const locale of this.fallback(locales)) {
    const value = this._data[locale]?.[key]
    if (value) result[locale] = value
  }
  return result
}
```

而 `Command.toJSON()` 正是用 `ctx.i18n.get(...)` 填 `description` 的（同文件 1125 行）。
框架自己的 help 插件也绕开了 toJSON，改用 `session.text(['commands.X.description',''])`
渲染（`plugin-help/lib/index.js:170`）。

**正确做法**：`ctx.i18n.render([], [path, ''], params).join('')`。
第二段路径 `''` 是兜底 —— 文案缺失时返回空串而**不会**打 `missing` 警告，
否则 124 条里只要有一条没写说明，日志就会被刷屏。

### 坑 B：`session.argv` 在 `before-send` 里**永远是空的**

这是本次最隐蔽的一个。第一版自动出图**一次都没触发**，日志显示：

```
before-send 判定：指令=(没有 argv) 名单命中=-
```

根因在 `@satorijs/core` 的编码器：出站时它 **new 了一个 session**，然后把原 session 上
**可枚举**的键逐个拷过去（`lib/index.cjs:739-742`）：

```js
for (const key in this.options.session || {}) {
  if (key === 'id' || key === 'event') continue
  this.session[key] = this.options.session[key]
}
```

而 `argv` 是 Koishi 用 `defineProperty` 挂上去的（`@koishijs/core:1285`）——**不可枚举**，
于是被这个循环漏掉。

**`chatluna-guard` 的 `__guardControl` 之所以一直有效，正是因为它是一次普通赋值。**
所以两处都改成：在 `command/execute`（指令真要执行的那一刻）打一个**普通赋值**的标记：

```js
ctx.before('command/execute', (argv) => {
  const s = argv?.session
  if (s && argv?.command) s.__pageCommand = argv.command     // guard 里叫 __guardIsCommand
})
```

> 这条经验是通用的：**任何「在中间件里打标记、在 before-send 里读」的写法，
> 标记都必须是一次普通赋值**，不能用 `defineProperty`。

### 坑 C：Markdown 会把单个换行折成一个空格

状态命令的输出是「一行一条」（`render.status` 六行）。第一版出图后，
**六行被折成了一整段**，完全没法读 —— 因为 CommonMark 规定单个 `\n` 是软换行，
渲染成空格。

**修法**：渲染时开 GFM 硬换行（`marked.parse(content, { breaks: true })`）。
但它会改变 `render_image` 工具出图的风格，所以做成**按次覆盖的参数**：
`chatluna-render` 默认 `false`（保持原样），`chatluna-page` 传 `true`。

### 坑 D：`fullPage` 截图**不会小于视口高度**

第一版每张短图下面拖着约 900px 空白（`emotion` 是 1320×1350，内容其实只占 300px 高）。

`page.screenshot({ fullPage: true })` 只会**向下**扩展到内容高度，**不会向上缩到视口以下**。
所以把视口高度设成一个很小的值，让 fullPage 贴着内容收边：

| 视口高 | 短页面 | 长页面（40 行表格） |
| --- | --- | --- |
| 900（旧） | 1320×1350 | 1320×1962 |
| **10（现）** | **1320×437** | 1320×1962（**不受影响**） |

`chatluna-render` 新增 `viewportHeight`，默认 10。
只有当页面用了 `height:100vh` 这类依赖视口的布局时，才需要调回 900。

> 注意 `page.evaluate` 量高度这条路**走不通**：`allowJavaScript: false` 时页面脚本是关的，
> 所以只能用「视口高度 + fullPage」这个不需要页面 JS 的办法。


> ★ 日志级别的一处刻意选择：`出图 …` 与 `自动出图 …` 走 **`logger.info`**，
> 不走 debug 门控的 `log()`。出图是低频事件（有缓存），而生产 `debug=false` ——
> 用 `log()` 的话生产日志里**看不到任何出图记录**，出了排版问题没法回查是哪个键、多大、多久。
> 「命中缓存」那条仍然留在 debug（那个会很频繁）。
> 这条规则和坑 35 里「自检必须走 info」是同一个教训：**门控日志会让"没发生"和"没开日志"分不清**。

### 9.4 ★ 端到端已在生产验过（而且是用户自己触发的）

用户在 **01:32:57**（上一轮实例里）真的发了一次 `/help`，产出的图落在
`koishi-app\data\page-cache\79595a30f378c3e16855.png`（1320×1073，116 KB）——
内容就是「大肥鱼 · 指令总览」：11 个类目、每类条数、可用数、等级徽章、底部导航提示。

这一张图顺带证明了三件事：

1. **生产链路通**：指令 → 渲染 → 图片 → 下发，全程无人工干预。
2. **图片库跨重启存活**：01:35 重启后新实例打出 `图片库已载入：1 张 / 0.11 MB`。
3. **内容哈希失效是真的有效**：那张图是**修类目规则之前**生成的，写着「11 类 / 其他 7 条」；
   现在总览页的内容变成「10 类 / 未归类 0 条」→ 哈希不同 → **旧图不会被复用**，
   用户下次 `/help` 会拿到修正后的新图。这正是第 4.2 节想要的自动失效，不用手工清缓存。

# 24 指令页面化 · 第二轮

> 属于 [24 —— 指令页面化：帮助体系 / 图片库 / 思考过程](../24-指令页面化与图片库.md) 的一段（2026-10-07 按轮次切开，编号未变）。

## 12. 第二轮：用户在真群里试出来的一批问题（2026-10-03 上午）

用户原话：

> 可以观察我在"My test"群聊中发送的消息与会话，有蛮多内容需要修改的，比如命令没有效果
> （或者是我没正确使用？），还有就是我怀疑图片压缩会对所有大小的图片起作用（应该是超过大小的
> 才压缩），导致图片没有正确理解到，然后是 ai 对于图片的理解出现了串行……然后是 ai 引用消息
> （以及 @群友）的功能，似乎目前还没实现？还有偶尔回复的延迟很高，需要单独 @ 才会产生回复，
> 不清楚是否是模型的延迟

**五条，四条是真 bug，一条（引用/@）确实是没实现。** 逐条对应下面 12.1–12.5。
取证材料全部来自生产日志 `prod-2026-10-*`（测试群的 8 条 receive / 8 条 send 全在）。

### 12.1 图片压缩：用户是对的，代码就是无条件压

见 **docs/04 坑 37**（含实测数字和修法）。核心：

- 旧行为 `sharp().resize().jpeg(q85)`，只要压完更小就采用 → **123KB 的表情包也被压成 78KB**；
- 新判据「不压会付代价」才压：长边 > 1024 **或** 字节 > 256KB（另加 EXIF 摆正的例外）；
- 缓存键是原图 sha256，所以加了 `v` 列做版本失效，否则改了参数不生效。

### 12.2 图片理解「串行」：描述被当成用户说的话

生产日志里两条直接证据：

```
01:52:13 [I] chatluna-vision 图片已解析（7013 ms）：金发紫眼的女孩穿着校服趴在地上，一只手用枪指着她的头。
01:52:22 [send] ……你这描述也太渗人了
               所以刚那张是枪指着头的图啊，刚才还以为是「鰻子」呢
```

「**你这**描述」——模型把视觉插件塞进去的描述当成了**用户自己打的字**。
原因是 `textTemplate` 默认值就是裸的 `{desc}`，替换进用户消息后与用户原话无从区分。

三处改动：

1. 正文默认 `[图片{i}] {desc}`，引用默认 `[引用的图片{i}] {desc}`；
2. `{i}` 在一条消息里有多张图时展开成 ` 1`/` 2`，单图时是空串（单图仍是 `[图片] …`）；
3. **正文和引用用不同模板** —— 之前共用一套，模型分不清哪张是"他刚发的"、哪张在引用里。

### 12.3 延迟：解析是同步阻塞的，大图会拖死整轮

`handleElements` 跑在 `transform` 里，`await task` 一直等到视觉模型返回。
生产里最夸张的一张是 **5.6MB 的 GIF 表情**（01:55:34）。那期间用户发什么都排在后面。

加了 `blockingTimeoutMs`（默认 15s）：超时就先塞一句占位文字放行本轮，
**task 不取消** —— 它在后台继续跑、照常写缓存，所以同一张图下次出现直接命中，代价只付一次。

### 12.4 「引用消息 / @群友」：确实没实现（不是配错了）

全仓搜过：`chatluna` / `followup` / `vision` / `proactive` 里的 `quote` **全是入站判定**
（"这条消息引用了我吗"），出站侧一个 `h('quote')` 都没有；`@` 只有 followup 往 elements
前面插一个**指向 bot 自己**的 at。`chatluna` 核心里那个 `allowQuoteReply` 也是入站闸门
（`lib/index.cjs:2952`）。

新插件 **`chatluna-reply-style`**，挂在 `before-send` 上（一个点覆盖所有出站路径）：

| 配置 | 默认 | 说明 |
|---|---|---|
| `quote` | `first` | `off` / `first`（一轮只第一条）/ `always` |
| `mention` | `first` | 同上；私聊由 `mentionInDirect` 单独控制 |
| `maxAgeSeconds` | 180 | 触发消息太旧就不引用了 |
| `skipCommands` | `true` | 指令输出不加（回执是功能性的，加了是噪声） |

指令：`/replystyle`（看状态）、`/replystyle.quote <off|first|always>`、
`/replystyle.mention <off|first|always>`（运行时临时改，重启回配置值）。

★ 两个坑都记在 **docs/04 坑 36**：`ctx.on('message')` 来得太晚（Processor 的监听器注册得更早）、
`ctx.before('message')` 注册的其实是 `before-message`（没人 emit）。**正解是 prepend 中间件。**

★ 顺带让 `chatluna-page` 容忍开头的 `quote`/`at` 前缀：原来"有一个非 text 就整条放行"，
装上 reply-style 之后**自动出图会静默失效**。现在前缀原样留在外面，只把后面的纯文本换成图。

### 12.5 「需要单独 @ 才会产生回复」：是整群熔断，跟模型无关

生产日志：

```
01:52:17 [I] chatluna-followup 群 454444539 触发整群熔断（120s 内最多 3 条），跳过 2791932480
```

4 个人的群、120 秒最多接 3 条，第 4 句就撞上，而且**一个字都不发**。
详见 **docs/04 坑 38**。当时改了两处：`burstNotice`（熔断时发一句提示）+
`groupMaxPerWindow` 可按群覆盖。**★ 这两个改动在当天第三轮被全部推翻** ——
用户指出了更根本的问题（重复造闸 + 不该用固定语句填黑箱），见**第 13.2 节**。

### 12.6 验证记录

| 剧本 | 验什么 | 结果 |
|---|---|---|
| `43-unknown-command.json` | 未知指令兜底 | `/ext` → 「是**类目代号**不是指令名…发 `/help ext`」；`/zzzznope` → 通用提示；`/help basic` **照常出图**（没被抢）；`/hel` 让给 Koishi 自己的 suggest |
| `44-reply-style.json` | 引用 + @ | 出站变成 `{reply,id:100003},{at,qq:2791932480},{text}`；`quote off` 后只剩 `@`；`mention off` 后只剩引用；指令输出全程不加 |
| `45-vision-compress.json` | 压缩阈值 | 24KB/800px → **未压缩**；62KB/1000px → **未压缩**；2349KB/1000px → 已压缩省 79%；300KB/2400px → 已压缩省 92%（**四步零 API 消耗**） |
| `46-followup-no-fuse.json` | ~~熔断提示~~ → 熔断删掉后不再误伤 | 连着 4 条不 @ 的消息全部「跟进触发」，**0 次**「令牌桶空」、**0 次**「整群熔断」（改造前第 3 条就会被 `groupMaxPerWindow=2` 打掉） |

`45` 用到的 `/vision.probe <路径或URL>` 是这一轮新加的**零 API 诊断指令**：
只跑「取图 → 元数据 → 压缩」并报告判定，用来随时复核压缩策略。

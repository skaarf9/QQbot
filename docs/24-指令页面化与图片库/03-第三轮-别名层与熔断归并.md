## 13. 第三轮：指令别名层 + 熔断并入令牌桶（2026-10-03 下午）

用户原话（两件事一起提的）：

> 「现在的命令列表的命令有前缀，有的甚至使用的发 "xingyuan" 这个过时的名称前缀，
> 可能是插件本身的命令也全都搜集过来了。给当前的命令抽象一层，一是只有那些可能经常
> 用到的命令才列出来，二是只显示别名（别名为英文，一个单词，不重复），命令也是使用
> 斜杠加别名的方式调用，也就是建立一个抽象层命令与原本的命令的映射，同时保留一个
> 查看原有命令的参数，比如 -all 什么的」
>
> 「你提到的整群熔断是按照群的规模来变的，这个应该就是那个出站令牌规则了吧，但是我设想
> 的仅仅是按照时间添加令牌，其他的没有额外的限制，熔断机制还有必要吗？另外不要发送固定
> 语句『我先安静一会儿…急事直接 @ 我』，除了命令产生的回复以及 ai 做出的回复，我不想要
> 逻辑代码额外产生的回复，宁愿不说话（因为人也可能断线，但是人不会说固定的话）」

### 13.1 别名层（新插件 `chatluna-alias`）

**问题**：`/help` 首页曾经把运行期**全部 126~147 条**指令铺开，里面绝大多数是
`chatluna.use.model`、`xingyuan.inspect` 这种带命名空间前缀的诊断/运维指令。
对使用者来说那不是"能用的命令表"，是插件的内部结构。

**做法**：用 Koishi 原生的 `Command#alias()` 建一层映射，别名表就是那层抽象：

```js
cmdr.get('chatluna.use.model').alias('model')   // 之后 /model 与全名完全等价
```

- **只列常用的**：表里 43 条（`/help` 首页只画这些），其余 ~104 条留在 `/help -all`。
- **别名规则**：英文、单个单词、小写、全局唯一。复数专门用来区分"列表"和"操作"：
  `model` 切模型 / `models` 列模型，`room` 看当前会话 / `rooms` 列会话。
- **为什么是原生别名而不是转发指令或改写消息**：见 **docs/04 坑 39**（两条死路都会静默失效）。
- **注册时机**：`ready` 之后（`_registerAlias` 名字被占用时会抛异常，必须等指令表齐了才能判）。
  被占用/目标不存在一律 warn 跳过，绝不带崩插件。启动自检会把两个计数打出来：

```
[I] alias 指令别名层已挂载：43 个别名可用；目标缺失 0，名字冲突 0，表内重复 0
[I] help 常用别名层就绪：43 个别名（/help 首页只列这些）；126 条原始指令在 /help -all
```

**`/help` 的四级结构**（原来是三级）：

| 发什么 | 得到什么 |
|---|---|
| `/help` | **常用指令**：只有别名列（别名 / 用途 / 等级），18 条一页，`/help 2` 翻页 |
| `/help -all` | **全部指令**：原来的类目总览（147 条 / 10 类），点进 `/help <代号>` 看某一类 |
| `/help <代号>` | 类目页。有别名的指令显示成 `` `/model` `chatluna.use.model` ``（别名在前、原名缩小跟在后面） |
| `/help <别名或原名>` | 详情页。**多一行「原名」**：`` | 原名 | `chatluna.use.model`（`/model` 与它完全等价） | `` |
| `/help <代号> 2` | 类目页第 2 页（★ 这条从第一轮起就是坏的，第三轮复核分页才发现，见 docs/04 坑 42） |

`-all` 的三种写法都能用：`-a`、`--all`、`-all`。最后一种用的是选项 `symbols`
（Koishi 的 `-all` 会被当成组合短选项 `a`/`l`/`l`，只定义 `-a` 也能出结果，
但会顺手给 `options.l` 塞一个空值 —— 用 symbols 精确匹配整个 `-all` 就没这条尾巴）。

**别名表在哪改**：`koishi.yml` 的 `chatluna-alias.aliases`（也支持 Koishi 控制台的表格式编辑）。
`chatluna-help` 通过 `ctx.get('chatlunaAlias')` 读它来画首页；**读不到就退回原来的全量总览** ——
两个插件各自独立，少装一个也不开天窗。

**上线时的两个数字（都是校验器报出来的，不是我数出来的）**：

| 环境 | 可用别名 | 说明 |
|---|---|---|
| 测试台（rig） | **43** | 校验器的理想值：目标缺失 0 / 名字冲突 0 |
| 生产 | **42** | 少一个 `echo` —— 生产 `koishi.yml` 里挂了官方 `echo:fyrru2`，`echo` 这个名字已被它占了。启动日志如实打印 `别名不可用（名字已被占用或非法）：echo（已被 echo 占用）` 并**跳过**，不影响其它 42 条，也不会让插件崩。既然 `/echo` 本来就是可用的（那个插件干的是同一件事），表里就把这条删掉了 |

### 13.2 熔断并入出站令牌桶（`chatluna-followup` 删掉一整块配置）

用户问「熔断机制还有必要吗」——**没必要，删了**。理由是原来的设计犯了两重错：

1. **重复造闸**：`chatluna-guard` 早就有真正的令牌桶（`outboundBurst` 容量 +
   `outboundPerMinute` 按时间匀速补，挂在 `before-send` 上，是所有出站路径的总闸）。
   followup 的「整群熔断」是在它之上**又加了一道固定窗口计数**：
   两套口径、两处参数，算法还更差 —— 固定窗口能跨边界连发 `2×limit` 条
   （t=119s 发 3 条、t=121s 又发 3 条），令牌桶不会。
2. **拿固定语句填黑箱**：静默确实让用户困惑，但解法不该是让逻辑代码说人话。

**最终形态**（就是用户设想的那一条规则：**按时间补令牌，别的限制没有**）：

```
followup 入站判定 → ctx.get('qqbotGuard').bucket.peek(群号)
    桶空 → 安静跳过（连模型调用都不发生，因为它在 allow_reply 之前）
    桶有 → 照常跟进；真正的扣令牌仍然只发生在 before-send 一处
```

- `peek` **只看不扣**：扣令牌只有 `before-send` 一处，两处都扣等于额度减半。
- 为什么要提前 peek：令牌桶挂在出站，等它拦下来时模型已经跑完、钱已经花了。
- 附带的一个好处：直接 @ 的对话、主动插话、跟进**共用同一个桶** ——
  人主动要的回复天然优先，bot 自己找话说的那部分先被饿死，这个优先级正是想要的。
- 删掉的配置：`groupMaxPerWindow`、`groupWindowSeconds`、`burstNotice`（全局 + 按群各一套）。

`guard` 侧新增对外口子（`ctx.provide('qqbotGuard')` 的 `bucket`）：

```js
bucket: { params(gid), peek(gid), text(gid) }
```

### 13.3 顺带：清掉其它「逻辑代码产生的固定语句」

按用户的原则（除了命令产生的回复和 AI 的回复，逻辑代码不许额外说话）全仓审计了一遍
`session.send` / `bot.sendMessage`：

| 位置 | 是什么 | 处置 |
|---|---|---|
| `chatluna-followup` 熔断提示 | 「我先安静一会儿…急事 @ 我」 | **删**（触发它的熔断本身也没了） |
| `chatluna-guard` 开关回执 | 「好，我先不说话了」等 | **留** —— 用户敲了 `/guard.mute` 或裸词「闭嘴」，这是命令产生的回复 |
| `chatluna-help` 未知指令兜底 | 「没有 `/ext` 这个指令…」 | **留** —— 同样是用户敲了指令才有的回执（而且这正是第二轮修的那个 bug） |
| `chatluna-scene` 自动中断提示 | 「……行吧，那这局就算了。」 | **本来就是 `notifyOnAbort: false`**（默认关），保持关 |
| `chatluna-selfext` 申请私聊主人 | 「【插件安装申请】…」 | **留 + 新加开关** `notifyOwnerOnRequest`（默认开）。这是**命令驱动**（有人敲了 `/apply`）且**只发给主人私聊**，不进群 |
| `chatluna-render` / `sticker-admin` | 出图、发图 | 都是命令驱动 |

## 14. 第四轮：长文本也图片化 + 出站最小间隔 + AI 自己出图（2026-10-03 晚）

用户原话（四条，同一轮提的）：

> 1. 我尝试了一下大多数的命令，把那个"别名就是简写…"的这一段删掉，不需要在这个界面说明这些
> 2. 我注意到令牌桶虽然给群聊添加了限制，但似乎没有限制短时间能够回复的上限？就是每个回复之间的间隔，
>    既确保不会短时间回复多条，也确保不会调用 api 超时
> 3. ai 自己能将自己的话变成图片吗？甚至是让 ai 自己输出一段 html 渲染成图片然后发出来，这是可能的吗？
> 4. 群聊中的回复有一部分仍是大段文字，将其图片化吧，数据太多可以分页，指令上添加数字则翻页，类似 /help 那样

四条里有一条半是"其实已经能做到"，所以这一节的重点是**先把事实查清楚**（3 与 2 的前半），
再把真缺的东西补上（2 的后半、4）。

### 14.1 首页那段说明删掉了（第 1 条）

`chatluna-help` 的 `shortcutPage()` 里那段 `<div class="pg-note">别名就是简写…</div>` 整块删除。
首页只回答"有哪些能敲"，不讲机制；机制留在本文档与 `/help <别名>` 的详情页。
**别在帮助页里解释自己** —— 用户是来用指令的，不是来读设计文档的。

### 14.2 三条出图规则（第 4 条的上半）

第四轮之前，只有 `autoRenderCommands` 名单里那 18 条指令出图。
用户在真机上一敲就发现了不一致：`/mood` 是图、`/pics` 是文字、`/room` 是文字 —— 看起来像坏了。
于是把"要不要出图"从**白名单**改成**三条规则**（`chatluna-page`，`before-send` 单点）：

| 优先级 | 命中条件 | 出图？ | 理由 |
|---|---|---|---|
| ① | 指令在 `autoRenderCommands` / `autoRenderPatterns` 名单里 | **总是**（多短都出） | 老行为。状态卡（`/emotion`、`/guard.status`、`/scene`）就是"一张卡片"的语义 |
| ② | 名单**外**的指令输出，且 `autoRenderAllCommands` 开、文本 ≥ `minImageChars`（40） | 出图 | 用户抱怨的那条不一致。短回执（"没有待审图片"）仍然发文字 |
| ③ | **模型自己说的**文本，≥ `longTextMinChars`（180 字符）或 ≥ `longTextMinLines`（6 行），默认仅群聊 | 出图 | "AI 把自己的话变成图片"的**自动档**：模型什么都不用做，也不需要它愿意 |

两个例外（`keepTextCommands`，默认 `cmdname.scan` / `page.text` / `guard.mute|allow|reset|refill`）：

* **要抄的标识符**：输出里有要复制进下一条指令的东西（`cmdname.scan` 的诊断原文）。
* **开关回执**：`/guard.mute` 那种"好，这个群我先不说话了"是**对话里的确认**，不是给人看的数据。
  ★ 这条是 rig 49 用血换来的：测试台把 `minImageChars` 压到 1 之后，连"我恢复了"都被做成了图片。

另外**正文会转义裸 HTML**（`escapeBodyHtml`，默认开）：模型随口打一个 `<`（"3<5"）会被 marked
当成标签，轻则吃掉后面一整段、重则打乱整页排版。要的就是 HTML 时走 `render_image` 工具（那条路不转义）。

### 14.3 分页与 `/more`（第 4 条的下半）

超 `pageMaxChars`（生产 1200）字符的内容按**行边界**切成多页，只发第 1 页，
页脚写 `下一页：/more 2`；其余页留在内存里（每个会话只留最近一次，`pagerTTLMinutes` 15 分钟），
靠新指令 `page.more [page:number]`（别名 **`/more`**，见 `chatluna-alias`）翻：

* `/more` 不带数字 = **下一页**（记录里存着当前页号）
* `/more 3` = 跳到第 3 页；越界自动夹到 `[1, 总页数]`，不报错
* 记录过期或没有 → 一句"这里没有可翻页的内容了"，不抛错
* 用户切了文字模式（`/page.text on`）→ 退回纯文本（`plainify`），翻页不会因为渲染问题失效

**为什么不一次把 N 张图全发出去**：那正好撞上 guard 的出站限流（令牌桶 + 最小间隔），
3 张图要排 6 秒队，还容易被桶丢掉几张 —— 用户看到的会是"图发了一半"。
一页一图、要看自己翻，才是既省流量又不会被限流打脸的形态。

### 14.4 出站最小间隔（第 2 条）

用户说得对：**令牌桶是容量语义，不是节奏语义**。容量 3 的意思正是"头 3 条可以立刻一起冲出去"，
它拦得住第 4、5、6 条，拦不住前 3 条挤在同一秒。而 QQ 侧真正会炸的恰恰是**瞬时并发**
（retcode 1200、NapCat 的 send 排队到超时）。所以 `chatluna-guard` 里补了第二半：

| 规则 | 语义 | 超限时 |
|---|---|---|
| 令牌桶 `outboundBurst` / `outboundPerMinute` | **总量**：这段时间能说多少 | **丢**消息（宁可少说） |
| 最小间隔 `outboundMinGapSeconds`（默认 3s） | **节奏**：两条之间至少隔多久 | **排队等**（模型已经花过钱的回复不该被静默扔掉） |

实现上有四个点值得记：

1. **先过桶，再排队** —— 否则被桶丢掉的消息会白占一个坑位，把后面真正要发的挤走。
2. **"先占坑再等待"**：`before-send` 可能同时进来好几条（一轮回复拆成多条、主动插话与跟进撞车），
   只记一个"上次发送时刻"会让并发的两条读到同一个值、又同时发出去。这里用一条 per-群 的 promise 链
   把"读 `nextAt` → 写 `nextAt`"串行化（`claimGap`），谁先占到谁先走，后面那条拿到的是"前一条 + 间隔"。
3. **`before-send` 里可以 `await`**：`@satorijs/core` 的 `MessageEncoder.send()` 用 `app.serial` 调监听器，
   而 cordis 的 `serial` 是 `for await (const result of dispatch(...))` —— **逐个 await**。
   所以这一等会真的把发送推后，而不是只延迟一个回调。（这个事实本轮才确认，写进 docs/04 坑 45。）
4. **安全阀**：等超过 `outboundGapMaxWaitSeconds`（30s）就丢掉这条。正常碰不到 ——
   桶容量最大 6、间隔几秒，队伍最多排十几秒。

指令驱动的回复**既不占配额也不排队**（沿用 `outboundExemptCommands`）：
`/help` 这类是用户主动要的，条数与时机由人控制，把它算进节奏会让帮助页在真群里被拖慢。

**A/B 证据**（rig `51-outbound-gap.json`，零 API）：同一份剧本跑两遍，只改测试实例的
`outboundExemptCommands`。三条指令在同一秒里挤进来：

```
A) 不豁免（outboundMinGapSeconds: 2）
   [I] chatluna-guard 出站排队：群 454444539 等 2.0s 再发
   [I] chatluna-guard 出站排队：群 454444539 等 3.9s 再发
   发 05:54:37 / 05:54:39 / 05:54:41        ← 正好 2 秒一条
B) 豁免（生产默认）
   发 05:57:49 / 05:57:49 / 05:57:50        ← 同一秒内，且没有"出站排队"日志
```

### 14.5 AI 自己出图（第 3 条）—— **能做到，而且早就能**

先把事实摆清楚：`chatluna-render` 早就注册了 `render_image` 工具
（生产启动日志：`render_image 工具已注册（模型可自己决定把结构化内容渲染成图）`），
而且它**确实在模型的 tools 列表里**（生产日志里那几行 `chatluna-sandbox.model-request`
的请求体可以直接看到 `{"name":"render_image","description":"把一段 HTML 或 Markdown 渲染成一张图片发出去…"}`）。
模型自己写 HTML / Markdown → puppeteer 渲染成 PNG → `session.send` 发到当前会话，
走的是**和普通回复同一个发送通道**（照样受 guard 限流、照样被 reply-style 加上引用与 @）。

所以这一轮对第 3 条做的事只有两件：

1. **补一行可观测的日志**：`chatluna-render render_image 被模型调用：html / 734 字符 → 113654 字节（454444539）`。
   以前出图记录里**没有一行**能说明"这次是模型自己决定的"（page 的出图和它的出图长得一样）。
2. **把能力写进预设**：`default-persona` 的【能力边界】原来只写"你目前只会聊天、看图、发表情包、记事、陪玩"，
   和工具列表自相矛盾。补了一句"需要摆表格/榜单/对比/清单/卡片时调 render_image"。
   ★ 这属于**人设层的自我认知**，不改的话模型会以为自己做不了。

rig `50-ai-self-image.json` 实测（真模型，两步都成）：

```
[D] chatluna Call tool: render_image with {"kind":"markdown","content":"| 水果 | 颜色 |…"}
[I] chatluna-render render_image 被模型调用：markdown / 58 字符 → 14903 字节（454444539）
[发] 群454444539：[reply][@2791932480][图 …]
[D] chatluna Call tool: render_image with {"kind":"html","content":"<div style=\"width:420px…"}
[I] chatluna-render render_image 被模型调用：html / 734 字符 → 113654 字节（454444539）
[发] 群454444539：[reply][@2791932480][图 …]
```

模型第二张写的是一个带渐变、圆角、阴影、"CAPABILITY TEST" 小标题的卡片 —— 排版完全是它自己的。

**两条路各有用途，别合并**：

| 路径 | 谁决定 | 什么时候用 |
|---|---|---|
| `render_image` 工具 | **模型** | 它觉得"这段该漂亮地呈现"（表格、榜单、卡片） |
| 14.2 规则③（自动档） | **逻辑代码** | 它写长了（≥180 字符 / ≥6 行）—— 不需要它配合，也拦不住 |

### 14.7 这一轮踩到的坑

| 坑 | 一句话 |
|---|---|
| docs/04 坑 43 | Koishi 的 logger 走 Node `util.format`，**不支持 `%.1f`** —— 会打出「等 %.1fs 再发 1.764」这种半截话 |
| docs/04 坑 44 | `h.image(buffer)` 把 Buffer 放在 `attrs.src`，**不在 `attrs.file`** —— 拿它算字节数永远是 0 |
| docs/04 坑 45 | cordis 的 `serial` 是**顺序 await**（不是并发）—— 这既是"能在 before-send 里排队"的前提，也意味着一个监听器 await 会挡住后面所有监听器 |
| docs/04 坑 46 | 验一条规则要先排掉另一条规则的干扰：`minImageChars` 压到 1 之后，才发现 guard 的开关回执也被出图了 |

## 15. 留给后续

1. ~~端到端还没验~~ → **已验**（第 9.4 节，用户在 01:32:57 自己发了一次 `/help`）。
   剩下值得留意的是**图片在手机 QQ 上被压缩后清不清楚** —— 1.5x / 1320px 宽，实测肉眼看是够的，
   如果觉得糊就把 `chatluna-page.deviceScaleFactor` 调到 2（体积约 +30%）。
2. **`/think` 现在是空转的**（见 6.3）。要真正用起来，得往兜底队列里加一个会思考的模型。
3. **状态命令还有一批没进名单**：`sticker.stat`、`emotion.list`、`selfext.search` 等。
   加名字即可，不需要改任何插件。
4. **帮助页的「相关指令」**：单条详情页目前只提示同类目，可以考虑加「常用搭配」。
5. **图片库没有跨重启的命中率统计**（`stats.hit` 是内存态）。要长期观测得落盘。
   （存量/体积是从磁盘扫出来的，所以那两项跨重启是准的。）
6. **图片描述缓存 v1 的存量还没清**：改了压缩参数之后旧描述会被判为过期自动重解析，
   但如果想立刻回收空间，可以手动清一次 `chatluna_image_cache` 里 `v < 2` 的行。
7. **`chatluna-reply-style` 的运行时开关不落盘**：`/replystyle.quote off` 重启即失效（这是有意为之，
   避免配置有两份真相）。要长期生效请改 `koishi.yml`。
8. **引用时机的竞态**：`__rsTrigger` 拿不到时会退到"这个频道最近一条入站消息"。
   同一频道高频并发时理论上可能引错一条（有 `maxAgeSeconds` 和"一轮只引用一次"兜着）。
   真遇到再说，暂时不值得为它加复杂度的锁。

> 属于 [踩坑记录（重来一次会浪费几小时的东西）](../04-踩坑记录.md) 的一份。
> **按类型切分**（2026-10-07）：koishi.yml 的改写与注释、必填字段、scopeId 这类"一次改就是换命名空间"的字段。坑号未变；本文件覆盖坑 13、17、60、83。

### 坑 13：`chatluna-storage-service` 的 `storageBackend` 必填，不填会连报三个错

`chatluna` 的 **peerDependency** 里有 `koishi-plugin-chatluna-storage-service ^1.0.6`——
**光装 `chatluna` 不够**，还得装它。但装上后如果配置写 `{}`，会看到**三个**错误：

```
[E] app ValidationError: $.storageBackend missing required value
[E] app TypeError [ERR_INVALID_ARG_TYPE]: The "path" argument must be of type string. Received undefined
        at new LocalStorageBackend (... storage-service/lib/index.cjs:361:42)   ← path.join(storagePath,"temp")
[E] app TypeError: Cannot read properties of null (reading 'backendPath')
```

第三个是第二个的连带（服务构造失败 → 拿到 null）。**根因只有第一个**：
`schema` 里 `storageBackend` 是 `.required()` **没有默认值**（尽管代码里写了 `?? "local"`）：

```js
storageBackend: Schema.union([
  Schema.const("?").description("别选，特么的"),   // ← 作者的玩笑，别选
  Schema.const("local"), Schema.const("s3"), Schema.const("webdav"), Schema.const("r2")
]).required()
```

正确配置：

```yaml
  chatluna-storage-service:
    storageBackend: local
    serverPath: http://127.0.0.1:5140
    storagePath: ./data/chatluna-storage
    backendPath: /chatluna-storage
```

修好后日志出现 `[I] chatluna-storage-service Storage backend initialized: local`。
另注意它自己的说明：**需要 Koishi 与适配器在同机或同局域网**（本地后端靠 Koishi 的 HTTP 服务发文件）。

### 坑 17：`proxy-agent` 插件配 `{}` 等于没配

`@cordisjs/plugin-proxy-agent/lib/index.js`：

```js
var Config = z.object({ proxyAgent: Schema.string() })   // 没有默认值
function apply(ctx, _config) {
  ctx.on("http/fetch-init", (url, init, config) => {
    const proxy = config?.proxyAgent ?? _config.proxyAgent;
    if (!proxy) return;          // ← 没配就直接返回，什么都不做
```

所以 `proxy-agent: {}` **不会**自动读 `HTTP_PROXY`。
本项目实际走代理靠的是环境里的 **`NODE_USE_ENV_PROXY=1`**（Node 内置 undici 的 EnvHttpProxyAgent，
启动日志里那串 `[UNDICI-EHPA] Warning: EnvHttpProxyAgent is experimental` 就是它在生效）。
要在 Koishi 层面强制走代理，得显式写：

```yaml
  proxy-agent:
    proxyAgent: http://127.0.0.1:7890
```

### 坑 60（★ 改配置 = 换数据库命名空间）：affinity 的 `scopeId` 同时当**指令根**用

**背景**：用户提出「`/rank` 显示的依然是 `xingyuan.rank`，检查所有的 xingyuan 部分，
全部替换成功能性描述」——`xingyuan` 是小号的旧名「星源」。

**为什么不能只改 koishi.yml**：`chatluna-affinity` 拿配置里的 `scopeId` 干两件事：

| 用途 | 表现 |
|---|---|
| **数据库命名空间** | 所有读写都带 `where scopeId = '…'`（`chatluna_affinity_v2` / `_blacklist_v2` / `_user_alias_v2` / 两个 snapshot 表 / `_migrations`，主键里都有 `scopeId`） |
| **指令命名空间** | `buildScopedCommandName(scopeId, suffix)` → 指令全名是 `<scopeId>.rank` / `.inspect` / `.adjust` …（lib/index.js:1206） |

所以只改配置 = 换了一个命名空间：`/rank` 会**突然空掉**、所有人好感度回到初始值
（旧行还躺在库里，只是再也读不到），而 `qqbot-auth.affinityScopeId`、预设里的
`{affinity("…")}`、别名表的 target、帮助页的 prefixes 也全得跟着改 ——
**一处不改就是"静默失效"**（变量渲染成空串、别名目标缺失）。

**修法**（这一次是完整的五步）：

1. `koishi-app/tools/migrate-affinity-scope.cjs`：扫 sqlite_master 找出**所有带 `scopeId` 列的表**
   （不写死表名，插件以后加表也跟得上），`update … set scopeId='affinity' where scopeId='xingyuan'`。
   有 `--apply` 才真写，默认 dry-run；幂等。
2. `koishi.yml`：`chatluna-affinity.scopeId` + `qqbot-auth.affinityScopeId` → `affinity`
   （生产、测试两份配置 + `tools/gen-test-config.cjs` 三处）。
3. 预设 `default-persona.yml`：`{affinity("xingyuan")}` → `{affinity("affinity")}`
   （不写参数会**静默返回空串**，这是老坑，见 docs/13）。
4. `chatluna-alias` 的 5 条 target：`xingyuan.inspect/rank/adjust/block/unblock` → `affinity.*`。
5. `chatluna-help` 的类目前缀：`['affinity','xingyuan']` → `['affinity']`（留着旧的也无害，但没必要）。

**执行顺序**：**先停 Koishi** → 迁移 → 改配置 → 起。运行中的实例会拿旧 scopeId 继续写，
边跑边迁 = 两边各有半份数据。

**顺带查清的命名权归属**：`scopeId` 的 schema 里本来就写着「**不要使用与 bot 名称相同的
scopeId**，建议优先使用英文」—— 换成功能性名字（`affinity`）正是它推荐的用法，
`xingyuan` 属于历史遗留。

### 坑 83（★ 会擦掉文档）：`loader.writeConfig()` 是 `yaml.dump` **整份重写** —— 注释全丢

**症状**：在测试实例上按了一次 `/stages.set`，回执说"已写回 koishi.yml"，
但打开 `koishi-test/koishi.yml` 一看：**我加的中文注释全没了**，
缩进、空行、键序也都被压成机器格式。

**根因**：`@koishijs/loader` 的 `writeConfig()` 内部就是
`fs.writeFile(this.filename + '.tmp', yaml.dump(this.config))` ——
**它 dump 的是解析后的对象**，而 YAML 注释**根本不在对象里**，所以必然丢；
格式也一律按库的默认来。（控制台里保存插件配置走的也是这条路，所以官方行为如此。）

对普通项目这无所谓；对本项目是**硬伤** —— `koishi-app/koishi.yml` 是**靠注释讲"为什么这么配"**的。

**修法**：**运行时生效**与**落盘**分开：
1. 运行时：`loader.reload(父作用域, key, 新配置)` —— 这是控制台同款官方路径，
   而且它**自己不会写盘**（先给 fork 打 `kUpdate` 标记，于是 `internal/before-update` 直接 return，
   见 `@koishijs/loader/lib/shared.js:383-393`），所以不用担心它顺手把文件洗掉；
2. 落盘：自己**按行改** —— 定位 `<插件>:<id>:` 那一行，在它的子树里找 `字段: 值` 并替换；
   没有这一行就插在插件块的第一个子行；`undefined` 就删掉这一行。
   其余字节**一个都不动**（注释、空行、CRLF 全保留）。

`.scratch/check-models-state.cjs` 的判据 I 拿**真的 `koishi-app/koishi.yml`** 当输入，
断言：**只改了 1 行**、**行数不变**、**注释一条没少**、重新 `yaml.load` 后值是对的。

**顺带修掉的一个同源 bug**：`run-rig.cjs --default-model` 用 `next === text` 判断"没找到
`defaultModel` 行"—— 当文件里**已经是目标值**时（上一次跑台被中途打断、没走到还原），
`replace` 出来的字符串和原文一模一样，于是**误报"找不到"并 `exit 1`**，
而这个 `exit 1` 又不影响 PowerShell 的退出码，看上去像"跑完了但什么都没发生"。
改成用 `re.test(text)` 判断匹配。

**教训**：**"写回配置文件"这种操作，默认会毁掉人写的东西** ——
凡是要落盘的自动改动，先问一句"它会不会重排/丢注释"，会的话就自己按行改。
信号很明确：**这个仓库的配置文件里有注释，那就是契约的一部分**；

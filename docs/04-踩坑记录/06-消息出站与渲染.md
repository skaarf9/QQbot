### 坑 33（★ 出图必踩的两个排版坑）：Markdown 折平换行 + `fullPage` 不会小于视口

**症状一**：把「一行一条」的状态输出渲染成图片，**所有行被折成一整段**，完全没法读。
**根因**：CommonMark 规定单个 `\n` 是**软换行**，渲染成空格。
**修法**：`marked.parse(content, { breaks: true })`（GFM 硬换行）。
★ 它会改变 `render_image` 工具出图的风格，所以做成**按次覆盖的参数**：
`chatluna-render` 默认 `false`，`chatluna-page` 传 `true`。

**症状二**：每张短图下面拖着约 900px 空白（内容只占 300px 高，图却有 1350px）。
**根因**：`page.screenshot({ fullPage: true })` 只会**向下**扩展到内容高度，
**不会向上缩到视口以下**。
**修法**：把视口高度设成很小的值（`chatluna-render` 的 `viewportHeight`，默认 10），
让 fullPage 贴着内容收边 —— 短页面 1320×1350 → 1320×437，**长页面完全不受影响**。

> 注意：**「用 `page.evaluate` 量内容高度」这条路走不通** ——
> `allowJavaScript: false` 时页面脚本是关的。只能用「视口高度 + fullPage」。

### 坑 34（★ 想拿指令说明就必踩）：`Command.toJSON().description` 是 `[object Object]`

**症状**：用 `cmd.toJSON().description` 取指令说明，**每一条**都是 `[object Object]`。
本次第一版帮助页 124 条指令的说明栏全废。

**根因**（`@koishijs/core/lib/index.cjs:1648-1655`）：`I18n.get(key, locales)`
返回的是 **locale → 文案 的映射对象**，不是字符串：

```js
get(key, locales = []) {
  const result = {}
  for (const locale of this.fallback(locales)) {
    const value = this._data[locale]?.[key]
    if (value) result[locale] = value
  }
  return result
}
```

而 `Command.toJSON()` 正是用它填 `description` 的（同文件 1125 行）。
**框架自己的 help 插件也绕开了 toJSON**（`plugin-help/lib/index.js:170` 用的是
`session.text(['commands.X.description',''])`）。

**正确做法**：`ctx.i18n.render([], [path, ''], params).join('')`。
第二段路径 `''` 是兜底 —— 文案缺失时返回空串而**不会**打 `missing` 警告，
否则只要有一条指令没写说明，日志就会被刷屏。

### 坑 37（★ 用户凭直觉报的 bug，代码里确实写着）：图片压缩**对每一张图都生效**，不只看大小

**症状**（用户原话）：「我怀疑图片压缩会对所有大小的图片起作用（应该是超过大小的才压缩），
导致图片没有正确理解到」。而且他还怀疑 AI 会把一张图的理解安到另一张图上。

**根因**：`chatluna-vision` 的 `compress()` 是**无条件**的：

```js
const out = await sharp(buf).rotate().resize({...}).flatten().jpeg({ quality: 85 }).toBuffer()
if (out.length >= buf.length) return { buf, mime }   // 只有"压完更大"才不压
return { buf: out, mime: 'image/jpeg' }
```

**实测（生产日志 01:52:06）**：一张 **123727 字节的表情包**被压成 78633 字节。
省下的 45KB 对一次 7 秒的视觉调用毫无意义，而 JPEG 的有损重编码把图里的文字和细节抹掉了。
**用户是对的，代码就是那样写的。** 当时写这段的理由是"1.1MB 的 PNG 压到 68KB，耗时从 19 秒降到几秒"
—— 那条理由只对**大图**成立，实现却推广到了所有图。

**正确做法**：判据改成「**不压会付代价**」才压，两个条件满足其一：

| 条件 | 为什么 |
|---|---|
| 长边 > `maxEdge`（默认 1024） | 不缩就是几千像素，token 和时间都受不了 |
| 字节 > `compressMinBytes`（默认 256KB） | base64 之后进请求体，是真的贵 |

外加一个例外：带 EXIF 旋转信息的图（`orientation >= 5`）必须过一遍 sharp 才能摆正。
`metadata()` 只读文件头，比整图解码便宜得多。

**还有一个连带问题**：缓存键是**原图**的 sha256（当时的注释写着"换压缩参数不会让缓存失效"
—— 那时是特性，现在是 bug）。不处理的话，旧库里「被压糊了的描述」会一直被命中，
**改了参数却不生效**。所以给 `chatluna_image_cache` 加了一列 `v`，读的时候要求
`v >= CACHE_VERSION`，老的自动重解析。Koishi 会自己 `ALTER TABLE ... ADD COLUMN`（实测日志：
`sqlite auto updating table chatluna_image_cache` → `ADD \`v\` INTEGER NULL DEFAULT 0`）。

**顺带修掉的"串行"**：描述原来是**裸的 `{desc}`** 直接替换进用户消息，跟用户自己打的话长得一模一样 ——
模型于是回出「**你这描述也太渗人了**」这种把机器描述当成用户发言的话。
现在正文用 `[图片{i}] {desc}`、引用用 `[引用的图片{i}] {desc}`，
一条消息里多张图时 `{i}` 展开成 ` 1` / ` 2`。**正文和引用分开**这一点尤其重要：
之前两处共用一套模板，模型分不清"哪张是他刚发的、哪张在他引用的那条里"，描述会串。

### 坑 38（★ 静默的惩罚比报错更伤用户）：整群熔断触发后是**彻底静默**，用户只会以为"bot 不理我了"

**症状**（用户原话）：「偶尔回复的延迟很高，需要单独@才会产生回复，不清楚是否是模型的延迟」。
**跟模型延迟无关。**

**根因**：`chatluna-followup` 的**整群熔断**（`groupMaxPerWindow` / `groupWindowSeconds`）
在窗口内接满 N 条后直接 `SKIPPED` —— 一个字都不发。生产实测：

```
01:52:17 [I] chatluna-followup 群 454444539 触发整群熔断（120s 内最多 3 条），跳过 2791932480
```

4 个人的测试群、120 秒最多接 3 条，用户聊到第 4 句就撞上了。**他没有任何办法知道原因。**

**正确做法**：加 `burstNotice` —— 熔断时发一句
「（我先安静一会儿 —— 这 60 秒里已经接了 2 次话，约 20 秒后恢复。急事直接 @ 我。）」，
**每个时间窗最多一次**。默认关（活跃大群里主动出声本身就是噪声），小群/测试群按群打开。

**顺带发现的结构问题**：`groupMaxPerWindow` / `groupWindowSeconds` 原本**只有全局档**，
于是 4 人的测试群和 30 人的真群被迫共用「120 秒 3 条」—— 小群太紧、真群不够紧。
现在这两个也能按群覆盖（`resolveProfile` 一并扩展）。

**★ 同日晚些时候：这一整段被推翻了，`burstNotice` 也删了。**
用户看完这份说明后直接问：「这个应该就是那个出站令牌规则了吧，但是我设想的仅仅是按照时间
添加令牌，其他的没有额外的限制，熔断机制还有必要吗？」+「不要发送固定语句『我先安静一会儿…
急事直接 @ 我』，除了命令产生的回复以及 ai 做出的回复，我不想要逻辑代码额外产生的回复，
宁愿不说话（因为人也可能断线，但是人不会说固定的话）」。

**他是对的，这里犯了两个错**：
1. **重复造闸**：`chatluna-guard` 早就有**真正的令牌桶**（`outboundBurst` / `outboundPerMinute`，
   按时间匀速补令牌，`before-send` 总闸），而 followup 的「熔断」是在它之上**又加了一道
   固定窗口计数**。两套口径、两处参数，算法还更差：固定窗口能跨边界连发 `2×limit` 条
   （t=119s 发 3 条、t=121s 又发 3 条），令牌桶不会。
2. **用固定语句填黑箱**：静默确实让用户困惑，但解法不该是让逻辑代码说人话 ——
   那正是他讨厌的东西。正确解法是**把闸本身修好**（让限流不再频繁触发、规则只有一条），
   而不是在触发时解释。

**最终形态**：followup 的整群参数与 `burstNotice` 全部删除，改成入站时问 guard
`qqbotGuard.bucket.peek(gid)`（**只看不扣**，扣令牌仍只在 `before-send` 一处），
桶空就安静跳过 —— 连模型调用都不发生。见 [docs/24 第 14 节](../24-指令页面化与图片库.md)。

### 坑 41（★ 只有"文字模式"才会撞上）：Markdown 里的 `<br>` 会被 `h.parse` + OneBot 编码器**连子节点一起丢掉**

**症状**：rig 47 用 `/page.text on` 把帮助页切成文字后，`/help` 只剩标题和一句话 ——
**别名表格整张消失**；`/help -all` 的类目表也只剩上半截，页脚第二三行没了。
出图路径完全正常，所以之前几十轮都没发现。

**根因**：出图时 md 交给 marked 渲染（`<br>` 正常变换行）；文字模式下
`page.output()` 把 md **原样 return**，而调用方返回的字符串最终走
`session.send(string)` → `h.parse`。`h.parse` 把 `<br>` 解析成一个**元素**，
OneBot 编码器不认识 `br`，丢弃它时**把它的子节点一起丢了** ——
而 h.parse 的容错解析恰好会把 `<br>` 之后的内容都收成它的子节点。

**正确做法**：`chatluna-page` 新增 `plainify()`，在**所有非出图路径**（文字模式、没服务、
渲染失败）把 md 压成纯文本：`<br>` → 真换行、`</div>` → 收尾换行、其余标签剥掉。
★ **但 `&lt;别名&gt;` 这类实体必须原样留着，不能反转义成 `<别名>`** —— 压完的文本还是要过
`h.parse`，真写成尖括号就又被当成标签吃掉了（这是同一个坑的第二层，第一版 `plainify`
顺手做了反转义，结果页脚「单条详情：/help 」后面的占位符还是没了）。
留在实体态，`h.parse` 会在文本节点里把它还原成 `<别名>` 显示出来。
判据写进 rig 47 的步骤 ③：`/help` 的文字里**必须**能看到 `/model` 那一行表格。

### 坑 53（★ 主动插话被挂上"引用 + @"）：出站整形不能靠"频道里最近一条消息"兜底

`chatluna-reply-style` 的引用/@ 目标解析顺序是：
`session.__rsTrigger`（入站时打的标记）→ **退到"这个频道最近一条入站消息"**。

主动插话的伪 session 是**凭空造出来的**（`bot.session(event)`），没有 `__rsTrigger`，
于是走了兜底：2026-10-03 17:09 那次插话被挂成

```
17:09:37 [I] replystyle 出站形态：引用 1951933551 + @ 3912578627（群 1040488785）
```

—— 引用了一条不相干的群消息，还 **@ 了一个根本没跟 bot 说话的群友**。
提示词里那句"不要 @ 任何人"就这么被自己的插件推翻了。

**修法**：`before-send` 里认伪身份 `session.userId === '__proactive_trigger__'` →
主动插话不加引用/@。

**教训**：凡是"找不到目标就退到最近一条"的兜底，在**主动发送**这条路上都会挑错人 ——
主动发送没有"触发消息"这个概念，兜底等于随机。

### 坑 58（★ 整条消息一个字都发不出去）：元素标记当成正文打出来，又被解析回元素

**现象**：`/mem`（`episode.preview`）在 1040488785 群里必失败：

```
19:18:11 [D] onebot [response] { status: 'failed', retcode: 1200, data: null,
             message: '下载文件失败: Bad Request', echo: 48 }
19:18:11 [W] session Error: Error with request send_group_msg, args: {...16 个元素, 10 张图...}
```

同一条命令在 454444539 群**正常**（126 字符 → `page` 渲染成图）。区别只有一个：那个群近况里没图片。

**根因**：`session.content` 是**元素标记**不是文字 —— 图片消息存进库的是

```
<img src="https://multimedia.nt.qq.com.cn/download?appid=1407&amp;fileid=…&amp;rkey=…" summary="" file="…" sub-type="0"/>
```

`renderLines()` 原样把它打进 `{episode()}`，而 `/mem` 又把这个字符串**返回给框架发送** ——
Koishi 对指令返回值会 `h.parse()`，于是：

1. `<img src="…">` 变回**真的图片元素**，NapCat 去下载那个**早就过期**的 rkey 链接 → `retcode 1200` → 整条失败；
2. `<at id="123"/>` 变回**真的 at 元素** —— 打一行调试信息顺手 @ 一下群友；
3. 模型那份提示词里也塞满带签名的长 URL（一张图几百字符），纯噪音。

实测往返语义（`.scratch/probe-escape.cjs`）：

```
escape : 玩法 &lt;img src="…"/&gt; 结束 &lt;at id="123"/&gt;
解析回 : 玩法 <img src="…"/> 结束 <at id="123"/>      ← 往返一致，用户看到的字符不变
不转义 : 元素类型 = text,img,text,at,text             ← 这就是事故现场
```

**修法（两层，缺一不可）**：

| 层 | 位置 | 做什么 |
|---|---|---|
| 渲染层 | `chatluna-episode` 的 `plainText()`；`chatluna-proactive` 的 `plainTextOf()` | 元素标记 → 可读文字：`<img>` 丢掉（条数已由 `［含 N 张图］` 标注）、`<at id="x">` → `@x`、其余标记丢掉；顺手把 `img/image/video/audio` 翻成 `[图片]/[视频]/[语音]` |
| 出口层 | `episode.preview` / `focus.status` 的 `return` | `h.escape()`：**用户原文和模型产出**（滚动总结、专注标题）里任何 `<…>` 都只当字面量 |

**为什么出口层不能省**：渲染层只清得掉"我们已知的元素标记"，而这两段里混着**群友手打的字**
（有人真的会发 `<3`）和**模型写的总结**。`h.escape` 是唯一能保证"原样送到群里"的关口，
且已实测与 `h.parse()` 往返一致。

**验证**：新增 [rig 56](../../koishi-app/tools/scenarios/56-episode-preview-markup.json) ——
先发两条纯图片消息（保证近况里真有图片标记），再敲 `/mem`，判据三条：
出站**没有 http 图片段** / 正文**保留** `［含 1 张图］` / 正文**没有** `<img` 与签名 URL。
修复前那条消息是 16 个元素 10 张图，修复后是 **1 个 text**。

**附带收获**：`chatluna-proactive` 的 `plainTextOf()` 兜底原本也是 `return session.content`，
于是**纯图片消息**在插话提示词里就是一行 `<img src="…rkey=…">`。
除了噪音，它还会让**话题黑名单误命中** —— 图片链接里凑巧含 `lpl`/`vct` 这种子串，bot 就以为群里在聊电竞而闭嘴。
现在兜底走 `stripMarkup()`，提示词里那行变成 `[图片]`。

**教训**：**"给人看/给模型看/给框架解析"是三种不同的字符串**。
凡是把"存下来的消息"再拼出去的地方，都要先问一句：**这个字符串等下会被谁解析？**
Koishi 对**指令返回值**默认按元素解析，这一条尤其容易忘。

### 坑 66（★ 同一个 http 服务，`get` 和 `file` 拿到的字节数不一样）：`ctx.http.get(..., {responseType:'arraybuffer'})` 返回 **0 字节**

第九轮写 `chatluna-persona` 时要在启动时把 bot 的 QQ 头像拉下来当"参考形象图"，写法是：

```js
const res = await ctx.http.get(url, { responseType: 'arraybuffer' })
const buf = Buffer.isBuffer(res?.data) ? res.data : Buffer.from(res?.data || [])
```

实测（koishi-test，rig 61）：`参考形象图下载失败（https://q1.qlogo.cn/...）：下到 0 字节` ——
`res.data` 既不是 Buffer 也不是能 `Buffer.from` 出内容的东西，转完就是空。

**同一个 URL、同一个进程**，换成 vision 插件一直在用的写法就成功了：

```js
const res = await ctx.http.file(url, { timeout })   // Koishi 的 http 服务专门为这个封的
const buf = Buffer.isBuffer(res.data) ? res.data : Buffer.from(res.data)
```

教训：**Koishi 的 `ctx.http` 不是裸 axios**，`file()` 才是"要字节"的正路
（它内部处理 responseType / mime 嗅探 / 重定向）。写自研插件要下载文件时，
先去已有插件里搜 `ctx.http.file` 抄一份，不要凭 axios 的经验写 `get`。
→ 修法见 `chatluna-persona/lib/index.js` 的 `fetchToCache()`：**先 `file()`，失败了再退回 `get()`**。

**同一处的第二层坑（上线时才发现）**：头像 URL 里的 QQ 号我是从 `ctx.bots` 里猜的
（"找平台是 onebot 的第一个 bot"）。启动 5 秒后去取时**真正的 OneBot bot 还没连上**，
`ctx.bots` 里是个占位 bot，`selfId` 是 `20001` —— 于是拉回来一张**别人的**头像当成了参考形象图
（日志：`参考形象图已更新：…avatar-20001.jpg`）。占位 bot 在，所以连"拿不到 selfId"的兜底都没触发。
→ 现在生产/测试配置里都**写死** `chatluna-persona.avatarSelfId: '2178517838'`。
凡是"启动早期从 `ctx.bots` 推断自己是谁"的写法都有这个坑，能写配置就别猜。

### 坑 75（★ 出整页图必踩）：puppeteer 22 里 `clip` 与 `fullPage` **互斥**

**症状**：网页预览的"整页模式"一调就抛

```
Error: 'clip' and 'fullPage' are mutually exclusive
```

**根因**：想同时要"整页"和"高度上限"，很自然会写成
`page.screenshot({ fullPage: true, clip: { x:0, y:0, width, height } })`。
但 puppeteer 22 明确禁止这两个参数共存（旧版本允许，所以网上抄来的写法会炸）。

**修法**：整页模式不要 `fullPage`，改成**自己量高度 + `clip` + `captureBeyondViewport`**：

```js
await page.screenshot({
  type: 'png',
  clip: { x: 0, y: 0, width, height: Math.min(scrollHeight, maxCaptureHeight) },
  captureBeyondViewport: true,
})
```

顺带就有了"整页高度上限"，不会出现一张几万像素高的图。

**★ 随之而来的第二个坑（判据写错，不是代码错）**：`scrollHeight` 对**百度首页**量出来**等于视口**
（它的整页布局是视口高、内容在内层容器里滚）。那时整页模式截出来和首屏一样高是**正确行为**。
第一版验收脚本拿百度当判据，于是把一个正确行为判成了失败 —— 换 `news.qq.com`（`scrollHeight` 1967px）才对。

### 坑 76：URL 的结尾不能按空白切 —— **中文标点必须当分隔符**

**症状**：群里发「看这个 https://a.com/x），挺好的」，预览必然失败，报"打不开这个网址"。

**根因**：抽链接用的 `/https?:\/\/[^\s]+/` 只把空白当分隔符，于是抽出来的是
`https://a.com/x），挺好的` —— `new URL()` 不会报错（中文会被百分号编码成路径），
于是真的去请求一个不存在的超长路径。

**修法**：正则里把中文标点也算作终止符：

```js
/https?:\/\/[^\s\u3000<>"'`，。；：！？、（）【】《》「」『』…·]+/gi
```

外加一次尾部清洗（`cleanUrlText`）兜住 ASCII 标点。
判据写成了单测：`.scratch/check-webpreview-guard.cjs` 的 D 组 5 条。

### 坑 23（★ 踩了两次）：子指令必须用**点号全名**注册，`ctx.command('a/b')` 出来的指令**用户根本敲不出来**

```js
ctx.command('scene/begin <title:string>')   // ✗ 子指令的 name 只有 'begin'
ctx.command('scene.begin <title:string>')   // ✓ 子指令的 name 是 'scene.begin'
```

原因在 `Commander` 的解析：`_resolve(key)`（`@koishijs/core` core:1432）把 `key` 按 `.` 切开后，
**每一段都拿"整名"去 `_commandList` 里查 `_aliases`**（core:1411 `get`）：

```js
_resolve(key, session) {
  const segments = Command.normalize(key).split('.')
  let i = 1, name = segments[0], command
  while ((command = this.get(name, session)) && i < segments.length) {
    name = command.name + '.' + segments[i++]
  }
  return { command, name }
}
```

点号注册的子指令 `name` 就是完整路径（core:1485-1491 `parent.name + seg`），所以 `get('scene.begin')` 命中；
斜杠写法只取最后一段（`name = 'begin'`），`get('scene.begin')` 永远是 `undefined`
→ 解析失败 → 不是指令 → 消息原样往下走。

**实测现象极具误导性**：`/scene.begin 猜数字 …` **完全没反应**（日志里连 `command scene` 都不打），
而同一次会话里 `/scene` 一切正常 —— 因为父指令的名字恰好就是 `scene`。
2026-09-29 这一轮把 `emotion/set`、`emotion/list`、`emotion/reset`、`vision/stat`、
`vision/forget`、`proactive/speak`、`scene/begin`、`scene/end` 全部改成点号全名，
并用 `tools/scenarios/24-commands.json` 把每条指令都敲了一遍（20/20 通过）。

> 注意这跟 `qqbot-auth` 提权表里的 `'父名>子名'` 写法**不冲突**：`resolveCmd` 会依次比
> `c.name === 子名`、`c.name === 父名 + '.' + 子名`、`_aliases`，两种风格都能命中。

### 坑 25（★ 自研插件必踩）：`ctx.model.extend` 忘了写 → `cannot resolve table`，而且**写入是静默失败的**

写 R15 时忘了注册表模型就直接 `ctx.database.get('qqbot_guard', {})`，运行期报
`cannot resolve table "qqbot_guard"`。**真正致命的是它的表现方式**：

- 读失败被 `reload()` 的 catch 吃掉了 → 只看到一串 `[W]`，功能看起来"在跑"
- **写失败被中间件的兜底 catch 吃掉** → 用户在群里发 `开口`，bot **什么都不回**，
  日志里只有一行 `屏蔽判定出错（放行）`；而如果写路径在指令里，用户会看到"操作成功"其实没生效

教训（已落进代码）：
1. `ctx.model.extend(表名, {...}, { primary: [...] })` 必须写在 `apply()` 里，别拖到用的时候才想起来
2. **每一条写库路径都要包一层 `tryWrite`**，失败了要**说出来**（`开关没改成：<原因>`），
   否则"以为已经闭嘴了，其实还在说"是最坏的结果
3. 读库失败的 `warn` 要做限流（每分钟最多一条），否则轮询会刷满屏

判据：日志里出现 `cannot resolve table` = 模型没注册，不是数据问题。

### 坑 27（★ 自研 chatluna 插件必踩）：从自研插件里 `require('koishi-plugin-chatluna/...')` 会解析到**另一份** chatluna

自研插件是用 **junction** 挂在 `<app>/node_modules/` 下的（`file:external/...`），
Node 默认按 **realpath** 解析，于是 `require('koishi-plugin-chatluna/lib/...')`
会顺着**真实源码路径**走回 `koishi-app/node_modules/`，而不是"当前正在跑的那个实例"的
`node_modules`。生产实例里两者恰好是同一份，所以**只有测试实例会炸**；
但一旦哪天跑第二个实例、或者 npm 提升方式变了，生产也会炸。

症状（rig 32b 实测，全是"看起来像模型没配好"的假象）：

```
[W] chatluna-long-memory The model bge-small-zh-v1.5 is not embeddings, return empty embeddings
[E] chatluna Error: Embedding dimension is 0, Try to change the embeddings model.
```

真因是 chatluna 内部那句 `model instanceof ChatLunaBaseEmbeddings` —— 两份 chatluna = 两个类 = `false`。

**正确写法**（见 `external/koishi-plugin-chatluna-local-embeddings/lib/index.js`）：

```js
const Module = require('node:module')
/** 从宿主应用根目录解析，保证拿到"正在运行的那一份" */
function appRequire(ctx, spec) {
  const req = Module.createRequire(path.join(ctx.baseDir, 'index.js'))
  return req(spec)
}
// 运行时类必须走它，而且要在 apply/ready 里现取现拼（不能写在模块顶层 class extends）
const { PlatformEmbeddingsClient } = appRequire(ctx, 'koishi-plugin-chatluna/llm-core/platform/client')
const { ChatLunaEmbeddings } = appRequire(ctx, 'koishi-plugin-chatluna/llm-core/platform/model')
const { ChatLunaPlugin } = appRequire(ctx, 'koishi-plugin-chatluna/services/chat')
```

例外：**只用来拼 Config schema 的那种**（`ChatLunaPlugin.Config`）可以照常顶层 `require`，
schema 是纯数据、不存在类 identity 问题，而且顶层 require 才能在模块加载期拿到。

顺带两个同源小坑：

- `BasePlatformClient` 上有个 **`get config()`**（返回 configPool 里那条平台配置），
  子类里 `this.config = ...` 会报
  `Cannot set property config of #<BasePlatformClient> which has only a getter` → 自己的字段要叫 `_config`。
- `super(ctx, plugin.platformConfigPool)` —— 传的是 `platformConfigPool`，不是 `configPool`。

### 坑 32（★ 通用陷阱：**装好了、日志干净、功能完全不工作**）：`session.argv` 在 `before-send` 里永远是空的

**症状**：在 `ctx.on('before-send', ...)` 里读 `session.argv?.command` 判断「这条消息是不是
指令产生的」，**一次都不会命中**，而且没有任何报错。

**根因**（`@satorijs/core/lib/index.cjs:739-742`）：出站编码器会 **new 一个 session**，
再把原 session 上**可枚举**的键逐个拷过去：

```js
for (const key in this.options.session || {}) {
  if (key === 'id' || key === 'event') continue
  this.session[key] = this.options.session[key]
}
```

而 `argv` 是 Koishi 用 `defineProperty` 挂上去的（`@koishijs/core:1285`）——**不可枚举**，
被这个循环漏掉。

**正确做法**：在 `command/execute`（指令真要执行的那一刻）打一个**普通赋值**的标记：

```js
ctx.before('command/execute', (argv) => {
  const s = argv?.session
  if (s && argv?.command) s.__pageCommand = argv.command
})
```

`chatluna-guard` 的 `__guardControl` 一直有效，正是因为它是一次普通赋值。

> ★ 提炼成通用规则：**任何「中间件里打标记、`before-send` 里读」的写法，
> 标记必须是普通赋值，不能用 `defineProperty`。**

**排查手法**：`before-send` 里加一行 debug 日志把识别到的指令名打出来 ——
打印 `(没有标记)` 就是命中本坑。见 [docs/24 第 8 节](../24-指令页面化与图片库.md)。

### 坑 35（★ 装新插件前必查）：同名指令的多个 action **按顺序取第一个非空返回**

**症状**：自己注册的 `help` 指令明明写了 action，`/help` 却还是框架那套输出。

**根因**：框架的 `@koishijs/plugin-help` 也注册 `ctx.command("help [command:string]")`
（`plugin-help/lib/index.js:129`，而且 `authority: 0`）。同名指令的多个 action 串在一条队列里，
**谁先返回非空谁生效**。

**正确做法**：`koishi.yml` 里摘掉 `help:3nsrbd`，并在插件启动时**自检这个指令名到底指向谁**：

```js
const c = cmdr.get('help')
if (c?.name !== 'help') logger.warn('`help` 解析到了 %s —— 多半是 @koishijs/plugin-help 没关掉', c.name)
```

★ 这条自检**必须走 `logger.info`，不能走 debug 门控的 `log()`**：
生产 `debug=false`，用 `log()` 的话「通过」永远不打印，于是「没打印」既可能是没通过、
也可能是没开 debug —— 自检就失去意义了。（第一版就是这么写的。）

### 坑 36（★ 和坑 32 同类，**最会浪费时间的一个**）：`ctx.before('message')` 注册的是 `before-message`，而 preend 中间件跑在 `attach` 之前

**症状**：新插件 `chatluna-reply-style`（出站加引用和 @）装好、启动日志正常、零报错，
但**一次都没生效** —— 每条出站都打印「出站无触发记录」，引用一个都没加上。

**根因是两条叠在一起，得分开看：**

**① Koishi 的中间件链不是在 `dispatch` 里跑的，而是在一个 `message` 监听器里。**
`@koishijs/core:679` —— `Processor` 构造时就 `ctx.on("message", this._handleMessage)`
（Processor 是随 app 一起建的，**注册得极早**），而 `_handleMessage` 的最后一步才是
`if (result) await session.send(result)`（core:839）。
所以插件里写普通的 `ctx.on('message', fn)`，fn 永远排在 Processor **后面** ——
等我们来打标记，回复早就发出去了。

**② `ctx.before(name, fn)` 根本不是"排在 name 前面"。**
`@koishijs/core:2399`：

```js
before(name, listener, append = false) {
  const seg = name.split('/')
  seg[seg.length - 1] = 'before-' + seg[seg.length - 1]   // ← 给事件名加前缀
  return this.on(seg.join('/'), listener, !append)
}
```

于是 `ctx.before('message', fn)` 注册的是 **`before-message`** —— 一个没人会 emit 的事件。
`ctx.before('command/execute')` / `ctx.before('attach')` 之所以能用，是因为框架真的会 emit
`command/execute` / `attach` 的 `before-` 版本（生命周期），**不是所有事件名都有这一层**。

**正确做法**：用 prepend 中间件，本项目里这条路已经验证过（`chatluna-guard` 闸门 1）：

```js
ctx.middleware((session, next) => {
  session.__myMark = { ... }   // 普通赋值 = 可枚举 = 出站时会被编码器拷过去
  return next()
}, true)                       // ← 第二个参数 true = unshift
```

**附带踩到的第三个坑**：prepend 中间件比 `ctx.before('attach')` 还早，而
`session.stripped.prefix` 是在 attach 里才写上去的（core:1275-1284）。
同在 `chatluna-help` 的未知指令兜底里，第一版直接读 `session.stripped.prefix` 来切前缀，
拿到的永远是 `null`，于是 token 是 `/ext`（带斜杠），正则 `^[a-z]...` 不匹配 ——
**一次都没兜底，日志里连一行都没有**。正解是自己按 `_resolvePrefixes()` 切：

```js
let content = String(session.stripped.content || '').trim()
for (const p of prefixList(session)) {
  if (content.startsWith(p)) { content = content.slice(p.length).trim(); hadPrefix = true; break }
}
```

★ 这一条和 **坑 32**（`session.argv` 在 `before-send` 里永远是空的）是同一类错误：
**代码本身没错，是"什么时候被调用"错了，于是静默失效**。
以后再遇到"装好了、日志干净、功能完全不工作"，先问一句：**我这个回调到底在什么时候被调用？**

### 坑 39（★ 做"指令别名层"的两条死路，都会静默失效）：要抽象指令名，只能用 `Command#alias()`

**背景**：用户要求「给当前的命令抽象一层……只显示别名（英文，一个单词），命令也是使用
斜杠加别名的方式调用」。直觉上有三种做法，**前两种都是坑**：

**死路 A：转发指令**（自己注册 `model`，action 里再 `session.execute('chatluna.use.model …')`）
参数和选项得自己抄一遍，抄漏了就**静默丢参数**；`argv.command` 指向假指令，
权限判定、`-h` 用法、`/help model` 的详情页全部错位。

**死路 B：改写内容**（prepend 中间件里把 `/model` 换成 `/chatluna.use.model`）
**群里直接失效**。`ctx.before('attach')` 是先从 content 上切前缀、再解析
（`@koishijs/core:1275-1289`），而 `inferCommand` 里有一句
`if (argv.root && stripped.prefix === null && isStrict) return`（core:1447），群聊恒为 strict。
**内容里没有前缀 = 这条消息根本没有指令可解析**，而且不报错。要把前缀拼回去就得自己
再实现一遍 `_resolvePrefixes`，纯属重复造轮子。

**正解：`cmd.alias('model')`**（core:963）。别名与主名挂在**同一条指令对象**上：
参数解析、选项、usage、i18n、authority 门槛全部自动继承，一行都不用抄。
rig 47 实测：`/model` 返回的正是 `chatluna.use.model` 自己的文案
「请指定目标模型，或使用 `-a` 恢复跟随默认模型。」，`/models` 正常列模型。

**附带的一个"为什么必须等 ready"**：`_registerAlias` 在名字**已被别的指令占用**时
**直接抛异常**（core:934-940 `duplicate command names`），而各插件的指令是在自己的 apply
里建的。只有 `ready` 之后 `_commandList` 才是完整的，这时判「这个别名有没有被占用」才有意义。
所以我们自己先 `cmdr.get(name)` 查一遍，被占用就 warn 跳过 —— 绝不让一条配错的别名
把整个插件带崩。

### 坑 42（★ 第一轮就带着、第三轮复核分页才发现）：`[arg:string]` 是**贪婪**的，第二个位置参数永远拿不到值

**症状**：`/help` 类目页的页脚一直写着「下一页：`/help chat 2`」，但真发 `/help chat 2`
得到的是「**找不到「chat 2」**」。同一条指令的单条详情、`/help 2` 都正常，
只有"目标 + 页码"这种两个位置参数的写法是坏的 —— 而且**不报错**，只是查不到。

**根因**：Koishi 把 `string` 这个类型域定义成**贪婪**的
（`@koishijs/core:1331-1333`，`ctx.domain("string", h.unescape, { greedy: true })`；
`text` / `rawtext` / `el` 同样贪婪）。解析位置参数时有一条：

```js
// core:385-388
if (content[0] !== "-" && this.ctx.$commander.resolveDomain(argDecl.type).greedy) {
  args.push(this.ctx.$commander.parseValue(Argv2.stringify(argv), "argument", argv, argDecl))
  break                                    // ← 把**剩下所有 token** 一次性塞给第一个参数
}
```

而 `Argv.stringify()` 是把剩余 token 全拼起来（`core:239-248`）。
所以 `help [target:string] [page:number]` 里：
`/help chat 2` → `target = "chat 2"`、`page = undefined` → 拿整串去查类目 → 查不到。

**正确做法**（两种，按需要选）：
1. **自己切**：声明照旧，在 action 里把结尾的数字切出来 —— 指令名/类目代号里不可能有空格：
   ```js
   const tail = /^(.+?)\s+(\d+)$/.exec(String(target ?? '').trim())
   if (tail) { target = tail[1].trim(); pageNo = Number(tail[2]) }
   ```
2. **别用贪婪类型**：把第一个参数换成自定义的非贪婪域，或者干脆只留一个位置参数、
   页码用选项传（`-p 2`）。

**怎么发现的**：第三轮把 `/help` 首页从"三级"改成"四级"时顺手复核了一遍每个页脚里写的
下一步命令到底能不能用 —— 凡是**页面上教用户敲的东西，都必须真的敲一遍**。
这类 bug 藏得深：页面看起来完全正确，错的只是它给出的那行提示。

### 坑 43（★ 只坑日志，但坑得很像 bug）：Koishi 的 logger 走 Node `util.format`，**不支持 `%.1f`**

```js
logger.info('出站排队：%s 等 %.1fs 再发', key, wait / 1000)
// 实测输出：[I] chatluna-guard 出站排队：454444539 等 %.1fs 再发 1.764
//                                              ^^^^^ 占位符原样打出来，参数被甩到行尾
```

`console.log` / `util.format` 只认 `%s %d %i %f %j %o %O %c %%`，**精度写法 `%.1f` 不在其中**
（那是 C 的 printf / Python 的 %）。它不会被当成占位符，于是既原样留在字符串里，
又把多出来的那个参数按"多余的参数"追加到末尾 —— 一行日志同时错两处。

**正确做法**：

```js
logger.info('出站排队：群 %s 等 %ss 再发', key, (wait / 1000).toFixed(1))
```

**怎么发现的**：rig 51 验"出站最小间隔"，日志里要读等待秒数，一眼看到 `%.1fs`。
排查方向一度跑偏到"是不是 logger 的参数顺序错了"—— 记住这条：**要精度就先自己 `toFixed`**。

### 坑 44（★ 静默给出错误数据）：`h.image(buffer)` 把 Buffer 放在 `attrs.src`，**不在 `attrs.file`**

想给"模型自己出图"记一行带体积的日志，写了 `el.attrs.file.length`，实测**永远是 0**：

```js
const el = await renderElement(kind, content)   // h.image(buf, 'image/png')
logger.info('... %d 字节 ...', el?.attrs?.file?.length ?? 0)   // → 永远是 0，而且不报错
```

`satori` 的元素里，图片源就是 `attrs.src`（可以是 URL，也可以是 Buffer）；
`file` 是 **OneBot 编码时**才出现的字段（`base64://` 那一份）。
`?.` 一路可选链下来得到 `undefined`，`?? 0` 把错误数据**包装成一个合理的数字**
—— 这种"不报错的空值"比抛异常难查得多。

**正确做法**：要字节数就在**渲染那一步**拿（`renderToBuffer` 直接返回 Buffer），
别去元素上反推：

```js
const buf = await renderToBuffer(kind, content)
const el = h.image(buf, 'image/png')
logger.info('render_image 被模型调用：%s / %d 字符 → %d 字节', kind, content.length, buf.length)
```

**怎么发现的**：rig 50 里模型真的调了工具、图也真的发出去了，但日志写着 `734 字符 → 0 字节`。
凡是"看着像 0 但又没报错"的地方，都要怀疑是不是取错了字段。

### 坑 45（★ 想改"发送时机"必须知道的事实）：cordis 的 `serial` 是**顺序 await**，不是并发

`@satorijs/core` 的 `MessageEncoder.send()` 用 `app.serial(session, 'before-send', ...)` 调所有出站监听器。
`serial` 到底怎么跑，决定了"能不能在这里排队"：

```js
// @cordisjs/core/lib/index.cjs
async serial(...args) {
  for await (const result of this.dispatch("serial", args)) {
    if (isBailed(result)) return result
  }
}
```

`for await` 逐个 await 每个返回值 → **监听器是一个接一个跑的**（不是 `Promise.all`），
而且返回值非空（`bail`）会**立刻中止**后面的监听器。

这条事实有两个方向的影响：

* **能做**：在 `before-send` 里 `await` 一个定时等待，就真的把这条消息的发送推后了；
  后面几个监听器（page 的出图、reply-style 的引用/@）也会一起等 —— 这正是"两条消息之间至少隔 N 秒"。
  （注意顺序：先注册的先跑，所以 guard 的等待发生在 page 渲染**之前**，总延迟是相加而不是重叠。）
* **不能忘**：一个监听器 await 很久，会把**同一条消息**后面的监听器全堵住；
  别在 before-send 里做慢查询或长网络请求。

**怎么确认的**：写最小间隔之前先把 `node_modules/@cordisjs/core` 里的 `serial/parallel/emit`
三个实现读了一遍（`parallel` 是 `await Promise.all`，`emit` 是同步派发不等结果）。
**别凭直觉猜事件语义** —— 猜错的表现是"插件装了但没效果"，本项目已经栽过两次（坑 39 的两条死路）。

### 坑 50（★ 会往仓库里丢垃圾文件）：位置参数要先滤掉 `--flag`

```
node .scratch/seed-episode.cjs seed onebot:channel:777000333 6 3 --near
```

脚本里 `args[3]` 被当成 db 路径 —— 于是 `--near` **成了数据库文件名**，
整批数据写进仓库根下一个叫 `--near` 的文件。而检查脚本还在看真正的 `test.db`，
表现是"**报了写入 6 条，表里一条没有**"。

**规矩**：`const args = argv.slice(1).filter(a => !a.startsWith('--'))`，
布尔开关一律 `argv.includes('--flag')`；写完顺手
`Get-ChildItem -Force | ? Name -like '--*'` 看一眼有没有多出文件。

### 坑 64（★ 别名"被自己撞了"）：Commander 会给 `a.b` 自动建出父指令 `a`

`scopeId` 改成 `affinity` 之后，别名表里那条 `{ alias: 'affinity', target: 'affinity.inspect' }`
启动即报：

```
[W] alias 别名不可用（名字已被占用或非法）：affinity（已被 affinity 占用）
```

被"自己"占了：`ctx.command('affinity.rank')` 这种带点全名会让 Commander
**逐段 resolve 并建出父指令 `affinity`**，于是 `affinity` 这个名字已经存在
（而那个父指令没有 action，`/affinity` 敲下去**毫无反应**）。
→ 别名换同义词 `favor`（`/favor` = 看好感度），`affinity.*` 留给原始指令名。
**自查方式**：rig 日志里那句「指令别名层已挂载：N 个别名可用；目标缺失 0，**名字冲突 0**，表内重复 0」——
三个 0 缺一个都说明表里有问题。

### 坑 74（★ 静默、只影响"长的那一半"，而且**"写在配置前面"根本不算数**）：`inject` 会推迟 `apply`，`before-send` 的先后只能靠 `prepend` 自己声明

做「出站文本替换层」（[docs/29](../29-出站文本替换层.md)）时，替换必须发生在
`chatluna-page` 把长回复转成图片**之前** —— 一旦先出了图，`session.elements`
里只剩一个 image 元素，文字改不动了。

**现象**：短回复替换正常、`[image]` 也照常出，**只有长回复里的 😏 留着**。
不报错、日志里看不出异常。

**第一反应（错的）**：把插件在 `koishi.yml` 里挪到 `chatluna-page` 前面。**没用。**
实测日志顺序仍然是 `page → replystyle → replacer`。`loader apply plugin` 明明是按
新顺序打印的（`replacer` 在 `page` 之前），但 `before-send` 里就是最后跑。

**根因**：`inject` 会**推迟 `apply`**。

- 本插件声明了 `inject = { required: ['database'] }` → `apply` 要等 database 就绪；
- `chatluna-render` / `chatluna-page` / `chatluna-reply-style` 没有这层等待，
  `apply` 立刻完成、`before-send` 监听器**先**注册；
- `app.serial` 是按**注册顺序**遍历的（`@cordisjs/core:523` `dispatch('serial')`
  + `:534` `hooks[prepend ? 'unshift' : 'push']`）。

于是"配置里排第 28、page 排第 31"完全不影响执行顺序 —— **配置顺序 ≠ 注册顺序 ≠ 执行顺序**。

**修法**：位置由插件自己声明。

```js
ctx.on('before-send', handler, true)   // 第三参 true → { prepend: true } → unshift()
```

`ctx.on(name, listener, options)` 里传布尔会被规范化成 `{ prepend: options }`
（`@cordisjs/core:545-548`），`register()` 走 `unshift`，插到队首，
**从此与插件加载顺序无关**。改完实测日志变成
`chatluna-replacer 出站替换… → page 长回复出图…`，顺序正确。

★ **怎么确认顺序真的对了（这条最容易自欺）**：不能只看"出图了没有"——
顺序反了**照样出图**，只是图里留着没换掉的字。要同时满足：

1. 有替换层的日志（`出站替换：3 处 / 2 条规则`）；
2. 同一条消息落成 `[image]`；
3. **最硬的一条**：看 `page 长回复出图：… （正文 N 字符）` 里的 **N**。
   原长 295、替换后 293（`😏😏→哈哈` 少 2 个码元）—— 日志报 **293**，
   就证明 page 拿到的是**替换后**的文本。

★ **顺带纠正一条容易写错的日志**：「N 处」在长正文里是**替换次数**，
不是"命中的规则条数"（😏 命中 2 次 + 😏😏 1 次 = 3 处，但只有 2 条规则）。
第一版把后者当"处"打，排查顺序问题时差点被自己这行日志带偏 —— 两个数都打出来。

**教训表**：

| 想知道 | 别用 | 用 |
|---|---|---|
| `before-send` 里谁先跑 | `koishi.yml` 里的先后（受 `inject` 推迟 `apply` 影响） | `ctx.on(事件, 回调, true)` 显式 `prepend` |
| 替换有没有发生在出图之前 | "出图了没有"（顺序反了也出图） | 替换日志 **+** `page 长回复出图` 的**字符数** |
| 出站消息的"处数" | 把它当成"命中规则条数" | 次数与规则数分开打 |

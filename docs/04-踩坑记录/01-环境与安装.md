# 踩坑记录 · 环境与安装

> 属于 [踩坑记录（重来一次会浪费几小时的东西）](../04-踩坑记录.md) 的一份。
> **按类型切分**（2026-10-07）：装 Koishi / NapCat、启动与端口、进程与日志、QQ 版本。坑号未变；本文件覆盖坑 1、2、3、4、5、6、7、8、9、26、72、78。

### 坑 1：官方 OneBot 适配器已废弃

`@koishijs/plugin-adapter-onebot@6.0.2`（2024-05）拖着 `@satorijs/satori@3.7.0` →
嵌套 `@satorijs/core@3.7.0`，与根 `4.6.0` 冲突 → **`Session2 is not a constructor`**。
安装时 npm 会警告 `official support for onebot has been dropped`。

**改用 `koishi-plugin-adapter-onebot@6.9.4`**（repo `koishijs/koishi-plugin-adapter-onebot`，
peer `koishi ^4.18.6`，依赖只有 `qface`，无 satori 链）。

### 坑 2：`@koishijs/cli` 不能用

它内嵌 **cordis 2.10.3**，而当前插件代用 **cordis 3.18.1** → 两份实例 →
`Cannot set property name of #<_MainScope>` / `this.ctx.debounce is not a function`。

**`koishi` 包自带 bin**（`node_modules/koishi/bin.js` → `lib/cli`），不要装 `@koishijs/cli`。

### 坑 3：配置字段是 `endpoint` 不是 `url`

写错会报 schemastery 校验错误。

### 坑 4（最坑）：`help` / `echo` 是独立插件

`@koishijs/plugin-commands` **不带** `help` 和 `echo`。少了它们，
发 `/help` 的现象是**彻底静默**——不回复、不报错、日志无痕，跟链路断了长得一模一样。
必须装 `@koishijs/plugin-help` 和 `@koishijs/plugin-echo`。

依据：[指令系统 | Koishi](https://koishi.chat/zh-CN/manual/usage/command.html)
「help 指令由 help 插件提供……echo 指令由 echo 插件提供」。

### 坑 5：debug 日志开不出来

- 环境变量是 **`KOISHI_LOG_LEVEL`**（不是 `LOG_LEVEL`），且**必须是数字**（3 = debug）
- **CLI 会把它清空**：`koishi/lib/cli/index.js` 里 `process.env.KOISHI_LOG_LEVEL = logLevel || ""`

**只能用命令行参数**：`node node_modules/koishi/bin.js start --log-level 3`

### 坑 6：重复启动实例 → 静默半死

新实例抢不到 5140 会报 `Error: No open ports available` + `server closing`，
**但适配器仍照常连 NapCat**。极易把"控制台起不来"误判成"机器人不工作"。
重启前先查：`Get-NetTCPConnection -State Listen -LocalPort 5140`

### 坑 7：`koishi.yml` 由 Koishi 自己重写

启动后它会：给插件名加实例 ID（`server:meey6h`）、**删掉所有注释**、规范化引号。
→ **手改配置前必须先停进程**，否则改动被覆盖。

### 坑 8：`PacketBackend` 报错是**有条件的**无害 —— 它一挂，戳一戳等功能直接失效

```
[error] [Core] [Packet] PacketBackend 不支持当前QQ版本架构：9.9.36-53644-x64
```

> ⚠️ **本条 2026-10-06 更正过。** 原来的结论是「报这个错功能也正常，不必降级」，
> 那是**错的** —— 当时只用 `get_login_info` 验证过，而它根本不走 PacketBackend。

**这个报错到底影响什么**

- `PacketBackend` 是 NapCat 自带的原生模块（`native\packet\MoeHoo.<platform>.node`），
  它把 QQ 内部**收发函数的地址**写死了 —— 地址随 QQ 构建号变化，所以 NapCat 里是一张
  **「构建号 → 地址」硬编码表**，只能一个版本一个版本地适配（不是 QQ 的 bug，也不是
  NapCat「修一下」就能覆盖所有版本）。
- 表里没有你这个构建号 → 模块不加载 → **一切走 PacketBackend 的能力全废**：
  戳一戳（`send_poke` / `group_poke` / `friend_poke`）、私聊文件直链
  （`get_private_file_url`）等。它们**不会报错给调用方**，只在 action 结果里回
  `{"status":"failed","retcode":1400,"message":"packetBackend发包能力不可用…"}`。
- 不依赖它的（收消息、发消息、`get_login_info`）照常工作 —— 所以"功能正常"的假象很容易成立。

**判据（30 秒分清）**：绕开 Koishi 直接打一次真实调用，看回包：

```powershell
node tools\napcat-probe.cjs call group_poke '{"group_id":454444539,"user_id":2791932480}'
```

`status: ok` = 通；`retcode 1400` = 这个 QQ 构建不在表内。

**怎么知道哪些构建号在表内**：别信文档。直接读本地 NapCat bundle 里那张表：

```powershell
# 表里所有 Windows 构建号（含 send/recv 地址），看最大到哪
Select-String -Path D:\deepseek\QQbot\NapCat.Shell\napcat.mjs -Pattern '"9\.9\.\d+-\d+-x64"' |
  ForEach-Object { $_.Line.Trim() }
```

2026-10-06 实测 NapCat **4.18.30** 的表里有 100 条 Windows 记录，最高到 `9.9.36-53489`。
官方文档写的「Windows 支持 28418-36580」**已经过期**，别拿它当依据。

**根治：把 QQ 换成表里有的构建号**（历史版本镜像：<https://rodert.github.io/qq-versions/>；
NapCat release 里给的 `dldir1.qq.com` 链接已 404）。本机 2026-10-06 换到
`9.9.33-52230` 之后 `group_poke` / `send_poke` 都返回 `status: ok`。

> 顺带一个坑：`chatluna-toolbox` 的 `poke_user` 工具**不看** action 的 `status`，
> NapCat 明明回了 1400，它还告诉模型「已在群 X 戳了一下 Y」。查问题时别拿工具的话当证据。

### 坑 9：反向 WS 到 8080 的 ECONNREFUSED 是无害的

NapCat 在往**旧的 NoneBot 项目**（`ws://localhost:8080`）重连，它没运行。
想消噪音：把那条 `websocketClients` 的 `enable` 改成 `false`。

### 坑 26（★ 最容易误判成"bot 坏了"）：QQ 客户端自己掉线，Koishi 侧一切正常

2026-09-29 深夜用户报"群里和私聊发消息都没反应，可能你屏蔽了"。实际排查结果：

| 观测 | 值 | 说明 |
| --- | --- | --- |
| Koishi 日志里的 `onebot [receive]` | **只有 heartbeat，一条 message 都没有** | 事件根本没到 Koishi |
| `get_login_info` | 正常返回 `大肥鱼` | 走本地缓存，不代表在线 |
| `get_group_list` | 正常返回 1 个群 | 走客户端本地库，**也不代表在线** |
| `send_private_msg` / `send_group_msg` | **`retcode:1200` → `result: 1006514, errMsg: "网络连接异常!"`** | ★ 决定性证据：腾讯侧会话断了 |
| 数据库最后活动 | `chatluna_conversation.updatedAt` = 15:57 | bot 最后一次真听见话是 7 小时前 |

**判据（30 秒分清是谁的问题）**：`tools/napcat-probe.cjs info` 能连上、`get_status` 报
`online:true, good:true`、但 `send_private_msg` 报 `网络连接异常!` → **QQ 客户端 IM 会话死了**，
只能重启 QQ（NapCat 是注入进 QQ.exe 的，所以必须用 `launcher-user.bat` 重启，重启后可能要扫码）。
跟 Koishi、跟权限分级、跟 R15 屏蔽开关**都无关** —— 别在后端瞎改。

诊断工具（本轮新写，绕过 Koishi 直连 OneBot WS，不影响 Koishi 收事件）：

```powershell
node tools\napcat-probe.cjs info                        # 账号状态 / 群列表 / 好友列表
node tools\napcat-probe.cjs watch --seconds 120         # 看事件流（心跳折叠；--verbose 全看）
node tools\napcat-probe.cjs send-group 454444539 "测试"  # 直发一条，看客户端到底能不能发
```

★ 别忘了 `--no-warnings`：Node 22 的 `[UNDICI-EHPA]` 警告会走 stderr，PowerShell 会把它当
`NativeCommandError` 报 exit 1（跟"命令失败"是两回事）。

### 坑 72（运维）：让 bot 活着的那个进程，不该是我的会话的后台任务

第九轮的实例是当**后台 job** 起的（项目一直这么干）。当天它被杀了两次：

| 时间 | 谁杀的 | 证据 |
|---|---|---|
| 15:24 | **另一个会话按命令行匹配收测试实例时误杀**（见坑 70 最后一条） | 坑 70 自己记着「停了 7 分钟（15:31:40 才被重新拉起）」 |
| 15:29 | 同类清理（我 15:26 刚起的那个又被带走） | 日志停在 15:29:13，无 `[E]`、无堆栈 |

**判据**：日志**戛然而止且没有错误**= 被外部杀，不是崩。所以"看日志找崩溃原因"这条思路在这里是死路。

**做法**：把生产**脱离当前会话的进程树**启动（WMI 起进程，父进程是 `WmiPrvSE.exe`）：

```powershell
$cmd = 'node.exe "D:\deepseek\QQbot\koishi-app\tools\run-prod.cjs" --log-level 3'
Invoke-CimMethod -ClassName Win32_Process -MethodName Create `
  -Arguments @{ CommandLine = $cmd; CurrentDirectory = 'D:\deepseek\QQbot\koishi-app' }
# 回执：ReturnValue=0 PID=<run-prod 的 pid>；父进程链应为 WmiPrvSE.exe → node.exe → node.exe → node.exe
```

日记照旧写 `tools/logs/prod-<UTC 日期>.log`，不受影响（run-prod 自己 tee 到文件，不依赖控制台）。

**代价（要记住）**：这样起的实例**没有窗口**，控制台里也看不到 —— 正是坑 70 里
「我没有自己启动 koishi」那种困惑的来源。所以：

| 想知道 | 敲什么 |
|---|---|
| 有没有实例在跑 / 有几个 | `node tools\run-prod.cjs --check`（看 5140 与"谁连着 NapCat"） |
| 停掉它 | 先 `Get-NetTCPConnection -LocalPort 5140 -State Listen` 拿 PID，再 `taskkill /PID <pid> /T /F`（**按 PID**，别按命令行 —— 坑 70） |
| 它今天说了什么 | `tools\logs\prod-<日期>.log` |

★ 另外：`IsHidden`/无窗口**不影响**新增的 `onebot-singleton-guard` —— 那道闸门在 Koishi 进程内部，
不管实例是从哪条命令、哪个终端、哪个会话起来的都会拦（这正是它存在的意义）。

### 坑 78（运维）：`run-prod.cjs --takeover` 单独用**根本不动手** —— 文档与代码不一致

**症状**：按 `docs/17` 和脚本自己的文件头写的"重启 = `node tools\run-prod.cjs --takeover`"，
跑出来却是：

```
✗ 已经有孤儿实例连着 NapCat（3001 端口）：PID
  端口没被占 **不等于** 没有实例在跑：……
```

而 PID 那一栏**是空的**（当时 `orphans` 为空、端口被健康实例占着）—— 报错信息与事实不符。

**根因**（`run-prod.cjs`）：`targets = takeover ? clients : orphans`，
但真正执行杀进程的分支条件写的是 `if (has('kill-orphans'))`。
`--takeover` 单独用时 `kill-orphans` 为假 → 掉进 `else` → 打印"孤儿"报错并 `exit 1`。
**只有 `--takeover --kill-orphans` 才真的动手**。

第二个半边：注释里说 `--takeover` 覆盖"端口被占、但占它的进程没连 NapCat"的情形，
可那时 `clients` 为空 → `targets` 为空 → 上面整段跳过 → 端口检查再报错退出，**也收不掉**。

**修法**（2026-10-06）：
1. 执行分支改成 `if (takeover || has('kill-orphans'))`（并区分打印"旧实例已清掉 / 孤儿已清掉"）；
2. 补一段：`takeover && 端口忙 && 占它的不是 NapCat 客户端` 时，**只在该进程是 `node.exe` 时**才
   `taskkill /T /F`，否则拒绝启动并让人自己确认。

**教训**：这条属于"文档写了、代码没做、报错还指向别处"的三重错位 ——
**改完启动器要在真实状态上跑一次 `--check` + 一次真重启**，别只读代码。

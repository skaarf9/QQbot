# 踩坑记录 · 插话与记忆

> 属于 [踩坑记录（重来一次会浪费几小时的东西）](../04-踩坑记录.md) 的一份。
> **按类型切分**（2026-10-07）：R9 主动插话（频率/池/黑名单）+ 短期情景记忆与长期记忆的落库。坑号未变；本文件覆盖坑 29、52、54、55、59、62、69、71。

### 坑 29（★ 进真群才暴露）：紧跟机制的窗口是**按人**开的，人一多就叠成刷屏

`chatluna-followup` 的 `maxConsecutive`（默认 20）是**每个人** 20 条。
测试群 4 个人时完全看不出来；拉进 30 人真群后，放行 2 分半就发了 **20 条**，
随后 `send_group_msg` 开始报 `retcode: 1200`（腾讯限流）。

```
00:44:50 [I] chatluna-followup 2969981414 跟进触发（第 2 条，还剩 576s 硬上限）
00:45:26 [I] chatluna-followup 3101329639 跟进触发（第 5 条，还剩 505s 硬上限）
```

**教训**：这类"每人 N 条"的上限，在群里必须再配一个**按群的总闸**——
本轮补了 `groupMaxPerWindow` / `groupWindowSeconds`（整群熔断）和 `groups`（按群覆盖参数）。
真群参数见[真群接入与限流事故](../16-真群接入与限流事故.md)。

**判性质的方法**（别一看 1200 就以为掉线）：`node --no-warnings tools\napcat-probe.cjs send-group <测试群> "自检"`
返回 `retcode: 0` ⇒ 出站是通的，1200 只是限流，**不用重启 QQ**。

### 坑 52（★ 主动插话的提示词被当成群友发言存进了短期记忆）

`chatluna-proactive` 是靠把一段提示词伪装成"某人的消息"塞进 `chatChain` 的：

```
【自动插话】群里的消息你一直在看着，现在轮到你说点什么了（不是有人叫你，是你自己想插一句）。
当前时间：… 群聊名称：… 你上次说话之后，群里又聊了这些：…
```

ChatLuna 会把这条**合成消息**也 emit 成 `chatluna/message-observed`
（payload 的 `userId` 就是伪身份 `__proactive_trigger__`）。`chatluna-episode` 照单全收 →
整段提示词落进 `chatluna_episode`，下一轮 `{episode()}` 又把它注回提示词。

实测：1040488785 的 39 条近况里有 2 条就是这两段提示词。
危害有二：白烧上下文；模型可能把它当成"群友 proactive 说了一段莫名其妙的话"。

**修法**：`chatluna/message-observed` 里按 `userId === '__proactive_trigger__'` 直接丢，
再按 `^【(自动插话|群聊冷场)】` 兜底一次；已污染的行用
[.scratch/clean-episode-proactive.cjs](../../.scratch/clean-episode-proactive.cjs) 删掉（76 → 74）。

**教训**：只要插件往会话管线里**合成**消息，就得同时问"我自己的其它插件会不会把它当真人消息收走"。

### 坑 54（★ 设计缺陷，不是 bug）：清历史池把"群聊热度"一起清了，于是最该插话时分数永远起不来

`chatluna-proactive` 的历史池语义是"**bot 上次说话之后**群里聊了什么"，
所以每轮正常回复后 `proactive-pool-reset` 会把它清空（这是对的，避免重复作答）。

但活跃度分数**也是拿这个池子算的** —— 于是：一群人在刷屏，中途有人 @ 了 bot 一句，
bot 正常回话 → 池子清零 → 热度归零 → **这一波最该插话的时刻，分数永远到不了阈值**。
实测频率：10-02 全天 28 次评估、10-03 白天 270 次评估，**只有 1 次越过 0.6 阈值**。

**修法**：把"热度"独立出来 —— `pool.heat`（只收非 direct 消息的时间戳，清池不影响，上限 240 条）
专供 `activityScore`；池子 `pool.msgs` 继续只服务提示词与条数兜底。
顺带把"决定插话"的那行日志改成**不看 debug 开关**的 INFO，并把
`活跃度 / 阈值 / 热度 N 条 / 待插话 M 条` 全打出来 —— 否则"到底判没判它插话"在日志里根本看不见。

**教训**：一个数组别背两种语义。**"给模型看的上下文"和"用来做决策的统计量"必须分开存。**

### 坑 55（★ 一次匹配毒化后面全部判断）：关键词黑名单必须限定"最近几条"，拒绝之后还要截池

第六轮续加的"话题黑名单"（群在聊电竞就**直接**不插话）。第一版拿**整个历史池**去匹配：

```js
const text = pool.msgs.filter(m => !m.direct).map(m => m.content).join('\n')   // ← 全池
```

rig 55 第一次跑就露馅 —— 6 次触发**全部**命中：

```
决定插话（活跃度触发）：… 热度 18 条，待插话 18 条
放弃插话：命中话题黑名单「比分」（10 秒内不再试）        ← 群里早就换话题了
```

成因：池子的语义是"**bot 上次说话之后**群里聊了什么"，而它**只在 bot 真开口之后才清空**。
"不插话"这条路上池子永远不清 → 十分钟前那句"看比分好像是2-0了"会**永久**把后面每一轮挡掉。

**两处修正**（缺一不可）：

| 修正 | 做法 | 语义 |
|---|---|---|
| 黑名单限定窗口 | 只看**最近 6 条**非 direct 消息 | "**现在**在聊这个话题"，不是"**聊过**这个话题" |
| 拒绝后截池 | 闸门拒绝 → `pool.msgs` 只留最后 3 条，`state.msgCount = 0` | 看过、判过、决定不说的材料留着只会继续毒化判断，还白花把关调用 |

**教训**：任何"按内容做判断"的门禁，都要先问一句 **"这段内容什么时候算过期？"** ——
池子/缓存/窗口这类"攒起来的东西"，攒的语义和判的语义往往不是一回事。

### 坑 59（★ 一条咽喉全程静默，日志里连一行都没有）：`session.uid` 是**两段**的，我按三段写

**现象**：短期情景记忆（`chatluna-episode`）号称"入站 + 出站双向落库"，入站那半一直好好的，
**出站那半一条都没记过** —— 而且不报错、不打日志、没有任何异常：

```
sqlite> select isBot, kind, count(*) from chatluna_episode group by isBot, kind;
isBot=0  kind=chat  n=417          ← 全是别人说的话
（isBot=1 一行都没有）
```

历次日志里的 `渲染 {episode()}：… 其中 bot 自己 N 条` 也**全是 0**（含专门验情景记忆的 rig 52）。
更糟的是：这条咽喉正是当初用户提的那个 bug 的解药 ——
「ai 和我说了晚安，我两小时后找它，它却不觉得我起太早」= **它连自己说过什么都不记得**。

**根因（两层，第二层是顺手挖出来的）**：

1. **`session.uid` 只有两段**。`@satorijs/core` 的 `src/session.ts:79`：

   ```ts
   get uid() { return `${this.platform}:${this.userId}` }   // onebot:2178517838
   ```

   而事件处理器里写的是 `/^(?<platform>[^:]+):(?<channel>[^:]+):(?<bot>[^:]+)$/` ——
   三段式，`exec()` 永远返回 `null`，于是**每一条出站消息都在第一行 `return`**。
   出站 session 上真实存在的是 `platform` / `channelId` / `selfId` 三个独立字段
   （`userId` 是**触发者**、`uid` 是 `platform:userId`，都认不出"这是 bot 自己发的"）。

2. **出站 session 的 `session.content` 不是"要发的文字"，是"同一段内容的标记串"**：

   ```ts
   get content() { return this.event.message?.elements?.join('') }
   ```

   实测它长这样（含 reply-style 刚加上的引用/@ 前缀）：

   ```
   content 字段="<quote id=\"100003\"/><at id=\"2791932480\"/>在。\n\n<p>你今天第几遍了啊…"
   ```

   照它入库 = 把 `<quote>`/`<at>` 标记写进情景库 —— 坑 58 的同类（`/mem` 打出来会被当元素解析、
   `<at>` 还会真的 @ 到人）。**只能从 `session.elements` 重建纯文本**（page / replyshaper /
   reply-style 读的也都是 elements）。

**修法**：出站咽喉改成从 `session.platform / channelId / selfId` 三个字段分别取值
（私聊频道号是 `private:<对方>`，`scopeKeyOf` 要用对方拼 scope），正文用递归的元素遍历重建：
`text` 取 `attrs.content`、`img` 计入张数、`at` → `@id`、`face` → `[表情]`、`quote` 丢掉、
`br` → 换行、其余容器**递归进 `children`**。

**为什么必须递归**：模型回复里写 `<p>…</p>` 时，编码器会把它解析成真的 `p` 元素 ——
文字在 `children` 里，不在 `attrs.content`。第一版只取后者，实测把
`在。\n\n<p>你今天第几遍了啊……有事直接说</p>` 记成了 `在。  [p]`（尾巴整段丢了）。

**刻意的例外**：带 `__guardIsCommand` 标记的**指令输出**（`/help`、`/mem`、`/guard.*` 的回执）
仍然不记。这既符合直觉（"bot 说过的话"指的是它自己聊的内容），也挡住一个真会咬人的反馈环：
`/mem` 打印的是记忆本身，把它再记回记忆里，下一轮就会读到上一轮的转储，越滚越大。

**验证**：[rig 57](../../koishi-app/tools/scenarios/57-episode-outbound.json)（`/guard.allow` →
@bot 闲聊一句 → @bot 让它调 `render_image` 发图 → `/mem`），判据 A–E 全过：

```
记录出站消息：onebot:channel:777000556 ｜元素 5 个（图 0）｜content 字段="<quote id=…/><at id=…/>在。…"
              ｜入库=@2791932480在。 你今天第几遍了啊……有事直接说，别老「在吗在吗」的。
记录出站消息：… ｜元素 4 个（图 1）｜入库=@2791932480喏，出站测试。
/mem：实取 6 条（…，其中 bot 自己 3 条）      ← 修复前恒为 0
```

**教训**：**"没报错"不等于"跑了"**。一条只在开头做形状判断就 `return` 的咽喉，
失败姿势是**完全静默**的 —— 所以落库类逻辑必须有一行"我记了什么"的日志（rig 57 的判据就是它），
而验收判据不能只看"条数对不对"，要专门看**分方向的分项计数**（`其中 bot 自己 N 条`）。
rig 52 当初放过了这个 bug，就是因为它的判据只数了窗口总条数。

**同族小坑（这一轮又踩了一次）**：剧本 JSON 里混进 ASCII 双引号（坑 56）→ 伪服务端启动即崩、
日志里一条群消息都没有，看着像"插件没生效"；另外**别用 PowerShell 的
`Get-Content -Raw` + `Set-Content` 去改 UTF-8 剧本** —— 会把中文整段变成乱码
（`_说明` 变 `_璇存槑`），JSON 还是"合法"的，只有内容没了。改剧本统一用编辑器/写文件工具。

**附带查清的一件事（"入库文本里能不能有 `<`"）**：rig 57 第三轮里模型把自己的 HTML 卡片尾巴
写进了正文（`喏，你要的卡片</caption>`），于是入库文本带了个**孤立闭合标签**。写判据时别一刀切
"不许有 `<`" —— 实测（`.scratch/probe-stray-html.cjs`）三种情况完全不同：

| 输入 | `h.parse` 结果 | 危险吗 |
|---|---|---|
| `喏</caption>`（孤立闭合标签） | `text("喏")` —— 标签**直接丢掉** | 不危险（不产生元素、不发请求） |
| `<caption>x</caption>`（孤立开标签） | `caption("")` —— **内容被吞掉** | 不下载，但会丢字（模型自己写坏的） |
| `<img src="…"/>` / `<at id="…"/>` | 真的 `img` / `at` 元素 | ★ 危险：下载过期 rkey → `retcode 1200`；真 @ 到人 |

所以出站入库文本的判据只该盯**会变元素的那几种标签**（`img/image/at/quote/face/button`），
其余 `<` 照原样留着才是忠实的记忆；真正的安全网是**出口的 `h.escape()`**
（`h.parse(h.escape(s)) === s`，三种情况都往返一致）。

### 坑 62（★ 出站 session 上 `userId` 恒为 `undefined`）：说话人只能从消息内容里认

**现象**：垫片挂上、记账代码跑到了，但一条都不记。加探针后一眼看穿：

```
【探针】before-send 进来了：guard=- user=undefined self=2178517838 elems=1
【探针】记账跳过：self-or-broadcast
```

**根因**：Satori 建出站 session 的方式（`@satorijs/core` index.cjs:733-742）：

```js
this.session = this.bot.session({ type: 'send', channel: {...}, guild: {...} })
for (const key in this.options.session) this.session[key] = this.options.session[key]
```

它只搬入站 session 的**自有可枚举属性**，而 `userId` / `selfId` / `channelId` 都是
**Session 原型上的 getter**（分别读 `event.user.id` / `event.self.id` / `event.channel.id`）。
新 session 的 event 是现造的、里面只有 channel 和 guild —— 所以搬过来的 session 上
`selfId` 有值、**`userId` 是空的**。
（坑 59 的注释里写着"出站 session 上 `userId` 是触发者"，那句是**错的**；
episode 之所以没受影响，是因为它压根不需要说话人。）

**修法**：按可靠性三级认人，全失败就**不记账**（宁可漏记，也不能把 A 说的话记到 B 头上）：

| 级别 | 依据 | 说明 |
|---|---|---|
| ① | `<quote id="…">` 元素的 id | 就是被回复的那条**入站消息 id**，查"入站 messageId → 说话人"索引，一一对应 |
| ② | `<at id="…">` 元素 | reply-style 的 `@ first` 会带上，排除 bot 自己 |
| ③ | 本频道最近一个说话的人 | 兜底，`fallbackSeconds`（默认 180s）窗口内；填 0 可关 |

**还有一步不能省**：affinity 读的是 `session.userId`，所以喂进去的不能是出站 session 本身，
而是一个 `Object.create(出站session)` 出来的**伪 session** —— 只覆盖 `userId`（+私聊标记），
`bot` / `guildId` / `platform` / `selfId` 沿原型链继承，这样它内部的
`fetchMember(session, userId)` 还能正常去 NapCat 查群名片建档。

### 坑 69（★ 上游"记忆总结"根本不认识 bot 的发言）：long-memory 把 ai 消息整条丢弃

第九轮要回答"记忆总结的模型知不知道哪句话是自己发的"，静态读完
`koishi-plugin-chatluna-long-memory@1.4.0`（npm 包，非自研）：

```js
// lib/index.mjs:166-168（唯一的历史格式化入口 selectChatHistory）
if (m.getType() === "system" || m.getType() === "tool" ||
    m.getType() === "function" || m.getType() === "ai") {
  return ""              // ← bot 说过的话在这里被丢掉
}
// :174  剩下的一律压成两个硬编码标签
return `${role}: ${content}`     // role 只有 "User" / "Assistant"
```

配套事实：
- `MessageRecord.name`（昵称）**全包没被使用**；
- 记忆条目 `EnhancedMemory`（lib/types.d.ts:16-23）只有 `content/type/importance/expirationDate/id/retrievalLayer`，
  **没有 userId、没有说话人字段**，本插件一张表都不建（走向量库 + `DataBaseDocstore`）；
- 唯一"不用 patch 就能改提示词"的口子是 `preset.config.longMemoryExtractPrompt`（`lib/index.mjs:180`），
  但它**未被 ChatLuna 核心定义**（全包 grep 零命中，UI 里配不到），且模板必须自带 `{user_input}` 占位符。

结论：**长期记忆这边不存在"认错说话人"，因为它压根收不到 bot 的发言**（这符合它的定位：记群友）。
要让它知道"哪句是 bot 说的"，只能 patch `lib/index.mjs:166-169` 或整段覆盖提示词 —— 本轮权衡后**没动**
（覆盖要抄 121 行英文提示词，维护成本大于收益）。真正有"你/我"歧义的是**短期情景总结**，
那条链在自研插件里，已改成第三人称「大肥鱼（机器人）」（见 docs/28 §2.4）。

### 坑 71（★ 单位混了一次，"只有一半功能生效"）：作息表的**进入语**从来没写进记忆

第九轮新增的 `chatluna-routine` 在 `stateAt()` 里把 `absStart` 算成 **epoch 分钟**
（`baseMin + w.start`），而 `tick()` 里却是 `(now - cur.absStart) / 60000` —— `now` 是**毫秒**。
两个单位一减，任何"**进入**某个时段"的转换都得到两千万分钟，直接命中 `tooLate`
（`catchUpMinutes` 默认 20）那一条，于是 `enterText` **一次都没写过**。

**它的伪装性极强**：只有"进入时段"这一侧错，"离开时段 → 醒着"那一侧是对的
（醒着状态的 `absStart` 是 `null`，`lateMin` 走 0 分支）。所以上线当天生产里看到的是：

```
2026-10-04 07:48:24 作息切换：sleep → 醒着（写入记忆）      → 我睡醒了。        ✅
2026-10-04 11:46:25 作息切换：awake → 午饭，已开始 29850929 分钟（★ 错过太久，只更新状态、不写记忆）
2026-10-04 12:26:25 作息切换：lunch → 醒着（写入记忆）      → 吃完了，回来啦。   ✅
```

**"我睡醒了""我吃完了"都正常，"我先去吃饭啦"永远不出现** —— 如果只看"有没有生活事件进记忆"，
这条链是"好的"；只有把三句话对着作息表逐条数，才看得出少了一句。
（29850929 分钟 ≈ 56 年，就是这个 bug 的指纹：`(ms - min) / 60000`。）

**修法**：`stateAt` 里的 `absStart/absEnd` 一律改成**毫秒**（`absStart * 60000`），
`startedAt/endsAt` 由它派生；并把这条算式写成注释钉在代码里。

**验证方式**（不等真实时间点）：把测试实例的午饭时段临时改成"两分钟后开始"、`jitterMinutes: 0`，
起实例跑一轮，看日志与库：

```
修复前：[I] 作息切换：awake → 午饭，已开始 29850929 分钟（★ 错过太久，只更新状态、不写记忆）
修复后：[I] 作息切换：awake → 午饭，已开始 0 分钟（写入记忆）
        [I] chatluna-episode 作息事件写进 8/8 个群会话：我先去吃饭啦！这个你测一下~
```

★ 这类"时间/单位"改动的测试**必须用"把时间点挪到眼前"的办法**，不要等真实作息 ——
否则一轮验证要花半天，而且会让人误以为"没触发就是没到点"。

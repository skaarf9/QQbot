### 坑 12：PowerShell 里读 UTF-8 文件会显示乱码

PowerShell **5.1** 的 `Get-Content` 默认按 ANSI 解码，读 UTF-8 文件时中文变乱码
（如 `鑷缓`）。**文件本身没问题**，别被吓到、别去"修"它。
要看内容请用 read 工具，或 `[System.IO.File]::ReadAllText($p,[Text.Encoding]::UTF8)`。

### 坑 40（★ 我自己制造的事故，**静默写坏文件**）：PowerShell 5.1 的 `Get-Content -Raw` 默认按 GBK 解码，改一行 UTF-8 文件 = 双重编码

**症状**：往 `package.json` 里插一行依赖，用的是最常见的写法：

```powershell
$t = Get-Content $p -Raw            # ← 这里就已经坏了
$t = $t.Insert($idx, $line)
Set-Content -Path $p -Value $t -NoNewline -Encoding utf8
```

结果 Koishi 启动时报：

```
[W] app failed to migrate manifest  SyntaxError: Unexpected token '﻿'
[E] app Error: Invalid package config \\?\D:\deepseek\QQbot\koishi-test\package.json.
```

**根因**：PowerShell **5.1**（不是 pwsh 7）的 `Get-Content -Raw` 不指定 `-Encoding` 时
按**系统 ANSI（这台机器是 GBK/936）**解码，而文件是 UTF-8。于是中文被"UTF-8 字节当成 GBK
读出来"变成乱码字符串，再以 UTF-8 写回 —— 双重编码：

```
自建 → 鑷缓      测试实例 → 娴嬭瘯瀹炰緥      跳过 → 璺宠繃
```

更糟的是 `）`（U+FF09）这类字符在 GBK 里落到未映射区，来回一趟**丢掉一个字节**，
直接写出一个非法 JSON（`Bad control character in string literal`）。
另外 `-Encoding utf8` 在 5.1 里**会写 BOM**（`EF BB BF`），Node 读 `package.json` 时是 BOM 开头。

**正确做法**：改文本文件一律用 `edit` / `write` 工具（它们按 UTF-8 处理，不碰其它字节）。
实在要在 PowerShell 里做，用 .NET 显式指定编码：

```powershell
$enc = New-Object System.Text.UTF8Encoding($false)   # false = 不写 BOM
$t = [System.IO.File]::ReadAllText($p, $enc)          # 会正确识别并吃掉 BOM
[System.IO.File]::WriteAllText($p, $t, $enc)
```

**怎么发现和修的**：`.scratch/fix-pkg-json.cjs`（按行替换回原文，不做有损的编码反转）
+ `.scratch/check-pkg-encoding.cjs`（扫全文件非 ASCII 行，标出乱码特征字）。
**教训**：这类事故**不报错也能跑很久** —— package.json 里只有 description 和一句
`postinstall` 提示受影响，功能完全正常，只有 Koishi 自己解析 manifest 时才会炸。

> **★ 2026-10-06 复发记录（明知故犯，代价最大的一次）**：为了把 `run-prod.cjs` 里两处
> "坑 74" 改成 "坑 78"，又顺手用了 PowerShell 往返：
>
> ```powershell
> (Get-Content tools\run-prod.cjs -Raw) -replace '坑 74','坑 78' | Set-Content -NoNewline tools\run-prod.cjs -Encoding UTF8
> ```
>
> 结果与坑 40 一模一样：中文全变 `绔彛` 那种双重编码、`Set-Content` 还加了 BOM，
> 文件当场**语法都过不了**（`SyntaxError: Invalid or unexpected token`）。
> **这次比上一次更严重的地方**：`run-prod.cjs` 是**未被 git 跟踪**的新文件（`git status` 显示 `??`），
> `git checkout` 救不回来；而且它的注释是全中文的，重写成本很高。
>
> 三条新知识，写下来免得再有第三次：
>
> 1. **这种损坏是"字节级丢信息"的，不能指望机械反转**。
>    还原公式是「当前字符串按 GBK 取回字节 → 按 UTF-8 解码」（.NET：`GetEncoding(936).GetBytes` 再 `UTF8.GetString`），
>    能把 95% 的中文救回来，但 `。）（）》` 这类全角标点的**第三个字节落在 GBK 未映射区时会被补成 `?`**，
>    更坑的是：GBK 解码器会把「前一个字节 + 紧跟其后的那个字节」**一起**当成一个非法双字节序列替换掉 ——
>    于是**换行符也被吃掉**（295 行的文件还原出来只剩 278 行）。
>    所以还原是**有损**的：代码里 `${busy` 会变成 `?{busy`（`$` 被吃掉），必须逐处人工确认。
> 2. **未跟踪的新文件没有后悔药**：这个仓库里 `koishi-app/tools/run-prod.cjs`、
>    `koishi-app/external/` 下的自写插件等，很多是 `??`（没提交）。改它们之前先 `git add`（等于建立还原点），
>    或者别用会重写整文件的工具。
> 3. **恢复手段（最后一条路）**：`.scratch/recover-run-prod.cjs` + `.scratch/fix-mojibake.ps1`
>    （GBK→UTF-8 反变换脚本）**留着**，万一下次再犯能省半小时。
>    本次最终是**用 `write` 工具整文件重写**（原内容在会话上下文里有），再用 `node --check`
>    + `node tools\run-prod.cjs --check` 双向确认行为一致。
>
> **一句话**：这个仓库里，除了 `edit` / `write` 工具，**不要用任何别的东西改带中文的文本文件**。

### 坑 49（★ 看起来像插件 bug，其实是脚本）：短命脚本写 sqlite **必须 `db.close()`**

用 `node:sqlite` 的 `DatabaseSync` 写测试库，写完不关也能正常退出，但**退出前一直握着文件锁**。
那几秒里 Koishi 侧的写全部失败，群里表现是**这一轮完全不回话**，
而日志里连一条 ChatLuna 的查询都没有 —— 非常像"闸门把消息吃了"。

**规矩**：脚本里一律包一层 `try { … } finally { db.close() }`（`.scratch/seed-episode.cjs`
里的 `withDb()` 就是干这个的），并且**写完立刻自检**：同一连接数一遍、关闭后再开新连接数一遍，
两次不一致就当场报警。

### 坑 68（★ 一个"看起来还能用"的生成脚本会把手工配置删掉）：`tools/gen-test-config.cjs`

`tools/gen-test-config.cjs` 是用模板**整体重写** `koishi-test/koishi.yml` 的。它的模板停留在
几轮之前，而这几轮里测试配置是**手工加块**的（episode / toolbox / page / alias / watchdog /
variable-extension / multi-adapter…）。第九轮为了加 persona/routine 两个块跑了一次：

```
before lines 485  →  after lines 243
只在旧文件里（被删掉的）：chatluna-episode:aa0032 / chatluna-toolbox / chatluna-variable-extension /
                        chatluna-page:pg0001（含 keepTextCommands！）/ chatluna-help / chatluna-think /
                        chatluna-reply-style / chatluna-alias / onebot-watchdog / chatluna-multi-adapter …
```

**已从备份还原**，并给脚本加了 `--force` 闸门（不加就直接拒绝执行并打印原因），
同时在文件头写明"测试配置现在是手工维护的"。

教训：**凡"生成式"脚本，模板和产物同时存在时，产物一定是被手工改过的那个**。
跑之前先 `Copy-Item` 备份、跑完 diff（这次就是靠 `.scratch/koishi-test.before.yml` 救回来的）。
更好的做法是让脚本只**合并**它负责的那几个块，而不是整体重写。

### 坑 81（跑台）：`node … | Select-Object -First N` 会**掐掉上游进程**；
### 还有一条：想验"失败三次"必须先把冷却基数压小

**症状 A**：想少看点火柴盒似的输出，写了
`node tools\run-rig.cjs … | Select-Object -First 60` —— 结果整场跑台**第 1 步就被掐死**，
日志停在 24 秒，而作业却报 exit 0（看着像"跑完了"）。

**根因**：`Select-Object -First N` 取够 N 条就**结束管道**，上游的原生进程会被一起终止。
长跑命令的"看输出"不能用它，要用**重定向到文件**（`*> file`）之后再按需 `grep`。

**症状 B**：用伪上游（`fake-broken` 恒 403）验"同一模型失败 3 次就本次登录不再试"，
三句话打完却只攒到 **2 次**失败。

**根因**：上游的冷却梯度是 `基数 × [1,2,10,30,60]`，**默认基数 30 秒** ——
第一次失败后那个首选要 **30 秒**后才被再试；三句话间隔 12 秒，
中间那次它还在冷却里，**根本没被请求**（这恰恰说明冷却是对的）。
按 30/60 秒 spacing 跑，光攒三次就要 100 秒以上。

**修法**：**只把测试实例**（`chatluna-multi-adapter:aa0030`）的 `endpointFailureCooldown`
压到 **3000**（梯度 3s/6s/30s），生产那份保持 30000。

**教训**：**"验不到"要区分是"功能没做"还是"测试设计没给它机会"**。
冷却/退避/熔断这类**带时间常数**的机制，验证前先算一遍"要多久才会触发"，
把常数调成测试想要的量级，而不是把等待时间拉长。

# R6/R7/R8 图片策略

> 属于 [QQ 机器人项目 —— 进度与交接](../进度与交接.md) 的分册。
> 旧编号（如「第八·十三节」）的去向见索引页的章节对照表。

自写 `chatluna-vision`：私聊解析、群聊引用图解析、解析缓存。表情包（R5/R7）见本文件第二部分。

### 需求原文（用户说法）

> 私聊时需要每个图片都解析成模型能看懂的文字,所以回复应该等待图片解析,而在群聊中,由于大伙会非常频繁的发图,
> 则忽略图片的解析,默认不解析图片,ai也不对图片进行回复(什么ai不知道用户发了图片(如果用户只发图的情况)),
> 除非这张图是解析过的,记录在数据库里面的则提前将其替换成能理解的文字,这样不会消耗token,也增加bot理解
>
> 当用户@了bot并附带了图片(附带的图片可以在用户的信息中,也可以在用户引用的信息中),
> 这时候如果图片没有被解析过则需要等待解析完成然后回复

### 产物

`D:\deepseek\QQbot\koishi-app\external\koishi-plugin-chatluna-vision\`
（`package.json` + `lib/index.js`，约 330 行）
已通过 `New-Item -ItemType Junction` 链到 `node_modules/`，并写进 `package.json` 的 `dependencies`
（`"koishi-plugin-chatluna-vision": "file:external/koishi-plugin-chatluna-vision"`）。

### 它解决的是什么问题

ChatLuna 默认把图片变成提示词里的 **`[image:http://127.0.0.1:5140/...]`**——
一个模型**根本打不开的本地 URL**，所以老版本模型只会说"图挂了,我看不见"。

### 机制（★ 三条都是从 chatluna 1.4.0 源码实证的，别凭印象改）

源码文件：`node_modules/koishi-plugin-chatluna/lib/services/chat.cjs`

1. **挂钩点**：`ctx.chatluna.messageTransformer.before(fn, priority)`（第 1174 行）
   - 回调签名 `(session, elements, message, model, options)`（第 1304 行 `_runBeforeTransform`）
   - `elements` **就是待处理数组本身，可以原地 splice / 替换元素**
   - `priority` **小的先跑**（插入时按 `item.priority > priority` 找位置）→ 我们传 `-100` 抢在最前
2. **引用消息会自动递归再跑一遍**（第 1107-1122 行）
   - `session.quote.elements` 会被当作新的一轮 `transform()` 调用，带 `options.quote = true`
   - 所以"引用里的图"**不需要特判**，同一个回调会被再调一次
3. **`_processElement` 在 `_runBeforeTransform` 之后才跑**（第 1096-1106 行）
   - 所以我们在 `before` 里把 `<img>` 换成 `<text>` 或删掉，ChatLuna 默认的图片处理**根本不会看到它**

### 策略表（当前默认配置）

| 场景 | 行为 |
|---|---|
| 私聊 · 有图 | 下载 → 算 sha256 → 查库 → 命中则直接换文字（零 API）；未命中则**阻塞解析**后换文字 |
| 群里 · @了 bot（或叫了昵称） | 同上（含**引用消息里的图**） |
| 群里 · 没叫 bot | 未解析的图**整段删掉**，模型完全不知道有图；已解析过的换成文字（白嫖） |
| 同一张图重复出现 | sha256 命中 `chatluna_image_cache`，**不再调用视觉模型** |
| 一轮里出现多张图 | **并行解析**（`Promise.all`），同一张图并发请求会被 `inflight` 表合并成一次 |

### 几个关键实现细节（踩过的）

- **必须当场下载**：图片 URL 带 rkey 有 TTL（见[硬约束](05-硬约束.md)第 1 条）。插件在事件到达的同一轮里就
  `ctx.http.file(url)` 把字节抓下来，**不入队**。
- `ctx.http.file(url, { timeout })` 的签名来自 `@cordisjs/plugin-http`：
  `file(url, options: FileOptions = {})`，`FileOptions = { timeout?: number | string }`，
  返回 `{ type, mime, filename, data: ArrayBuffer }`。**`type` 可能带 `;charset=...`**，要切掉再拼 data URL。
- 调模型：`const ref = await ctx.chatluna.createChatModel('deepseek/deepseek/<模型>')` → `ref.value`。
  **`createChatModel` 是两参函数** `(platformName, model)`，只传一个参数时它内部会
  `parseRawModelName()` 按**第一个 `/`** 切开：`deepseek/deepseek/deepseek-v4-flash-vision-exp`
  → platform `deepseek` + model `deepseek/deepseek-v4-flash-vision-exp`。
- 消息体：`new HumanMessage({ content: [{ type:'text', text: 提示词 }, { type:'image_url', image_url:{ url: 'data:image/jpeg;base64,...' } }] })`
  —— 这个结构和 chatluna 自己构造图片时完全一致（`lib/index.cjs:3777`）。
- `HumanMessage` 从 `@langchain/core/messages` 拿，走 `@langchain/core` 0.3.80（全树只有一份，别装第二份）。
- **@bot 的判定**要看**整条消息**，不能只看当前这一段（引用那一段自己可能没有 at）。
  实现里同时看四处：`session.stripped.appel/atSelf`、`session.elements`、当前 elements、`session.quote.elements`。
  （`stripped` 的语义见 `@koishijs/core` 的 `get stripped()`：`appel` = 开头 @ 了自己**或**以 `nickname` 开头）
- **压实数组要原地改**：并行处理时先把要丢的位置置 `null`，最后
  `elements.length = 0; elements.push(...kept)` —— **不能**换成新数组，ChatLuna 持有原引用。

## 一、R5/R7 表情包：已实现并端到端验收（现成插件）

### 需求原文

> R5「主动发表情包」；R7「表情包库 + 建立索引去重，避免重复识别同一张图」

### 产物：`koishi-plugin-chatluna-sticker@1.1.13`（**不是自写**）

```
koishi-app/node_modules/koishi-plugin-chatluna-sticker/
koishi-app/data/sticker-library/<pHash 前两位>/<pHash>.png   ← 图片本体（按哈希分桶）
koishi-app/data/koishi.db → sticker_occurrence / sticker_meta ← 索引与元数据
```

配置（生产 `koishi.yml` 的 `chatluna-sticker:stk001`）：

```yaml
storageDir: data/sticker-library
judgeThreshold: 3                     # 出现 3 次才交模型判断是否收藏（测试台用 1，跑得快）
judgeModel: deepseek/deepseek/deepseek-v4-flash-vision-exp   # ★ 必须显式配，见下
phashThreshold: 5                     # 汉明距离 ≤5 视为同一张图
maxSendableImages: 2000
occurrenceTtlDays: 10
judgeTimeoutMinutes: 10
```

### 机制（读源码得到的准确链路）

```
① 收集：群聊里**任何**图片都会进 `ctx.middleware`（不需要 @bot、不需要斜杠）
        → 下载 → pHash（imghash，64 bit）→ 记 count
② 去重：pHash 精确匹配不到时，全表比汉明距离，≤ phashThreshold 就归到已有那条
        → 「同一张图」只会有一条记录，count 递增（这就是 R7 的索引去重）
③ 判断：count 达到 judgeThreshold 且状态还是 new → 转 pending_review
        → 调 judgeModel（**必须是多模态模型**）问「这图值不值得收藏」
        → 值得就写 sticker_meta（tags / description / usageHint），状态转 collected
④ 发送：注册 ChatLuna 工具 `sticker_send`，参数只有 intent（「嘲讽」「无语」…）
        → 按 intent 关键词给 tags/description/usageHint 打分 → 取最高分那张
        → `session.send(h.image(...))` **真的把图发出去**，并记 useCount
⑤ 清理：未收藏且超过 occurrenceTtlDays 未再出现 → 删；收藏数超过 maxSendableImages
        → 按「最久未使用」淘汰
```

### ★ 三个必须知道的坑

1. **`judgeModel` 的默认值在本项目里是坏的**：默认 `deepseek/deepseek-v4-flash`
   少了平台前缀。ChatLuna 的模型全名是三段（`平台/厂商/模型`）——
   本项目中转的模型 id 自带斜杠，所以正确写法是
   `deepseek/deepseek/deepseek-v4-flash-vision-exp`。
   写成默认值 → 判断永远失败（日志 `模型 … 不可用，跳过判断`）。
2. **启动瞬间有一行吓人的 warn**：`[W] auto-sticker 未能获取 Chatluna 模型列表，
   judgeModel 回退为 deepseek/deepseek-v4-flash`。这是首次 `ready` 的竞态，
   几秒后会自己再打一行 `[I] auto-sticker 判断模型已就绪: <你配的模型>` —— **不用管**。
3. **包的 `name` 和包名不一致**：`koishi-plugin-chatluna-sticker` 导出的
   `module.exports.name` 是 **`auto-sticker`**（日志前缀、控制台卡片名都是它），
   但 yml 里的 key 仍然要写 **`chatluna-sticker`**（loader 按 `koishi-plugin-<key>` 解析），
   实测 `chatluna-sticker:stk001` 能正常加载。

### 为什么没启用 `emojiluna`（装了但没进 `koishi.yml`）

`koishi-plugin-emojiluna@1.3.3` 已装（124 个包，jimp/vue/console 前端一整套）。它的定位是
**表情包管理 + AI 打标 + WebUI + HTTP 接口**，和 `chatluna-sticker` 高度重叠：

| | `chatluna-sticker` | `emojiluna` |
|---|---|---|
| 自动收集 | ✅ 群聊图片 → pHash | ✅ 也可（`autoCollect`） |
| 去重 | ✅ pHash 汉明距离 | ✅ `similarityThreshold` |
| **AI 判断/打标** | ✅ 多模态模型判断「值不值得收藏」+ tags/description | ✅ 分类+标签（另一套视觉调用） |
| **主动发送** | ✅ **`sticker_send` 工具真的把图发出去** | ❌ 只把图片 URL 清单塞进提示词变量 `{emojis}`，**没有发送侧转换**（源码里没有 messageTransformer） |
| 管理 UI | ❌ 只有 `/sticker.*` 指令 | ✅ 控制台 WebUI |

**决定性理由**：R5 要的是「bot 真的发出表情包」，只有 `chatluna-sticker` 有发送能力；
`emojiluna` 的模型输出是 markdown 图片链接，在 QQ 上不会变成图。
两个都开还会让每张群图被两套收集器各下载一次、各烧一次视觉调用。
→ **先只用 `chatluna-sticker`**。哪天想要 WebUI 管理/标签检索，可以再开 `emojiluna`
并把它的 `autoCollect` 关掉（只当管理后台）。

### 其它

- 预设 `default-persona.yml` 里加了【表情包】段，明确告诉模型「想发就调 `sticker_send`，
  别再文字描述这张图，也别每次都说『给你个表情』」——不加这段工具很少被想起来。
- 图片本体是 `base64://` 走 OneBot 发出去的（实测 155 KB 的 base64），QQ 能正常收。

## 二、2026-10-02 表情包机制升级（预筛 / CRUD / 修正 / MIME）

> 背景：用户提出「AI 应能管理自己的表情包库（CRUD）」「判断是不是表情包应该有逻辑闸（压缩率等）」「库要有上限与淘汰」「认错图要能自己改描述」。全部落地。

### 2.0 先回答「判断是谁做的」

**两层判定，各司其职：**

| 层 | 判定者 | 依据 | 成本 |
|---|---|---|---|
| ① **逻辑预筛**（新） | 纯代码（sharp 读元数据） | 面积 / 体积 / **压缩率** / 长宽比 | **零 API**，毫秒级 |
| ② 内容判断（原有） | 视觉模型（judgeModel） | 「有趣/有梗/可复用吗」 | 一次视觉调用 |

「压缩率」的定义：`文件字节 ÷ (宽 × 高 × 通道数)`。表情包在群里反复流转、
被压过很多次，这个值通常 0.05~0.4；截图/原图/无损图接近 1。
实测抽样：库里 40 张追踪图被拦下 26 张（全是 1920×1080 级别的大图/长截图——正是该拦的），
**已收藏的表情 0 误伤**。

⚠️ 调参注意：**PNG 是无损格式，天生压缩率高**，所以阈值别调太低（默认 0.85 只拦"几乎没压过"的图），
否则会误伤 PNG 表情包。要观察拦截分布就用 `/sticker.admin.stat`，调参期间可开 `dryRun`（只记不拦）。

### 2.1 产物

| 东西 | 位置 | 干什么 |
|---|---|---|
| **`koishi-plugin-chatluna-sticker-admin`**（自写） | `koishi-app/external/` | 预筛逻辑与配置（服务名 `stickerGuard`）+ 5 个 AI 工具 + 4 条管理指令 |
| **`tools/patch-sticker.cjs`**（自写） | 仓库根 `tools/` | 给市场插件打 4 个小补丁（幂等、可 `--revert`、postinstall 自动跑） |

为什么用「自写插件 + 一处补丁」而不是纯自写：市场插件**没有任何对外钩子**
（不 provide 服务、无配置项），预筛必须插进它的收集中间件、候选池必须改它的检索语句——
只能补丁。但**逻辑与配置全在自写插件里**，补丁里只有 4 行调用；不装自写插件时补丁整段跳过，
行为与原生一致。

### 2.2 四个补丁的内容（`tools/patch-sticker.cjs`）

1. `middleware.js`：落盘前插 `ctx.stickerGuard.check(buf)` —— 预筛不过 → 直接标 `rejected`，**不落盘、不烧视觉调用**
2. `tools.js`：候选池 `listCollected(20)` → **2000**。原代码只取"按使用次数排序的前 20 张"，新库 useCount 全 0 → **AI 永远只能在那 20 张里挑**（这是隐藏 bug 级限制）
3. `library.js`：加 `mimeOf(buf)` 按魔数认真实格式
4. `tools.js`/`commands.js`：发图不再写死 `data:image/png` —— 原代码把 GIF/JPEG 的表情也声明成 PNG（文件按原字节存），**QQ 侧按 MIME 解会显示不出来**，这是真 bug

### 2.4 使用方针（回答「分类？常用？检索？」）

**落地方针 = AI 自己检索 + 常用微加权，不做显式分类。**

- **检索**为主：`sticker_search(query)` 打分 = 关键词命中×100 + useCount + pinned×50，在全库上做，库大也成立
- **常用（pinned）**为辅：`/sticker.admin.pin <pHash>` 或 AI 调 `sticker_update(pinned=true)`；检索 +50 分——不是"只有常用能用"，只是"常用优先"
- **不搞分类目录**：tags 已经是软分类（判断/打标时自动生成、可补可换），再建一套目录是重复抽象
- 预设【表情包】段已教模型「先 search 再 send_hash；认错了 update；好图 learn」

### 2.5 图片描述修正（vision_correct）

场景：识图模型说"蓝色小女孩"，群友提醒"这是你自己"——AI 应能**改掉已缓存的描述**，
否则这张图每次都被替换成错误描述。

- 定位（按可靠性）：hash 前缀（sha256/pHash）→ 原描述包含匹配 → 最长公共子串 ≥4 字 → 15 分钟内唯一一条；命中多条**不猜**，把候选列回去
- 改完同步：vision 缓存（内存索引 + 库）+ 表情包库 `sticker_meta`（pHash 汉明 ≤5 对上）
- 手动指令：`/vision.list`（看最近解析的图+hash）、`/vision.correct <hash> <新描述>`（authority 2）

### 2.6 上限与淘汰

| 机制 | 参数 | 行为 |
|---|---|---|
| 收藏上限 | `maxSendableImages: 300`（原 2000） | 超过 → 按 `lastUsedAt`（没用过用 `collectedAt` 兜底）**最久未使用优先**淘汰（记录+文件全删）。即"用得少的先死"，时间只是平局键 |
| 未收藏 TTL | `occurrenceTtlDays: 10` | 未收藏且 10 天没再出现 → 清掉 |
| 预筛 | `maxPixels / maxBytes / maxCompressionRatio / maxAspectRatio` | 不达标直接 rejected，**根本进不了库**——省空间从源头省 |

用户原话：

> 目前模型插入群聊对话的频率非常低，看看是什么导致的？插话模型一直判定不插话吗？

---

## 0. 结论（一句话）

**不是模型不插话 —— 它从来没拒绝过。** 频率低是**触发闸门**的问题（一天 297 次评估只有 1 次越过阈值），
外加**两次真的开了口，一次没发出去**；而当天 17:03 起机器人还陷在**每 30 秒自断一次的重连死循环**里。

---

## 1. 先回答"插话模型一直判定不插话吗" —— 不是

ChatLuna 的会话链里**没有**独立的"插话判定模型"。判定完全在 `chatluna-proactive` 插件里
（活跃度分数 / 条数兜底 / 空闲时长），一旦判定通过就直接把提示词塞进主模型让它说话。

主模型**确实有**一个"我不想说"的出口：预设【是否开口】那段告诉它"不想说话就只输出 `[SKIP]`"，
由 `chatluna-replyshaper` 在发送口把整条消息吞掉。

**它一次都没用过。** 判据：ChatLuna 每次请求都会把整段会话消息数组落成一份临时 log
（`C:\Users\...\Temp\chatluna\logs\*.log`），如果模型某轮回过 `[SKIP]`，那条 ai 消息必然出现在
**后续**请求的消息数组里。扫描 2026-09-28 ～ 10-03 的全部 **271 份 prompt log**：

```
扫描 271 个 prompt log：解析成功 271，失败 0
命中（模型整条回复就是一个哨兵）：0
```

（脚本：[.scratch/diag-skip.cjs](../.scratch/diag-skip.cjs)。基线是系统提示词里本身就写了 2 次 `[SKIP]`，
所以判据是"**非 system 消息**里整条等于哨兵"，不是"文件里出现过 SKIP"。）

顺带：`chatluna-replyshaper` 的 `debug` 原来是 `false`，**哨兵命中在日志里完全不可见** ——
已改成 `true`（它只在真命中时打一行），以后这类问题不用再靠扫描临时文件。

## 2. 闸门在触发判定：公式 + 可达性

`chatluna-proactive` 的活跃度打分（照搬上游 `chatluna-proactive-trigger`）：

```
recent  = 90 秒窗口内的条/分钟
instant = 20 秒窗口内的条/分钟
score   = logistic((recent - 10)/3) * 0.65 + logistic((instant - 9)/2) * 0.35
burst   = 30 秒窗口速率 > 12/分钟时再补 0~0.25
score  *= 0.55 + 0.45 * exp(-Δ/60min * ln2)      # 新鲜度：最后一条消息越久远，乘得越小
```

把"群里以 r 条/分钟匀速聊"代进去（新鲜度=1，无突发加成）：

| 群聊速度 r（条/分钟） | 相当于 | 分数 | 0.25 阈值 | 0.5 阈值 | 0.6 阈值 |
|---|---|---|---|---|---|
| 0.5 | 2 分钟一句 | 0.031 | ✗ | ✗ | ✗ |
| 2 | 30 秒一句 | 0.053 | ✗ | ✗ | ✗ |
| 4 | 15 秒一句 | 0.104 | ✗ | ✗ | ✗ |
| 6 | 10 秒一句 | 0.199 | ✗ | ✗ | ✗ |
| 8 | 7.5 秒一句 | 0.352 | ✓ | ✗ | ✗ |
| 10 | **6 秒一句** | 0.543 | ✓ | ✓ | ✗ |
| 12 | 5 秒一句 | 0.716 | ✓ | ✓ | ✓ |
| 15 | 4 秒一句 | 0.880 | ✓ | ✓ | ✓ |

**关键读法**：`logistic` 的中点是 **10 条/分钟**（`RATE_SUSTAINED`）和 **9 条/分钟**（`RATE_INSTANT`）。
门槛 0.6 意味着"**连着 90 秒、平均每 6 秒一条**"——这只在真正的刷屏突发里才成立；
而新鲜度因子还会在群里一停下来就把它乘回去。
换句话说：**这套参数是给大群刷屏场景调的，小群正常聊天连 0.1 都到不了。**

## 4. 六个成因（按影响排序）

### ① 阈值不可达（主因）

见上表。0.6 需要"每 6 秒一条、连续 90 秒"。**已下调**（见第 5 节）。

### ② 清历史池把"群聊热度"一起清了 —— 最该插话的时刻分数永远起不来

历史池 `pool.msgs` 的语义是"**bot 上次说话之后**群里聊了什么"，所以每轮正常回复后
`proactive-pool-reset` 都会清空它（这是对的：别重复作答）。

**但活跃度分数原来也是拿这个池子算的。** 于是：一群人在刷屏 → 中途有人 @ 了 bot → bot 正常回话
→ 池子清零 → 分数归零 → **这一波最该插话的时刻，分数永远到不了阈值**。
（详见 [docs/04 坑 54](04-踩坑记录.md)。）

**已修**：新增 `pool.heat`（只收非 direct 消息的时间戳，清池不影响，上限 240 条）专供打分。

### ③ 真的开了口，也可能发不出去

14:04:22 那次空闲触发，模型写的是「拿个棍子就上去了，这勇气我先敬为敬。」，**发送失败**：

```
14:04:19 [D] onebot [response] { status: 'failed', retcode: 1200, … 'errMsg': 'rich media transfer failed' }   ← 先发的那张表情
14:04:22 [D] onebot [response] { status: 'failed', retcode: 1200, … 'errMsg': '网络连接异常!' }
14:04:22 [W] session Error: Error with request send_group_msg, args: {"group_id":1040488785,"message":[{"type":"text","data":{"text":"拿个棍子就上去了，这勇气我先敬为敬。"}}]}
```

当天 `send_group_msg` 共 466 次成功、6 次失败，其中**这 2 次就是它**。
NapCat/QQ 侧的瞬时错误，不是插件问题 —— 但用户侧的表现就是"它根本没插话"。

### ④ 当天 17:03 起，机器人陷在"每 30 秒自断一次"的重连死循环里

NapCat 17:04:45 重启后，看门狗开始**自己掐自己刚接好的连接**（详见 [docs/04 坑 51](04-踩坑记录.md)）：
一天 40 次 OFFLINE、21 次重连。断线窗口里进群的消息直接丢、出站发送报 `网络连接异常!`。
**已修**（`recover()` 里"已是 ONLINE 就不许再 stop()" + 屏蔽自己造成的 OFFLINE 事件）。

### ⑤ 插话被挂上"引用 + @"，看起来像在回某人

17:09 那次插话被 `chatluna-reply-style` 挂成
`引用 1951933551 + @ 3912578627` —— 引用了一条不相干的群消息，还 @ 了一个没跟 bot 说话的群友
（提示词里明明写着"不要 @ 任何人"）。原因是它的引用目标解析顺序里有一层
"退到**这个频道最近一条入站消息**"，而主动插话根本没有"触发消息"这个概念。
**已修**（见 [docs/04 坑 53](04-踩坑记录.md)）。

### ⑥ 插话的提示词自己被当成群友发言，写进了短期记忆

`chatluna-episode` 把 `【自动插话】…` 整段提示词当成群消息存了下来，
下一轮 `{episode()}` 又注回提示词（1040488785 的 39 条近况里有 2 条是它）。
**已修**（见 [docs/04 坑 52](04-踩坑记录.md)）。

### ★ 窗口收窄（为什么要多这一步）

`suppress` 是**频道级 + 时间窗**的：窗口内**同频道的正常回复**也会被一起放过。
第一版设 120 秒，上线后立刻看到代价 —— 18:16:38 插话之后，群里开始跟 bot 正常聊天，
18:17:23 与 18:17:41 两条**正常回复白丢了引用/@**（18:18:32 那条在窗口外，形态是对的）。

所以改成"**两个时间**"：

```
开口前   suppress(guildId, 120_000)   ← 兜底：万一这一轮抛错/卡死，窗口不会一直挂着
await receiveCommand(...)             ← 这一轮的话在这句返回**之前**就发出去了
finally  suppress(guildId, 10_000)    ← 收窄：只给可能的分条/补充消息留 10 秒
```

依据：`[Middleware] request_conversation completed in 9.53s` 这行**出现在发送之后**
（14:04 那次更明显：`出站排队 → send_group_msg retcode 1200 → request_conversation completed`），
所以 `await` 一返回就能安全收窄。

## 7. 调参手册

配置文件：`koishi-app/koishi.yml` → `chatluna-proactive:pr0001`（**必须先停进程再改**，见坑 7）。

| 旋钮 | 作用 | 想更频繁 | 想更克制 |
|---|---|---|---|
| `activityThreshold` | 分数门槛 | 降到 0.15~0.2 | 升到 0.4+ |
| `thresholdCeiling` | 每插一次后门槛往这儿挪 10% | 设得比 threshold 还低 = 越聊越积极 | 0.6+ |
| `activityMessageInterval` | 累计多少条群消息必插一次（0=关） | 10~20 | 80+ |
| `cooldownSeconds` | 两次插话的最小间隔 | 180 | 900 |
| `idleMinutes` | 多久没说话算冷场 | 90 | 360 |
| `quietHours` | 免打扰（默认 `01:00-08:00`） | 留空 = 全天可插 | 拉长 |

**经验值**：小群（10~30 人、一天几十条）用 `threshold 0.2~0.3 / ceiling 0.35~0.45 / interval 20 / cooldown 300`；
大群刷屏用 `0.5~0.6 / 0.65~0.8 / 60 / 600`。

**判据怎么定**：`(ceiling - threshold) * 0.1` 是每次插话后门槛的上移量，
所以 `ceiling` 一定要**比 threshold 高一点但别高太多**，否则插了一两次之后就再也够不着了。

## 9. 理解之后再开口（把关 + 话题黑名单，第六轮续）

用户原话：

> 插入对话前需要能够**理解对话再插入**，不然会出现**牛头不对马嘴**的情况，
> 群在聊**电竞**的时候**直接不插入**，因为电竞信息太新了，**即使是提供网页搜索也不可能明白**。

第六轮前半段把频率从"一天两次"拉到"十几分钟一次"之后，问题就露馅了 ——
插话内容开始变成这类东西：

```
11:13这数字都刻进CN基因里了
这加油喊得，跟给人上坟似的
指挥一死就崩，纯缩影了属于是
守点守点，人都守没了
```

它们**看起来像在聊比赛，其实什么都没说**。群友聊的是 VCT / 天禄 / 某选手的操作，
bot 没有任何可靠来源，只能靠"电竞语气的词"拼一句像模像样的话 —— 这正是"牛头不对马嘴"。

### 9.1 设计：两道闸，一硬一软

```
活跃度/空闲触发
   ↓
闸 A：话题关键词黑名单（零成本、确定性）  ← 用户要求的是"直接不插入"，不能交给模型赌
   ↓
闸 B：把关模型判 SPEAK / SKIP（便宜模型，默认免费档）
   ↓
主链发言（人格、表情包、工具都在这一层）
```

**闸 A 为什么必须存在**：模型判定有失手率，而用户要的是"群在聊电竞的时候**直接**不插入"。
关键词是确定性的，而且零成本 —— 它在把关之前，所以被它拦下时**连把关模型都不调**。

**闸 B 为什么不是"再问一遍同一个模型"**：把关用的是**另一个更便宜的模型**（默认 `cc/q.memory`），
它拿到的是"最近的群聊 + 一份严格的取舍标准"，任务只有一件事：**能不能接**。
主模型那一轮带着人格、情绪、好感度、表情包工具，它天然倾向于"说点什么"。

**闸 B 的取舍标准**（`judgePrompt` 原文要点）：

- 只有同时满足"**真看懂**（能说清大家在聊哪件事、聊到哪一步）"与"**有一句具体的话可接**"才放行；
- 出现任何一条就 SKIP：话题靠**太新或太专**的信息（电竞赛事与比赛进程、直播、实时比分、
  选手操作与战术、股票行情、体育比分、突发新闻）；只是"大概知道"；只能想到
  "确实/草/?/笑死"这种没信息量的附和；大家在聊私事或在跟特定的人说话；记录里没有实质内容。
- 输出只有两种、各一行：`SPEAK: <要说的那句话>` / `SKIP: <不超过 15 字的理由>`；
  **解析不出来按 SKIP 处理**（宁可少说），**把关调用报错也按 SKIP 处理**。

### 9.2 拒绝之后必须"把看过的材料收掉"

第一次实现里闸 A 拿**整个历史池**去匹配关键词，rig 55 一跑就露馅：
"比分"两个字出现一次之后，**在池子被清空之前每一轮都命中** ——
群里早就换到午饭话题了，bot 还在因为十分钟前那句"看比分好像是2-0了"闭嘴。

两处修正（都在 [坑 55](04-踩坑记录.md)）：

| 修正 | 做法 | 为什么 |
|---|---|---|
| 黑名单限定窗口 | 只看**最近 6 条**非 direct 消息 | 语义是"**现在**在聊这个话题"，不是"**聊过**这个话题" |
| 拒绝后截池 | 闸门拒绝 → 池子只留**最后 3 条**，`msgCount` 归零 | 看过、判过、决定不说的材料留着只会毒化后面的判断，还白花把关调用 |

### 9.4 新增配置

| 项 | 默认 | 说明 |
|---|---|---|
| `judgeEnabled` | true | 总开关。关掉就退回"只按活跃度开口" |
| `judgeModel` | `cc/q.memory` | 把关模型；拿不到就退到 `chatluna.config.defaultModel` |
| `judgeTimeoutMs` | 30000 | 超时按"不可接"处理 |
| `judgeSkipSeconds` | 240 | 判不可接后多久不再重判（否则每 5 秒问一次模型） |
| `judgePrompt` | 见上文 | 把关提示词，变量同 `activityPrompt` |
| `skipTopics` | 15 个词 | 话题黑名单。**纯拉丁/数字词按词边界**（`VCT` 不命中 `VCTF`），含中文的词按包含匹配 |

> ★ 词表刻意**不放单字缩写**（瓦 / 狙 / jee）：中文单字会误伤（"瓦"命中"瓦斯""瓦片"），
> 这类交给把关模型按上下文判。

### 9.5 代价与取舍（要如实说）

- **插话会明显变少**。1040488785 平时聊的主要内容就是电竞赛事，黑名单一拦，
  那个群里的主动插话会从"十几分钟一次"掉到"偶尔一次"。**这是用户明确要的**：
  宁可不说，也不要说外行话。
- 每次触发多一次**免费档**模型调用（`cc/q.memory`），但因此省下的是主链那次
  ~1 万 token 的调用 —— 总体是**省**的。
- 判定不是万能的：把关模型也可能误判成可接。真觉得它还是乱接，
  先扩 `skipTopics`（确定性），再考虑把 `judgePrompt` 的取舍标准写得更死。

## 10. 观测面（下次再问"为什么它不说话"，按这个顺序看）

1. `决定插话（…）` 有没有出现 → 没有 = **闸门**问题，看下一行评估日志的"活跃度/阈值/热度"
2. 出现了但跟的是 `放弃插话：命中话题黑名单「…」` → 话题太新太专，**这是设计如此**
3. `放弃插话：把关判定不可接（…）` → 理解闸拦下的，看括号里的理由（理由本身就是诊断信息）
4. 出现了但 `已主动发言` 没跟上 → `出现 失败退避 / 处于屏蔽状态 / 还没有可用的 session`
5. 两个都有，但群里没看到 → **出站**问题：`send_group_msg` 的 `retcode`（1200 = NapCat/QQ 侧）
6. 一切正常但"它说的不像插话" → 看 `replystyle 出站形态`（引用/@ 是不是挂错人了）
7. `[SKIP]`（replyshaper debug 已开）→ **主模型**自己选择不开口

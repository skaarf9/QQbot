## 2. `/models`：为什么不是"提个 issue 等上游改"

上游 `chatluna.model.list` **本身支持翻页**（`-p <page>` / `-l <limit>`，
`koishi-plugin-chatluna/lib/index.cjs:632`），问题纯在文案（坑 65）：

```
header: 以下是目前可用的模型列表：
footer: 你可以通过 chatluna.new -p [preset] 或 chatluna.switch 为会话设置默认模型。
pages : 当前为第 [page] / [total] 页
```

`pages` 只说"你在第几页"，`footer` 讲的是预设/会话切换 —— **没有一处告诉你怎么翻页**。
改上游要动 `node_modules`（会被下次安装覆盖），所以自己接管这条命令：

```
可用模型（共 12 个 · 第 1/2 页 · 每页 10 个）

1. cc/q.dialogue　★当前会话 · 模型组 2 个
2. cc/q.memory　模型组 3 个
…

→ `/models 2` 看下一页；`/models -l 20` 每页 20 个；`/stages` 看各阶段实际在用的模型
```

三个刻意的设计：

1. **页码是位置参数**：`/models 2` 与 `/models -p 2` 都能用（上游只有后者）。
2. **改过 `-l` 之后，提示会把 `-l` 一起带上**（`/models 3 -l 3`）——
   页码和每页条数**不联动**，只提示 `/models 2` 会跳到另一个"第 2 页"，等于把人带沟里。
3. **越界给可执行的建议**，不是报错：`只有 4 页（共 12 个模型）。用 /models 4 看最后一页。`

> ★ 生产把 `models` / `stages` 放进了 `chatluna-page.keepTextCommands`。
> 理由**不是长度，是要能复制** —— 这两个命令的输出下一步就是粘进 `/model <名字>`，
> 渲染成图片等于把名字变成不可复制的像素（当初 `chatluna.model.list` 也是文字）。

## 3. `/stages`：各阶段在用什么模型

> ⚠️ **2026-10-06（第十五轮）这一条命令改版了**：不再只列"配置里写了谁"，
> 而是**实际在用哪个模型**（读 `chatluna-multi-adapter` 运行期队列注册表的 `plan()`），
> 并且显示每个候选的失败次数 / 冷却剩余 / "本次登录停用"；换模型用 `/stages.set`。
> 新版输出与原理见 [模型运维命令与队列自愈](31-模型运维命令与队列自愈.md)；
> 下面是**第八轮当时**的样子，保留作对照。

```
【各阶段模型】
当前会话：一句在线回应 ｜ 群 777000560
会话模型：cc/q.dialogue（＝全局默认 defaultModel）
预设：default-persona ｜ 聊天模式：plugin

阶段 → 模型
  主对话：cc/q.dialogue ★
    └ 组内顺序：stealth/space-bunny-alpha → deepseek/deepseek-v4.1-flash（策略：出错才切换）
  看图识别：cc/q.vision
    └ 组内顺序：…
  表情包判定：cc/q.sticker
  主动插话把关：cc/q.memory
  短期情景总结：cc/q.memory
  长期记忆抽取：cc/q.memory
  长期记忆图谱：cc/q.memory
  嵌入（记忆检索）：local/bge-small-zh-v1.5
  向量库：luna-vdb
```

**数据从哪来**：`ctx.loader.config.plugins` —— **运行期那份**配置树，不是文档、不是默认值。
各阶段的模型散在七八个插件里（`chatluna-vision.visionModel`、`chatluna-proactive.judgeModel`、
`chatluna-episode.summaryModel`、`chatluna-long-memory.longMemoryExtractModel` …），
只有 loader 手里那份是"此刻真的生效的值"，控制台改完重启后这里立刻反映出来。

**为什么不一个个插件去 `ctx.get(...)` 问**：Koishi 没有"读别的插件 config"的公开 API，
各插件也没把模型暴露成服务；真要那么干得改 8 个插件，而 `ctx.loader.config` 一份就够。

**模型组会额外解一层**：`cc/q.dialogue` 不是一个模型，是 `chatluna-multi-adapter` 配的**组**。
`/stages` 从多适配器配置里把组内顺序解出来一起显示 —— 这正是第 ⑤ 条困惑的来源（见 §4）。

**"（未显式配置 → 用插件默认）"是什么意思**：很多插件的 schema 有默认值
（例：vision 的 `visionModel` 默认就是 `deepseek/…-vision-exp`），那种情况下 `koishi.yml`
里本来就不会有这一行。这里如实写"没显式配"，**不等于没生效** —— 别被误导成"漏配了"。

## 4. `/model -a` 到底做了什么（回答第 ⑤ 条）

`chatluna.use.model -a`（`lib/index.cjs:396-424`）走的是
`conversation.updateConversationUsage(session, { model: undefined, auto: true })`
→ `applyAutoModelUpdate()`：**按路由规则/全局默认重算一次，把结果写回 `conversation.model`**。

所以：

- 它不是"切到某个固定模型"，而是"**恢复自动**" —— 重算的依据是
  `chatluna.defaultModel`（我们配的是 `cc/q.dialogue`）。
- 显示成 `cc/q.dialogue` 并**不代表没切到 space-bunny**：`q.dialogue` 是
  `chatluna-multi-adapter` 的**模型组**，组内顺序是
  `stealth/space-bunny-alpha → deepseek/deepseek-v4.1-flash`，**真正跑的是第一个**，
  只有出错才切下一个。`/stages` 就是为这件事加的（它会把组内顺序列出来）。
- ConversationRecord 里**没有单独的 `auto` 标记位**（`services/conversation.d.ts:17` 的结构体里没有），
  存的就是"路由最后选出来的那个名字"。所以 `/stages` 不去猜"自动还是手动"，
  只显示"现在用的是谁"，并把全局默认列在同一个头部里让人对照。

**结论：你对命令的理解没错（"切到默认"，默认本来就是 `cc/q.dialogue`），
误解的是"默认模型 = 某个具体模型" —— 它其实是一个会自动兜底的组。**

## 5. 联网搜索 MCP

### 5.1 架构

```
Koishi (chatluna-mcp-client:mcp001)
   │  stdio (JSON-RPC 2.0)
   └─ node koishi-app/mcp/websearch-server.cjs     ← 我们自己的 MCP 服务器
         ├─ web_search       搜网页 → 标题+URL+摘要
         ├─ web_browse       给 URL → 洗干净的正文
         ├─ web_search_read  搜 + 读前 N 篇（一步到位）
         └─ web_engines      引擎连通性自检
```

用的是**已装**的 `@modelcontextprotocol/sdk@1.29.0`（`koishi-plugin-chatluna-mcp-client`
的依赖），**零新增依赖**。工具注册链路（读源码确认，不是猜）：

`mcp-client` L593 `registerTool(langChainTool.name, …)`
→ `chat.cjs` L5897 → `platform/service.cjs` L72-79 存进 `_tools`
→ `llm-core/agent/index.cjs` L1666 `createToolsRef()` 里对每个工具跑 `selector`
→ 通过的作为 LangChain `StructuredTool` 交给模型做 tool-calling。
**没在 `tools` 表里显式配过的工具默认启用**（L561 `enabled ?? true`），
所以最小配置下四个工具全部生效。

### 5.2 为什么是 Bing，而且必须是 `cn.bing.com`

用户要求「不要用百度，Google 或 Bing 优先」。实测（子代理逐条做过排除法）：

| 入口 | 中文查询表现 |
|---|---|
| `www.bing.com/search?q=…&format=rss` | ★ **串味**：`今天上海天气` → "合成大泡泡 - 小米应用商店"；`koishi 机器人框架` → "禁漫天堂" —— 返回了结果但**完全无关** |
| `cn.bing.com/search?q=…&format=rss` | ✅ 三个中文查询全部命中，**更快**（118–270ms vs 190–3400ms） |
| `www.bing.com` 的 HTML 结果页 | 同样串味 |
| Google | 通（今天 200/90.6KB），但可能按 IP 弹 consent 页；有检测，不保证长期可用 |
| DuckDuckGo html | 通，偏慢（~1s） |

排除过"是不是代理缓存"：同 URL 连打 3 次结果完全一致、加 `_cb=` 破坏参数无效、
**直连（不走代理）结果一样**；`mkt` / `setlang` / `cc` / `ensearch` / `SRCHLANG` Cookie 都不稳定。
→ 默认链路 `cn RSS → www RSS → cn HTML → www HTML`，并且加了**相关性兜底**：
返回了结果但一条都没命中关键词 token 就判为"串味"，继续下一级；
全挂才报错。**宁可报"搜索失败"，也不返回垃圾结果。**

### 5.3 网页简化流程（照抄"人搜索后读网页"那套）

抓回来的 HTML **绝不原样喂模型**（又慢又贵，导航广告还淹掉正文）。顺序是：

1. 去噪声标签：`script / style / noscript / svg / iframe / nav / header / footer / aside / form`
2. 提取块级结构（标题、段落、列表项），**内联标签不切块**（`<p>a <b>b</b> c</p>` 必须是一段）
3. HTML 实体解码 → 折叠空白与多余空行 → 块内先按行 trim 再 join
4. **截断**并标记：`web_browse` 默认 4000 字符、`web_search_read` 每页约 3000，都可以调（上限 20000）
5. 直接发 HTTP：带 `Accept-Encoding`，**只检测 gzip 魔数**（undici 已经自动解压过了，
   再按响应头解一次会 `incorrect header check`）

拿不到的如实说：JS 客户端渲染的页面（不做 JS 执行）、`baike.baidu.com`（对无头抓取返 403）
只能拿到搜索摘要，抓不到正文 —— 工具会返回
`(正文为空：可能是 JS 渲染页面、需要登录，或被反爬拦截)`。

### 5.4 配置（`koishi.yml`）

```yaml
  chatluna-mcp-client:mcp001:
    servers: |
      {
        "mcpServers": {
          "websearch": {
            "command": "node",
            "args": ["D:/deepseek/QQbot/koishi-app/mcp/websearch-server.cjs"],
            "cwd": "D:/deepseek/QQbot/koishi-app",
            "env": {
              "HTTP_PROXY": "http://127.0.0.1:7890",
              "HTTPS_PROXY": "http://127.0.0.1:7890",
              "ALL_PROXY": "http://127.0.0.1:7890",
              "NO_PROXY": "localhost,127.0.0.1,::1",
              "NODE_PATH": "D:/deepseek/QQbot/koishi-app/node_modules"
            }
          }
        }
      }
```

三条硬规矩（每一条都是踩出来的）：

| 规矩 | 为什么 |
|---|---|
| `servers` 必须是 **JSON 字符串**（YAML `\|` 块标量），写成 YAML 对象会 `JSON.parse` 失败并**跳过全部工具** | `_parseServerConfigs()` L361-380 |
| **必须显式写 `env` 里的代理** | MCP SDK 的 `StdioClientTransport` 在 Windows 上只继承 `APPDATA/PATH/TEMP/…` 白名单，**不含 `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`** —— 不写子进程就没代理，Bing 直接连不上 |
| **不要在 server 项里加 `timeout`** | 整个对象会被原样交给 SDK 的 `StdioClientTransport`，多字段可能让它抛错；单次调用超时用 `tools.<名字>.timeout` 或工具自带的 `timeout_ms` |

### 5.5 自检

1. 启动日志：`MCP client initialized successfully with N tool(s) available`（N 应 ≥ 4）
2. 群里问一句「搜一下 X」——日志里会出现 MCP 服务器自己的 stderr：
   `[websearch] web_search q=… engine=bing-rss hits=…`（**stdout 只有协议帧**，日志全走 stderr）
3. 搜不到内容时先跑 `web_engines` 看是网络/代理还是引擎的问题

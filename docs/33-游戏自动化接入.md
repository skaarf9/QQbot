## 1. 落地范围（2026-10-08）

新增自研插件 **`koishi-plugin-game-auto`**（`koishi-app/external/`），一个插件管两条游戏通道：

| 游戏 | 通道 | 状态 |
|---|---|---|
| 明日方舟（MAA） | MAA **官方远程控制协议**：我们当任务源，MAA 每秒来取任务、跑完回报 | ✅ **已端到端验证** |
| 终末地（MaaEnd / MXU） | MXU 内置 Web API + `autoRunOnLaunch` | ⚠️ 代码已写，**未真机验证**（默认关闭） |

**MAA 与模拟器都由 bot 按需拉起**（2026-10-08 补，见 §4.2）：MAA 是"每秒来取任务"的那一端，它必须活着；而它只能启动**模拟器里的游戏**，开不了模拟器本身。这两件事现在都在 `/maa.daily` 里自动做完，人的动作只剩"在群里说一声"。

设计底线（三条，都写进了插件头注释）：**不引入现成 MCP**（ChatLuna 的 MCP 客户端没有 elicitation，`maa-mcp-adapter` 的确认表单会失效）、**LLM 不进执行路径**（工具只暴露白名单枚举，任务清单永远来自 GUI 里保存的配置）、**本机调用一律走 `node:http`**（`fetch` / `ctx.http` 可能吃到 `HTTP_PROXY`，把 127.0.0.1 的请求送进代理）。

## 2. 两条通道为什么这么选

### 2.1 明日方舟 —— MAA 远程控制（不是 maa-cli，也不是 MCP）

MAA 官方协议要求被控端提供两个 HTTP 端点：MAA **每秒** POST 到「获取任务端点」取任务、每个任务跑完 POST 到「汇报任务端点」。文档里的范例工作流标题就是**「用 QQBot 控制 MAA」** —— 我们不是硬凑。

任务类型里对我们有用的：`LinkStart`（= 启动一键长草，即 GUI 里勾选的那整条队列）、`LinkStart-<子功能>`、`StopTask`、`HeartBeat`、`CaptureImage(Now)`。

**为什么不用 `maa-cli`**：本机没装，要另装一份 MaaCore + 资源（GB 级），而且任务清单要另维护一份 → 和 GUI 里的队列必然漂移。**为什么不用 `maa-mcp-adapter`**：它的安全设计建立在"执行前弹确认表单"上，而 ChatLuna 的 MCP 客户端没实现 elicitation（`koishi-plugin-chatluna-mcp-client/lib/index.mjs` 里 grep 不到 `elicit`/`sampling`）→ 只能退到 `confirmation = "none"`，等于把它最值钱的部分拆掉，还多背十几个工具的 schema。

### 2.2 终末地 —— `autoRunOnLaunch`（不是 Web API 的 `tasks/start`）

MXU 确实有 `POST /api/maa/instances/{id}/tasks/start`，但它要求**请求方自己**把界面选项解析成 `pipelineOverride`（那段逻辑在前端 TS 里），而且 Web API **暴露不了 preActions**（MXU [Issue #348](https://github.com/MistEO/MXU/issues/348)）—— 而「全套日常」实例正有一个 preAction 负责启动 `Endfield.exe`。

所以走 `autoRunOnLaunch`：让 MXU 自己按保存的配置**全套跑**（选项与前置动作都不丢），bot 只负责改 `lastActiveInstanceId` + 拉起进程 + 用 Web API 看状态/停。代价：每次换实例要改配置，且只在启动瞬间生效（已在运行时若要跑，得重启它 —— 由 `endfieldRestartIfRunning` 控制，默认关）。

## 3. 插件结构

```
koishi-app/external/koishi-plugin-game-auto/
  package.json
  lib/index.js        # 单文件，约 640 行，分五段：状态 / 小工具 / MAA 侧 / 终末地侧 / 指令与工具
```

### 3.1 指令（一律 `authority: 4`）

| 指令 | 作用 |
|---|---|
| `/maa.daily` | 跑一次当前 GUI 队列的日常（下发 `LinkStart`），**立即回执**，不阻塞 |
| `/maa.status` | MAA 连接时间、最近心跳与当前任务、正在跑什么、上次结果 |
| `/maa.stop` | 下发 `StopTask` |
| `/maa.probe` | 只下发 `HeartBeat` —— 验证链路用，不会真跑日常 |
| `/endfield.daily` `/endfield.status` `/endfield.stop` `/endfield.probe` | 终末地对应功能；`probe` 打印 MXU 原始状态结构（真机验证用，不改任何东西） |

### 3.2 ChatLuna 工具

`game_auto({ game: 'arknights'|'endfield', action: 'daily'|'status'|'stop' })` —— **只暴露白名单枚举**，不接受模型生成的任务参数。`selector` 按群白名单放行，`authorization` 读 `session.user.authority`。这样「帮我清理方舟日常」这种自然语言能触发，而 prompt injection 的最坏结果只是「多跑一次日常」。

### 3.3 关键配置项

| 项 | 默认 | 说明 |
|---|---|---|
| `minAuthority` | 4 | 触发门槛（4 = 主人） |
| `allowGroups` | 空 | 群白名单，空 = 不限制群（仍受限权限） |
| `maaExePath` | `F:\MAA\MAA.exe` | **远程控制要求 MAA 常驻**，所以触发时会按需拉起 |
| `maaToken` | 空 | 空 = 自动生成一次并写到 `data/game-auto-control.json`，**重启复用** |
| `maaLaunchIfDown` | true | 触发时 MAA 没在跑就拉起来 |
| `maaCheckEmulator` | true | 下发前先确认模拟器真的开机了（判据见下） |
| `maaLaunchEmulator` | true | 模拟器没开就自动拉起来（`MuMuManager control -v N launch`） |
| `maaEmulatorExePath` | MuMu 的 `MuMuManager.exe` | 官方 CLI，用来查开机状态 + 开机；**用别的模拟器就留空**，此时只按 `maaEmulatorAdb` 探 |
| `maaEmulatorVmIndex` | `'0'` | 多开实例序号（对应 CLI 的 `-v`） |
| `maaEmulatorAdb` | `127.0.0.1:16384` | adb 地址，TCP 兜底探测用；**要和 MAA 连接设置里的地址一致** |
| `maaEmulatorWaitSeconds` | 180 | 开机最多等多久；超时**不下发任务**，直接回报失败 |
| `maaDispatchTimeoutMinutes` | 5 | 下发后多久没被领走 → 判失败并回报（多半是 MAA 没起来/端点填错） |
| `endfieldEnabled` | **false** | 终末地未真机验证，验完再开 |

令牌为什么要落盘复用：**MAA 只存一个死 URL**，它没法像 `chatluna-guard` 的消费者那样去读我们的文件；令牌每次重启换新，就等于把你填进 MAA 的端点 URL 弄失效。

## 4. 验证证据

### 4.1 协议往返（rig 25，2026-10-08）

剧本 `koishi-app/tools/scenarios/25-game-auto.json`（管理员喊一次、主人查状态、主人喊一次）+ 模拟 MAA 客户端 `.scratch/maa-emulator.ps1`（每秒 `getTask`，领到任务后延迟回报）。
跑法：`node tools\run-rig.cjs tools\scenarios\25-game-auto.json --settle 14000 --run 100000 --keep-log`（模拟客户端要**先起**，它像真 MAA 一样持续轮询）。

| 验的是什么 | 实测结果 |
|---|---|
| **权限闸门** | 管理员（10002，等级 3）发 `/maa.daily` → 回 `权限不足。`，**没有下发任务**（日志里没有「已下发方舟日常」） |
| **状态查询** | `/maa.status` → `MAA 连接：0 秒前（device sim-devi…）` / `当前没有在跑的任务。` / `上次结果：方舟日常 成功（10 秒前）` + 端点 URL |
| **触发回执** | `/maa.daily`（主人）→ 26 ms 内回执「好，方舟日常已下发／预计 20 分钟左右／跑完我在这儿说一声」，**不等它跑完** |
| **协议往返** | 模拟 MAA `GOT LinkStart id=…` → `REPORT LinkStart -> HTTP 200`；插件侧 `MAA 回报：task=… status=SUCCESS` |
| **收尾回报** | 群里收到 `[reply][at][游戏自动化] 方舟日常 跑完了（用时 13 秒）。` |
| **端点鉴权** | 正确令牌 200 `{"tasks":[…]}`；错令牌 403；无令牌 403 |

> 回复在**生产**里会被 `chatluna-page` 渲染成图片（`keepTextCommands` 没列 `maa.*`），这是本项目既定行为；测试实例里把 `maa.*` 加进了 `keepTextCommands`，只为让测试脚本能读到文字。

### 4.2 环境自启：MAA 与模拟器都由 bot 拉起来

需求是"群里说一声就跑完"，那就不能有"你得先打开 MAA / 先开模拟器"这一步。这两件事都是真的验过的：

| 问题 | 结论 | 证据 |
|---|---|---|
| MAA 必须常驻吗？ | **必须** —— 它是**发起轮询的一端**，我们只是被动应答它的 POST | 协议文档：[远程控制协议](https://docs.maa.plus/zh-cn/protocol/remote-control-schema.html) |
| 拉起 MAA 后还要人去点开关吗？ | **不用**。端点填过一次就存在它的配置里，之后每次启动它自己就开始轮询 | `F:\MAA\debug\gui.log`：03:19:23 用 exe 直接拉起、全程没人碰界面，日志里 03:20:03~03:20:07 连续 `HTTP: OK POST http://127.0.0.1:5140/maa/getTask?token=…`，直到 03:20:07 `Shutdown called by OnClose`（窗口被关）才停 |
| 模拟器呢？ | **MAA 开不了模拟器**（它的"启动模拟器"是另一套设置，`StartGame` 只能启动模拟器**里的游戏**）→ 只能由 bot 补这一环 | 官方 CLI：`MuMuManager.exe control -v 0 launch` |
| "起来了"怎么判？ | 用 `MuMuManager.exe info -v 0` 的 **`is_android_started`**，不是 adb 端口 | 冷启动实测：adb 端口比系统进桌面早得多，只看端口会让 MAA 连上还在开机的系统 |

rig 26 冷启动实测（`tools/scenarios/26-game-auto-emulator.json`，模拟 MAA 客户端 + **真** MuMu，开跑前实例是关的）：

| 时刻 | 发生了什么 |
|---|---|
| 03:25:51 | `/maa.daily` → 探测到模拟器没开 → `MuMuManager.exe control -v 0 launch`，群里立刻回"已经把它拉起来了，正在等它开机（最多 180 秒）" |
| 03:26:06 | `/maa.status` → `★ 正在跑：方舟日常（正在等模拟器开机，还没下发），已跑 15 秒` |
| 03:26:14 | `模拟器就绪，方舟任务已下发` → 这之后 MAA 才来领 `LinkStart` |

即：**从喊一嗓子到任务真下发，全程 23 秒**（MuMu 自报 `launch_time: 20607ms`），人的动作是零。等待期间任务槽是"预占"状态（`phase: preparing`），所以这时候 `/maa.stop` 是本地撤销、不会往 MAA 扔一个没有对象的 `StopTask`。

### 4.3 真跑一次（2026-10-08 19:31 → 19:50，真 MAA + 真模拟器 + 真方舟）

本机重启之后 5140 被系统抢走（见 §5 第 8 条），端口修好、生产重启之后，用户**只在群里发了一条 `/maa.daily`**：

| 时刻 | 日志 |
|---|---|
| 19:31:31 | `已拉起 MAA：F:\MAA\MAA.exe` —— 此前 MAA 是关着的 |
| 19:31:31 | `已拉起模拟器：…MuMuManager.exe control -v 0 launch` —— 模拟器也是关着的 |
| 19:31:40 | `模拟器就绪，方舟任务已下发`（9 秒；这次模拟器其实早就开着，是 §5 第 8 条那个误判造成的一次多余等待） |
| 19:31:42 | `下发任务 LinkStart (e19d17ff-…)` —— MAA 起来后第一次轮询就领走了 |
| 19:50:08 | `MAA 回报：task=e19d17ff-… status=SUCCESS payload=` |
| 19:50:09 | `已回报到 1040488785：方舟日常 跑完了（用时 18 分 26 秒）。` |

**这就是原始需求的闭环**：群里喊一声，bot 自己拉起 MAA 与模拟器 → 下发 → 等 MAA 跑完 → 结果发回群里。
全程唯一的人工步骤是"MAA「设置 → 远程控制」里那两条 URL 填过一次"（填完存在 MAA 配置里、重启不变，所以 §7 那两条只在换端口/换令牌时才需要重填）。

## 5. 实施中踩到的 8 个坑

1. **`ready` 时 `ctx.server.port` 还是 undefined** —— server 是在 `ready` **之后**才 `listen()` 的（日志里「就绪：端口 (未知)」恰好排在「server listening」之前）。后果：测试实例（5141）的端点 URL 被写成 5140。→ 落盘与打印延后到 ready 后 2.5 s，并在注释里写明时序。
2. **令牌必须跨重启稳定**（见 §3.3）—— 最初写成"留空 = 不校验"，那等于把端点裸奔；改成"生成一次 → 落盘 → 复用"。
3. **残留 job 会把插件永久卡死** —— `state.job` 是「现在有人在跑」的唯一真相且落在磁盘上。一次没被领走的 `LinkStart`（MAA 没开/bot 中途重启）会让之后每次 `/maa.daily` 都回「已经有一个在跑了，已跑 3 天 7 小时」。→ 加 `reconcileJob()`：启动时按「还在等 MAA 来领的窗口内」判定，窗口内就**重新武装看门狗**，窗口外就判失败并清槽；另有 6 小时硬上限。
4. **"用时"的分母错了** —— 用 `job.startedAt`（入队时刻）算，会把"bot 入队 → MAA 才起来领走"这段等待算进去。实测一个 4 分 49 秒前入队、刚被领走就报完的任务，显示成"用时 4 分 49 秒"。→ 改用任务的 `dispatchedAt`。
5. **命令的权限是框架先判的** —— `ctx.command(def, desc, { authority: 4 })` 会先拦住越权者并回一句 `权限不足。`，**根本轮不到**插件里的 `gate()`；所以 `gate()` 的"静默"分支实际只在 ChatLuna 工具那条路上生效（命令这条路留着是为了纵深）。
6. **"adb 端口通了"不等于"模拟器开机完成"** —— 最初想拿 `TCP 127.0.0.1:16384` 当就绪判据；实际 VM 的 adbd 一启动就监听这个端口，此时安卓还没进桌面，MAA 连上去只能白等。→ 主判据换成 MuMu CLI 的 `is_android_started`（`player_state: start_finished`），TCP 只在"没配 CLI / 用别的模拟器"时兜底。
7. **"等模拟器开机"这段时间也得占住任务槽** —— 不占槽，这 20 多秒里再喊一次 `/maa.daily` 就会重复拉起模拟器、重复入队；但占了槽又带来新问题：`/maa.stop` 会往 MAA 扔一个**没有对象**的 `StopTask`。→ 用 `phase: 'preparing' | 'queued'` 区分：`preparing` 时 `/maa.stop` 走**本地撤销**（不打扰 MAA），真入队后才切 `queued`。
8. **5140 被 Windows 抢走 → `/maa.*` 整组指令静默消失**（2026-10-08 机器重启后实测）—— 症状是"bot 一切正常，就是没有 `/maa`"：
   `server` 插件绑不上被系统保留的 5140（`listen → EACCES`），抛 `No open ports available` 之后 **server 服务被销毁**，
   而本插件声明了 `inject = { required: ['server'] }`，于是它连着自己那 18 条指令一起被 Cordis 销毁 ——
   实例不崩、不报错、照常连着 NapCat，`--check` 也显示一切正常。判断：`node tools\run-prod.cjs --check` 会报"空闲，但**绑不上**"；
   修复：跑 `tools\fix-port-5140.ps1`（会弹 UAC）。完整取证、以及"为什么删表没用、必须停 winnat"见 [坑 85](04-踩坑记录/01-环境与安装.md)。
   **同一次还发现**：MuMu CLI 偶发把"开着且早就进桌面"的模拟器报成 `is_android_started: false`（19:31:31 那次就是这样），
   导致插件白拉起一次、白等几秒；现在改成「字段不是布尔 → 退回 TCP 探」「报 false → 1.5 秒后复查一次」「判没开机时把 `player_state`/`error_code` 打进日志」。

顺带一条设计上的"为什么能这么简单"：MAA 是**主动轮询**的那端，所以"先把任务排进队列、等它起来自己来领"是完全成立的 —— 我们不需要等 MAA 起来才回执，也不需要跟它同步状态。

## 6. 未验证 / 下一步

- **终末地整条链路未真机验证**（代码已写、默认 `endfieldEnabled: false`）。要验：拉起 `MaaEnd.exe` → `curl http://127.0.0.1:12701/api/maa/state` 与 `/api/maa/config`，再跑 `/endfield.probe` 看真实状态结构，据此补「跑完自动回报」（现在只做启动/状态/停止）。注意 MXU 的 Web 服务**没有鉴权**，`allowLanAccess` 必须永远保持 `false`。终末地是 PC 端游戏，**不需要模拟器**，"环境自启"对它就是拉起 `MaaEnd.exe`（已实现）。
- **方舟"真跑一次"已于 2026-10-08 19:31–19:50 真跑通过**（18 分 26 秒、`SUCCESS`、结果回群，见 §4.3）。MAA 里的两条端点也确认填好（`F:\MAA\debug\gui.log` 里 03:11:44 / 03:12:02 两条 `RemoteControl*Uri has been set`，DPAPI 解出来就是本机 5140 那两条），填一次就够、重启不变。
- 还没做：进度分段回报（`HeartBeat` 轮询当前任务名）、截图回报（`CaptureImageNow`，base64 几十 MB 别过网关）、`endfield` 的完成检测。
- 可以考虑：日常跑完**自动关掉模拟器**（现在跑完就留着，MuMu 占内存）；以及给 `/maa.daily` 加"跑完是否关机"的开关。

### 2.2 免费档现状：**没有"免费且支持视觉"的模型**

## 3. `/stages`：从"配置里写了谁"改成"实际在用谁"

### 3.1 数据从哪来（三段拼接，全部是运行期真值）

| 显示项 | 来源 | 为什么 |
|---|---|---|
| 各阶段的**配置值** | `ctx.loader.config.plugins`（运行中的 loader 配置树） | 只有这份是"此刻真的生效的值"，控制台改完重启即反映 |
| 各阶段**实际在用** | `chatluna-multi-adapter` 的 `RotationRegistry.plan(组名)[0].model` | 配置里写的常常是**模型组**（一串候选），`plan()` 正是 requester 每次要走的顺序（`requester.js:170`） |
| **失败次数 / 冷却剩余 / 本次登录停用** | 同一个注册表的 `_failures`（键 `组\0接口序号\0模型`） | 这是队列"记住谁坏了"的地方，也是我们要显示的那份缓存 |

### 3.2 为什么敢读私有字段

- 入口是**公开的**：`ctx.chatluna.platform.getClient(platform)` 返回运行期平台客户端实例
  （`lib/index.cjs:5277` 也是这么用的），注册表挂在它的 `_registry` 上。
- 字段名在 [docs/22](22-模型兜底队列与群聊上下文.md) 里逐行核对过，且**版本 0.0.3 钉死**。
- 全程 **try/catch + 只读**：拿不到就退化成"只看配置值"，并打印一行
  `⚠ 拿不到队列注册表`——**绝不影响主流程**。

## 4. 「本次登录不再尝试」——上游缺的那一级

### 4.1 上游已有 / 缺什么

`chatluna-multi-adapter/lib/rotation.js` 里已经有整套"记住谁坏了"的机制：

```
reportFailure()  failures += 1
                 cooldownUntil = now + 基数 × [1,2,10,30,60][min(failures-1,4)]   （30 分钟封顶）
plan()           过滤掉还在冷却的候选；全在冷却则挑冷却最浅的那个（fail-open）
reportSuccess()  删掉这条失败记录（说明它恢复了）
```

⇒ 用户描述的"标记失效一段时间 → 用后续模型 → 过期后再试首选 → 再失败就延长"**一模一样**。
**缺的只是最后那一级**：30 分钟封顶之后，它**永远**还会再试（每隔 30 分钟撞一次墙）。

### 4.2 做法：每 5 秒扫一次，把冷却抬到 `Infinity`

```js
table.forEach((state, key) => {
  if (state.failures >= cfg.sessionFailureLimit)   // 默认 3
    state.cooldownUntil = Number.POSITIVE_INFINITY // ← 注册表的 isCooling() 会认这个值
})
```

- `isCooling(state, now) = state.cooldownUntil > now` → `Infinity > now` 恒真 →
  `_planGroup()` 过滤候选时**只要还有别的可用就永远不选它**。
- **只写这一个字段**，不碰上游代码、不动 `node_modules`（会 `npm i` 覆盖）。
- 状态**只在内存**里 ⇒ 天然就是"本次登录"：重启即复原（正是用户要的语义）。
- **fail-open**：万一整个组都被停用，注册表仍会 `pickLeastCooling()` 挑一个出来试 ——
  宁可撞墙也别让某个阶段彻底不可用。`/stages` 的页脚会把这句话写出来。
- 可关：`sessionFailureLimit: 0`；扫描间隔 `queueSweepSeconds`（默认 5 秒）。

日志留痕（运维一眼能看到）：

```
[I] chatluna-models 队列自愈已开启：同一模型累计失败 3 次 → 本次登录不再尝试（每 5 秒扫一次）
[I] chatluna-models 队列自愈：q.failover 的 fake-broken 累计失败 3 次 → 本次登录不再尝试（重启即复原）
```

## 5. `/stages.set`：按阶段换模型（含热重载）

### 5.1 命令与选项

| 命令 | 作用 |
|---|---|
| `/stages.set` | 列出 11 个阶段 + 各自当前值 + 是否"要视觉"/"只读" |
| `/stages.set <阶段>` | 列出该阶段的**候选模型**（分页、带能力标注、带价格备注） |
| `/stages.set <阶段> <序号>` | 选定（序号按上面那份列表，**支持翻页后的绝对编号**） |
| `/stages.set <阶段> <模型名>` | 直接写模型名（能力未知时会从严判定） |
| `/stages.set <阶段> -p 2 [-l 15]` | 翻页；页脚会把带 `-l` 的完整命令写出来 |
| `/stages.reset <阶段>` | 回到**本进程启动时**的状态（含"当时没配 → 删掉这一行"） |

阶段参数中英文/别名都认：`vision` = `看图` = `识图` = `视觉`；
`episode` = `短期情景总结` = `情景`；`memory` = `记忆` = `记忆抽取`……（键、中文名、别名三套都匹配）。

### 5.2 视觉闸门（用户第二个诉求的正面回答）

`/stages.set` 对"要视觉"的阶段（主对话 / 看图 / 看图兜底 / 表情包判定 / 表情包打标）
**拒绝**没有 `image_input` 的候选：

```
❌ 拒绝：cc/q.memory 不支持视觉（✖无视觉）。
看图识别 这个阶段收到的是图片，换成它会让图片被降级成占位符，等于瞎了。
用 `/stages.set vision` 看带 ✅视觉 的候选。
```

能力判定是**三值**（`true / false / 未知 null`）：
- `false` → 拒绝（理由如上）；
- **未知（null）也拒绝** —— 既不在适配器列出的模型里、也没在模型组里声明能力，
  就没法保证它吃图，宁可让人先把它加进模型组（在那里声明 `modelCapabilities`）；
- `true` → 放行。

候选列表里 ✖无视觉 的**照样列出来**（不藏），只是排在后面 —— 因为有些阶段
（记忆/把关）**就该选纯文本模型**。

### 5.3 改动是怎么落地的：走 loader 的官方热重载路径

阶段模型都**不是**本插件的配置，而是别的插件的字段（`chatluna-vision.visionModel`、
`chatluna-episode.summaryModel`……），所以"切换"= 改 `koishi.yml` + 让那个插件带新配置重启一次。
Koishi 本来就支持这件事 —— **控制台"保存并重启该插件"走的就是同一条路**
（`@koishijs/plugin-config/lib/shared/index.js:261`）：

```js
await loader.reload(parentCtx, 'chatluna-episode:aa0032', nextConfig)  // 只重启这一个插件
await loader.writeConfig()                                             // 写回 koishi.yml（带 $if/$filter 归属处理）
```

**为什么不用"改内存对象"这种轻量办法**：schema 解析会给插件一份**新的** config 对象，
改 `loader.config.plugins[...]` 里的那份**不会**影响已经 apply 的插件 —— 看着"改成功了"，
实际上模型根本没换（静默失败）。走 `reload()` 才是既写盘又生效。

实测日志（rig 66）：

```
[I] loader reload plugin chatluna-episode:aa0032
[I] chatluna-models 阶段 episode：cc/q.memory → cc/q.dialogue（已热重载）
…（/stages.reset 之后）
[I] loader reload plugin chatluna-episode:aa0032
[I] chatluna-models 阶段 episode 恢复为启动值 cc/q.memory（已热重载）
```

⚠️ **代价**：会重启目标插件。对 vision / sticker / proactive / episode 这些是毫秒级；
对 `主对话`（字段在**主 `chatluna` 插件**上）是重连上游、几秒 —— 所以回执里会明说
"已热重载 `chatluna`"，而且提醒：改的是**全局默认**，已有会话要 `/model -a` 或处于自动模式才会跟着变。

### 6.3 「三次后本次登录不再试」的确定性验证

测试台的 `fakemulti` 平台指着一个伪上游（`tools/fake-openai.mjs`），
`fake-broken` **恒 403**、`fake-flaky` 头一次 403 —— 正好用来反复击打首选。

⚠️ **上游冷却基数是 30 秒**，梯度 30s/1min/5min… ⇒ 想在一次 rig 里攒够 3 次失败要跑 100 秒以上。
所以**只把测试实例**（`chatluna-multi-adapter:aa0030`）的 `endpointFailureCooldown` 压到 **3000**，
梯度变成 3s/6s/30s，20 秒内就能攒满三次（生产那份仍是 30000，配置里写了注释说明）。
判据 I 的四条：伪上游收到 ≥3 次 `fake-broken`、日志出现"队列自愈"、
`/stages` 显示 `⛔ …本次登录停用`、**停用之后的请求不再先打 `fake-broken`**
（最后一条最硬：证明冷却真的生效，不只是显示得好看）。

## 9. 运维备忘

- **看队列真值只需要一条命令**：`/stages`。它同时回答"配了谁""实际在用谁""谁在冷却""谁被停用了"。
- **换模型不必改文件、不必重启整个 bot**：`/stages.set <阶段> <序号>`，写盘 + 热重载那个插件。
- **每月看一眼额度**：`deepseek/deepseek-v4.1-flash` 是 $60/月（≈15.4 万请求），
  `-fast` 是 $60/月但只 ≈5.75 万请求（它的单价更高）；`Qwen/Qwen3.8-Flash` 只有 $20/月。
  真被限流时，把 `/stages` 里"实际在用"的那一档往下调（比如主对话降到 `-fast` 或 Qwen）。
- **有新模型上线时**：`node .scratch/probe-cc-models.cjs` 看列表 →
  `node .scratch/probe-cc-candidates.cjs <模型id>` 实测三项（视觉 / 工具 / 中文）→
  三项都过了再写进 `modelGroups`（**能力要如实写 `modelCapabilities`**，否则组的交集会失真）。

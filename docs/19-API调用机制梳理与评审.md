> **本文是"体检报告"，只做梳理与判断，不改代码。** 建议项在末尾按优先级排序。

## 一、一轮对话的完整触发链路（谁会打 API）

这是全文最重要的一张图。**「bot 回复一句话」背后可能有 1～5 次模型调用**，
而每一层都有独立的开关和参数，散落在 8 个插件里。按"谁先跑"排序：

| # | 层 | 谁 | 干什么 | 关键参数（生产值） | 是否打 API |
|---|---|---|---|---|---|
| 1 | 入站闸门 | `chatluna-guard` | 白名单外的群**直接短路**（不建库行、不解析指令、不回复） | `defaultPolicy: silent`；`allowGroups: [454444539, 1040488785]` | ❌ |
| 2 | 指令解析 | Koishi `Commander` | 带前缀才进指令表 | `prefixMode: strict` | ❌ |
| 3 | 识别闸门 | ChatLuna `allow_reply` | 判定"是否在叫 bot"：@bot / 昵称开头 / 引用 bot（`allowQuoteReply`）/ botNames 开头 / 预设 keywords 开头 | 默认全开 | ❌ |
| 4 | 跟进窗口 | `chatluna-followup` | 叫过 bot 后，同一用户短时间内的**后续消息也算触发** | 按人 120s/600s/20 条；**整群熔断 3 条/120s**；真群档 45s/60s/1 条 | ❌（只改 session） |
| 5 | 主动插话 | `chatluna-proactive` | **不走 Koishi 中间件**，直接 `chatChain.receiveCommand(session, '', {is_proactive})` | 轮询 5s；冷却 600s；活跃度阈值 0.5/0.6；空闲 180/240 分钟；免打扰 01:00-08:00 | ❌（触发后才打） |
| 6 | 聚合延迟 | ChatLuna `messageQueue` | 同一用户连续消息 **debounce 合并**成一条输入 | `messageQueueDelay: 3`（秒） | ❌ |
| 7 | 图片预处理 | `chatluna-vision` | 私聊/群@时**阻塞解析**图片；群未 @ 时整段丢掉 | 视觉模型 `deepseek-v4-flash-vision-exp`；sha256 缓存 | ✅ **视觉调用** |
| 8 | 表情包收集 | `chatluna-sticker` | 群里**任何**图片都下载 + pHash；出现 3 次触发视觉判断是否收藏 | `judgeThreshold: 3`；`judgeModel` 需显式配 | ✅ **视觉调用** |
| 9 | 记忆检索 | `chatluna-long-memory` | `before-chat` 按当前消息检索各层记忆并注入 | HippoRAG + luna-vdb + 本地 bge 嵌入 | ✅（嵌入，本地，不烧 Key） |
| 10 | **主对话** | ChatLuna | 拼提示词（情绪/好感度/记忆/场景四段变量）→ 请求主模型 | `deepseek-v4-flash-vision-exp` | ✅ **主调用** |
| 11 | 工具轮 | 各插件 | 模型可能调 `emotion_set` / `affinity_affinity` / `memory_add` / `sticker_send` / `plugin_request` | 8 个工具 | ✅ **每轮工具=一次追加调用** |
| 12 | 记忆抽取 | `chatluna-long-memory` | `after-chat`，**每 3 轮**抽一次写长期记忆 | `longMemoryExtractInterval: 3` | ✅ **抽取调用** |
| 13 | 出站闸门 | `chatluna-guard` | `before-send` 拦"已在生成中"的那一轮 | 3 道闸门 | ❌ |

**结论（成本视角）**：一次普通 @ 回复 = **1 次主调用**；
如果带图且未命中缓存 → **+1 次视觉**；如果这张图在群里出现过 ≥3 次 → **+1 次 sticker 判断**；
如果触发了工具 → **+1～N 次**；每第 3 轮 → **+1 次记忆抽取**。
**最坏情况一轮能打 4～5 次 API**，且没有任何"总预算"约束。

## 二、调用时机是否合适 —— 逐条判断

### 2.1 ✅ 合适的部分（保持不动）

- **入站闸门在最前**（guard 用 `ctx.middleware(fn, true)` = unshift）——新群绝对安全，
  真群接入时"34 条消息全被丢弃"已验证。这是设计得最好的一层。
- **`allow_reply` 是链上第一个中间件**，未 @ 的消息根本进不了 transformer，
  "群里 AI 不知道有图"天然成立，不依赖任何自写插件。
- **聚合延迟用 ChatLuna 内建**（坑 21），没有重复造轮子——符合"先本地后自研"。
- **跟进窗口与图片策略解耦**：followup 插的 at 恰好让 vision 认为"叫了 bot"，
  两个插件互不知道对方存在却联动正确。
- **主动插话绕过 Koishi 管线**（`receiveCommand`）——这是唯一能让"没被叫的发言"进对话的正确姿势。

### 2.2 ⚠️ 时机不合适 / 有风险的部分（建议处理）

| 级别 | 问题 | 现状 | 建议 |
|---|---|---|---|
| **高** | **延迟叠加，群聊体感偏慢** | 总延迟 ≈ 图片解析(3~5s) + `messageQueueDelay:3s` + 模型(2~6s) = **8~14s** | 文档自己已写"可能偏慢，可调到 2"。建议：私聊保持 3（要准），**群聊可降到 2**；或对"纯文字 @ 消息"跳过 3s 窗口 |
| **高** | **出站没有全局速率闸** | 只有 followup 的**整群熔断** + proactive 的 **冷却**；普通 @ 回复、多人同时叫 bot **没有总闸** | 加一个**按群的出站令牌桶**（如每群每 60s 最多 N 条），作为所有出站路径的总兜底。真群限流（retcode 1200）已经发生过一次，别只堵 followup 一个口 |
| **中** | **`messageQueueDelay` 是"按人"debounce，与 followup 的"按群"熔断不是一套口径** | 两套机制在不同层，参数各配各的 | 可接受（分层是对的），但**调参时要同时想**：熔断放 1 条，debounce 可能又把它合并，实际开口数会少于熔断值 |
| **中** | **主动插话无"接得上话"的语义判断** | 纯数值触发（活跃度/空闲），只有历史池注入 | 已能"接上话题"（验收时接住了"忘记做日常"），够用；若想更稳，可让 proactive 先让模型**判一句"该不该插"**再发言（多一次调用，谨慎） |
| **中** | **真群活跃度阈值仍偏敏感** | `activityThreshold: 0.6`，文档实测 2 分钟就开口 | 文档建议 0.7~0.75，或 `activityMessageInterval` 提到 120。**建议先调 0.7** |
| **低** | **免打扰是全局的 01:00-08:00** | 真群若凌晨活跃，bot 完全不出声 | 按群覆盖免打扰（followup/proactive 已有 `groups`，加一个字段即可） |
| **低** | **裸 @（@bot 但无内容）不建 turn** | 延迟从"下一条有效消息"才起算，不是从裸 @ 起算 | 差 1~2 秒，文档判定"可接受"。保持 |

### 2.3 一个必须点名的结构性问题：**没有 API 预算 / 降级机制**

现在每个插件各自决定"要不要调模型"，**没有任何一层知道"这一轮已经花了多少"**。
风险场景：群里一张图出现第 3 次 + 用户 @bot 问它 + 这正好是第 3 轮对话 + 模型调了两个工具
→ 一轮 4 次调用，其中 2 次是视觉（贵）。**建议**（不急，但值得记）：
在链上加一个轻量"成本计数中间件"，同一轮超过阈值就降级
（如跳过 sticker 判断、跳过记忆抽取、vision 改用缓存的旧描述）。

## 三、五大机制完整性评审

### 3.1 情绪控制（R14 / R18）—— **骨架完整，深度可加强**

| 维度 | 状态 |
|---|---|
| 落库 / 隔离 | ✅ `chatluna_emotion`，默认按会话（一群一情绪），可切 user/global |
| 衰减 | ✅ 半衰期指数衰减（`halfLife: 60`） |
| 过期 | ✅ 绝对保质期（`expireMinutes: 180`）+ 后台清扫（`sweepSeconds: 60`），**逻辑代码控制，模型绕不过** |
| 注入 | ✅ `{emotion()}`，预设里写死了语气规则 |
| 模型自更新 | ✅ 工具 `emotion_set` |
| 人工干预 | ✅ `/emotion` 系列 |

**缺口**：
1. **粒度是"群"不是"对人"**。多人群聊里"我现在的心情"被所有人共享，粗糙。
2. **未与活跃机制联动**：心情好不更爱说话、烦躁不更少说话（只在提示词里做语气提示）。
   情绪目前**只影响措辞，不影响行为**。
3. **文档与实现不同步**：本分册（08）末尾仍写"**尚未实测**模型是否会真的调用 `emotion_set`"，
   但 R4 分册的工具清单已列出 `emotion_set`、索引页也标"已实测跑通"。→ **应更新 08 的这句**。

### 3.2 记忆管理（R3 / R16 / R17）—— **完整度最高的一块**

| 维度 | 状态 |
|---|---|
| 短期 | ✅ ChatLuna 会话上下文 |
| 过期 | ✅ `autoArchive`（1 小时）—— 针对"隔几小时翻旧账"的正解 |
| 长期 | ✅ HippoRAG + luna-vdb 向量库 + 本地 bge 嵌入 + EMGAS 概念图（跨重启仍在，已验收） |
| 分层 | ✅ Guild / User 两层，按人隔离已验收（主人问得到、陌生人问不到） |
| 写入 | ✅ 三条路：自动抽取 / 模型 `memory_add` / 人工指令 |
| 过期 | ✅ 记忆自带 `expirationDate`（1~10 年） |

**缺口（按影响排序）**：
1. **★ 自动抽取只写 `User` 层（源码写死）** → 想让 bot 记住"群里发生的事"，
   只能靠模型自己 `memory_add` 时显式指定 `layer:["guild"]`。**群层记忆实际上很难积累**，
   这直接影响"基于群聊内容的长期记忆"（R3 原意）的达成度。**这是最值得改进的一条。**
2. **不 @ 不记**（坑 28）：没轮次就没抽取。群聊记忆稀薄的根因之一。
3. **检索质量受嵌入模型上限**：bge-small-zh 512 维，中文够用但非最强；离线零依赖是刻意的取舍。
4. **备份三件套容易漏**（docstore 表 + vector_store 目录 + hippo 图），运维要写进清单。

### 3.3 活跃机制（R9 / R10 / R11 + R15）—— **可用，但缺一道总闸**

| 维度 | 状态 |
|---|---|
| 聚合 / 延迟 | ✅ 内建 `messageQueue` |
| 跟进触发 | ✅ `chatluna-followup`（按群覆盖 + 整群熔断，限流事故后已修） |
| 主动插话 | ✅ `chatluna-proactive`（活跃度 + 空闲双触发，阈值爬升，免打扰） |
| 会话生命周期 | ✅ `chatluna-scene`（模型自开局/收局，收局真清上下文，避开回合内死锁） |
| 快速静默 | ✅ `chatluna-guard`（四道闸门，`闭嘴`一句话秒级生效） |

**缺口**：
1. **缺全局出站速率闸**（见 2.2 高风险项）——这是 2026-10-02 限流事故的**真正教训**：
   只堵了 followup，其它出站口（普通 @ 回复、proactive）仍无总闸。
2. **真群参数沿用测试群思路**，文档已提醒"真群和测试群要分开配"，目前只有 followup 分了档，
   **proactive 的真群档仍需调紧**。
3. scene 与 proactive 无显式联动（正在玩游戏时不应"空闲起话头"）——目前靠提示词让模型自己看 `{scene()}`。

### 3.4 识图功能（R6 / R7 / R8）—— **核心完整，去重口径要统一**

| 维度 | 状态 |
|---|---|
| 私聊 | ✅ 阻塞解析后回复 |
| 群 @ / 引用图 | ✅ 引用自动递归，不需特判 |
| 群不 @ | ✅ 未解析图整段删除（成本保护） |
| 缓存 | ✅ sha256，命中零 API |
| 并发 | ✅ `Promise.all` + `inflight` 合并 |
| 压缩 | ✅ sharp 长边 1024 / q85 |

**缺口**：
1. **★ 缓存是 `sha256` 精确匹配，不是感知哈希**。同一张图被**转发/重压/换格式** → 字节变了 →
   重新烧一次视觉调用。而 sticker 用的是 **pHash**。**两套去重口径不统一**，
   建议 vision 复用 pHash（或直接查 sticker 的库）。
2. **`visionModel` 是 `-exp` 实验版**，通用性/长期可用性存疑，需盯着。
3. **群聊路径其实已实测**（09 分册第二节覆盖三条场景），但 **06 分册的"⭐ 眼下该做的第一件事"仍写着"只实测过私聊"** → **文档滞后，应更新**。

### 3.5 表情包（R5 / R7）—— **可用，注意隐性成本**

| 维度 | 状态 |
|---|---|
| 收集 | ✅ 群图全收（不需 @） |
| 去重 | ✅ pHash 汉明距离 ≤5 |
| 判断/打标 | ✅ 多模态模型判"值不值得收藏" + tags/description/usageHint |
| **发送** | ✅ `sticker_send` 工具**真的把图发出去**（这是它胜过 emojiluna 的决定性理由） |
| 清理 | ✅ TTL + 按最久未使用淘汰 |

**缺口**：
1. **与 vision 插件重复劳动**：同一张群图会被**两个插件各下载一次**，
   若同时满足条件（图出现 3 次 + 被 @ 引用）会**各烧一次视觉调用**。
   建议：让 vision 与 sticker **共用一份图库/缓存**，或把 sticker 的收集关掉只留 vision 缓存。
2. **`judgeModel` 默认值是坏的**（少平台前缀），必须显式配——已在配置里做对，但要写进新环境 checklist。
3. **与情绪/场景无联动**（"烦躁时更爱甩图"），目前只靠提示词提示。
4. 只支持"从已有库里挑一张"，不能生成新表情。

## 四、总体看法（可直接执行的建议，按优先级）

| 优先级 | 建议 | 类型 |
|---|---|---|
| **P0** | 加**按群出站令牌桶**（所有出站路径的总闸），把"只堵 followup"升级为"全局防限流" | 稳定性（限流事故的直接教训） |
| **P0** | 更新三处**文档与实现不同步**：08 的"emotion_set 尚未实测"、06 的"群聊路径只测过私聊"、索引页"阶段 2 第 1 步"表述 | 文档可信度 |
| **P1** | 真群 `activityThreshold` 0.6 → **0.7**，`activityMessageInterval` 60 → **120** | 体验（别刷屏） |
| **P1** | vision 与 sticker 的**图片去重口径统一为 pHash**，并消除重复下载/重复视觉调用 | 成本 |
| **P1** | 让**群层记忆真的能被自动写入**（改写不了源码，就加一个"群聊定期摘要 → memory_add guild 层"的小任务） | 功能完整性（R3 原意） |
| **P2** | 群聊消息队列延迟 3s → 2s，或对纯文字消息跳过窗口 | 体验 |
| **P2** | 情绪/表情包与行为联动：心情高 → 主动发言阈值略降；烦躁 → 更倾向甩图 | 拟人度 |
| **P2** | 加一个"单轮 API 预算"中间件，超限降级（跳过 sticker 判断 / 记忆抽取） | 成本可控 |
| **P3** | 免打扰按群覆盖；情绪从"群级"细化到"人级" | 打磨 |

## 五、结论一句话

**链路机制是完整的，且大部分关键判断（闸门顺序、聚合复用、记忆分层、情绪过期）
都是从源码实证来的、质量很高；真正的短板不在"有没有功能"，而在三处：
① 出站限流只堵了一个口；② 群层长期记忆实际上写不进去；③ 图片去重两套口径。
这三条修完，这套机制就从"能跑"进入"能长期养在真群里"。**

## 一、权限机制调研（实现前）

（这部分是实测出来的，不是推断，设计 R13 时直接用）

### 1. 数据模型

sqlite 里 5 张表，`@koishijs/plugin-admin` 自带：

| 表 | 关键列 | 用途 |
|---|---|---|
| `user` | `id, name, authority, permissions, locales` | 用户；**`authority` 就是 0–4 等级** |
| `group` | `id, name, permissions` | **用户组**（R13 的"管理员组"就建在这） |
| `perm_track` | `id, name, permissions` | 用户组路线 |
| `channel` / `binding` | — | 频道 / 账号绑定 |

**关键发现：组成员关系不是一个关联表，而是写在 `user.permissions` 里的 `group:<id>` 标记**
（逗号分隔）。Koishi 启动时就是这么查的，日志原文：

```sql
SELECT count(distinct `id`) FROM `user`
WHERE (',' || `permissions` || ',') LIKE '%,group:1,%'
```

### 2. 控制台操作路径

`http://127.0.0.1:5140/admin/`（侧边栏双人图标）→ 右上角 `+` 建用户组 →
选中组后有 **「用户管理」（添加用户）** 和 **「权限列表」（添加权限）** 两块。

- 「权限列表」填的是**指令名**，即"这个组能用哪些指令"
- 「用户管理」把具体 QQ 用户加进组

### 3. 已确认的 authority 门槛样例

框架和插件注册指令时都带 `authority`，实测看到的：

| 指令 | 门槛 | 出处 |
|---|---|---|
| `plugin.install <name>`（别名 `.i`） | **4** | `@koishijs/plugin-market` |
| market 的 DataService 本身 | **4** | `super(ctx, "market", { authority: 4 })` |

→ **R12 的"装插件"环节框架已经自带并卡在最高等级**，不用自己写。

### 4. 待设计（还没做）

0–4 五个等级各自对应谁、哪些指令放哪一级、普通群友默认哪一级。

## 二、R13 权限分级：已实现并端到端验收（自写插件）

### 需求原文

> 「对 bot 发出的命令需要有权限校验，比如某一些命令必须管理员权限才能使用，
> 而其他的普通群友也能随便使用」

### 产物

`koishi-app/external/koishi-plugin-qqbot-auth/`（`lib/index.js`，约 420 行）
生产配置已接上：`qqbot-auth:auth01`，`ownerIds: ['2791932480']`。

### 五级模型

| 等级 | 名字 | 能力 |
|---|---|---|
| 4 | 主人 | 装卸插件、开关指令、`/权限设置` 授权。框架已把 `plugin.install/uninstall/upgrade` 卡在 4 |
| 3 | 管理员 | 删会话 / 停对话 / 切模型 / 换预设 / 清空 / 归档 … |
| 2 | 信任 | 查长期记忆（`/chatluna.memory.search`）；其余预留给 R4 好感度 |
| 1 | 普通 | **默认等级** |
| 0 | 拉黑 | 连 `/权限我的` 都拒绝 |

### ★ 五条实测出来的硬事实（都踩过，别再凭印象改）

1. **`autoAuthorize` 默认就是 1**（`koishi/lib/index.cjs:2433`，
   `Schema.natural().default(1)`）。任何给 bot 发过消息的人都会自动建 user 行并拿到 1 级。
   而且这个值**只在建行时写一次**（`core:1916`，`getUser` 查不到才用），
   改配置不影响已有行 —— 想降级必须显式写库。
2. **权限判定的语义是 `!user || user.authority >= +value`**（`core:2127`）。
   `!user` 直接放行，所以**别指望靠"库里没这行"来拦人**。
3. **一个指令的有效门槛 = 它自己与所有祖先上 `authority:N` 的最大值**
   （判定时整条链都要过）。只看自己的 `config.permissions` 会漏。
4. **`/命令/子命令` 这种写法在 Koishi 里根本不存在**。
   `Argv.parse` 只按**空格**切词，`Commander._resolve` 再按**点号**拆段
   （`core:1432-1439`）。所以 `/chatluna/stop`、`/权限/我的` 一律解析不到，
   只有 `/chatluna.stop`、`/权限.我的` 有效。**中文名一律用扁平单 token 别名**
   （`权限我的`、`权限设置`），不带任何分隔符。
5. **`c.name`、别名、用户实际敲的写法三者可能都不一样**：
   - `ctx.command('emotion/set …')` 里的 `/set` 是**下一层的名字**，
     注册出来是 `emotion` 的子指令 `set`（名字=别名=`set`），
     **`emotion.set` 这个名字压根不存在**；
   - 而 `chatluna.admin.purge-legacy` 的 `c.name` 是它自己，用户却敲 `chatluna.admin`。
   → 要按"用户能敲出来的名字"解析（`ctx.$commander.get(spec)` 会同时查名字与别名），
   层级复杂的用 `父名>子名` 下钻 `parent.children`。

### 怎么做的

**(a) 名单 → authority**：挂在 `attach-user` 钩子上。这个钩子在 `session.observeUser()`
**之后**触发（`core:803-804`），此时 `session.user` 已存在且被 observe 包裹 ——
改 `authority` 会被自动写回数据库，同时又早于指令解析，当次消息即生效。
实测落库正常（测试库 `10002→3`、`10003→3`、`10004→0`、`2791932480→4` 全部持久化）。

**(b) 危险指令提权**：ChatLuna 把一批**破坏性指令只挂在 1 级**，任何普通群友都能触发：

```
chatluna.delete / stop / restart / wipe / switch / rollback / archive /
use.model / use.preset / voice
```

其中 `/chatluna.stop` 能让 bot 停止回话、`/chatluna.delete` 能删掉别人的会话、
`/chatluna.use.model` 能把全群的模型换掉 —— 这正是 R13 要解决的核心问题。

做法是**运行期改 `cmd.config.permissions = ['authority:3']`**。
实测生效，因为权限判定每次读的都是该属性的当前值（不是建指令时的快照）。

扫描时机很关键：ChatLuna 的指令注册在**嵌套的第二个 `ready`** 里
（`chatluna lib:8109`），一次扫描抓不全 → 启动后按 `scanSeconds`（默认 120s）
每 2 秒重扫，一旦所有规则命中就自行停止（实测：生产实例首轮扫描就命中，
日志 `提权规则已全部命中（指令表 67 条；其中 6 条本来就达标、未改动），停止重扫`）。
指令表是**扁平**的（`Commander._commandList`，`core:907`），别套 `children` 递归。

**(c) 自带 `/帮助` 与 `/回声`**：框架的 `@koishijs/plugin-help` 与
`@koishijs/plugin-echo` 在本组合下**根本没进指令表**
（`ctx.$commander.get('help')` 查不到，`/help`、`/echo` 都解析不出来）。
这两个对本需求（"普通群友也能随便用"）是必需的，所以本插件自带一份。

### 依赖与坑

- **★ 提权表里的"指令名"不能凭直觉写 —— `c.name`、别名、用户实际敲的写法三者可能都不一样。**
  两种都踩过：
  - `ctx.command('emotion/set …')` 里的 **`/set` 是"下一层的名字"**，
    实际注册成 `emotion` 的子指令 `set`（名字和别名都是 `set`）。
    **`emotion.set` 这个名字根本不存在**，`get('emotion.set')` 永远查不到。
    本插件用 `'父名>子名'`（如 `emotion>set`）表达这种父子关系。
  - 反过来 `chatluna.admin.purge-legacy` 的 `c.name` 是它自己，
    但用户实际敲的是 `chatluna.admin`。
  - **还有第三种：点号注册的子指令，`c.name` 是"完整路径"。**
    `ctx.command('a.b.c')` 会被按 `/(?=[./])/` 切成 `['a', '.b', '.c']`，
    点号段走 `parent.name + 段`（`core:1491`），所以子指令名字是 `a.b.c` 而不是 `c`；
    而斜杠写法的 `ctx.command('a/c')` 只取最后一段 `c`。
    R3 时就栽在这：提权表里写了 `chatluna.memory>add`，
    而 `resolveCmd` 当时只比 `c.name === 'add'` → 四条规则**扫了 120 秒都没命中**，
    日志 `重扫到时（120 秒），这些指令一直没注册出来`。现在两种都比。
  - 结论：**按"用户能敲出来的名字"解析**（`ctx.$commander.get(spec)` 会把名字与别名
    都查一遍），复杂层级再用 `>` 手动下钻到 `parent.children`。
    **点号层级直接用全名即可，`>` 只对斜杠写法需要。**
  - 排查这种问题最快的办法：启动后把 `_commandList` 逐条打出
    `name / aliases / parent / 有效等级`（本插件 `debug: true` 时会打一份摘要）。
- **`module.exports.inject = ['database', 'commands']` 会让插件永远不被 apply**。
  这两个服务名在本环境里解析不到，cordis 就静默跳过（现象：日志有
  `loader apply plugin …`，但插件自己一行日志都没有，极难查）。**别写 `inject`**，
  用 `ctx.get('database')` 在动作里取。
- **别用 `app.plugin` 打桩做诊断**。`OneBotBot` 是 class，被包成普通函数后
  `new` 会抛 `Class constructor OneBotBot cannot be invoked without 'new'`，
  适配器整个坏掉 —— 现象是"所有指令都没反应"，会把人带到完全错误的方向（本轮的坑）。
- **别在 `before('parse')` 里调 `ctx.bail('before-parse', …)`**：递归，
  日志刷屏并最终 `Maximum call stack size exceeded`。
- 别名注册的 `options` 是**直接存进 `_aliases[name]`** 的，`inferCommand` 会把它
  **整体**赋给 `argv.args`（`core:1456`），随后 `Command.parse` 又把解析结果 push
  到同一数组后面（`core:372`）。所以 `alias(name, { args: [声明对象] })` 会让
  handler 的第一个参数变成声明对象本身。**别名的 `args` 给空数组即可**，
  参数声明只写在主命令名的 `def` 里。
- `ctx.command()` 返回的是**叶子**对象；父指令相当于分组，**必须自己挂 action**，
  否则单独发 `/权限` 会"解析成功但返回空串" —— 现象和没反应一模一样。
- 指令的**参数名会从别名里被剥掉**：`CMD_HELP` 里写 `/权限设置 <QQ号> <0-4>`
  发出去会变成 `/权限设置`（`<…>` 被当作参数声明吃掉）。要显示字面尖括号得避开这种写法。

### 调参入口

控制台 `/plugins/` → `qqbot-auth`：`ownerIds` / `adminIds` / `trustedIds` /
`blockedIds`（数组，填 QQ 号字符串）、`raiseDangerousCommands`（默认开，
**关掉等于把停对话/改模型的能力放给所有人**）、`scanSeconds`、`debug`。

# 网页预览（第十四轮）

> 属于 [QQ 机器人项目 —— 进度与交接](../进度与交接.md) 的分册。
> 用户原话（2026-10-06）：**「我想要给 bot 提供你的网页 preview 插件功能」** ——
> 即把 DSH 里那套 `browser_open / browser_screenshot / browser_read` 搬给机器人。

---

## 1. 一句话总览

**给机器人一双"真的会开网页"的眼睛**：给它一个网址，它用本机浏览器（Edge，经 `ctx.puppeteer`）
真的把页面打开、渲染、截图发到会话里；同时把**渲染完成之后**的正文交给模型。

| 通路 | 谁触发 | 出图 | 花 API | 默认 |
|---|---|---|---|---|
| 指令 `webpreview.get <网址>` | 群友/自己敲 | ✅ 一张图 | **不花** | 开 |
| 指令 `webpreview.text <网址>` | 同上 | ❌ 纯文字（正文） | **不花** | 开 |
| 指令 `webpreview.status` | 同上（3 级） | ❌ 状态 | 不花 | 开 |
| 工具 `web_preview` | **模型自己决定** | ✅ 一张图 + 正文摘要 | 花 | 开（可关、可按群限） |
| 自动预览 | 群里有人贴链接 | ✅ 一张图 | 不花 | **关**（要显式打开并配群） |
| 服务 `ctx.chatlunaWebPreview` | 别的插件调用 | —— | —— | 开 |

**它不是"又一个渲染插件"**：`chatluna-render` / `chatluna-page` 渲的是**模型/指令给的字符串**，
从不访问网址；这一件专门做「**真实网址 → 浏览器**」。

## 2. 硬约束第 0 条的取证（先本地 → 再市场 → 最后自写）

### 2.1 ① 先查本地：能力在，但**缺口是确定的**

| 已有的 | 它做什么 | 为什么不够 |
|---|---|---|
| `koishi-plugin-puppeteer@3.9.0` | 提供 `ctx.puppeteer.page()` | 只是"能力"，没有任何指令/工具/防护 |
| `chatluna-render`（自写） | 模型给的 HTML/Markdown → 图 | 走的是 `page.setContent`，**从不访问网址**；默认关 JS、拦掉一切外部请求 |
| `chatluna-page`（自写） | 指令输出 → 图 + 图片库 | 同上，只处理文本 |
| `mcp/websearch-server.cjs` 的 `web_browse` | 抓网址 → 洗干净的**正文** | **没有浏览器**：纯正则抽正文，JS 渲染的站直接返回 `(正文为空：可能是 JS 渲染页面…)`（见 [模型总览与联网搜索](27-模型总览与联网搜索.md) §5 与 `.scratch/mcp-websearch-notes.md` §5.1） |

⇒ **"访问真实网址并出图"这件事，本地一件都没有。** 缺口明确。

### 2.2 ② 再查市场：6 个指名候选 + 2 个关键新发现，逐个看过源码

方法：`npm pack` 下真源码解包读（探针物料在 `.scratch/webpreview-probe/`，
含 4727 包全量快照 `registry.json`、152 条强相关命中、16 个包的真实源码）。

| 候选 | 触发方式 | 怎么抓 | SSRF 防护 | 能给模型调 | 结论 |
|---|---|---|---|---|---|
| `screenshot-links@1.0.3` | 指令 + 中间件（`workmodel` 默认 `allways`） | `ctx.puppeteer` | ❌ 白/黑名单默认空数组，无私有 IP 逻辑；`formatUrl` 还会把 `127.0.0.1:3080` 补成合法 URL | ❌ 不注册工具、不导出 service | 最接近用户要的形态，但**不可调用 + 裸奔** |
| `screenshot@1.0.5` | 仅指令 `shot` | `ctx.puppeteer` | ⚠️ 只做协议白名单，**但留了官方钩子 `screenshot/validate`**（市场里唯一为防护预留的扩展点，无人实现） | ❌ | 引擎好，缺 LLM 通道 |
| `capture-website@1.5.5` | 指令 | **自建浏览器**（`exports.using = []` 完全绕开 `ctx.puppeteer`） | ❌ 还接受 **`file://`** | ❌ | 依赖是 **git 地址**（大陆无代理装不上）+ 2022 年停更 → 排除 |
| `og@1.3.2` | 任意含链接消息 | **无浏览器**，`ctx.http` + cheerio，只复述页面自带的 `og:image` | ❌ `ignored` 默认 undefined = 不设防 | ❌ | 不截图；没 OG 标签就零输出 |
| `og-fix@1.2.5` | `ctx.middleware` | 全局 `fetch`（**不走代理**） | ❌ | ❌ | `exports.name = 'OpenGraph'` 与 `og` **同名冲突**；`forEach(async)` 不 await + 空 catch 吞错 |
| `discourse-linkshot@1.0.7` | middleware | 自建 playwright-core | ✅ 但只认**一个** `forumOrigin` | ❌ | 只服务指定论坛，对任意网址零覆盖率 |
| ★ `chatluna-search-service@1.4.0` | **22 个原生工具** | `ctx.puppeteer` | ❌ **零 URL 校验**：`page.goto(input.url)` 直接走 | ✅ | 「模型驱动浏览器」市场**已解决**，但 `browser_screenshot` 只 `writeFile` 后**返回路径字符串** —— 聊天里没有图；且强制 peer `chatluna-agent` + AGPL |
| ★ `chatluna-gemini-tools@0.0.5` | `url_context` 工具 | Gemini API（不是本机浏览器） | ✅ 完整实现 | ✅ | 只回文字、要 Gemini key，与"本机截图"不是一回事（**它的 URL 校验可作为写法参考**） |

**结论**：市场里「**模型驱动浏览器**」有人做了（`chatluna-search-service`），
「**截图变成图片发进聊天**」和「**内网 SSRF 防护**」**没有人做**。
后者正是本项目必须自己承担的那一半（这台机器上 3001/5140/6099 全是只绑 127.0.0.1 的敏感端口）。

### 2.3 ③ 自写：只写最薄的一层适配

和 `chatluna-render` 同一个套路 —— **渲染能力继续用市场插件**（`koishi-plugin-puppeteer`），
自写的只有三件事：

1. **网址安全校验（SSRF）+ 渲染 + 截图 + 取正文** → 包成稳定服务 `ctx.chatlunaWebPreview`；
2. **ChatLuna 工具 `web_preview`**（模型可自己决定"这个链接截个图看看"）；
3. **指令 `webpreview.get / .text / .status / .test`**（不花 API 的确定性通路，也是测试台的抓手）。

规模：`koishi-app/external/koishi-plugin-chatluna-webpreview/lib/index.js` 一个文件。

## 3. 安全：SSRF 是这里的头号风险

「服务端去访问一个**别人给的**网址」是 SSRF 的教科书场景。这台机器上
NapCat 的 3001、Koishi 的 5140、NapCat WebUI 的 6099 **全都绑在 127.0.0.1** ——
只要能让机器人去"预览" `http://127.0.0.1:6099/…`，就等于把控制台送给群友。

> ⚠️ **代理不是防护**：Chromium 对 loopback 有**隐式直连绕过**，就算配了 `--proxy-server=http://127.0.0.1:7890`，
> 访问 `127.0.0.1:3080` 照样通。必须靠显式校验。

### 3.1 四道闸

| # | 闸门 | 实现 |
|---|---|---|
| 1 | **协议** | 只允许 `http:` / `https:`，其余（`file:`/`ftp:`/`data:` 页面导航）一律拒 |
| 2 | **主机名** | `localhost` / `*.localhost` / `*.local` / `*.internal` / `*.lan` / `*.home`、十进制整数形式（`http://2130706433/` = 127.0.0.1）、`0x…` 形式，一律拒 |
| 3 | **IP 字面量** | IPv4：`0/8`、`10/8`、`127/8`、`169.254/16`（含云元数据 `169.254.169.254`）、`172.16/12`、`192.168/16`、`100.64/10`（CGNAT）、`192.0/24`、`198.18-19`、`≥224`（组播/保留）；IPv6：`::`、`::1`、`fc00::/7`、`fe80::/10`、`2001:db8`、IPv4 映射地址 |
| 4 | **DNS 解析** | 域名要 `dns.lookup({all:true})` **逐个地址**检查（防"域名解析到内网"与 DNS rebinding） |

追加两道：

* **跳转后复查**：`page.goto` 之后再看一眼**最终 URL** —— 否则「公网 URL 302 到 127.0.0.1」就绕过了前面全部检查；
* **页面内请求拦截**：`page.setRequestInterception(true)` + `request` 事件，非 http(s)、私有主机字面量、
  `media` 资源一律 `abort()`（最后一条只是为了别去下视频）。

`blockedHosts` 是配置层的额外黑名单（含子域）。

### 3.2 唯一的例外开关

`allowPrivateHosts`（默认 **false**）= 允许访问本机/内网，**只给自动化测试台用**
（测试台要预览 127.0.0.1 上的假页面）。打开时启动日志会**额外打一行警告**，
`webpreview.status` 里也会显示成 `**允许（测试台专用！）**`。

## 4. 实现细节（都是量出来的，不是猜的）

### 4.1 `clip` 与 `fullPage` 在 puppeteer 22 里**互斥**

第一版整页截图写的是 `page.screenshot({ fullPage: true, clip: {...} })`，实测直接抛：

```
Error: 'clip' and 'fullPage' are mutually exclusive
```

（`.scratch/probe-webpreview.cjs` 复现）。所以整页模式改成
`{ clip: { x:0, y:0, width, height: min(内容高, maxCaptureHeight) }, captureBeyondViewport: true }` ——
高度自己量、自己裁，顺带就有 `maxCaptureHeight` 上限，不会出现一张几万像素高的图。

### 4.2 体积：**像素密度是旋钮**（与 `chatluna-page` 同一个结论）

`.scratch/bench-webpreview.cjs` 三个站 × 三档（2026-10-06 实测）：

| 站点 | 1024px / 1.0x | 1280px / 1.0x | 1024px / 1.5x |
|---|---|---|---|
| example.com（极简） | 49 KB | 50 KB | 89 KB |
| baidu.com | 101 KB | 105 KB | 168 KB |
| news.qq.com（首屏） | 381 KB | 406 KB | 702 KB |
| news.qq.com（整页 1967px） | 1218 KB | 1386 KB | 2392 KB |

⇒ 默认 `viewportWidth: 1024` + `deviceScaleFactor: 1` + **首屏模式**（100~400 KB，手机 QQ 上够看）。
另外留一条兜底：PNG 超过 `maxBytes`（默认 700 KB）就**再截一张 JPEG(q82)**，哪个小用哪个 ——
上面那张整页图 PNG 1218 KB、JPEG 337 KB（**省 72%**）。

> ⚠️ **整页高度以页面自己报的 `scrollHeight` 为准**：`news.qq.com` 量出来 1967~2458px（截得到），
> 而**百度首页量出来就等于视口**（整页布局是视口高、内容在内层容器里滚）——
> 那时整页模式截出来与首屏一样高是**正确行为**。第一版验收脚本拿百度当判据，
> 把一个正确行为判成了失败（见 [踩坑记录](04-踩坑记录.md) 坑 75 的后半段）。

### 4.3 正文从哪来：`innerText`，不是正则

`page.evaluate` 里取 `document.body.innerText`（浏览器渲染**之后**的可见文本）+
`document.title` + `og:description`/`description`。
这正是 `web_browse` 做不到的那部分 —— 它拿的是原始 HTML 再正则抽，JS 渲染的站是空的。

### 4.4 JS 默认**开**（与 `chatluna-render` 相反）

`chatluna-render` 默认 `allowJavaScript: false`（它渲的是模型给的字符串，开 JS 只会挨打）。
**这里必须开**：真实网页大半是客户端渲染的，关掉就只剩骨架。
页面跑在 Chromium 沙箱里，且所有请求仍过 §3.1 的拦截。

### 4.5 占资源的闸门（模型连调也不怕）

* `maxConcurrent: 2` —— 自己实现的小信号量（`ctx.puppeteer.page()` 本身**没有上限**，
  群里几个人同时贴链接就会同时开一堆页面，每个几十 MB）；
* `queueWaitMs: 8000` —— 排不上队就回一句"预览队列满了"；
* `toolCooldownSeconds: 20` —— 同一个群里模型两次 `web_preview` 的最短间隔
  （**失败不占冷却**，让模型能换个网址重试）；
* 出站那一段交给 `chatluna-guard`（它才是总闸，本插件不重复造）。

### 4.6 代理：不是代码，是配置

`koishi-plugin-puppeteer` 的启动代码里写着（`src/index.ts:37-41`）：若 `ctx.http.config.proxyAgent` 存在，
它会**自动**追加 `--proxy-server=<那个代理>`。而本项目 `koishi.yml` 的 `proxy-agent` 段是 `{}`
（[坑 17](04-踩坑记录.md) 说了：`{}` 等于没配）—— 所以浏览器实际走的是**系统代理/直连**。

本机实测（`.scratch/probe-webpreview.cjs`）：**不加 `--proxy-server` 也能打开 example.com / baidu.com**，
所以没有动配置。但插件启动时会把这件事实打出来（有代理 / 没代理各一行），
哪天外网站点大面积超时，照那行提示在 `puppeteer.args` 里补 `--proxy-server` 即可。

## 5. 配置速查（`koishi.yml`）

```yaml
  chatluna-webpreview:wpv001:
    enabled: true
    toolEnabled: true          # 注册 web_preview 工具（模型可自己调）
    groups: []                 # 空 = 不限群；填了就只有这些群能看见这个工具
    toolCooldownSeconds: 20
    autoEnabled: false         # ★ 自动预览默认关（原因见下）
    autoGroups: []             # 自动预览生效的群
    autoCooldownSeconds: 60
    viewportWidth: 1024
    viewportHeight: 768
    deviceScaleFactor: 1       # ★ 体积主旋钮
    mode: viewport             # viewport（首屏）| full（整页，受 maxCaptureHeight 限）
    maxCaptureHeight: 3000
    maxBytes: 700000           # 超过就改截 JPEG，哪个小用哪个
    allowJavaScript: true      # 真实网页必须开
    allowPrivateHosts: false   # ★★ 生产必须 false（测试台才开）
    blockedHosts: []
    timeout: 30000
    idleWaitMs: 2500
    maxConcurrent: 2
    maxTextChars: 6000
    debug: false
```

**为什么自动预览默认关**：本项目 2026-10-02 刚因为刷屏被腾讯限流过
（[接入第一个真实群 + 第一次限流事故](16-真群接入与限流事故.md)），
「每条链接都出一张图」在活跃群里等于自找限流。要用就显式打开 `autoEnabled` **并**指定 `autoGroups`，
`autoCooldownSeconds` 兜住频率；自动预览**失败一律安静**（群里没人要它做这件事，报错就是刷屏）。

## 6. 与别的东西的分工（别混）

| | `web_browse`（MCP） | `web_preview`（本插件） | `chatluna-render` |
|---|---|---|---|
| 输入 | 网址 | 网址 | 模型/指令给的 HTML·Markdown |
| 出网 | `fetch`（带代理） | **浏览器**（能跑 JS） | 不出网 |
| 产物 | 纯文本正文 | **图片** + 渲染后正文 | 图片 |
| 贵不贵 | 便宜、快 | 贵、慢（起页面 3~5s） | 便宜 |
| 适合 | "读一篇文章" | "这页长什么样"、JS 渲染站 | 表格/卡片 |

`chatluna-page` 只把**纯文本**消息换成图片（它自己的注释：「`render_image` 工具发出来的图、
sticker 发的表情包都是非纯文本，天然不受影响」），本插件返回的是 `h.image(...)`，不会被它二次加工。

* 第一轮（21:25）：**模型确实自己调了** ——

⇒ 所以 F 是**软判据**：不调不等于坏，但**两轮日志一起看，"模型会用这个工具"是有据可查的**。

**A/B 对照（最有说服力的一条）**：第一轮跑 rig 65 时插件**还没装进测试实例**（见坑 77），
模型对同一个请求的思考过程是 ——


## 8. 这一轮踩到/修掉的坑

1. **`clip` 与 `fullPage` 互斥**（puppeteer 22）—— 见 §4.1 与 [踩坑记录](04-踩坑记录.md) **坑 75**。
2. **中文标点必须当 URL 分隔符** —— 群里发「看这个 https://a.com/x），挺好的」，
   按空白切会抽出 `https://a.com/x），挺好的`，`new URL()` 把中文当成路径，预览必然失败。
   正则里显式排除 `，。；：！？、（）【】《》「」『』…·`（[踩坑记录](04-踩坑记录.md) **坑 76**）。
3. **测试实例的 `node_modules` 不是 junction 到 `koishi-app/node_modules`**（虽然 `setup-test-app.cjs`
   当初是这么建的），而是**真实目录 + 每个外部插件一条独立 junction**（532 项）。
   新插件只建 `koishi-app\node_modules` 那条，测试实例会报
   `[E] app cannot resolve plugin "chatluna-webpreview"` —— **两条都要建**（[踩坑记录](04-踩坑记录.md) **坑 77**）。
4. **`run-prod.cjs --takeover` 单独用根本不动手**（[踩坑记录](04-踩坑记录.md) **坑 78**）：
   修前只能用 `--takeover --kill-orphans`，现在与文档一致。

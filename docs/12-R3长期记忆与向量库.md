# R3 长期记忆（现成插件）

> 属于 [QQ 机器人项目 —— 进度与交接](../进度与交接.md) 的分册。
> 旧编号（如「第八·十三节」）的去向见索引页的章节对照表。

`chatluna-long-memory` 1.4.0 + Emgas/HippoRAG + 真向量库。**R16 知识过期（第二部分）与 R17 向量库（第三部分）是这条线的续集。**

### 需求原文

> 「长短期记忆（基于群聊内容）」——短期 = 会话内的上下文（ChatLuna 本来就有）；
> R3 要补的是**跨会话的长期记忆**：bot 得记得住以前聊过的事，还得记得住"谁说过什么"。

### 产物：`koishi-plugin-chatluna-long-memory@1.4.0`（**不是自写**）

```
koishi-app/node_modules/koishi-plugin-chatluna-long-memory/   ← npm 装的，1.4.0（与 chatluna 1.4.0 同版本线）
koishi-app/data/chatluna/long-memory/emgas/<id>.json          ← EMGAS 记忆图（每层一个文件）
koishi-app/data/koishi.db → chatluna_docstore 表              ← 记忆正文就存在这张表里
```

配置（生产 `koishi.yml` 的 `chatluna-long-memory:lm0001`）：

```yaml
enabledLayers: [Guild, User]          # 群层 + 用户层
layerEngines:
  - { layer: Guild, engine: Emgas }   # ★ 不能留默认的 HippoRAG，见下
  - { layer: User,  engine: Emgas }
longMemoryExtractModel: deepseek/deepseek/deepseek-v4.1-flash-fast
longMemoryExtractInterval: 3          # 每 3 轮抽一次记忆
longMemoryQueryRewrite: false         # ★ 关掉，否则每次回话前多一次模型调用
emgasExtractModel: deepseek/deepseek/deepseek-v4.1-flash-fast
```

### ★ 为什么是 Emgas 而不是默认的 HippoRAG（本轮最重要的判断）

插件有三种记忆引擎，默认表给 Guild/User/Preset 配的是 **HippoRAG**：

| 引擎 | 检索方式 | 要不要 embedding / 向量库 |
|---|---|---|
| `Basic` | 全量塞进上下文（不检索） | ❌ 不要（只用 `DataBaseDocstore`） |
| `HippoRAG` | 向量召回 + 图上的 PPR 随机游走 | ✅ **要**（`createVectorStoreRetriever` → `ctx.chatluna.createEmbeddings(...)` + `platform.createVectorStore(...)`，见插件 `lib/index.cjs:2027-2053`） |
| `Emgas` | 概念图 + 扩散激活 + 时间衰减/剪枝 | ❌ **不要**（用 `DataBaseDocstore` + 本地 jieba 分词抽概念，`lib/index.cjs:2503-2565`） |

而**本项目的模型中转（commandcode）84 个模型里一个 embedding 模型都没有**
（`/models` 过滤 `embed|bge|m3e` 命中 0），ChatLuna 的 `defaultEmbeddings` 默认是 `"无"`。
→ 选 HippoRAG 会在 `chatluna/before-chat` 里直接抛错，记忆整条链废掉。
→ **选 Emgas：零外部依赖，还有衰减/剪枝（比 Basic 的全量塞强得多）。**

> 想要真正的语义检索（HippoRAG）需要：一个 embedding 模型 + 一个向量库
> （`chatluna-vector-store-service` 的 `luna-vdb` 是本地 Rust 实现，不用外部服务）。
> 现在没有可用的 embedding 来源，这条路留着以后接（自建 Ollama / 换带 embedding 的中转）。

### 记忆是怎么进去、怎么出来的（读源码得到的准确链路）

```
① 存（三条路）
   a. 自动抽取：`chatluna/after-chat` 钩子，每 longMemoryExtractInterval 轮调一次
      longMemoryExtractModel 把对话提炼成结构化记忆（type/importance/expirationDate）
   b. 模型自己调工具：memory_add / memory_search / memory_delete / memory_update
      （预设里已明确指示"值得记的事就调 memory_add"）
   c. 人敲命令：/chatluna.memory.add|search|delete|clear|edit
② 取：`chatluna/before-chat` 钩子按当前消息检索各层 → 塞进 promptVariables
③ 进提示词：插件用 `registerFunctionProvider('long_memory', …)` 暴露 `{long_memory()}`，
      预设里写上就会被渲染成 "## User Memories / ## Guild Memories" 文本
```

### ★ 两个必须知道的硬事实

1. **自动抽取只写 `User` 层**（源码写死的）：
   `if (!defaultLayerTypes.includes(USER)) { logger.warn('only support user layer'); return }`
   → **`enabledLayers` 里必须包含 `User`**，否则自动记忆完全不工作（只打一行 warn）。
   群层记忆只能靠**模型自己调 `memory_add` 时指定 `layer: ["guild"]`**。
2. **`layerEngines` 必须覆盖 `enabledLayers` 里的每一层**，否则
   `initMemoryLayers` 抛 `Memory layer xxx not found`。

### ★ 权限分级（已接进 R13）

`chatluna-long-memory` 一装上，ChatLuna 就多出 `/chatluna.memory.*` 一族指令
（注册在 `ctx.inject(['chatluna_long_memory'])` 里，`chatluna lib:579-623`）。
默认全在 `chatluna` 根指令的 **1 级**下，等于**任何群友都能清空 bot 的记忆**，所以提权表加了 5 条：

| 指令 | 等级 | 原因 |
|---|---|---|
| `/chatluna.memory.search <关键词>` | 2（继承父指令） | 读自己的记忆 |
| `/chatluna.memory.add <内容>` | **3** | 会污染 bot 的长期记忆 |
| `/chatluna.memory.delete <id>` | **3** | |
| `/chatluna.memory.clear` | **3** | 一键清空 |
| `/chatluna.memory.edit <id>` | **3** | |

### 调参入口与代价

- 控制台 `/plugins/` → `chatluna-long-memory`：层开关、引擎表、抽取模型、
  `longMemoryExtractInterval`、HippoRAG/EMGAS 各路阈值。
- **每 3 轮对话多一次模型调用**（抽取）→ 用 `deepseek-v4.1-flash-fast`（实测 1.5s，
  对比 `v4.1-flash` 2.7s）。想更省就调大 `longMemoryExtractInterval`。
- **`longMemoryQueryRewrite: true` 会让每次回话前多一次模型调用**（延迟直接加在
  回复上），本项目关掉了 —— 检索查询直接用用户原话。
- 记忆有 `expirationDate`（按类型给 1~10 年），过期由插件每 10 分钟清一次。

### 踩过的坑

- **子指令名是完整点号路径**（`chatluna.memory.add`），不是最后一段 ——
  提权表写成 `chatluna.memory>add` 时四条规则永远不命中（详见[R13 权限分级](07-R13权限分级.md)坑列表新增条）。
- **装完必须在 `koishi-app` 里也 `npm install`**（loader 从应用目录解析插件名）；
  测试实例还要再装一次 + 跑 `npm install`（`tools/gen-test-config.cjs` 会同步依赖与预设）。
- **预设必须自己加 `{long_memory()}`**，插件不会自动往提示词里塞东西 ——
  只在 `promptVariables` 里放了个数组 + 注册了个函数变量。
  忘了加的现象是"记忆库里明明有，bot 就是想不起来"。
- 测试实例的预设是**独立一份**（`koishi-test/data/chathub/presets/`），
  改完生产预设要同步（`gen-test-config.cjs` 现在会自动拷）。
- EMGAS 图文件写在 `<应用目录>/data/chatluna/long-memory/emgas/`，
  测试实例与生产实例各一份，互不干扰。

## 一、R16 知识过期：用 chatluna 自带的 autoArchive

### 需求原文
> 「可以看到 bot 回复了我吃饭相关的话题，但上一次我表达"饿了"的情形已经过了很久了，
>   应该给知识添加过期时间的设置」

### 先查清楚"这句话是从哪来的"（别猜）

`chatluna_message.content` 是 **gzip 压缩的 BLOB**（列类型 blob、前两字节 `1f 8b`），
所以 `LIKE '%饿%'` 永远搜不到 —— 要先解压。写好工具 `tools/peek-memory.cjs` 之后真相是：

| 层次 | 生产库里的实际情况 | 是不是这次的真凶 |
| --- | --- | --- |
| **会话历史**（`chatluna_message`） | 群会话 `f2cf321b` 里**存着 15:54 的原话**：「好饿啊，要消失了」「吃了吗」「吃了。米饭。」 | ★ **就是它**：23:48 那轮回复时它们还在上下文里 |
| 长期记忆（`chatluna_docstore`） | **0 行**（空）；EMGAS 图日志一直说 "No existing EMGAS graph found" | 不是（而且见下面的隐患） |
| 互动状态（`chatluna_scene`） | 空 | 不是 |
| 情绪（`chatluna_emotion`） | 1 行，`updatedAt` 停在 14:38 —— **也没有过期机制** | 潜在隐患，见"还没做的" |

结论：**"知识过期"首先要管的是会话历史**，因为模型每轮都把整条会话的历史塞进上下文。

### 用了什么开关（零代码，chatluna 自带）

源码依据 `koishi-plugin-chatluna/lib/index.cjs:6774-6779`：

```js
infiniteContext:          Schema.boolean().default(true),
infiniteContextThreshold: Schema.percent().min(0.5).max(0.95).default(0.85),
autoArchive:              Schema.boolean().default(false),                    // ★ 默认关
autoArchiveTimeout:       Schema.number().default(Time.day * 10 / Time.second) // ★ 默认 10 天
                            .min(Time.hour / Time.second),                     // ★ 下限 1 小时
autoPurgeArchive:         Schema.boolean().default(false),
autoPurgeArchiveTimeout:  Schema.number().default(Time.day * 30 / Time.second).min(Time.hour / Time.second),
```

`setupAutoArchive`（index.cjs:8228-8277）：**启动时立刻跑一次，然后每 5 分钟一次**，
把 `updatedAt < now - autoArchiveTimeout` 且 `status='active'` 的会话交给
`archiveConversationById(id, cutoff)` 归档。归档 = 快照落盘到
`data/chatluna/archive/<会话id>`（可导出、可恢复）+ `status='archived'`；
**下次说话会另起一条新会话，上下文从零开始。**

生产配置（`koishi-app/koishi.yml` → `chatluna:03llpk`）：

```yaml
autoArchive: true
autoArchiveTimeout: 3600     # 1 小时（schema 下限就是 1 小时，想要更细得自己写，见下）
autoPurgeArchive: false      # 归档的会话要不要在 30 天后彻底删掉（默认关；开了会真的丢聊天记录）
autoPurgeArchiveTimeout: 2592000
```

### 验收（`tools/scenarios/29-guard-cmd-and-ttl.json`，测试台）

1. 前置：`node --experimental-sqlite --no-warnings tools\seed-old-conversation.cjs`
   —— 把群会话做旧到 3 小时前，并塞一条很好认的旧消息「我昨天说我饿了想吃烤鱼」
   （★ 写入时同样要 gzip + JSON 字符串，否则 chatluna 读不出来）
2. 起 Koishi → 启动瞬间：

```
[I] chatluna Auto archive task running
[D] sqlite > UPDATE chatluna_conversation SET updatedAt=?, status=?, archivedAt=?, archiveId=? ... [ 'archived', ... ]
[S] chatluna Successfully archived 1 conversations
```

3. 库里对得上：旧会话 `1730de45` → `archived`，`chatluna_archive` 里多了一条快照
   （`messageCount=20｜size=7498｜state=ready`，目录 `data/chatluna/archive/1730de45-…`）；
   绑定 `shared:onebot:2178517838:454444539` 指向**新**会话 `fb0ab2d4`（active）。
4. 语义验证：接着问它「你还记得我之前说过我饿了想吃啥吗」
   → 新会话里模型调了 `memory_search`，返回 `[]`，**旧话题不再出现**（这就是"过期"）。

### 阈值下限与"更细的过期"（想要的话再做）

chatluna 把 `autoArchiveTimeout` 卡在 **≥3600 秒**，所以"1 小时不说话就翻篇"是它的最细粒度。
要更细（比如 20 分钟就不许再提）得自己写一层：在 ChatLuna 链里注入一句时间断层提示
（"上一轮对话是 X 分钟前，之前的话题别当现在的事"），或者自己扫库裁剪历史。
本轮没做 —— 1 小时已经覆盖用户遇到的现象（隔 8 小时翻旧账）。

### 顺带发现的隐患：长期记忆其实**没有落盘**（★ 这一条后来被 R17 修正了，见下）

**当时的判断（2026-09-30 00:00，部分正确、部分错误）：**

`chatluna_docstore` 在生产库里是 **0 行**，long-memory 的日志一直在说
"No existing EMGAS graph found… A new one will be created"。
原因猜的是"没有配置 `defaultVectorStore` 时用的是内存里的临时向量库"。

**R17 查清后的修正（2026-09-30 01:30）：**

- **EMGAS 引擎根本不用向量库**。它的持久化是 `DataBaseDocstore`（写 `chatluna_docstore` 表）
  + 一张概念图 JSON（`data/chatluna/long-memory/emgas/<memoryId>.json`）。
  ⇒ 所以"配不配 `defaultVectorStore`"跟 EMGAS 的持久化**无关**。
- **真正用向量库的是 `HippoRAG` 引擎**（`createVectorStoreRetriever` →
  `ctx.chatluna.platform.createVectorStore(defaultVectorStore, …)`），
  而且 **HippoRAG 才是 chatluna-long-memory 的默认引擎**（User/Guild/Preset 三层默认都是它，
  Global 层是 Basic）。我们当初把它改成 Emgas，很可能就是因为没有向量库时
  HippoRAG 会直接抛 `Vector store retriever 无 not found`。
- 生产库 `chatluna_docstore` 之所以是 0 行，更可能是**群里长期默认静默（R15）→ 根本没有对话轮次 → 记忆抽取压根没跑**。
- ⇒ 结论：当时那句"R3 长期记忆目前是会话内有效、重启即失"**不准确**，8 小时后由 R17 一次性做对：
  装向量库 + 本地嵌入 + 引擎换回 HippoRAG，并机台验证了写入 / 语义检索 / **跨重启仍在**。

## 二、R17 长期记忆接真向量库

### 需求原文

> 1. 为记忆添加对应的向量库，安装依赖，如果需要我操作告诉我

**结论：不需要你做任何事**（没有 API Key、没有注册、没有额外服务）。模型 23MB 已经下到本机，之后**离线可用**。

### 先搞清楚 chatluna 里"向量库"到底接在哪（别猜）

| 事实 | 出处 |
|---|---|
| `defaultVectorStore` 的取值来自"注册过的向量库 provider"，没配就是 `无` | `chatluna/lib/utils/schema.cjs:145 getVectorStores()` |
| provider 由 **`koishi-plugin-chatluna-vector-store-service`** 提供：`faiss` / `redis` / `milvus` / **`luna-vdb`** | 该包 `lib/index.cjs:416/737/998/1198` |
| luna-vdb 是 **Rust→WASM、零原生依赖**，索引落盘在 `<baseDir>/data/chathub/vector_store/luna_vdb/<key>/`（`docstore.json` + `luna_db.index`），正文同时写 `chatluna_docstore` 表 | 该包 `lib/index.cjs:737-800` |
| **光有向量库没用**：`createVectorStoreRetriever` 会先 `ctx.chatluna.createEmbeddings(defaultEmbeddings)`，没有嵌入模型 → `embedQuery('test')` 返回空 → 抛 `Embedding dimension is 0` | `long-memory/lib/index.cjs:2027-2052`、`vector-store-service:757-765` |
| ★ **EMGAS 引擎不用向量库**；**HippoRAG 才用**，而 HippoRAG 正是该插件的**默认引擎** | `long-memory`: Emgas 用 `DataBaseDocstore`（2550/2587），Hippo 用 `createVectorStoreRetriever`（1784）；默认 `layerEngines` 见 `index.cjs:3646-3673` |

### 嵌入模型选了"本地自建"（这是本轮最大的一块）

现成选项全是"要 Key + 要外网"：`chatluna-embeddings-service` 只支持 HuggingFace **推理 API**（要 token）；
OpenAI/通义/智谱/Gemini 都要注册。而本项目的既有路线就是"避开外部依赖"，
所以**自己写了一个本地嵌入插件**：

`D:\deepseek\QQbot\koishi-app\external\koishi-plugin-chatluna-local-embeddings\`

- 运行时：**transformers.js 3.8.1**（`@huggingface/transformers`，ONNX Runtime，CPU）
- 模型：**`Xenova/bge-small-zh-v1.5`**，q8 量化 **约 23MB**，512 维，中文优化
- 缓存目录：`<仓库根>/models/hf-cache`（**生产实例和测试实例共用一份**，不重复下）

### 唯一需要留意的运维点：模型缓存别删

模型只有**第一次**要联网（huggingface.co）。缓存已经在 `D:\deepseek\QQbot\models\hf-cache`（约 23MB），
**日常运行完全离线**。但如果哪天缓存被删/换机器，而本机又不通 huggingface：
启动日志会停在 `transformers.js … 就绪` 之后加载失败。两个修法：

```powershell
# 1) 给 Koishi 进程带上代理再启动（本项目平时就有 127.0.0.1:7890）
$env:HTTPS_PROXY='http://127.0.0.1:7890'; $env:HTTP_PROXY='http://127.0.0.1:7890'
node node_modules\koishi\bin.js start --log-level 3

# 2) 或者直接把 models\hf-cache 整个目录拷到新机器同一个相对位置（仓库根下）
```

下好之后可以把插件配置里的 `allowRemote` 关掉，彻底锁死离线。

1. **记忆按人隔离**：user 层记忆挂在说话人身上。主人问"王小明爱吃什么"是查不到的，
   必须由王小明本人问（或者改成 `Global`/`Guild` 层共享，但那样所有人共享一份记忆）。
2. **不 @ 就不记**：群聊里 ChatLuna 默认只在被 @/被叫名字时才开一轮对话，
   没开轮次就不会触发记忆抽取。⇒ 想让 bot 记住群里的事，得让它参与那轮对话。
   （想让它听全群，得开 `randomReplyFrequency` 或走 R9 主动插话那条路。）
3. `/chatluna.memory.search` 只能搜**当前会话所在路由**的记忆，而且没建过会话时
   会直接回「搜索记忆失败。」（`getMemoryScope` 返回 null）——先让 bot 在群里说过话再用。

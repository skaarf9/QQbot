### 怎么跑

**★ 首选：一条命令跑完**（`tools/run-rig.cjs`，会按正确顺序起两个进程、跑完自动收尾）：

```powershell
cd D:\deepseek\QQbot\koishi-app
node tools\run-rig.cjs tools\scenarios\09-final.json --settle 16000 --run 90000
# 剧本回放会写到 tools\last-run.log（终端里多行正文容易看漏，回放文件更可靠）
```

为什么要串起来：伪服务端是"客户端一连上就开始演"，所以**必须先起它再起 Koishi**。
分两次手动起很容易把两条时间线错开（踩过好几次）。

**手动跑（排障用）：**

```powershell
# 1) 先把测试实例连到伪服务端（生成配置用的脚本会从生产配置抄 key）
node D:\deepseek\QQbot\tools\gen-test-config.cjs     # 只在新装/改 key 时跑
# 2) 起伪服务端（会自动在 3003 起图片服务器）
cd D:\deepseek\QQbot\koishi-app
node tools\fake-onebot.mjs tools\scenarios\09-final.json --port 3002 --imgPort 3003 --settle 16000 --log tools\last-run.log
# 3) 另开一个进程起测试实例
cd D:\deepseek\QQbot\koishi-test
node ..\koishi-app\node_modules\koishi\bin.js start --log-level 3
```

**跑权限剧本前先重置测试库**，否则上一次提权的结果会留在库里、结果不可复现：

```powershell
cd D:\deepseek\QQbot
node --experimental-sqlite --no-warnings tools\seed-test-users.cjs --reset
# 只看不写：--dump
```

伪服务端会把整条时间线打出来，一眼就能看出 bot 什么时候回、回了什么：

### 关键设计点（踩过的）

- **`koishi-test/node_modules` 现在是真实目录，不是 junction 了。**
  最初是 `mklink /J koishi-test\node_modules koishi-app\node_modules` 复用生产的，
  但在 koishi-test 里跑一次 `npm install` 就把它**换成了真实目录**（npm 会先删掉）。
  现在两边各有一份 64MB，能跑就行 —— **别再假设它是 junction**。
- **装了自研插件后，必须在 `koishi-app` 里也装一份**：loader 解析插件名是
  `require('koishi-plugin-xxx')`，从 **`koishi-app/node_modules`** 起找。
  只在测试目录装，报的是 `[E] app cannot resolve plugin "xxx"`。
  （坑：cordis 对解析失败**不抛错**，只打一行 `[E]`，然后插件就静默不生效。）
- ★ **2026-10-04 补：反过来也要** —— 只在 `koishi-app` 装、测试台没链，测试实例照样
  `cannot resolve plugin`。**新插件两边都要建链接**，用
  `node tools/link-plugin.cjs <插件名>`（一次建好两边 + 写进两份 package.json + 自测解析），
  `node tools/link-plugin.cjs --list` 看全部自研插件的链接体检表。见 [坑 63](04-踩坑记录.md)。
- **`tools/gen-test-config.cjs` 里自研插件指向 `file:../koishi-app/external/<name>`**，
  不是照抄生产的 `file:external/...` —— 相对路径的基准是各自的应用目录，
  照抄会得到 `koishi-test\external\...` 这个不存在的路径，junction 是坏的。
  指向真实源码还有个好处：改插件代码测试实例立刻生效（junction 不是拷贝）。
- 测试实例也有 `chatluna-storage-service`，`serverPath` 要指 **5141**（自己的端口）
- **图片别去蹭 ChatLuna 的 `/chatluna-storage/` 静态路由**：
  它只服务**登记在自己库里**的文件，手动拷进目录的文件会 404。
  伪服务端自带一个 3003 图片服务器，绕开这个问题
- 测试库是 `koishi-test/data/test.db`。权限剧本要用
  `tools\seed-test-users.cjs --reset` 重置（会把 5 个测试号的等级写回已知值）
- **不会打扰生产实例**：5140 那份照常连真 QQ（3001）
- 剧本里的 `["reply", "$bot"]` 表示"引用 bot 刚发的那条"，伪服务端实现了 `get_msg` 支持
- 剧本 JSON **不能带 BOM**：用 PowerShell `Set-Content -Encoding utf8` 写会带 BOM，
  `JSON.parse` 直接抛错（现象是伪服务端刚起就退出）。用编辑器/`write` 工具写
- `run-rig.cjs` 收尾用 `taskkill /T /F` 带走整棵进程树：Koishi 的 CLI 会 fork 一个
  daemon 子进程，只 kill 父进程会留下孤儿占着端口（就是"静默半死"的来源）
- **★ 别把 `run-rig.cjs` 的输出接进 `| Select-String … | Select-Object -First N`**：
  PowerShell 凑够 N 条就会**提前掐掉上游进程**，表现是"剧本跑到一半就没了"
  （本轮踩过：12 步剧本只跑到第 4 步，日志停在半路，还以为是插件崩了）。
  要么直接让输出全打出来（`run_in_background`），要么改用 `--log` 指定的剧本回放文件

### 已经用它跑出来的对照数据（2026-09-29 16:15，干净库）

| 事件 | 耗时 | 结论 |
|---|---|---|
| pig.jpg（123KB JPEG）首次解析 | **8045 ms** | |
| pig.jpg 再发一次 | **缓存命中，0 次 API 调用** | ✅ R7 去重成立 |
| big.png（1148KB PNG）首次解析 | **19112 ms** | ⚠️ 太慢，见下 |
| 大图解析期间 bot 的排队提示 | 发完 2 秒后被 `delete_msg` **自动撤回** | ChatLuna 自带，不用管 |

**大图解析慢 —— 已解决（2026-09-29 16:31 复测）**

原来 1.1MB 的 PNG 要 19~24 秒，期间整条 `transform_chat_message` 被卡住。
原因是插件把**原图** base64 塞进视觉请求（1.1MB → 1.5MB base64）。

修法：装了 **`sharp`**（`koishi-app` 里 `npm i sharp`），在 vision 插件里加了
「解码 → 长边缩到 1024 → 垫白底 → JPEG q85」这一步（压缩本身只要 30~80ms）。

| 图 | 压缩前 | 压缩后 |
|---|---|---|
| pig.jpg（123727 B） | 8045 ms | **5373 ms** |
| big.png（1148026 B） | 19112 ms | **6412 ms**（压成 78617 B） |
| `transform_chat_message` 阻塞 | 19.14 s | **6.43 s** |

附带好处：描述质量反而更好（压缩前模型去读图里的字「底部文字：超级头锤！」，
压缩后开始描述画面「银发黑角少女跃出海面撞起白色水花，超级头锤！」）。

⚠️ `sharp` 是**可选依赖**：插件里 `try { require('sharp') } catch`，
没装就退回用原图，不会因为压缩失败丢图片。压缩参数：
`compress` / `maxEdge`(1024) / `jpegQuality`(85)。**缓存 hash 用原图算**，
所以改压缩参数不会让已有缓存失效。

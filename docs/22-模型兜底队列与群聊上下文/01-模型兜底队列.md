## 1. 人格预设改功能化命名（已落地）

### 1.1 改了什么

| 项 | 旧 | 新 |
|---|---|---|
| 文件名 | `data/chathub/presets/xingyuan.yml` | `data/chathub/presets/default-persona.yml` |
| 预设 id / 显示名 | `keywords[0] = 星源` | `keywords[0] = default-persona` |
| `keywords` | `[星源, 大肥鱼]` | `[default-persona, 星源, 大肥鱼]` |
| `koishi.yml` | `defaultPreset: 星源` | `defaultPreset: default-persona` |

两份实例都改了（生产 `koishi-app`、测试 `koishi-test`），另修 `tools/setup-test-app.cjs:24-27` 的复制路径
与 6 处文档引用（`docs/04` 坑 15、`06`、`08`、`09`、`18`、`20`）。

**校验**（已跑）：两份预设 YAML 均可解析，`keywords[0]` 与各自 `koishi.yml` 的 `defaultPreset` 一致，`prompts` 段数 2。

### 1.2 为什么这样改是安全的（依据）

`koishi-plugin-chatluna/lib/preset.mjs`：

- **文件名不参与身份识别**：`loadAllPreset()`（`:90-110`）只按扩展名筛，解析只看 YAML 的 `keywords`
  （`lib/llm-core/prompt/index.mjs:86-98` → `triggerKeyword: rawJson.keywords`），文件名只用于去重与日志。
  → 单纯改文件名 **100% 安全**。
- **id 只看 `keywords[0]`**：`_updateSchema()`（`:241-253`）用 `Schema.const(preset.triggerKeyword[0])` 填下拉框。
- **匹配用的是数组 includes**：`getPreset(k)`（`:176-192`）= `triggerKeyword.includes(k)`。
  → **旧会话里存的 `conversation.preset = 星源` 依然能解析**，这就是"改了也不会立刻炸"的原因。
- **keywords 同时是触发词**：消息**以关键词开头**时会切到该预设并把词剪掉（`lib/index.mjs:2881-2905` + `:3599-3645`）。
  → 「星源」「大肥鱼」留在数组里，触发行为不变。
- ⚠️ **`{affinity("xingyuan")}` 与 `scopeId: xingyuan` 当时一律没动**：那是**好感度数据作用域**（数据库命名空间），
  跟文件名/人格名无关，改了会读不到既有好感度数据（见坑 15 与 [R4 好感度](../13-R4好感度.md)）。
  > ★ **2026-10-04 更新**：用户后来要求「检查所有的 xingyuan 部分，全部替换成功能性描述」，
  > 于是 scopeId 连数据一起迁到了 `affinity`（`tools/migrate-affinity-scope.cjs`）——
  > 上面这条"不改"的结论只在"不想迁数据"的前提下成立，**要改就必须配套迁移**（[坑 60](../04-踩坑记录.md)）。

> 生效时机：**不重启也不会坏**（运行中的实例内存里仍是旧 `defaultPreset: 星源`，而 `星源` 仍在 keywords 里）。
> 下次重启 worker 后按新配置走。回滚 = 文件名改回去 + `defaultPreset: 星源` + keywords 去掉第一项。

## 2. 模型兜底队列

### 2.1 现状：到底谁在调模型（代码实证）

| 角色 | 配置字段（`koishi-app/koishi.yml`） | 调用点 | 兜底 |
|---|---|---|---|

| **识图** | `chatluna-vision.visionModel` / `fallbackModel`（`:89-90`） | `external/…/chatluna-vision/lib/index.js:342-359`（`describeWith`）、`:375-383`（`describe`） | ⚠️ 1 次，裸 catch、**无冷却** |
| **表情包判断** | `chatluna-sticker.judgeModel`（`:157`） | `node_modules/koishi-plugin-chatluna-sticker/lib/library.js:77,252` | ❌ 静默失败 |
| **表情包学习** | `chatluna-sticker-admin.learnModel`（`:173`） | `external/…/chatluna-sticker-admin/lib/index.js:574-596` | ❌ 空 label + warn |
| **记忆抽取 / 图谱** | `longMemoryExtractModel` / `hippoExtractModel`（`:149,152`） | `node_modules/koishi-plugin-chatluna-long-memory/lib/index.cjs:964/1790` | ❌ 同模型重试 2 次后返回 `[]` |
| **插话** | 无自己的模型字段 | `external/…/chatluna-proactive/lib/index.js:436`（`chatChain.receiveCommand`） | ❌ 冷却重试 |

**两个关键事实**：

1. **所有角色都是通过 `ctx.chatluna.createChatModel(名字)` 拿模型的**，没有任何插件自己拼 HTTP
   —— key/baseURL 全在适配器的 `apiKeys` 三元组里。
2. **`ccfree/stealth/space-bunny-alpha` 是三个角色的单点**（vision 主模型、sticker 判断、sticker 学习）。
   它抖一次，只有 vision 会切走，另外两个静默死。

### 2.2 框架层已有什么、缺什么

ChatLuna 1.4.0 内建三层重试（`lib/llm-core/platform/model.mjs:264,279-366`）：

- **同模型重试**：`maxRetries + 1` 次（默认 5），退避 `2s·2ⁿ`，**已吐 chunk 就不重试**；
- **多 key / 多端点池**：`ClientConfigPool`（`config.mjs:10-168`），失败指数封禁 1s→10min —— **换的是 key，不是模型**；
- ❌ **没有任何"跨模型 fallback"**：全包 grep `fallback` 零命中，`modelPool` 只是客户端内模型缓存。

→ 所以"403 就换下一个模型"必须由一个**能改模型名**的层来做。可选位置只有两处：适配器，或每个插件自己写。

### 2.3 方案：市场插件的"模型轮换组"（遵守硬约束第 0 条：先本地 → 再市场 → 最后自写）

市场已有现成的：**[`koishi-plugin-chatluna-multi-adapter`](https://www.npmjs.com/package/koishi-plugin-chatluna-multi-adapter) 0.0.3**
（fork 自官方 `chatluna-openai-like-adapter`，作者 Minecraft-1314）。

它补的正是这一块：**给一个自定义名字挂多个真实模型，出错自动切下一个**（`src/rotation.ts` + `src/requester.ts`）：

- 策略 `出错才切换`（failover）：**固定用首选，只有失败才切**，不会轮流烧免费额度；
- **失败判定**：`isFailoverable()` 只排除"用户主动中止"和"没有可用配置" → **403 / 401 / 404 / 429 / 5xx / 超时全都触发切换**；
- **冷却退避**：失败的「模型+接口」按次数冷却 `30s → 60s → 5min → 15min → 30min`，期间跳过，冷却结束自动回切首选（`constants.ts` + `rotation.ts`）；
- **已吐 chunk 不切换**（`requester.ts` 的 `started` 标志）—— 半截流只能报错，这是对的（重发会出现两段内容）；
- 组的能力/上下文由候选**取交集 / 取最小**，不虚报；
- `debug: true` 会打 `route ok/fail: 组名 -> 真实模型 @ api#0` —— 这正是"到底哪个模型答的"的证据来源。

**为什么它能一次覆盖全部 6 个角色**：组名在 ChatLuna 里**就是一个模型名**，而所有角色都是按模型名取模型的
（2.1 的两个事实）。所以 `defaultModel`、`judgeModel`、`learnModel`、`longMemoryExtractModel`、
`hippoExtractModel`、`visionModel` **全都只是改一个字符串**，市场插件（sticker / long-memory）一行代码都不用动。

**风险与对策（必须承认它是新依赖）**：

| 风险 | 事实 | 对策 |
|---|---|---|
| 很新 | 2026-09-26 首发，3 个版本，3 次提交，近 30 天 494 次下载 | 版本**钉死**；先在 `koishi-test` 验（第 2.6 节） |
| 在主对话关键路径上 | 它接管适配器 | **保留** deepseek / openai-like 两个适配器不动，回滚 = 改回一个字符串 |
| fork 质量 | fork 自官方 `openai-like@1.4.x`，我们已逐行读过 `rotation.ts` / `requester.ts` / `config.ts` | 需要的话可以 diff 官方适配器；本仓库已记录要点 |

**明确不放进队列的**：

- `poolside/laguna-s-2.1-free`（免费但有）：poolside 是代码向实验室，做闲聊陪伴人设与中文语境不匹配；
- `inclusionai/ling-3.0-flash-sante:free`：被 3.1 取代，只在 3.1 也挂掉时才有意义；
- `jev-*`：TypeSafe 的结构化判定模型（对状态问 yes/no、打分），**不生成自由文本**，当聊天模型是拿螺丝刀当锤子；
- `deepseek-v4-flash-fast`：额度只有 5,210/月还更贵。

**两个必须知道的取舍**：

1. **组的上下文 = 候选里最小的那个**。把 `ling-3.1-flash:free`（262K）放进 `q.dialogue`，整组上下文就变 262K
   （ChatLuna `maxContextRatio` 默认 0.35 → 可用约 91K token，对 QQ 群聊够用）。
   想要保住 1M，就**只放 1M 的候选**（DeepSeek + bunny），把 Ling 留给 `q.memory` / `q.gate`。
2. **组的能力 = 候选的交集**。往 `q.vision` 里塞一个不吃图的模型，整组就不再声明 `image_input`，
   ChatLuna 会把图片降级成 `[图片:xxx]` 占位符（`lib/index.cjs:3954-3960`）。

### 2.6 验证结果（2026-10-02 已跑，测试实例 + 假上游，确定性）

仓库里原本**没有任何假模型设施**（`tools/` 搜 `chat/completions` 零命中），所以按 `fake-onebot.mjs` 的结构新写了：

1. **`tools/fake-openai.mjs`**（新）：`node:http` 起 `GET /v1/models` + `POST /v1/chat/completions`，
   按 `body.model` 分流 —— `fake-broken` 恒 403、`fake-broken500` 恒 500、`fake-flaky` 前 N 次 403 之后 200、
   `fake-ok`/`fake-ok2` 恒 200（正文 `FAKE_OK_A_n` / `FAKE_OK_B_n`，带请求序号，一眼看出用的是哪个）。
   每个请求打一行 `[upstream] #n model=… → 状态码`。
2. **`tools/run-rig.cjs`** 加 `--upstream`（第三个进程，3005）与 `--default-model <名>`（临时改测试实例的
   `defaultModel` 并在收尾时**还原**）—— 轮换组是个模型名，只有真让某个角色去用它，兜底链路才会被走到。
3. **`tools/seed-test-group.cjs`**（新）：给测试库播种一个 `guard` 放行的干净测试群 `777000111`。
   为什么必须播种：`chatluna-guard` 在测试实例里是 `defaultPolicy: silent` + 空白名单，
   而它的闸门排在 ChatLuna 链**最前面** —— 群没放行就根本走不到模型（不是"回复被吞"，是"没请求模型"）。
   用新群而不用现成的 `454444539`，是因为那个群开着 proactive（3 秒轮询），会给"数上游请求次数"引入噪音。
4. **`tools/scenarios/36-failover.json`**：三句话验三件事（首选 403 / 冷却跳过 / 冷却到期回切）。

**实测结果（403 组 `q.failover` = [fake-broken, fake-flaky, fake-ok2]）：**

| 轮次 | 上游请求序列 | `route` 日志 | 群里收到 |
|---|---|---|---|
| 第 1 句 | `#1 fake-broken→403`、`#2 fake-flaky→403`、`#3 fake-ok2→200` | `route fail` ×2 → `route ok` | `FAKE_OK_B_1` |
| 第 2 句（+14s，冷却 30s 内） | **只有** `#4 fake-ok2→200` | 直接 `route ok`，**没有 fail** | `FAKE_OK_B_2` |
| 第 3 句（+49s，冷却已过） | `#5 fake-broken→403`、`#6 fake-flaky→200` | `route fail` → `route ok` | `FAKE_OK_FLAKY_2` |

**500 组 `q.failover500` = [fake-broken500, fake-ok]** 同样成立（`route fail: … fake-broken500` → `route ok: … fake-ok`，三句话正文 `FAKE_OK_A_1/2/3`）。

四条结论：
- **403 会切、500 也会切**（不只是权限/额度类错误）；
- **冷却期内不会再打失败的候选**（第 2 句上游只收到 1 个请求）；
- **冷却到期会自动回切首选**，而且**恢复了的候选会被重新启用**（fake-flaky 第 3 句成功）；
- 兜底是**用户可见**的：群里拿到的是第 2/3 顺位的正文，不是"解析失败"。

两个坑（实测踩到，写下来免得下次误判）：
- **首轮会出现 4 次模型调用**：`#1~#3` 是主对话，`#4` 是 **ChatLuna 自动起标题**（`autoTitle`，也用会话的模型）。
  数请求次数时要把这个算进去，否则会以为"重试了"。
- **失败尝试会在日志里打 `[E] chatluna ======ChatLunaError:1====== Error: 403…`**，
  即使随后兜底成功。看到红字先看有没有紧跟 `route ok`，别急着当故障。

**生产灰度顺序**（一次只动一个角色，每步看一轮真实对话）：

`q.memory`（后台、静默，最安全）→ `q.sticker` → `q.vision` → `q.dialogue`（主对话，最后动）。

> ⚠️ 回切是**按"模型+接口"这个组合**独立计冷却的：`q.dialogue` 的首选挂掉后，
> 同一个真实模型在别的组（比如 `q.memory` 里也放了 `deepseek-v4.1-flash`）**不会**跟着被跳过热 ——
> 冷却 key 是 `${groupName}\0${endpointIndex}\0${model}`（`rotation.js:7`）。想全局共享要另想办法。

### 2.7 回滚

回滚任何一步 = 把那一行模型名改回原值 + 重启 worker。彻底卸载 = 删掉 `chatluna-multi-adapter` 段与依赖，
原两个适配器一直在，不受影响。

★ 2026-10-06 起，"改那一行"**不用改文件也不用重启**：群里
`/stages.set <阶段> <序号>` 会按行改 `koishi.yml` 并热重载那一个插件；
`/stages.reset <阶段>` 回到本进程启动时的值。见 2.8 与 [docs/31](../31-模型运维命令与队列自愈.md)。

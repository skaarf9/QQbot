### 用户原话

> 在群聊中的回复可以看出似乎目前必须@才能主动回复,需要一个机制,当用户@消息之后,这个用户在短时间内继续发出消息的时候则也会触发api调用尝试回复(不过也需要判断是否是在和bot对话),这主要是判断是否要调用模型api,由逻辑代码控制
>
> 另外,由于手机端无法@的同时发图,只能引用的方式,我们添加一个机制,当用户只@了bot,没有附带任何消息的时候,我们设置长一点的等待时间,3秒左右,然后再看用户发了别的消息,再触发api请求,这样如果用户发送了图片,则视为和"@bot 并附带图片"同样的情形,需要预先解析图片(当然如果解析过了则直接替换为文字),然后回复
>
> 另外需要确定的一点是现在的所有回复都需要加上一个延迟,这个延迟应该出现在收集用户发送信息之前,比如说用户@bot->触发3s延迟->用户发图->用户发消息->3s到了,收集用户当前发送的所有消息并尝试回复

### 拆解：两件事，一件用现成的，一件自己写

| @过 bot 之后，该用户短时间内继续说的话也算触发 | **自写插件 `koishi-plugin-chatluna-followup`** |

### ★ 挂载点（这是本轮最重要的发现，别再摸索一遍）

**`ctx.chatluna.chatChain` 是公开的**，而且有正规的中间件注册 API：

```js
ctx.chatluna.chatChain
  .middleware('followup', async (session, context) => { ... }, ctx)   // 第三个参数是 effect 的宿主 ctx
  .before('allow_reply')
```

源码依据：`lib/chains/index.cjs:156` 的 `middleware(name, fn, ctx)` 返回 `ChainMiddleware`，
`.before(name)` 往依赖图里加一条边（`chains/index.cjs:373`），`build()` 做拓扑分层（`:435`）。

**两个必须知道的性质：**

1. **同一层的中间件是并行跑的**（`chains/index.cjs:215` `_executeLevel` 用 `Promise.all`），
   只有跨层才保证顺序。所以必须用 `.before('allow_reply')` 排到**上一层**，
   不然改 session 会和 `allow_reply` 竞态。
2. `build()` 在**第一条消息进来时才跑**，而且遇到未知的 `before` 目标会
   `throw new Error('Unknown middleware "..." referenced by ...')`（`:471`）。
   所以启动不报错 ≠ 排序正确。

**★ 时序陷阱（踩到了，浪费两轮重启）：注册链中间件时，链上只有你自己**

ChatLuna 的初始化是**两层 ready 嵌套**的（`lib/index.cjs:8109-8133`）：

```js
function apply43(ctx, config) {
  ctx.on("ready", async () => {          // 第一层 ready
    setupServices(ctx, config, ...)      // ← chatluna 服务在这里才创建
    setupEntryPoint(ctx, config, ...)    // ← 注册 entryPointPlugin
  })
}
function setupEntryPoint(ctx, config, ...) {
  const entryPointPlugin = (ctx2, config2) => {
    ctx2.on("ready", async () => {       // ★ 第二层 ready（这个插件的 ready）
      await initializeComponents(ctx2, config2)   // ← 全部链中间件在这里注册
      setupMiddleware(ctx2)                        // ← ChatLuna 的 Koishi 中间件
    })
  }
}
```

推论：

- 我们的 `ctx.inject(['chatluna'], ...)` 在**服务创建那一刻**就跑，
  此时链上**只有我们自己**，`.before('allow_reply')` 的目标还不存在。
  **这时候去查"有没有 allow_reply"必然误报**（第一版自检就是这么翻车的）。
- 但**规则是存下来的**，`build()` 时才解析。而 `build()` 只可能在
  `setupMiddleware` 注册之后才被调用 → 那时 `allow_reply` 一定已经在链上 → **边一定成立**。
- 结论：**在 `inject` 回调或 `ready` 里查链上节点都是错的**；
  正确的验证点是**中间件第一次真正被调用时**——那时 `build()` 已经成功跑过。
  插件里现在的自检就是这么做的（`checkOrder()`，只报一次，会打印双方的层号）。
- 也顺带说明：ChatLuna 的链**不可能**在中间件注册完成前被调用，
  所以不会出现 `build()` 撞上"Unknown middleware"的竞态。

### 怎么让 `allow_reply` 放行（两条都做，互为保险）

`allow_reply` 是整条链第一个中间件，它返回 STOP 的话后面什么都不跑。它的判定用两个来源：

```js
let appel = session.stripped.atSelf                                   // 来源 1
appel = session.elements?.some(el => el.type === "at" && el.attrs?.id === botId)   // 来源 2
```

所以插件里：

```js
session.elements = [h('at', { id: session.selfId }), ...session.elements]  // 打来源 2
session._stripped = undefined                                             // 让来源 1 按新 elements 重算
```

- `session.elements` 在 Satori 里**有 setter**（`@satorijs/core/lib/index.cjs:248-253`），
  改的是 `event.message.elements` 本身
- `session.stripped` 是**带缓存的 getter**（`_stripped`），不清缓存就不会看到新 elements
- 插进去的 at **不污染提示词**：ChatLuna 的 at 拦截器对 `id === selfId` 什么都不加
  （`lib/index.cjs:3685-3697`），而 `h.select(elements, "text")` 也只看 text 元素

### 判定逻辑（"是否在跟 bot 对话"）

- **算"叫了 bot"**：`stripped.appel / atSelf`、elements 里有指向自己的 at、**引用了 bot 自己的消息**
- **跟进窗口**：`windowSeconds`（默认 120s，每接住一条就顺延）
- **硬上限**：`maxSeconds`（默认 600s，从最后一次真正叫 bot 算起，防止一直被牵着走）
- **条数上限**：`maxConsecutive`（默认 20）
- **认定在跟别人说话就不接**：`skipWhenAtOthers`（默认开，消息里 @ 了别人就跳过）

### 与图片策略的联动

跟进插件插进去的那个 at，正好让 vision 插件的 `isBotCalled()` 返回 true，
所以"@bot 之后用户补发的图片"会被**照常解析**——这就是用户说的
"视为和 @bot 并附带图片同样的情形"。两个插件不用互相知道对方存在。

### 关于"用户只 @ 了 bot、没附任何内容"

这种消息的转换结果为空，ChatLuna 在 `lib/index.cjs:3670` 会直接 STOP，
**不会**建 collecting turn。所以延迟是从**下一条有效消息**开始算的，不是从那个裸 @ 开始。
实际体验：@bot（没反应）→ 补发图/文字（触发）→ 3 秒静默后一起回复。
差个一两秒，可以接受；如果哪天要精确锚定在裸 @ 上，得给裸 @ 塞个占位文本，会污染历史，暂时不做。

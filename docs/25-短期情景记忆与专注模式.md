## 1. 「AI 看不到我引用的消息」——真实成因（生产日志实证）

用户在 2026-10-03 08:12 引用 bot 06:37 说过的一句话，回「诶，你都不记得了」。
把那一刻落盘的真实请求体解出来，`the Referenced message` 段落**是在的**：

```
群友[…说：The Referenced message is 2026/10/03 06:37:39 大肥鱼 说 said
<at id="2791932480"/>我知道，猜到了，这个点还在群里发消息的没几个睡着的。
你也太晚睡了吧，熬夜对身体不好……
 User's current message
诶，你都不记得了
```

也就是说：**引用被正常注入了，模型也真的"看见"了那一句**。它甚至知道自己该去查，紧接着调了
`memory_search("2026/10/03 早上 06:37 群里的对话 熬夜", layer=[guild,user,global])`。
问题出在**查不到**，而且是三层叠加：

| 层 | 事实 | 证据 |
|---|---|---|
| ① 工具直接报错 | 生产只启用了 `Guild`/`User` 两层，模型按工具描述填了 `global` → `initMemoryLayers` **抛异常** → 工具只回一句 "An error occurred while searching for memories." | `[E] chatluna-long-memory Error: Memory layer global not found`（08:12:43，栈顶 `initMemoryLayers`） |
| ② 长期记忆里本来就没有 | 抽取器每 3 轮跑一次，只提炼"值得长期记住的事"，不可能有"我 06:37 说过一句熬夜梗" | `longMemoryExtractInterval: 3` |
| ③ **那句话已经不存在于任何地方** | 会话上下文只保留**触发过的**消息；闲置 1 小时被归档后 `chatluna_message` 里整表删掉；上下文里"群里刚才在聊什么"只有最近 6 条且不带时间戳 | `autoArchiveTimeout: 3600` → `services/chat.cjs:2594` 的 `remove('chatluna_message')`；docs/22 §3.3 |

**结论**：模型能看到"被引用的那一句"，但看不到"那句话所在的对话"。
用户原先的猜测（"上下文不够长"）方向对、机制不对 —— 是**那段话从来没被存下来**。
所以补的不该是更长的上下文，而是：**① 自己说过的话也要存；② 近况要带时间戳；③ 要有一个能主动翻旧账的工具。**

## 2. 认知纠正：短期记忆不是"聊天全存档"

用户的原话是「短期记忆就是用来记忆你和谁谁聊了什么的……会比较杂，比较细致」。
前半句对，后半句要打个折：

| 说法 | 判定 | 说明 |
|---|---|---|
| 短期记忆 = 记「你和谁聊了什么」 | ✅ 对 | 但它的目标是**接得上话**，不是"记得住全部"。存档是日志，不是记忆 |
| 会比较杂、比较细 | ✅ 对 | 细 = 带时间戳、带人名、**带自己说过的话**；但必须有**注意力预算**（条数 + 时长双层上限） |
| 聊过的都该进短期记忆 | ⚠️ **要分层** | 无差别全塞进提示词会反噬：模型会张冠李戴（把 A 说的记成 B 说的）、把旧事当刚发生 |
| 「两小时后没惊异于我起这么早」= 缺短期记忆 | ✅ 对 | 只要时间戳在，模型自己就会惊讶。现在它连自己说过什么都不记得，因为 bot 自己的话**不在** `{latest_message}` 里（OneBot 不回显自己发的消息，docs/22 §3.3） |

本插件按这个认知落成**三层**：

| 层 | 内容 | 进不进提示词 |
|---|---|---|
| **日志层**（`chatluna_episode` 表） | 每条群消息 + bot 自己的每句话，48 小时 / 每会话 800 条滚动 | ❌ 不进，只给 `recall` 工具查 |
| **窗口层**（`{episode()}` 的正文） | 最近 18 条或 90 分钟的原话，带 `[时:分] 谁: …` 与引用标注 | ✅ 每轮都进 |
| **总结层**（滚动总结） | 更早的内容压成 ≤1200 字，只在累计 60 条新消息时跑一次（用免费的 `cc/q.memory`） | ✅ 每轮都进 |

## 3. 插件做了什么（`koishi-plugin-chatluna-episode`）

### 3.1 落库：补上 ChatLuna 的两个真空

| 入口 | 钩子 | 补的是什么 |
|---|---|---|
| 入站 | `chatluna/message-observed` | **没触发 bot 的群消息**（ChatLuna 只 emit 不落库）；`session.quote` 在这里能读到，所以引用关系也被记下来 |
| 出站 | `before-send`（guard 也挂在这） | **bot 自己说的每一句话**（含被 guard 拦下的）。会话历史被归档后，"我上一句说了啥"就只剩这一份 |

> ★ **坑 59（2026-10-03 修）**：出站这半条咽喉从上线起就是**断的** —— 判形状用的是
> `session.uid`，而它是 `platform:userId`（两段），按三段写的正则永远匹配不上，
> 于是每条出站消息都在第一行静默 `return`：生产库 417 条里 `isBot=1` 的 **0 条**、
> 日志里 `其中 bot 自己 N 条` 恒为 0。修完的实测：
> `渲染 {episode()}：… → 5 条（…，其中 bot 自己 3 条）`。
> 细节与"为什么不能拿 `session.content` 入库"见 [04 坑 59](04-踩坑记录.md)，
> 回归剧本 [rig 57](../koishi-app/tools/scenarios/57-episode-outbound.json)。
>
> **刻意不记的**：带 `__guardIsCommand` 标记的**指令输出**（`/help`、`/mem`、`/guard.*` 回执）。
> 除了"那不是它自己聊的话"这个理由，更重要的是挡住反馈环：`/mem` 打印的就是记忆本身，
> 记回去下一轮就会读到上一轮的转储，越滚越大。

三张表：`chatluna_episode`（消息）、`chatluna_episode_summary`（滚动总结与游标）、`chatluna_focus`（专注模式）。

**落库范围**：默认 `storeScopes: allow` —— 只记 guard 放行的群 + 跟 bot 的私聊。
实现上问 guard 的 `isAllowed()`（本轮新加的对外口子），**三态**处理：

- `true` 放行 → 记；
- `false` 屏蔽 → 不记；
- `null`（guard 还没把库读出来）→ **也不记**。这条是刻意的：启动那几百毫秒里"没读到屏蔽记录"
  是个假象，按它做决定会把该静音的群收进来。为此 guard 里加了 `ready` 标志位。

### 3.2 注入：`{episode()}`

```
【更早的概括（到 10-03 06:29 为止）】
（上一段总结正文）

【最近 18 条发言（时间从旧到新）】
[08:04] 绮罗星: 今天好累啊，我先去躺了
[08:28] 你（大肥鱼）: 晚安，早点睡，别又刷手机到两点  ← 引用了 绮罗星 08:04 说的话
...
```

配套的提示词段落（`data/chathub/presets/default-persona.yml`）明确要求模型：
别否认自己说过的话 / 注意时间差（深夜晚安 → 两小时后"我起了"就该觉得他起太早）/ **想不起就 `recall`，不要编**。

### 3.3 检索：`recall` 工具

`recall(keyword?, hours?, speaker?, limit?)` —— 从**自有库**里按关键词 / 时间范围 / 说话人捞原话，
返回带 `[MM-DD HH:MM｜N 小时前]` 的行。这是本次事故的直接解药：
以后模型遇到"记不清"，有**能查的东西**，不用编、也不会像 `memory_search` 那样直接报错。

### 3.4 专注模式：`/focus`

| 指令 | 作用 |
|---|---|
| `/focus <名字> [目标]` | 开局。此后**窗口层放宽到整局**（默认 400 条 / 24 小时），每个字都落库 |
| `/focus.note <事实>` | 手动往账本里记一条（主人也可以帮它记） |
| `/focus.status` | 看这一局的状态 + 账本条数 + 短期记忆与总结现状 |
| `/focus.end` | 收局 |

模型侧对应工具 `focus_note(text, kind)`，`kind ∈ fact/clue/rule/guess/todo`。
**账本是结构化的、永不被总结压缩掉** —— 这是"精确"的关键：总结会丢细节，账本不会。
账本超长时从最旧的条目开始丢（保最近的事实），上限 8000 字符。

与 `scene`（R11）的分工：**scene 管"这局是否进行中"，focus 管"记住整局 + 记事实"**。
两者独立，各自可用；用户选的就是这个方案。

### 3.5 `/episode.preview`（诊断用，第五轮新增）

按**模型看到的原样**打印「最近发生的事」：窗口条数、时间跨度、里面有多少条是 bot 自己说的、
总结层有多少字。排查"模型为什么不记得刚才说过的话"时**先看这个** —— `{episode()}` 是渲染期求值的，
从日志里只能看到它引发的 SQL，看不到它交出去的文本。别名 `/mem`。

> ★ **第六轮·续二修过它一个会"整条消息发不出去"的 bug**（[坑 58](04-踩坑记录.md)）：
> 窗口里有**图片消息**时，库里存的是元素标记 `<img src="…rkey=…"/>`，原样打印又返回给框架，
> Koishi 会 `h.parse()` 成**真的图片元素** → NapCat 去下载过期的 rkey 链接 →
> `retcode 1200 下载文件失败: Bad Request`，**一个字都发不出去**。
> 现在渲染层有 `plainText()` 清标记（`<img>` 丢掉、`<at>` → `@x`），出口再 `h.escape()`；
> 图片这件事不会丢 —— 行尾仍有 `［含 N 张图］`。验它的剧本是 rig 56。

## 4. 踩坑（这一轮新增 4 个，已进 [04-踩坑记录](04-踩坑记录.md) 坑 47~50）

- **坑 47**：`chatluna.createChatModel(name)` 是 **async**，而且返回的是**响应式 ref**，
  真模型在 `.value` 上。拿错的表现是 `model.invoke is not a function`（不是"模型不存在"），
  极易误判成模型名写错。正确写法照抄 vision 插件：
  `const ref = await ctx.chatluna.createChatModel(name); const model = ref?.value`
- **坑 48**：滚动总结的"留尾条数"**必须跟着触发条数缩放**。写死 12 时，rig 的触发条数 6 会变成
  "取 13 条 → 留 12 条 → 每轮只总结 1 条老消息"，游标几乎不动。修成
  `max(4, min(20, trigger/4))`。**定位手段**：在切分前后各打一行候选条数与时间范围。
- **坑 49**：短命脚本写 sqlite **必须 `db.close()`**。不关也能退出，但退出前一直握着文件锁，
  那几秒里 Koishi 侧写全部失败，表现是"这一轮群里完全不回话" —— 看起来像插件 bug。
- **坑 50**：位置参数要先滤掉 `--flag` 再取。`seed <scope> 6 3 --near` 会把 `--near`
  当成第 4 个位置参数（db 路径），于是整批数据写进仓库根下一个**名为 `--near` 的文件**，
  而检查脚本还在看真正的 test.db —— 表现是"报了写入 6 条，表里一条没有"，还会在仓库里留垃圾文件。
  （已加自检：写完立刻数一遍 + 关闭句柄后再数一遍，两次不一致就报警。）

另外两个**长期记忆插件的 bug**（不是我们写的，但必须知道）：

- `memory_search` 的工具描述**永远**列出 `user/preset/guild/global` 四层，却不知道哪些层真启用了；
  `_call` 又把模型给的层原样传下去，遇到没有 creator 的层**直接抛异常**，把整次检索带走。
  → 已用 `koishi-app/tools/patch-long-memory.cjs` 打补丁：**丢掉不可用的层，用剩下的继续搜**，
  一个不剩时退回服务默认层。⚠️ **重装/升级这个包之后必须重跑该脚本**。
- 该插件在**模型回合里**清历史/归档会死锁（见 scene 插件头部注释）。本插件只写自己的表，
  一次都不碰 `chatluna_message`，天然没有这个风险。

## 6. 上线后怎么确认注入真的生效（一次真对话就够）

1. 在群里 @ 一下 bot 说句话（触发一次真实模型调用）；
2. 立刻跑：

```powershell
cd D:\deepseek\QQbot
node .scratch\probe-request.cjs koishi-app/data/koishi.db "最近发生的事" 2
```

`chatluna-sandbox` 会把**完整请求体**写进 `koishi-app/data/koishi.db` 的
`chatluna-sandbox.model-request` 表。判据：

- 出现 `含「最近发生的事」： true` → **注入生效**，段落里应当能看到带 `[时:分]` 的行；
- 出现 `含未渲染的 {episode()}： true` → 渲染器没认这个变量（会连累整轮），**立刻回滚**：
  把预设里那两段（`【最近发生的事】`与`【专注模式】`）删掉即可，插件留着不影响。

也可以直接在群里发 `/mem`（= `/episode.preview`），它打印的就是模型会看到的那段内容。

## 7. 回滚

| 回滚对象 | 做法 |
|---|---|
| 注入（最常需要） | 删掉 `koishi-app/data/chathub/presets/default-persona.yml` 里【最近发生的事】与【专注模式】两段 ⚠️ **顺序要紧：先删预设里的变量再停插件** —— 渲染器遇到未注册的函数会抛 `Unknown function`，整轮对话直接失败（docs/22 §6 记过同一个坑） |
| 插件 | `koishi-app/koishi.yml` 里 `enabled: false`（或删段）+ 重启；`npm uninstall koishi-plugin-chatluna-episode` 彻底移除 |
| 长期记忆补丁 | `node koishi-app/tools/patch-long-memory.cjs` 打的是构建产物；回滚 = 重装该包 |
| 数据 | 三张表都在 `koishi-app/data/koishi.db`；`/focus.end` 收局即可，不必删表 |

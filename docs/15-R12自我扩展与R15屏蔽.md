# R12 自我扩展 + R15 群聊屏蔽开关

> 属于 [QQ 机器人项目 —— 进度与交接](../进度与交接.md) 的分册。
> 旧编号（如「第八·十三节」）的去向见索引页的章节对照表。

两个自写插件：`chatluna-selfext`（搜插件 / 申请 / 主人安装）与 `chatluna-guard`（四道闸门 + HTTP 控制口）。

## 一、R12 自我扩展

### 需求原文

> 「自我扩展：发现缺能力（如查天气）→ 搜插件 → 下载安装 → 运行」

### 安全底线（[硬约束](05-硬约束.md)第 2 条的落地）

NapCat / Koishi 的插件加载器**零沙箱**：插件就是往 Koishi 进程里 `import()` 一个 npm 包，
能读整个文件系统、能拿到 OneBot token。而「群里 @bot 说话」是不可信输入直达模型上下文的通道。
所以：

> **模型只能"搜"和"申请"，绝不能自己装。安装只有主人（authority 4）能触发。**

这不是保守：官方 registry 里**真的躺着** `koishi-plugin-boom2`，描述原文就是
「只要安装就会永久损坏你的Koishi,千万别装」。所以：
搜索结果里命中危险词的包会打 ⚠️ 标记；安装时命中危险词**直接拒绝**，除非主人显式加 `-f`。
另外包名先过 `PKG_RE` 白名单正则（`shell: true` 跑 npm，包名进命令行 = 命令注入面）。

### 三段实现

| 段 | 做法 | 关键事实 |
|---|---|---|
| **搜** | 拉 registry 的 `index.json` 缓存进内存（默认 30 分钟） | 4.9k 条 / 5MB；结构是 `{ objects: [ { package: {name, version, description}, manifest: {description:{zh,en}}, verified, downloads, installSize } ] }`；官方 `registry.koishi.chat` 会返回 HTML（得用 `koishi-registry.yumetsuki.moe` 这个镜像） |
| **装** | 优先 `ctx.installer.install({包名:版本})`（market 挂出来的，自己认 npm/yarn/pnpm），没有就自己 `npm install` | `@koishijs/plugin-market` 的 `src/node/installer.ts:189` |
| **跑** | 先试着 `loader.resolve(pkg)`：能解析就 `loader.reload(loader.entry, '包名:id', {})` 热挂载；**解析不到就 `loader.fullReload()` 重启** | 见下 |

### ★ "装好了但跑不起来"的两种原因，别混

第一次实测时拿到的是这个：

```
[I] chatluna-selfext 开始安装：koishi-plugin-weather@2.0.4（自己跑 npm.cmd）
[I] loader apply plugin koishi-plugin-weather:bil2fv
[E] app cannot resolve plugin "koishi-plugin-weather"
```

包确实已经躺在 `node_modules` 里（npm 退出码 0、`package.json` 里有依赖、`koishi.yml` 也写了），
但同一进程里解析不到。**根因是测试台的解析根不对**（用 koishi-app 的二进制起测试实例 →
解析根是 koishi-app/node_modules，而包装进了 koishi-test/node_modules）——
详见坑 24，已修（`run-rig.cjs` 改用测试实例自己的 `koishi/bin.js`）。

在**解析根正确**的环境里（生产就是：`ctx.baseDir` = 跑起来的那个 koishi 所在目录），
新装上的包**能立刻热挂载**，不需要重启。所以顺序是：

> **先 `loader.resolve(pkg)` 探一下 → 能解析就 `loader.reload(...)` 热挂载（不重启）；
> 解析不到才写配置 + `loader.fullReload()` 重启。**

兜底那条路不是白写的：`plugin-market` 自己**只**调 `fullReload()` 来让新依赖生效
（`fullReload()` → `process.exit(51)` → koishi CLI 的 daemon 重新 fork worker，
`koishi/lib/cli/index.js:84-98` 里 `shouldExit` 对 51 返回 false），
遇到装不到解析根里的情况（换包管理器、workspace、pnpm 之类）我们至少不会卡死。

另一个细节：**只调 `loader.reload()` 不写 config 的话重启就没了** ——
控制台的 `ConfigWriter` 是 `loader.reload()` + 改 `loader.config` + `loader.writeConfig()`
两个动作都做（`plugin-config/src/shared/writer.ts:144-169`）。我们在写盘前会先备份 `koishi.yml`。

## 二、R15 群聊屏蔽开关：自写插件

### 需求原文
> 在拉入真实群之前，检查是否有屏蔽某个群聊的开关，因为进入新的群聊之后可能产生意料之外的结果，
> 所以需要一个迅速响应的开关，并且告诉我如何使用，需要做到我(2791932480 QQ号)在需要屏蔽的
> 群聊中发送指令后立刻停止该群的回复，同时，你自己也可以调用脚本停止

用户当场选定的默认策略：**新群默认静默**（白名单外一律不回复），而不是"默认照常回复、需要时才闭嘴"。

### 先回答"有没有现成的开关"：没有

| 看起来像的 | 实际是什么 |
| --- | --- |
| chatluna 本体 | 只有 per-channel 的 `chatluna_constraint`（锁模型 / 锁预设 / 是否允许新会话），**没有"这个群不回复"** |
| chatluna-affinity | `chatluna_blacklist_v2` 是**拉黑某个人**，不是拉黑群 |
| chatluna-proactive | 只有"监控哪些群"的正向白名单（R9），且只管主动发言 |
| 老 `chathub_room_member.mute` | room 层的老表；1.4.0 正式版把 room 层删了（与坑 21 同源），是死字段 |

结论：**得自己写**。

### 产物

- 插件：`koishi-app/external/koishi-plugin-chatluna-guard/lib/index.js`
- 脚本：`tools/guard.cjs`（`status` / `mute` / `allow` / `reset` / `check`）
- 控制口：`GET|POST http://127.0.0.1:5140/qqbot/guard`，令牌写在 `<baseDir>/data/guard-control.json`（脚本自己读，不用手抄）
- 表：`qqbot_guard`（PK `scopeKey` = `onebot:channel:<群号>`）
- 生产配置：`koishi.yml` → `chatluna-guard:grd001`（`defaultPolicy: silent`，`allowGroups: ['454444539', '1040488785']`
  —— 后者是 2026-10-02 拉进来的真实群，见[真群接入与限流事故](16-真群接入与限流事故.md)）
- 服务：`ctx.provide('qqbotGuard', ...)`，别的插件可以问 `ctx.qqbotGuard.isBlocked(session)`

### 四道闸门（★ 每一道都不可省，这是从源码推出来再实测确认的）

1. **全局中间件（`prepend: true`）** —— 拦"用户发进来的消息"。
   Koishi 的中间件只有**一个全局数组**（`Processor._hooks`，core:730/737），`ctx.middleware(fn, true)` 是
   `unshift`，所以插件加载期注册就一定排第一 —— 比 `attach`、指令派发、ChatLuna 都早。
   不调 `next()` 就是整条管线短路：不建库行、不解析指令、不触发回复。
2. **ChatLuna 链中间件 `.before('allow_reply')`** —— 拦"绕过 Koishi 管线的调用"。
   R9 主动发言是直接 `chatChain.receiveCommand()`，**不走** Koishi 中间件，闸门 1 拦不到它。
   链上返回 `STOP`(1) 会让整轮 `_runMiddleware` 直接 `return false`（chains/index.cjs:178-190）。
   `ChainMiddlewareRunStatus = { SKIPPED:0, STOP:1, CONTINUE:2 }`（chains:883-887）。
   挂载时做了排序自检，实测日志：`排序自检通过：guard 在第 0 层，allow_reply 在第 1 层`。
   ★ 链闸门只拦得住"**还没开始**的回合"。
3. **`before-send`（发送口）** —— 拦"已经在生成中"的那一轮。
   用户喊闭嘴时上一个回合可能正跑着（模型要 10~20 秒），那条回复会在闭嘴**之后**才冒出来
   —— 剧本 27 实测真的发生过（第 8 步闭嘴后 3 秒，bot 又说了句"在，但不太想理你。"）。
   `before-send` 是 `app.serial` 调的勾子（@satorijs/core:752），返回非空即取消发送。
   开关操作自己产生的回复（"好，我先不说话了"、`/屏蔽状态`）靠中间件打在 session 上的
   `__guardControl` 标记放行 —— MessageEncoder 拿到的就是同一个 session 对象。
4. **指令自己的 `authority`** —— 拦"授权"。闸门 1 对控制词是**放行**的（否则被屏蔽的群里连"开口"都发不进去），
   权限判定交给 Koishi 的 `authority:N`（qqbot-auth 在 `attach-user` 里把主人抬到 4）。

### ★ 为什么"裸词兜底"必须放在 `next()` 之后

闸门 1 跑在 `attach` **之前**，那时 `session.user` 还不存在 —— 任何"你是不是主人"的判断都会得到 1。
所以没带前缀、也没 @ 的裸词（最顺手的用法：直接打「开口」）走的是：**先 `await next()` 让管线跑完**
（attach 会把权限算好），再回头处理。这样非授权者拿到的是**彻底静默**，而不是一句"权限不足"。
副作用的代价很小：裸词既不是指令（群里没前缀不解析），也不会触发 ChatLuna（`allow_reply` 要 @/引用/昵称）。

### ★ 屏蔽的语义（2026-09-30 按用户要求修正，别改回去）

用户原话：
> 「"/指令"应该由 bot 的逻辑代码处理，如果是模型被屏蔽了理应仍能收到命令，只是按照逻辑判断是否要回复」

第一版做成了"被屏蔽的群 = 一个字都不回，只有控制词能过"，用户实测后指出这不对：
**屏蔽的应该是"模型开口"，不是"bot 的逻辑"**。现在的三条规则：

| 消息类型 | 被静默的群里怎么处理 |
| --- | --- |
| **真指令**（带前缀 `/帮助`，或 `@bot 帮助`） | **照常解析执行**，回不回由指令自己的逻辑决定（闸门 4 放行它的输出） |
| 控制词（`闭嘴`/`开口`/`屏蔽状态`…） | 放行；裸词走 `next()` 之后判权限 |
| 普通聊天 / @bot 闲聊 / 引用闲聊 | 一个字都不回（模型产物被闸门 2、4 拦掉） |
| 假指令（`/随便什么`，指令表里没有） | 也丢弃 —— 静默就是静默，不允许冒出"指令不存在"之类的回执 |

开关：`allowCommandsWhenMuted`（默认 **true**）。关掉就是整群死寂（第一版的行为）。
判定用 `ctx.$commander.get(首词)` 查**真实指令表**，不是"看到前缀就算"。
另外：能让模型说话的那类指令（比如 `/proactive.speak`）在静默群里仍然发不出声 ——
它走的是 ChatLuna 链，被闸门 2 拦下，这符合"模型被屏蔽"的语义。

### 怎么用（用户视角，三选一）

| 场景 | 做法 |
| --- | --- |
| **在群里想让它闭嘴** | 直接打 `闭嘴`（不用前缀、不用 @），或 `/闭嘴`。它会回一句「好，这个群我先不说话了」然后彻底安静 |
| **想让它回来** | 群里打 `开口`（或 `/开口`、`@大肥鱼 开口`）。**被屏蔽的群里这几句话仍然听得见**，这是有意放行的 |
| **在私聊/不在那个群** | `/闭嘴 群号`、`/开口 群号`、`/屏蔽状态 群号` |
| **我在电脑前（脚本）** | `node tools\guard.cjs mute 454444539 原因` / `allow` / `status` / `check` |

- `屏蔽状态`（权限 1）：任何时候都能问"这个群现在是不是静默的"
- `屏蔽列表`（权限 2）：所有被显式设置过的群
- `清除屏蔽`（权限 3）：删掉设置，回到默认策略（`silent` = 白名单外静默）
- 开关门槛 `controlAuthority`（默认 3）：主人 4 / 管理员 3 能开关，普通群友**完全静默地**被无视

### 生效速度与状态存放

屏蔽态放内存 `Map`（启动 + 每 `refreshSeconds` 从 `qqbot_guard` 重载），热路径**不查库**，所以
指令 / HTTP / 脚本三条写入口都是**当次消息级别**生效。只有"直接改库"这条邪路最慢 `refreshSeconds` 秒。
私聊默认不受这套开关管（`applyToPrivate: false`）—— 私聊本来就只跟你说话。

### 验收三（`tools/scenarios/28-guard-send-gate.json`，闸门 3=发送口）

故意在**模型正在生成**的时候喊闭嘴：第 2 步让普通群友 @bot "用三百字认真介绍一下你自己"，
第 3 步在 8 秒后（此刻模型正在写）主人裸词 `闭嘴`。期望：**只看到闭嘴确认，看不到自我介绍**。

实测：`chatluna-guard 发送前拦下（群 454444539）` —— 那条已经在生成中的回复在发送口被丢掉了，
群里没有出现自我介绍；随后 `开口` → 确认正常发出（`__guardControl` 放行标记生效），
再 @bot 又能正常回复（证明闸门 3 没有过度拦截）。

### 调参入口

控制台 `/plugins/` → `chatluna-guard`：
`defaultPolicy`（新群策略）、`allowGroups` / `muteGroups`（进群前就能先写好）、`applyToPrivate`、
`controlAuthority`、`bareKeywords`、`confirmSeconds`、`refreshSeconds`、`token` / `controlPath`。

### 与其它插件的联动（都已改好）

- `chatluna-proactive`：`speak()` 开头先问 `ctx.qqbotGuard.isBlocked(...)`，省一次白烧的模型调用
- `chatluna-scene`：自动中断的"那这局就算了"提示（直发消息，绕过管线）也先问一次
- 两个插件都把 `qqbotGuard` 加进了 `inject.optional`，插件不在时照常工作

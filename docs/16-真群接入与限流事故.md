# 接入第一个真实群 + 第一次限流事故

> 属于 [QQ 机器人项目 —— 进度与交接](../进度与交接.md) 的分册。
> 旧编号（如「第八·十三节」）的去向见索引页的章节对照表。

2026-10-02。**第一个真实群 `1040488785`「空弓玄天下第一！」**：R15 默认静默当场生效 → 放行 → 2 分半发了 20 条被腾讯限流 → 补上两道闸。

### 背景

2026-10-02 凌晨用户把 bot 拉进了一个真实群（30 人）：**`1040488785`「空弓玄天下第一！」**。
（同时 NapCat/QQ 进程重启过，PID 换了一轮；生产 Koishi 也重启过。）

### R15 默认静默**当场就验证了**

拉进群之后的头一分钟，群里 34 条消息**全部被静默丢弃**、一条都没回：

```
[I] chatluna-guard 静默丢弃：群 1040488785｜晚安
[I] chatluna-guard 静默丢弃：群 1040488785｜我也要睡了
[I] chatluna-guard 静默丢弃：群 1040488785｜明天早八见
…
```

`node tools/guard.cjs check 1040488785` → `🔇 现在不会回复（走默认策略 silent）`。
这就是 R15"白名单外的群一律不回复"设计的实际效果 —— **新群绝对安全**。

### 用户选择：放行 **并且** 接入 R9 主动插话

改了三个地方：

| 位置 | 改动 |
|---|---|
| `chatluna-guard.allowGroups` | 加 `'1040488785'` |
| `chatluna-proactive.groups` | 加一条真群档位（见下） |
| `chatluna-proactive.cooldownSeconds` | 300 → **600**（两次主动发言最小间隔，防刷屏第一道闸） |

另加了一条**运行时**的 DB 行（立刻生效、不用重启，也是以后 `/闭嘴` 会覆盖的那一行）：

```powershell
node tools\guard.cjs allow 1040488785 "主人拉进真实群：放行 + 接入 R9 主动插话"
```

真群档位比测试群保守得多（真群消息密度高，同样的参数会让 bot 说话频繁得多）：

```yaml
      - guildId: '1040488785'
        enableActivity: true
        activityThreshold: 0.6      # 测试群 0.5
        thresholdCeiling: 0.8       # 测试群 0.65（说一次就更克制一点）
        activityMessageInterval: 60 # 测试群 15；消息数兜底
        enableIdle: true
        idleMinutes: 240            # 测试群 180
        idleJitter: true
```

免打扰时段是全局的：`quietHours` 默认 `01:00-08:00`，半夜不会主动开口。

### 实际发生了什么

放行后**约 2 分钟**，bot 就在真群里主动发言了（活跃度触发）：

```
00:42:51 [I] chatluna-proactive 群 1040488785 活跃度 0.443 / 阈值 0.600（候选 10 条…）
00:43:01 [I] chatluna-proactive 群 1040488785 活跃度 0.554 / 阈值 0.600（候选 12 条…）
00:43:21 [I] chatluna-proactive 已主动发言（活跃度触发）：群 1040488785，池内 14 条消息，3 张图，阈值调到 0.620
         send_group_msg → 「日常这东西，忘了就是忘了，跑一趟也救不回来」
```

观察结论（给以后调参用）：

- 真群活跃度涨得**很快**（十几秒一条消息 → 活跃度 0.4→0.55），
  `activityThreshold: 0.6` 对 30 人活跃群仍然**偏敏感**。想更安静就把真群那档调到 `0.7~0.75`，
  或者把 `activityMessageInterval` 提到 `120` 以上。
- "越聊越克制"机制确实在动：说一次阈值就 `0.600 → 0.620`（上限 `thresholdCeiling: 0.8`）。
- 说出来的话是**接得上话题**的（当时群里正在聊"忘记做日常了"），说明历史池注入是有效的。

### 想立刻让它闭嘴（两种，都是秒级）

```powershell
node tools\guard.cjs mute 1040488785 临时静默      # 脚本（DB 行，优先级最高）
```
或者在那个群里直接发 **`闭嘴`**（主人权限 4，`confirmSeconds: 5` 内生效）；
再发 **`开口`** 就恢复。只关主动插话、保留 @ 回应的话，把 `enableActivity`/`enableIdle` 关掉即可。

### ★ 放行后的第一次事故：**刷屏 + 被腾讯限流**（00:43–00:46，已修复）

放行后 2 分半，bot 往真群里发了 **20 条**，然后 `send_group_msg` 开始报
**`retcode: 1200`**（就是坑 26 里那个"网络连接异常"）。当时的处置顺序：

1. **先止血**：`node tools\guard.cjs mute 1040488785 "刷屏+发送1200…"` —— 群里立刻安静。
2. **判性质**：`node --no-warnings tools\napcat-probe.cjs send-group 454444539 "出站链路自检"` →
   `retcode: 0`。⇒ **出站是通的，1200 是腾讯的瞬时限流，不是掉线**，不用重启 QQ。
   （判据：入站也一直在正常收，`get_status` 那种客户端缓存字段不可信 —— 见坑 26。）
3. **找根因**：日志里 `chatluna-followup` 的判定说明了一切。

**根因：`chatluna-followup` 的跟进窗口是"按人"开的，在活跃大群里会叠加。**

```
00:44:50 [I] chatluna-followup 2969981414 跟进触发（第 2 条，还剩 576s 硬上限）
00:45:26 [I] chatluna-followup 3101329639 跟进触发（第 5 条，还剩 505s 硬上限）
00:45:29 [I] chatluna-followup 3101329639 跟进触发（第 6 条，还剩 502s 硬上限）
```

默认 `windowSeconds: 120 / maxSeconds: 600 / maxConsecutive: 20`。
**「最多 20 条」是每个人 20 条** —— 30 人群里 6 个人各叫一次 bot，就是 6 个窗口同时在跑，
每人再各接 20 条。小群里没事（就我们几个人），真群里立刻变成复读机。

#### 修法：给 followup 加了「按群覆盖」+「整群熔断」两道闸

改的是自写插件 `external/koishi-plugin-chatluna-followup/`：

| 新配置 | 作用 |
| --- | --- |
| `groups: [{guildId, enabled, windowSeconds, maxSeconds, maxConsecutive}]` | 按群覆盖参数；没列出的群走全局。`enabled: false` = 该群只回应 @，绝不自动接话 |
| `unlistedGroupPolicy: inherit \| off` | 没列出的群怎么办。生产用 `off` |
| **`groupMaxPerWindow` + `groupWindowSeconds`** | **整群熔断**：这个群在这个时间窗内最多自动接几条。★ 按人的上限挡不住"很多人各说一句"，必须有整群口径的闸 |

生产配置（`koishi.yml` → `chatluna-followup:fh2k9p`）：

```yaml
    groupMaxPerWindow: 3        # 整群：2 分钟内最多 3 条
    groupWindowSeconds: 120
    unlistedGroupPolicy: off
    groups:
      - guildId: '454444539'
        windowSeconds: 120
        maxSeconds: 600
        maxConsecutive: 20      # 测试群（自己人）宽松
      - guildId: '1040488785'   # 真群：一次只接 1 条，60 秒内说完就停
        enabled: true
        windowSeconds: 45
        maxSeconds: 60
        maxConsecutive: 1
```

#### 验收（测试台，2026-10-02 00:52 / 00:56，两次都零 `[E]`）

`34-followup-pergroup.json`（验"按群覆盖"）：

```
[I] 群聊跟进机制已挂载（… 按群覆盖 2 个 …；整群熔断 30s 内 2 条）
[I] 10001 叫了 bot，开启 45s 跟进窗口          ← 是 45s，不是全局的 120s
[I] 10001 跟进触发（第 1 条，还剩 66s 硬上限）  ← 是 90s 档，不是全局的 600s
[I] 10001 连续接了 1 条，停手                  ← 按群 maxConsecutive=1 生效
```

`35-followup-burst.json`（验"整群熔断"，把窗口调成 600s/1 条方便一次撞到）：

```
[I] 10001 跟进触发（第 1 条，还剩 66s 硬上限）
[I] 10003 叫了 bot，开启 45s 跟进窗口
[I] 群 454444539 触发整群熔断（600s 内最多 1 条），跳过 10003   ← ★ 第 2 个人被整群闸挡住
```

#### 经验（写下来免得再犯）

- **真群和测试群要分开配**。测试群 4 个人，参数怎么松都不会出事；真群 30 人，同一套参数就是刷屏。
- **凡是"按人"的上限，在群里都要再配一个"按群"的总闸**。这是本项目第一个真正被限流的教训。
- 出站报 1200 时，先用 `napcat-probe send-group`（打测试群，别打真群）判"是限流还是掉线"。

# 29 · 出站文本替换层（2026-10-05 第十三轮）

> 属于 [QQ 机器人项目 —— 进度与交接](../进度与交接.md) 的分册。

用户原话：

> 「给对话模型的输出之上添加一个逻辑层，原因是模型总是使用 😏 这个 emoji，感觉很拽的样子，
> 但它自己感觉不出来，又不想改提示词，所以添加一个逻辑替换层，将输出文字中的特定字符替换成
> 特定内容，由"管理员"级别以上的人维护，提供群聊中可用的 CRUD 命令」

一句话做法：**改发送口，不改提示词，也不改模型**。

新增自研插件 [`koishi-plugin-chatluna-replacer`](../koishi-app/external/koishi-plugin-chatluna-replacer/lib/index.js)
（配置块 `chatluna-replacer:rpl001`，两个实例都已接线）。

---

## 一、为什么挂在 `before-send`

「不想改提示词」把可选方案砍到只剩一个：**在出站口动手**。

`@satorijs/core` 的 MessageEncoder 是所有出站消息的唯一必经之路
（`encoder.send()` → `app.serial(session, 'before-send', …)`，core:752），
**返回非空即取消发送**。挂这里等于一个点覆盖模型回复 / R9 主动插话 /
followup 跟进 / 指令回执全部路径 —— 与 `chatluna-replyshaper`、
`chatluna-reply-style`、`chatluna-page` 是同一套路子。

> 「它自己感觉不出来」这句是需求里最关键的一条：**模型侧一个字都不动**，
> 所以既不用改预设，也不用重新教它。替换纯粹发生在"要说出去"和"真的说出去"之间。

## 二、替换语义（三条，别看代码猜）

| # | 规则 | 为什么 |
|---|---|---|
| 1 | **单趟最长匹配**：从左到右扫一遍，每个位置在所有「当前作用域适用且已启用」的规则里挑**命中最长**的那条 | 有 `😏` 和 `😏😏` 两条规则时，`😏😏` 命中后者，符合直觉。同长时**更具体的作用域优先**（群规则压过全局规则），再按 id 小的优先 |
| 2 | **替换出来的文本不再扫第二遍**（no re-scan） | 否则 `A→B` + `B→A` 就是死循环，`😏→嘿嘿😏` 会无限套娃。代价是单层替换，这正是要的可预测行为 |
| 3 | **只动纯文本元素**（`type === 'text'`） | 图片 / @ / 引用 / 表情包一律不碰 —— 不能把 reply-style 刚加的 `quote`、`at` 改掉，也不该改表情包里的字 |

三条语义都有离线单测钉着：[`tools/probe-replacer-core.cjs`](../koishi-app/tools/probe-replacer-core.cjs)
（**32 项全过**，毫秒级，改 `transform()` 后必跑）。

### 作用域：群规则 vs 全局规则

规则带一个 `scope` 字段：`*` = 全局，否则是群号。

- 群里 `/replacer.add` 默认**只对本群生效**（免得 A 群的管理员改掉所有群）；
- 加 `-g` 才是全局，**需要 4 级主人**；改 / 删全局规则同样只要 4 级能碰；
- 群规则 3 级管理员就能改（`qqbot-auth` 里管理员是**全局角色**，由主人授予）。

### 指令清单（写操作 3 级管理员，只读 1 级）

| 触发 | 等级 | 作用 |
|---|---|---|
| `/replacer`（= `/replacer.list`） | 1 | 看当前群生效的规则（含 id、开关、原文、替换文本、命中次数） |
| `/replacer.add 原文 [替换为]` | 3 | 新增；省略"替换为"= 删掉原文；`-g` = 全局（需 4 级） |
| `/replacer.set 编号 替换为` | 3 | 改某条的替换文本 |
| `/replacer.del 编号`（别名 `remove`） | 3 | 删除 |
| `/replacer.on` / `.off 编号` | 3 | 启用 / 停用（不删，随时开回来） |
| `/replacer.test 一段文字` | 1 | **dry-run 预览**会被换成什么，不改任何东西 |
| `/replacer.reload` | 3 | 从库里重新载入规则 |

```
/replacer.add 😏 嘿嘿          ← 最常用的一条：把 😏 换成 嘿嘿
/replacer.add "你 好" 嗨       ← 原文含空格用引号
/replacer.add 😏               ← 省略替换文本 = 直接删掉
```

★ **指令名一律英文**（2026-10-02 起的全局约定）：中文别名会被
`chatluna-cmdname` 在运行期摘掉，所以中文只写在描述与帮助文案里。

★ 参数为什么**不用** Koishi 的声明式 `<a:string>`：要替换的是**任意文本**，
而 Satori 的 `Element.escape()` 会把 `>` 变成 `&gt;`（@satorijs/element:113），
声明式参数拿到的是**转义后**的串。所以 `add` / `set` / `test` 直接读
`session.stripped.content`（原始正文）自己切词，`>` 就还是 `>`。

### 表与命中统计

表 `chatluna_replacer_rule`：`id / scope / pattern / replacement / enabled / hits /
createdBy / createdAt / updatedAt`（`ctx.model.extend`，启动自动建表）。

`hits` 用来一眼看出**哪条规则从来没生效过**（死规则）。它是**攒批落盘**的
（`hitFlushSeconds`，默认 20 秒），不每条消息写一次库；清单里显示的取内存实时值。

## 三、★ 这一轮踩到的两个真 bug（都是静默的）

### 3.1 自己的指令回执被自己替换掉了 —— [坑 32](04-踩坑记录.md) 原样重演

第一版在 `before-send` 里读 `session.argv?.command` 判断"这是不是指令回执"。
**读不到**：出站时编码器 new 了一个 session，只复制**可枚举**的键
（core:739-742），而 `argv` 是 Koishi 用 `defineProperty` 挂的 —— 不可枚举。
现象：

```
/replacer                →  「#1 开 [本群]「嘿嘿」→「嘿嘿」」   ← 原文 😏 被换掉了
/replacer.test 心情不错😏 →  「输入：心情不错嘿嘿 好耶哈哈」    ← 连"输入"都不是原话
```

管理员于是**永远看不到自己配的原文**；而"跳过自己的指令"这条防线、
连同 `skipCommands` 整个开关，一起静默失效（第一轮 17 条判据里 6 条因此不成立）。

修法照抄本项目已生产验证过的做法（`chatluna-page:591`、`chatluna-guard:960`）：

```js
ctx.before('command/execute', (argv) => {
  const s = argv?.session
  if (s && argv?.command) s.__replacerCommand = argv.command   // 普通赋值 = 可枚举
})
```

**教训**：`session.argv` 在 `before-send` 里永远是空的 —— 这条坑 32 早就写着，
我还是踩了。凡是要在 `before-send` 里知道"这是哪条指令产生的"，只能用
**普通赋值**往 session 上打标记。见 [坑 74](04-踩坑记录.md)。

### 3.2 ★ 排在配置文件前面 ≠ 先执行 —— 长回复静默换不掉

发现过程：短回复替换正常、`[image]` 也照常出，**只有长回复里的 😏 留着**。

原因是 `chatluna-page` 会把长回复（默认 ≥180 字或 ≥6 行、仅群聊）**转成图片**；
替换层一旦排在它后面，`session.elements` 里就只剩一个 image 元素 ——
😏 已经烤进图里了，代码看到的只是一个图片，**不报错、日志里也看不出异常**。

第一反应是把插件在 `koishi.yml` 里挪到 page **前面**。**没用**：实测日志顺序
仍然是 `page → replystyle → replacer`。根因是 **`inject` 会推迟 `apply`**：

- 本插件声明了 `required: ['database']` → `apply` 要等 database 就绪；
- `chatluna-render` / `chatluna-page` / `chatluna-reply-style` 没有这层等待，
  `apply` 立刻完成、`before-send` 监听器**先**注册；
- 而 `app.serial` 是按**注册顺序**遍历的（`@cordisjs/core:523` dispatch + `:534` `unshift/push`）。

**修法：位置由插件自己声明，不靠配置顺序。**

```js
ctx.on('before-send', handler, true)   // 第三参 true = prepend → hooks.unshift()
```

`ctx.on(name, listener, options)` 里传 `true` 会被规范化成 `{ prepend: true }`
（`@cordisjs/core:545-548`），`register()` 于是走 `unshift`，把自己钉在队首,
**从此与插件加载顺序无关**。

**判定顺序对不对的判据**（这条最容易自欺）：
长回复那一步**既要**有 `出站替换：N 处 / M 条规则` 日志、**又要**在
fake-onebot 那边落成 `[image]` —— 两者同时成立才说明"先换字、后出图"。
**只看 `[image]` 是不够的**：顺序反了照样出图。

★ **一个实测出来的副作用**：`chatluna-episode`（记 bot 自己的短期记忆）**也带 `inject`**，
同样被推迟 —— 实测整条链是
`replacer → render → page → reply-style → … → episode`，它反而排在**最后**。
所以它记到的**纯文本**回复是**替换之后**的文本（"我实际发出去的是 嘿嘿"），
这比记原文更贴合"对话记录 == 群友看到的"；长回复那头它看到的已经是 page 出好的
图片（记的是 `<img>`），那是 episode 与 page 之间既有的行为，与本插件无关。

> ★ 一开始我把这件事写成了"prepend 让它排在 episode 前面"，**是错的** ——
> 实测日志顺序是 `出站替换 → 长回复出图 → 出站形态 → 记录出站消息`。
> 结论（记的是替换后的文本）碰巧对，理由是错的。**别拿"我以为的顺序"当结论写进文档**，
> 要去日志里把四行捞出来看。

## 四、验证

`koishi-app/tools/scenarios/63-replacer.json`（18 步，判据 ①~⑧ 写在文件头）。

```
node tools\reset-replacer-rules.cjs                        # 规则落库，跑之前必须清
cd koishi-app
node tools\run-rig.cjs tools\scenarios\63-replacer.json ^
     --upstream --default-model fakemulti/q.replacer --run 175000 --keep-log
```

为什么能**确定性**地验：真模型什么时候吐 😏 由它自己决定，没法当断言依据。
所以给伪上游 [fake-openai.mjs](../koishi-app/tools/fake-openai.mjs) 加了一个
`fake-emoji` 模型 —— 正文固定是 `心情不错😏 好耶😏😏`；**本轮用户消息**里带 `ZZLONG`
时改吐一段 295 字的长正文（专门验 3.2 那个顺序问题）。

> ★ 这里有一个把第三轮跑成"假失败"的坑：一开始是拿**整段 messages** 找 `ZZLONG` 的，
> 而对话历史是**落库的** —— 第一轮跑完 `ZZLONG` 就留在 `chatluna_message` /
> `chatluna_episode` 里了，于是从那时起**每一次**回复都变成"长正文"，
> 短回复那几条判据（③⑤）全部落空，看着像插件坏了。
> 改成**只看 messages 的最后一条**（本轮这一条）之后，伪上游与本进程之外的
> 任何历史状态无关，剧本可以反复跑。
> **凡是"由历史决定的假上游分支"都会这样飘**，判据里写死具体文本的都要当心。

实测（2026-10-05 01:1x → 01:2x，8 条判据全过）：

| 判据 | 证据 |
|---|---|
| ① 权限门槛 | 10001 普通 → `权限不足。`；10002 管理员 → `新增替换规则 #3`；主人 → `#1`/`#2` |
| ② CRUD 全通 | 建 #1/#2/#3 → 删 #3/#2 → `set 1 嘿嘿嘿`；末尾清单 `#1 开 [本群] 「😏」→「嘿嘿嘿」 命中 4` |
| ③ 模型输出被替换 | 出站是 `心情不错嘿嘿 好耶哈哈`；**不存在** `text: '心情不错😏 好耶😏😏'` 的 `send_group_msg` |
| ④ 最长匹配 | 没有出现 `好耶嘿嘿嘿嘿`（😏😏 命中「😏😏→哈哈」） |
| ⑤ 停用生效 | `off 1` 之后出站变成 `心情不错😏 好耶哈哈`（单个 😏 保留、😏😏 仍换） |
| ⑥ 自己的指令不被替换 | 14 次「本插件指令回执，跳过替换」；清单里原文仍是 😏；test 的「输入：」是原话 |
| ⑦ **加载顺序** | `出站替换：3 处 / 2 条规则` **紧接着** `page 长回复出图：模型回复 → 第 1/10 页（正文 293 字符）` —— 293 = 295 − 2（😏😏→哈哈 少了 2 个码元）= **替换后**的长度，顺序确凿 |
| ⑧ 无自伤错误 | 本插件 0 条 `[E]`。★ 日志里出现过 `[E] chatluna … 429 Too Many Requests`，那是**真上游**的限流（long-memory / 滚动总结走真 API，不走伪上游），与本插件无关 |

★ 判据 ⑦ 的"293 字符"是这一轮**最硬的一条证据**：page 渲染的正文长度等于
**替换后**的长度，说明替换确实发生在出图**之前**；只看 `[image]` 是不够的
（顺序反了照样出图，只是图里留着 😏）。

## 五、调参、回滚、已知边界

### 调参入口

控制台 `/plugins/` → `chatluna-replacer`：

| 配置 | 默认 | 说明 |
|---|---|---|
| `enabled` | true | 总开关 |
| `skipCommands` | true | 指令回执不走替换。**本插件自己的指令无论如何都跳过**，否则清单里看不到原文 |
| `skipGuardControl` | true | guard 的「闭嘴/开口」回执也跳过 |
| `dropWhenEmpty` | true | 替换后整条消息变空就不发（规则把 😏 换成空串、而模型这一条只发了 😏 时会撞上） |
| `maxRules` | 200 | 规则条数上限 |
| `hitFlushSeconds` | 20 | 命中次数落盘间隔 |
| `debug` | false | 打印跳过原因 |

### 回滚

停用 `chatluna-replacer` 插件即可 —— 出站完全回到"模型说什么就发什么"。
规则留在 `chatluna_replacer_rule` 表里，重新启用后照旧生效；
想彻底清掉用 `node tools\reset-replacer-rules.cjs`（**要在 Koishi 没跑时执行**，sqlite 单写）。

### 已知边界

1. **模型自己的记忆记的是"实际发出去的话"**：`chatluna-episode` 也带 `inject`、被推迟到很后面
   （实测排在 page / reply-style **之后**），所以它记到的**纯文本**回复是**替换之后**的文本。
   长回复那头的记录里是 page 出好的图片（`<img>`），看不到文字 —— 那是 episode 与 page
   之间既有的行为，与本插件无关。
2. **不碰图片**：表情包、出图后的长回复、图片消息里的字都不动。长回复之所以还能替换，
   靠的就是"排在 page 前面"（3.2）。
3. **只有字面匹配，没有正则**：这是刻意的 —— 正则跑在**每条出站消息**的热路径上，
   一次灾难性回溯就能把发送卡住。真要正则，加之前先想清楚怎么限时。
4. **替换结果不再扫第二遍**（语义 2）：`😏 → 😏呀` 不会继续被换。
5. 出图后的长回复被分页（测试实例 `pageMaxChars: 30`），替换发生在**出图之前**，
   所以图里每一页都是替换后的文本。

# R14 / R18 情绪控制

> 属于 [QQ 机器人项目 —— 进度与交接](../进度与交接.md) 的分册。
> 旧编号（如「第八·十三节」）的去向见索引页的章节对照表。

**R14（情绪）与 R18（情绪过期）是同一件事的两个阶段**，所以放一份里。

## 一、R14 情绪控制：调研结论与方案

### 现状：生态里**没有**可直接用的"情绪"插件

搜遍官方注册表与 npm，带 emotion/mood/情绪/心情 的 Koishi 插件里，没有一个能直接用。
两个"看起来像"的都不是：

| 看着像 | 实际是 |
|---|---|
| `chatluna-scene-rules` | **名字骗人**。实际是 livingmemory 的**记忆池别名器**（让一个角色的私聊版/群聊版共享记忆），跟场景/情绪无关 |
| `chatluna-self-attention` | "把最近的 Koishi 指令调用暴露给提示词"，与情绪无关 |

### 但**机制**已经有现成的参考实现

`koishi-plugin-chatluna-affinity@0.3.15`（R4 好感度）做的就是**同构**的事：

- 状态落库，按 `scopeId` 实例隔离
- 向预设暴露**模板变量**：`{好感度}`、`{关系}`、`{黑名单}`
- 模型通过**工具调用**（XML 或原生 tool）更新状态
- 支持长期/短期双值 + 动态系数

**情绪和好感度的机制完全一样，只是语义轴不同**（好感度=对某人的关系，情绪=自己的内部状态）。

### ChatLuna 给自定义变量留的正式接口

`ChatLunaService.promptRenderer`（类型 `ChatLunaPromptRenderService`）：

```ts
registerVariableProvider(provider: VariableProvider): () => void;
registerFunctionProvider(name: string, handler: FunctionProvider): () => void;
setVariable(name: string, value: string): void;
renderTemplate(source: string, variables?): Promise<RenderResult>;
```

→ **写一个自己的小插件，注册 `{情绪}` 变量即可让预设直接引用**。不需要改 ChatLuna 任何文件。

### 三个方案

| 方案 | 说明 | 评价 |
|---|---|---|
| **A. 自写 `chatluna-emotion` 插件**（推荐） | 仿 affinity 的架构：自己的表 + `registerVariableProvider` 暴露 `{情绪}`/`{心情}` + 模型用标签或工具更新 + 时间衰减 | 完全可控；复用刚建好的 sqlite；与 R2 预设、R4 好感度、R9 插话天然兼容 |
| **B. 上 `elysia-ai` 框架** | `elysia-ai-homeostasis` 原生就有「能量/心情/社交/好奇心 + 朝基线松弛的恢复动力学」，13 个插件一整套 | 现成度最高，但是**另一套完整框架**（v0.2.2，需 `@elysia-ai/core`），自带 `dialogue`/`brain`/`persona`，**与刚选的 ChatLuna 栈重叠甚至打架** |
| **C. 用 `chatluna-affinity` 顶替** | 直接拿好感度当"情绪"用 | ❌ 语义不对。好感度是"我对你的关系"，情绪是"我现在的心情"，混用会两头都不像 |

### 若走 A，设计要点（待用户确认后再动手）

1. **状态模型**：离散情绪标签（开心/平静/烦躁/兴奋/低落…）+ 强度值，而非纯连续维度——更容易让模型理解和表达
2. **作用域**：群级情绪（整个群共享一个 bot 情绪）为主；是否需要"对某人的情绪"叠加待定
3. **更新方式**：模型在自己回复里吐结构化标签（如 `<emo mood="开心" v="0.7"/>`），插件**剥掉标签再发出**，同时落库
4. **衰减**：读取时按 `value = baseline + (value-baseline) * exp(-Δt/τ)` 计算，不同情绪不同半衰期——**这是"像真的"的关键**，没有衰减的情绪会显得随机
5. **注入**：`{情绪}` 变量 + 预设里写"你现在的心情是 {情绪}，用相符的语气说话"
6. **可分阶段**：先做「落库 + 变量注入 + 标签解析」跑通，再加衰减和强度

### 待用户决定

- 情绪按**群**算还是按**人**算？
- 用离散标签还是连续维度？
- 走 A 还是先试试 B？

## 二、R14 情绪控制：已实现（自写插件）

### 产物

```
koishi-app/external/koishi-plugin-chatluna-emotion/
├── package.json
└── lib/index.js          ← 全部逻辑在这一个文件，约 290 行
koishi-app/data/chathub/presets/default-persona.yml   ← 默认人格预设，引用 {emotion()}
```

安装方式（已做过）：`npm i ./external/koishi-plugin-chatluna-emotion`
启用：`koishi.yml` → `chatluna-emotion: {}`

### 做了什么

| 能力 | 实现 |
|---|---|
| 状态落库 | 自建表 `chatluna_emotion`（`scopeKey` 主键 / `emotion` / `intensity` / `reason` / `updatedAt`） |
| 隔离范围 | 默认**按会话**（一个群一种心情），可切 `user` / `global` |
| **时间衰减** | `intensity *= 0.5 ^ (Δ分钟 / halfLife)`，默认半衰期 60 分钟；低于阈值回到基线情绪 |
| 注入预设 | `registerFunctionProvider('emotion', ...)` → 预设里写 `{emotion()}` |
| 模型自己改情绪 | 注册原生工具 `emotion_set(emotion, intensity, reason)` |
| 人工干预 | `/emotion`、`/emotion/set <名> [强度]`(authority 3)、`/emotion/list`、`/emotion/reset`(authority 3) |

默认 10 种情绪：开心 / 兴奋 / 平静（基线）/ 无聊 / 烦躁 / 生气 / 难过 / 委屈 / 得意 / 害羞。

### ★ 两个必须记住的 API 事实（都是从 affinity 源码实证来的）

1. **注入变量必须用 `registerFunctionProvider`，不能用 `registerVariableProvider`。**
   `VariableProvider` 的签名是 `() => Record<string, unknown>`，运行时代码就是 `provider()` **无参调用**
   （见 `@chatluna/shared-prompt-renderer/lib/index.cjs` 的 `getAllVariables`），**拿不到 session**。
   而 `FunctionProvider = (args, variables, configurable) => string`，`configurable.session` 才是会话。
   → 代价：预设里得写 `{emotion()}`（带括号），不能写 `{emotion}`。

2. **注册工具走 `ctx.chatluna.platform.registerTool(name, tool)`**，不是 service 上的方法。
   工具写法（照抄 affinity）：

   ```js
   platform.registerTool('emotion_set', {
     selector: () => true,
     authorization: () => true,
     description,
     createTool: () => new (class extends StructuredTool {
       name = 'emotion_set'
       schema = z.object({ ... })
       async _call(input, _manager, runnable) {
         const session = runnable?.configurable?.session   // ← session 在这
       }
     })(),
   })
   ```

### 依赖与坑

- `@langchain/core`（`StructuredTool`）和 `zod` 都已由 chatluna 带进来，**不要装第二份**。
  验证：`node_modules` 下 `zod` 应只有一份（当前 3.25.76）。
- 本地插件要用 `npm i ./external/<包名>` 装，**不能只放目录**。
- `package.json` 里**不要写 `module.exports.default = module.exports`**（自引用会干扰 Koishi 加载器）。

### 还没做的

- **尚未实测**：模型是否会真的调用 `emotion_set`（取决于预设是否启用了原生工具、以及模型工具调用的稳定性）。
  若不调用，退路是在预设里改用"让模型在回复里吐标签 + 用 `session.send` 包装器剥掉"的方案。
- `/emotion` 系列指令还没在 QQ 里实测过。

### 调参入口

都在控制台 `/plugins/` → `chatluna-emotion`：`baseline`（基线情绪）、`halfLife`（衰减半衰期分钟）、
`resetThreshold`、`scopeMode`、`emotions`（情绪表，可增删改描述）。

> ★ **R18 之后又多了两个（2026-09-30）**：`expireMinutes`（绝对保质期，默认 180 分钟）
> 和 `sweepSeconds`（后台清扫间隔，默认 60 秒）。详见[R18 情绪过期](08-R14R18情绪控制.md)。
> 一句话区分：`halfLife` 管"越来越淡"，`expireMinutes` 管"一定会没"。

## 三、R18 情绪过期：绝对保质期 + 后台清扫

### 需求原文

> 2. 情绪需要过期机制，由逻辑代码控制

### 原来的毛病

R14 的情绪只有**半衰期衰减**（`halfLife` 默认 60 分钟，指数衰减）：

- 指数衰减**永远到不了 0**，`halfLife` 一设大，一个小情绪能挂一整天；
- 衰减是**惰性**的：只有"有人来读"才重算，没人说话时数据库里那行原样躺着
  （生产库里那行 `updatedAt` 一直停在 14:38，就是这个问题）；
- 强度掉到阈值以下只是把 `emotion` 写回基线，**行还留着**，`reason` 也留着 → 僵尸情绪行。

### 现在怎么做的（三条，全部是**插件逻辑代码**，模型既不知道也绕不过）

1. **绝对保质期 `expireMinutes`（默认 180 分钟）**：从情绪**被设置**那一刻算起，到点无条件回基线，
   不管强度还剩多少。"半衰期负责越来越淡，保质期负责一定会没。"
2. **后台清扫 `sweepSeconds`（默认 60 秒）**：`ctx.setInterval` 周期性扫表，
   该衰减的衰减、该过期的过期，**已经回到基线的行直接 `DELETE`**（过期 = 物理消失）。
   ★ 用 `ctx.setInterval` 而不是裸 `setInterval`，插件卸载/重载时 cordis 会自动清掉。
3. **TTL 锚点单独存 `setAt` 列**：★ 绝不能拿 `updatedAt` 当锚点 —— 那个每次读取都会被
   惰性衰减回写刷新，拿它当锚点 = 情绪**永远不会过期**。另外老数据没有 `setAt`（当时还没这列），
   代码里会把这种行**就地锚定为"现在"**，让它从此刻起最多再活一个保质期（不然老行 TTL 永远为 null）。

配套：`/emotion` 现在多显示一行 `距离过期：X 分 Y 秒`；新增 `/emotion.sweep`（authority 3）手动催一次。

### 配置（生产 `koishi-app/koishi.yml`）

```yaml
  chatluna-emotion:o5a8hl:
    halfLife: 60          # 衰减半衰期（分钟）
    expireMinutes: 180    # ★ 绝对保质期（分钟），0 = 不过期
    sweepSeconds: 60      # ★ 后台清扫间隔（秒），0 = 关掉清扫
```

数据库迁移是自动的（koishi 的 sqlite 会 `ALTER TABLE chatluna_emotion ADD setAt INTEGER NULL`），
不需要手工改库。

### 验收（`tools/scenarios/30-emotion-expiry.json`，2026-09-30 00:45，测试台）

测试配置故意把 `expireMinutes` 设成 `0.1`（6 秒）、`sweepSeconds` 设成 `2`，好在一次机台里看完：

```
/emotion.set 烦躁 0.9            → 已把情绪设为「烦躁」，强度 90%
/emotion（+3s）                  → 当前情绪：烦躁（强度 90%）；距离过期：2 秒（保质期 0.1 分钟）
00:45:19 （★ 期间群里没有任何消息）→ sqlite > DELETE FROM `chatluna_emotion` WHERE `scopeKey` = 'onebot:channel:454444539'
/emotion（+15s）                 → 当前情绪：平静；距离过期：不过期
/emotion.set 兴奋 1 ; /emotion.sweep → 清扫完成：扫了 1 行，过期/回落 0 行，删除 0 行。   ← 还没到期，正确地没删
00:45:41 （★ 又是零流量）         → sqlite > DELETE FROM `chatluna_emotion` WHERE `scopeKey` = 'onebot:channel:454444539'
```

**关键点**：两次删除都发生在**群里一句话都没有**的时候 —— 证明是逻辑代码在管，不是"碰巧有人来读"。

生产侧同样生效：重启后 01:24:13 日志里直接出现
`DELETE FROM chatluna_emotion WHERE scopeKey = 'onebot:channel:private:2791932480'`，
把那行挂了一整天的旧情绪清掉了。
